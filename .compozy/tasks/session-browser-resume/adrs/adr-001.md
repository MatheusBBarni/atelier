# ADR-001: V1 Scope — Session Browser & Resume (read-only preview in, fuzzy search deferred)

## Status

Accepted

## Date

2026-06-15

## Context

The "Session browser & transcript resume" feature is anchored on **crash/quit recovery**: reopen the lost thread and keep going. Initial scoping (user pick) was "complete browser + resume", which bundled a **fuzzy filter over goals/prompts** alongside a newest-first list, a read-only transcript preview, and the Resume action.

The council debated whether the fuzzy filter and preview belong in V1 (Tension T1). Three facts shaped the decision:

- The **foundation** — `HistoryStore::open()`, live session rebind, and a source for goal/outcome — is irreducible: even a bare "resume my last session" needs all of it. Trimming the UI saves little.
- The **read-only preview is the same production fold** (`ChatProjection::rebuild`) rendered read-only, and it is the user's only confirmation gate before committing the irreversible Resume swap.
- The **fuzzy filter serves a different, unvalidated hypothesis** (archival browsing — "find that thing I did last week"), and it introduces a searchable index over potentially sensitive stored prompts (a new at-rest attack surface flagged by the Security Advocate).

## Decision

**V1 scope** is:

1. A modal **session picker**: newest-first list with goal preview, timestamp, and run outcome.
2. A **read-only transcript preview** of the selected session (via the existing `ChatProjection::rebuild` fold).
3. A **Resume** action that re-adopts the session (see ADR-002, ADR-003, ADR-004).

A simple case-insensitive **substring narrow** over the visible list is acceptable. **Fuzzy/content search is deferred** to a follow-up and is grouped with the cross-session audit/search opportunity. The deferral is earned back by **resume-rate telemetry**: if users scroll deep or hunt for older sessions, that data justifies the search investment.

## Alternatives Considered

### Alternative 1: Full browser including fuzzy search (the initial scope)

- **Description**: Ship list + preview + fuzzy filter + Resume together.
- **Pros**: Feels complete; matches Gemini CLI's session browser.
- **Cons**: Bundles an unvalidated archival hypothesis with the crash-recovery anchor; adds an index-over-prompts attack surface for no anchor value; can't attribute which sub-feature earned its keep.
- **Why rejected**: Scope creep dressed as completeness; delays the core win.

### Alternative 2: Resume-last-only (no browser modal)

- **Description**: A single "reopen my last session" action / CLI flag; no list.
- **Pros**: Smallest surface.
- **Cons**: The foundation cost is identical, and a newest-first list + preview is cheap plumbing on top; loses multi-session recovery and the audit use case.
- **Why rejected**: Saves almost none of the real cost while discarding most of the value.

## Consequences

### Positive

- Fully delivers the crash-recovery anchor (the lost session is row one).
- De-risks the XL bet; ships a smaller, instrumentable surface.
- Preview doubles as the confirmation gate for the mutating Resume.

### Negative

- Users wanting cross-session search wait for a follow-up.

### Risks

- The preview renders untrusted historical bytes — must sanitize control/ANSI sequences (see ADR-004).

## Implementation Notes

Preview and Resume share the same fold; build the fold once and render it read-only for preview, then reuse it as the projection when Resume commits.
