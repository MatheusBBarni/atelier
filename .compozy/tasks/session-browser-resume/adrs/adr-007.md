# ADR-007: Drift detection model — extend GitContext, record a HEAD baseline, gate the first mutation

## Status

Accepted

## Date

2026-06-15

## Context

ADR-004 commits to a drift interlock that fires when the **cwd or git HEAD changed** since a session paused, gating the first state-mutating action after resume. The codebase does not yet support this:

- `GitContext` (src/app/git.rs:26) is only `{ repo_name, branch }` — **no HEAD SHA, no dirty flag**. `fetch_git_context` runs `git rev-parse` with a 500ms budget.
- `SessionMetadata` (src/history/mod.rs:76) records `working_directory` but **not** the git HEAD at session start, so there is no stored baseline to compare a live HEAD against.
- A dirty working tree is the *expected* state immediately after a crash, so dirtiness must not be a drift trigger (ADR-004).

## Decision

1. **Extend `GitContext`** with a short HEAD SHA and a `dirty: bool` flag (one extra `git rev-parse --short HEAD` + `git status --porcelain`, within the existing 500ms budget). The dirty flag is **display-only**, never a drift trigger.
2. **Record a HEAD baseline in the session log.** Capture the short HEAD SHA into the session's lifecycle events at run boundaries (e.g. on run start/end), so the session's *last-recorded* HEAD is recoverable by folding the log. This makes the baseline the world-state as of the session's last activity (not just its creation), which is the correct reference for "has the world moved since I paused."
3. **Drift = `live.working_directory != stored.working_directory` (moved/missing) OR `live.head_sha != session.last_recorded_head_sha`.** Computed during off-thread adoption (ADR-006).
4. **Interlock placement (ADR-004):** if drift is present, the **first** action whose decision modifies the workspace (`WriteFile`/`ApplyPatch`/`RunCommand`) folds the drift context into its approval prompt and requires positive acknowledgment. Browsing, previewing, opening, and read-only actions are never gated. The acknowledgment is recorded in the `session_resumed` event.

## Alternatives Considered

### Alternative 1: cwd-moved only in V1 (defer HEAD-drift)

- **Description**: Use the existing `working_directory`; ignore HEAD changes.
- **Pros**: No GitContext/log changes; ships sooner.
- **Cons**: Misses the common "same directory, different branch / rebased" case — the top trust-killer in the research.
- **Why rejected**: Leaves the most likely drift undetected.

### Alternative 2: HEAD-changed only

- **Description**: Compare HEAD; ignore cwd moves.
- **Pros**: Catches branch/rebase drift.
- **Cons**: Misses a relocated/missing working directory (resumed in a different checkout).
- **Why rejected**: Asymmetric; cwd is already cheaply available.

### Alternative 3: Baseline at session *creation* instead of last activity

- **Description**: Store HEAD once in `SessionMetadata` at create.
- **Pros**: One write.
- **Cons**: A long session that itself moved HEAD would false-positive on resume.
- **Why rejected**: Last-recorded HEAD is the more accurate "since I paused" reference.

## Consequences

### Positive

- Catches both real-world drift modes; the clean common path (same dir, same HEAD) has zero friction.
- Drift context is captured tamper-evidently in `session_resumed` (ADR-002).

### Negative

- One extra git invocation per context refresh; new fields on `GitContext` and new payload on lifecycle events.

### Risks

- Non-git workspaces have no HEAD. *Mitigation:* HEAD-drift simply doesn't apply (only cwd-moved is evaluated); never block on a missing HEAD.
- `git status --porcelain` on a huge tree could approach the timeout. *Mitigation:* dirty is display-only; on timeout, omit it (don't block).

## Implementation Notes

Drift evaluation happens once, during off-thread adoption, and its result is stored on the resumed session so the first-mutation gate is a cheap boolean check. Reuse `fetch_git_context`'s subprocess+timeout approach for the added calls.
