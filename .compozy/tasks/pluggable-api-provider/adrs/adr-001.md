# ADR-001: Generalize ZaiRuntime into Configurable HTTP API Runtime

## Status

Accepted

## Date

2026-06-17

## Context

Atelier needs to support BYOK (bring-your-own-key) API provider integration so users can point any OpenAI-compatible endpoint at any agent. The existing `ZaiRuntime` already implements OpenAI-compatible chat completions via `reqwest` with SSE streaming and bearer auth, but the `RuntimeKind` enum is closed and the auth scheme is hardcoded to `Authorization: Bearer`. Each new provider (OpenRouter, Verboo, DeepSeek, etc.) currently requires a new enum variant, new dispatch match arms, and new config validation branches — even when the HTTP protocol is identical.

The council debated three approaches: (1) create a new `RuntimeKind::OpenAiCompatible` variant per provider, (2) generalize ZaiRuntime into a configurable `HttpApi` kind, or (3) defer BYOK entirely and focus on making existing config more discoverable.

## Decision

Generalize `ZaiRuntime` into a configurable `HttpApi` runtime kind with parameterized auth headers. Rename `RuntimeKind::Zai` to `RuntimeKind::HttpApi` (or add `HttpApi` as an alias with `Zai` deprecated). Add `auth_header_name` (default: `Authorization`) and `auth_header_prefix` (default: `Bearer`) fields to `RuntimeConfig` so providers like Verboo (which uses `api-key: xxx` instead of `Authorization: Bearer xxx`) work without code changes. Every OpenAI-compatible provider becomes a TOML configuration entry, not a Rust enum variant.

## Alternatives Considered

### Alternative 1: New RuntimeKind per Provider

- **Description**: Add `RuntimeKind::OpenRouter`, `RuntimeKind::Verboo`, etc. as separate enum variants
- **Pros**: Each provider gets its own module with provider-specific logic
- **Cons**: Duplicates SSE parsing, body construction, and error mapping for identical protocols; grows dispatch sites; every new provider is a code change
- **Why rejected**: The HTTP protocol is identical across providers; only headers differ. Duplicating the runtime for header differences is disproportionate.

### Alternative 2: External Gateway (LiteLLM Proxy)

- **Description**: Deploy LiteLLM as a sidecar proxy; atelier talks to one local endpoint
- **Pros**: Provider-agnostic without any code changes; 100+ providers supported
- **Cons**: Adds operational complexity (sidecar process); contradicts terminal-native single-binary philosophy; external dependency
- **Why rejected**: Architecture mismatch — atelier is a single binary, not a service mesh.

### Alternative 3: Defer BYOK, Improve Config Discoverability

- **Description**: Ship no new code; document that users can already point ZaiRuntime at any OpenAI-compatible endpoint via TOML config
- **Pros**: Zero engineering cost
- **Cons**: Users must discover this capability manually; auth scheme is hardcoded to Bearer (breaks Verboo); no validation feedback; feature is effectively hidden
- **Why rejected**: The hardcoded Bearer auth means not all providers work today. The discoverability gap means even compatible providers go unused.

## Consequences

### Positive

- Every OpenAI-compatible provider (OpenRouter, Verboo, DeepSeek, Groq, Mistral, Together AI, Ollama, etc.) works via config-only additions
- ZaiRuntime's existing streaming-with-fallback and error classification logic is preserved without duplication
- Future model-agnostic task routing (V2 `[routing]` config section) is unblocked — the `model` field on `AgentProfile` already works with any runtime
- Duplicated redaction and parsing code is extracted into a shared module, reducing maintenance burden

### Negative

- The `RuntimeKind::Zai` name becomes misleading; requires a deprecation path or rename
- Config schema grows by two optional fields; must be documented clearly
- Provider-specific deviations (non-standard error formats, streaming quirks) beyond the OpenAI spec are out of V1 scope — users hitting these get clear error messages, not silent workarounds

### Risks

- **Provider deviation flood**: Document "OpenAI-compatible" scope prominently; return clear error for incompatible responses. Mitigate by validating at config time that the endpoint follows the chat completions schema.
- **Duplication refactor breaks existing behavior**: Consolidate into shared module with the same test coverage; run full test suite before merge.
- **Config confusion between `http_api` and CLI runtimes**: Document clearly: `http_api` is for API-key-based providers; `codex`/`claude`/`cursor` are CLI-based.

## Implementation Notes

1. Add `auth_header_name: Option<String>` and `auth_header_prefix: Option<String>` to `RawRuntimeConfig` and `RuntimeConfig`
2. Extract duplicated `redact_sensitive_text`, `redact_bearer_tokens`, and `parse_runtime_output` into `src/runtime/http_util.rs`
3. Update ZaiRuntime to read auth config from `RuntimeConfig` instead of hardcoding `.bearer_auth()`
4. Add config-roundtrip tests for the new fields
5. Add commented-out HTTP provider example to starter config template
6. Optionally: minimal `atelier --doctor` status for custom runtimes (env var check)
