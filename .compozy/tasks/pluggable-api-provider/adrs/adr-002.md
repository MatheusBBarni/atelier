# ADR-002: Rename RuntimeKind::Zai to RuntimeKind::HttpApi

## Status

Accepted

## Date

2026-06-17

## Context

The existing `RuntimeKind::Zai` variant is the only HTTP-based runtime in atelier. It implements OpenAI-compatible chat completions via `reqwest` with SSE streaming and bearer auth. As we generalize this into a configurable HTTP API runtime that supports any OpenAI-compatible provider (OpenRouter, Verboo, DeepSeek, etc.), the name "Zai" becomes misleading — it implies a single provider rather than a generic protocol implementation.

Two options exist: (1) rename `Zai` to `HttpApi` (breaking change), or (2) add `HttpApi` as a new variant with `Zai` as a deprecated alias (no breaking change).

## Decision

Rename `RuntimeKind::Zai` to `RuntimeKind::HttpApi`. This is a breaking change to the TOML config format (`type = "zai"` becomes `type = "http_api"`), but the rename is cleaner and avoids maintaining two code paths for the same protocol.

## Alternatives Considered

### Alternative 1: Alias (Add HttpApi, Deprecate Zai)

- **Description**: Add `RuntimeKind::HttpApi` as a new variant, keep `RuntimeKind::Zai` as a deprecated alias that maps to the same implementation
- **Pros**: No breaking change; existing configs continue to work; gradual migration
- **Cons**: Two enum variants for identical behavior; deprecation warnings add noise; config validation must handle both names indefinitely
- **Why rejected**: The maintenance cost of maintaining two names for the same thing exceeds the migration cost of a clean rename. Existing configs are few (starter template + user overrides).

### Alternative 2: Keep Zai Name, Add Fields

- **Description**: Keep `RuntimeKind::Zai` unchanged, just add `auth_header_name` and `auth_header_prefix` fields to RuntimeConfig
- **Pros**: Zero migration cost; simplest change
- **Cons**: "Zai" is a misleading name for a generic HTTP API runtime; users configuring OpenRouter would see `type = "zai"` which implies a specific provider
- **Why rejected**: The naming confusion creates a worse long-term UX than the one-time migration cost.

## Consequences

### Positive

- Clean naming: `type = "http_api"` accurately describes what the runtime does
- Every OpenAI-compatible provider uses the same runtime kind name
- No deprecation maintenance burden

### Negative

- Breaking change: existing `type = "zai"` in user configs must be updated to `type = "http_api"`
- Requires config migration documentation and potentially a migration helper

### Risks

- **Existing users break on upgrade** — Mitigate with clear changelog entry and a migration note in `--doctor` output that detects `type = "zai"` and suggests updating
- **Documentation drift** — The README and all docs must be updated to use the new name; grep for "zai" to catch stragglers

## Implementation Notes

1. Rename the `Zai` variant in `RuntimeKind` enum to `HttpApi`
2. Update all match arms in `execute_runtime_step_once`, `check_runtime_availability`, and `ProviderStatusProbe`
3. Update config deserialization to accept `type = "http_api"` (and optionally `type = "zai"` during a deprecation window)
4. Update starter config template to use `type = "http_api"`
5. Update README and all documentation
6. Add `--doctor` hint that detects legacy `type = "zai"` and suggests migration
