# ADR-002: V1 ships a thin hook dispatcher plus one built-in battery (cross-platform notifier); audit/webhook stay recipe-based; built-in shipping deferred

## Status

Accepted

## Date

2026-06-15

## Context

ADR-001 fixed the V1 scope (observer hooks, cross-runtime audit backbone, blocking veto deferred to V2). The PRD phase added three product decisions: the **primary persona is the solo developer** (DevEx and eng-manager secondary), the payload is a **pragmatic stable versioned schema** (uniform across runtimes, standards-aligned in spirit), and adoption is **measured locally via `atelier --doctor`** (no phone-home — atelier has zero telemetry today and its audience expects opt-in/privacy).

That left one strategic axis: **how "batteries-included" V1 should be.** Research found that the solo dev's #1 job-to-be-done is "ping me when my run needs me / finishes," and that getting cross-platform desktop notification right is genuinely hard for a user to DIY — OS backends are fragmented (terminal-notifier is macOS-only; notify-send is Linux), while terminal-native OSC 9/777 sequences work over SSH for free but are stripped by tmux without passthrough. Audit-to-file and webhook delivery, by contrast, are trivial one-liners over the user's own shell command (`cat >> audit.jsonl`, `curl`).

Three approaches were considered: (A) thin dispatcher with bring-your-own commands; (B) thin dispatcher plus a built-in cross-platform notifier; (C) an integration hub adding a built-in shipping/exporter to an allowlisted endpoint.

## Decision

**V1 commits to Approach B.** atelier dispatches each matched-event hook with the normalized payload on stdin, and ships exactly **one built-in battery: a cross-platform notification action** that "just works" — terminal-native by default so it functions over SSH, with OS-native fallbacks — so a solo dev can declare a notification without hand-writing per-OS shell. Everything else stays thin: **audit-to-file and webhook delivery are recipe-based** via the user's own command. atelier also ships an `atelier --events follow` JSON stream that doubles as the dry-run/test path. **No built-in network shipping/exporter in V1.**

## Alternatives Considered

### Alternative A: Thin dispatcher (bring-your-own commands)

- **Description**: atelier owns no backends; the user supplies every command, including the notify command.
- **Pros**: Smallest scope and maintenance; maximally flexible; no cross-platform backend to own; matches the council's "atelier dispatches, destination is the user's command."
- **Cons**: Pushes the cross-platform + SSH notification burden onto the *primary* persona — the exact fragmentation research flagged — so the headline solo-dev job is the worst out-of-box experience.
- **Why rejected**: The one thing the primary persona can't easily DIY is precisely the thing A makes them DIY.

### Alternative C: Integration hub

- **Description**: B plus a built-in shipping exporter (webhook / OTel POST) to an allowlisted endpoint, for turnkey pipeline delivery.
- **Pros**: Turnkey for the secondary DevEx/governance personas; gives the ADR-001 egress allowlist real teeth.
- **Cons**: Largest V1 scope; imports the network-egress security surface (allowlist, destination trust, data-exfil boundary) that ADR-001 deliberately deferred; overshoots a solo-dev-primary V1.
- **Why rejected**: Re-sequenced to V2 alongside the blocking veto, where the egress surface can be designed deliberately.

## Consequences

### Positive

- The primary persona's #1 job (notify) works out-of-box, including over SSH — a polish edge competitors fumble cross-platform.
- Everything beyond the notifier stays thin and flexible; no new network-egress surface in V1, so the egress allowlist is legitimately deferred.
- The normalized payload still backs every hook, preserving the cross-runtime differentiator and the V2 on-ramp.

### Negative

- atelier now owns a notification backend — cross-platform fallbacks and the tmux/SSH passthrough edge case become its maintenance burden.
- Slightly more V1 scope than pure dispatch.

### Risks

- **tmux strips OSC notifications** → require passthrough or fall back to an OS-native backend; treat SSH+tmux as a first-class supported case.
- **Notification fatigue** → ship noise-suppressing defaults (e.g., notify only on meaningful moments; consider an "only when terminal unfocused" option).
- **Built-in notifier scope creep** → keep the battery to notifications only; resist absorbing audit/webhook into built-ins (they stay recipes) until there is demand.

## Implementation Notes

This decision is recorded at PRD altitude — the OSC-vs-shell-out mechanics, fallback ordering, and tmux passthrough belong in the TechSpec. The user-facing contract V1 commits to: a declarative built-in notification that works across macOS/Linux and over SSH, configurable per event, with sane noise defaults. The `atelier --events follow` surface follows the existing flag-based CLI pattern (`src/cli.rs`), not a subcommand style.
