# ADR-005: Built-in notifier — OSC-native by default, with a configurable fallback command

## Status

Accepted

## Date

2026-06-15

## Context

The PRD makes "notifications work over SSH" a hard constraint, and the solo developer is the primary persona whose #1 job is the notify ping. Research on the notification landscape found: OS-native notifiers (`osascript`, `notify-send`, BurntToast) are fragmented per-platform *and* fire on the **remote host** over SSH — so they cannot satisfy the SSH constraint as a default. Terminal-native **OSC escape sequences** (OSC 9 `\033]9;…\007`, OSC 777 `\033]777;notify;…`) are rendered by the *terminal application*, so they work locally even when atelier runs over SSH (VS Code forwards them automatically). Their gaps: support varies by terminal, and **tmux strips OSC** without passthrough.

## Decision

A handler's `notify = true` (or a `[hooks.notify]` table for title/body templating) emits a **terminal escape sequence by default** — OSC 9, with the OSC 777 variant where applicable — to the controlling terminal. No external binary, works over SSH. For terminals or tmux configurations that strip OSC, a config key **`notify_fallback_command`** lets the user supply a notifier command (e.g. `terminal-notifier -message`, `notify-send`) that receives the title/body. The tmux passthrough requirement is documented, not auto-configured.

Notification content derives from the normalized payload (ADR-004); defaults fire only on the events the user configured. The notifier is implemented behind a small **injectable backend trait** so unit tests assert the emitted sequence (or the constructed fallback command) without real delivery.

## Alternatives Considered

### Alternative 1: OSC-native only (no fallback)
- **Description**: Emit OSC 9/777 and nothing else.
- **Pros**: Smallest surface; SSH-native.
- **Cons**: Silent no-op on terminals (and tmux without passthrough) that strip OSC.
- **Why rejected**: No recourse where OSC is unsupported; a silent failure of the primary persona's headline feature.

### Alternative 2: OS-backend shell-out as the default
- **Description**: Pick `osascript`/`notify-send`/BurntToast per platform.
- **Pros**: Reliable on a local desktop.
- **Cons**: Over SSH it fires on the server, not the user's machine — violates the PRD SSH constraint.
- **Why rejected**: Cannot be the default; retained only as the *opt-in* `notify_fallback_command`.

### Alternative 3: Auto-detect OSC support, fall back automatically
- **Description**: Probe the terminal and switch backends.
- **Pros**: No user configuration.
- **Cons**: There is no reliable capability query for OSC 9/777; detection is guesswork and tmux confounds it.
- **Why rejected**: An explicit `notify_fallback_command` is honest and deterministic; auto-detection would be flaky.

## Consequences

### Positive
- Notifications work over SSH out of the box, with zero dependency in the default path.
- The backend trait makes the notifier unit-testable without real OS delivery.
- A deterministic escape hatch covers OSC-stripping terminals/tmux.

### Negative
- atelier owns a notification path, including the tmux/terminal edge cases.
- OSC rendering varies by terminal — mitigated by the fallback command, not eliminated.

### Risks
- **tmux strips OSC** → document `set -g allow-passthrough on` and the fallback command; treat SSH + tmux as a supported, documented case.
- **Notification fatigue** → fire only on configured events in V1; an "only when terminal unfocused" option is a future refinement.

## Implementation Notes

The notifier backend lives in the new `src/hooks/` module beside the dispatcher. The default backend writes the escape sequence to the controlling TTY; the fallback backend spawns `notify_fallback_command` via the same subprocess idiom as a `command` handler. Exact OSC-9-vs-777 selection by terminal is an implementation detail inside the default backend.
