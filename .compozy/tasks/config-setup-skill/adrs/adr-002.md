# ADR-002: Deliver V1 via the skills.sh convention + repo bundle (not a native installer)

## Status

Accepted

## Date

2026-06-15

## Context

The idea phase (ADR-001) chose consent-based `skills.sh` delivery. During PRD research we found
atelier's own roadmap (`docs/feature-roadmap.md`) already plans a **native "Skill registry &
install command with lockfile"** — `atelier skill add/update/list/remove` that fetches a
`SKILL.md` into `.agents/skills` and records source + resolved ref + content checksum in
`.agents/skills/skills.lock`. This created a real fork for *how V1 ships*:

- ride the external `skills.sh` CLI now (`npx skills add owner/repo`),
- build or wait for atelier's native command,
- or a hybrid thin installer.

Constraints: ship soon; zero/minimal native Rust; faithful to the user's "skills.sh pattern" +
"install with npm" + "ask the user"; portable to both atelier's own runtime and external host
agents (Claude Code, Cursor, Codex). Skill roots are currently **hand-mirrored** across
`.agents/skills`, `.claude/skills`, `.pi/skills` (byte-identical copies; no sync tooling).

## Decision

Adopt **Approach A**. Author `config-setup` as a standard `SKILL.md` (+ `references/`) published
in the atelier repo so `npx skills add MatheusBBarni/atelier` installs it into any agent's skill
roots, and **mirror the same skill** into atelier's own `.agents/skills/config-setup/` and
`.claude/skills/config-setup/` so atelier's runtime and TUI `/skill:` surface it immediately. Any
npm lifecycle script only **prints a one-line install hint**; it never writes to skill roots.

Defer the native `atelier skill add` registry + `skills.lock` to its dedicated roadmap item. A
future ADR may supersede this once that command ships and config-setup migrates onto it.

## Alternatives Considered

### Alternative 1: Native `atelier skill add` registry (Approach B)

- **Description**: Deliver config-setup as the first payload of the roadmap's skill-registry
  command with a lockfile.
- **Pros**: atelier-owned versioning/provenance; no external tool; advances a charter goal.
- **Cons**: couples V1 to an M-sized feature (full registry + lockfile); much slower.
- **Why rejected**: over-scoped for shipping one config skill; sequence it as its own feature.

### Alternative 2: Hybrid — A now + thin `atelier skills install` (Approach C)

- **Description**: Approach A plus a minimal consent-prompting `atelier skills install` (`--yes`
  for CI) as a precursor to B.
- **Pros**: atelier-owned consent UX; removes the external dependency for atelier users.
- **Cons**: adds native Rust and a second documented install path now.
- **Why rejected for V1**: keeps V1 pure-Markdown; revisit as V1.1 if the external dependency
  proves friction.

## Consequences

### Positive

- Ships now with zero native Rust; portable to 20+ agents; faithful to the stated pattern.
- atelier's own runtime stays independent of `skills.sh` because the skill is repo-bundled.

### Negative

- Cross-agent install path depends on the external `skills.sh` CLI/registry.
- No atelier-owned versioning/lockfile yet.

### Risks

- **Repo layout** must expose `SKILL.md` where `npx skills add` resolves it (root vs a `skills/`
  layout) — resolve in techspec; document a manual-copy fallback.
- **npm v12 disables install scripts by default** — the postinstall hint may need to surface via
  README/first-run output instead of a lifecycle script.
- **Supersession** — migrate onto the native command when the registry roadmap item lands.

## Implementation Notes

- Keep `SKILL.md` body < 500 lines; push the full schema into `references/` (progressive
  disclosure); write a "pushy", trigger-rich description.
- Mirror the skill into every discovered root; version-sync with the config `schema_version`.
