# ADR-005: CI/CD — custom GitHub Pages build with build-time generation + a PR web-checks link gate

## Status

Accepted

## Date

2026-06-12

## Context

The current `.github/workflows/pages.yml` builds `web/` with the Node-only
`withastro/action@v6` on push to `main` touching `web/**`, and performs **no link-check**.
The generator (ADR-003) needs a **Rust toolchain at build time**, and reference fragments
are generated rather than committed (owner decision, ADR-003). Base `/atelier` links can
404 only in production, and no working cross-page link example exists today. Only
`pages.yml` touches `web/` (`release.yml`'s `npm ci` targets the `npm/` launcher, not
`web/`).

## Decision

Replace the opaque `withastro/action` deploy step with an explicit custom Pages workflow
that: checks out → installs Rust + Node → builds `atelier` → runs `atelier --emit-docs`
into the content collection → `npm ci && npm run build` (with `GITHUB_PAGES=true`) →
`actions/deploy-pages`.

Add a new **PR-triggered `web-checks.yml`** (on changes to `web/**`, the generator
sources under `src/**`, and the workflow itself) that runs the same generate → build
sequence and then a **link-check (lychee)** over `web/dist`, failing the PR on any broken
link or missing fragment. The Rust **coverage test** (ADR-003) runs in the existing Rust
test job. Local parity is provided by a `web/package.json` `generate` / `prebuild` script
that invokes the binary (`cargo run` in dev).

## Alternatives Considered

### Alternative 1: Keep `withastro/action` + commit generated fragments

- **Description**: Leave the Node-only deploy; commit the generator output.
- **Pros**: Simplest pipeline; no Rust in web CI.
- **Cons**: Committed generated artifacts; regeneration easy to forget.
- **Why rejected**: The owner chose build-time generation.

### Alternative 2: Link-check only, no coverage test

- **Description**: PR workflow builds and link-checks; completeness is manual.
- **Pros**: Less to set up.
- **Cons**: A newly-added flag/command can silently go undocumented.
- **Why rejected**: The coverage test is the anti-drift guarantee.

### Alternative 3: linkinator / htmltest instead of lychee

- **Description**: A different link checker.
- **Pros**: Node-native (linkinator) — no extra toolchain.
- **Cons**: Slower; less ergonomic in CI.
- **Why deferred**: Acceptable substitutes; lychee chosen for speed and a maintained
  GitHub Action. Revisit if it proves noisy.

## Consequences

### Positive

- Deploys are always fresh from source; no committed generated artifacts.
- Base-path 404s and missing fragments fail **before merge**, not in production.
- The previously-opaque deploy becomes explicit and testable.

### Negative

- Web deploys now require a Rust build (slower; a toolchain/build cache to manage).
- Two workflows to maintain (deploy + PR check) plus the `pages.yml` rewrite.

### Risks

- **Rust build flakiness blocking deploys** → cache the toolchain and reuse the release
  build artifact across the generate and deploy steps.
- **lychee false positives on external links** (e.g., GitHub rate limits) → scope the
  check to internal links or maintain an allowlist.

## Implementation Notes

- Cache cargo and reuse `cargo build --release --bin atelier` between the generate and
  deploy steps.
- Keep the `pages.yml` concurrency group `pages` with `cancel-in-progress: false`.
- `web-checks.yml` path filters: `web/**`, `src/cli.rs`, `src/config/**`,
  `src/slash_commands.rs`, and the workflow file.
