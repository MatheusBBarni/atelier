# ADR-003: Keymap Data Model and Resolution

## Status

Accepted

## Date

2026-06-15

## Context

Keybindings are hardcoded in two pure functions (`key_event_to_tui_command_with_ui`,
`src/tui/mod.rs:1056`; `key_event_to_tui_command`, `1388`). The composer is a single-line
`AppState.input: String` with a char-index cursor `TuiUiState.input_cursor: usize`, mutated by
`insert_input_character`, `remove_input_character_before_cursor`, and
`move_input_cursor(ui_state, input, InputCursorCommand)`. There is **no** existing
`KeyEvent`↔string formatter/parser. `RawConfig` uses `#[serde(deny_unknown_fields)]`. The PRD
(Approach A) wants a remap layer that is consult-before-fallback with byte-identical defaults,
plus five new readline editing actions. Two contract choices were made with the user: the
`[keybindings.normal]` table is keyed **action → key**, and key strings use **`ctrl+k`**
(lowercase, `+`-separated, case-insensitive parse).

## Decision

- **Context-scoped schema, `action → key`.** `[keybindings.<context>]` maps a stable action name
  to a key string, or to `false` to unbind. V1 wires only `[keybindings.normal]`; any other
  context is an unknown-context error (see ADR-004). Overriding an action replaces its default
  key; this makes merge-over-defaults and unbind trivial and removes "two keys for one action"
  ambiguity.
- **Closed action vocabulary.** A `KeyAction` enum enumerates the V1 remappable normal-mode
  actions (10): `toggle-roster`; `scroll-page-up`, `scroll-page-down`, `scroll-top`,
  `scroll-bottom`; and the new editing actions `input-line-start`, `input-line-end`,
  `input-kill-to-end`, `input-kill-to-start`, `input-kill-word-back`. An **exhaustive
  compile-checked `match` from `KeyAction` to the concrete `TuiCommand`** guarantees action names
  cannot drift from the routing enum. Action names serialize via serde rename to the kebab-case
  strings above.
- **New editing commands.** Add `InputCursorCommand::LineStart`/`LineEnd` (cursor moves, reuse
  `move_input_cursor`) and `TuiCommand::InputKill(InputKillCommand { ToLineEnd, ToLineStart,
  WordBack })` executed by a new `kill_input(state, ui_state, cmd)` that mutates `state.input` +
  `input_cursor` using the existing `byte_index_for_char` helper. `Ctrl-U` follows readline
  `unix-line-discard` (kill from cursor to line start); kills discard text (no kill-ring/yank in
  V1).
- **`keys` module.** Owns `parse_key(&str) -> Result<KeyChord>` and `format_key(&KeyChord) ->
  String`, where `KeyChord` wraps a crossterm `KeyEvent` (code + modifiers). Both enforce the
  portable allowlist (see ADR-004). `format_key` drives the Keys-tab rendering.
- **`Keymap` resolution and placement.** `Keymap` holds the resolved `KeyEvent → KeyAction`
  lookup, built once by `Keymap::resolve(&DEFAULTS, &overrides)` at TUI init from
  `EffectiveConfig`. It lives on **`TuiUiState`** (rendering + routing are TUI concerns; this
  avoids touching the event-sourced app core). `key_event_to_tui_command_with_ui` consults it in
  the **normal-input branch only** (after the modal cascade), then falls through to the
  unchanged hardcoded normal-mode handler for anything unmapped. No overrides ⇒ defaults applied
  ⇒ byte-identical behavior.
- **Keys tab is data-driven.** `keys_tab_lines(keymap, theme)` renders the active map via
  `format_key`, with reserved/fixed keys shown locked.

## Alternatives Considered

### Alternative 1: `key → action` schema

- **Description**: Table keyed by key string, value is the action.
- **Pros**: Reads like "this key does X"; familiar from helix.
- **Cons**: Remapping an action to a new key also requires disabling its old default key; must
  detect an action landing on two keys; messier merge-over-defaults.
- **Why rejected**: `action → key` makes override/unbind/merge unambiguous (user-confirmed).

### Alternative 2: String-typed action targets (no enum)

- **Description**: Store action as a `String`, resolve at runtime.
- **Pros**: Less code.
- **Cons**: Action names drift from the real commands; typos are runtime failures.
- **Why rejected**: An exhaustive `KeyAction → TuiCommand` match is compiler-enforced and free.

### Alternative 3: Keymap on `AppState` / event core

- **Description**: Carry the resolved keymap through the app/event-sourcing layer.
- **Pros**: Single source on the app snapshot.
- **Cons**: Touches the well-tested app core for a purely TUI input concern; higher risk.
- **Why rejected**: The charter demands near-zero risk to the routing/app core; `TuiUiState` is
  the right home.

## Consequences

### Positive

- Defaults unchanged with no config; the override is a localized lookup-before-fallback.
- Action↔command drift is impossible (exhaustive match); the editing actions reuse existing
  cursor/buffer helpers.
- The same `keys` module powers parsing, validation, and the live Keys tab (single source).

### Negative

- A closed `KeyAction` vocabulary must be extended (by one enum arm + one match arm) whenever a
  future action becomes remappable — intentional, compiler-guided.
- Keymap on `TuiUiState` means it is rebuilt per TUI session (acceptable; no hot-reload in V1).

### Risks

- **`Ctrl-U` semantics** may surprise users expecting "kill whole line" → documented as
  readline `unix-line-discard` in the `--init-config` comment and Keys tab.
- **Existing Keys-tab test** asserts hardcoded strings → rewrite to assert the default keymap
  renders the expected defaults (no-config ⇒ byte-identical).
