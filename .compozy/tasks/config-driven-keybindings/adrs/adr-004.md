# ADR-004: Config Trust Boundary and Validation Severity

## Status

Accepted

## Date

2026-06-15

## Context

Config merges through a ladder (`load_effective_config`, `src/config/mod.rs:1647`): builtin →
explicit `--config`/env → home (`~/.config/.atelier/atelier.toml`) → local
(`./atelier.toml`). Each layer calls `apply_config_file` → `apply_raw(raw, source_dir,
source_name)` (`909`), which applies fields **unconditionally** — there is **no per-layer
marker**. A local `./atelier.toml` ships inside any cloned repo, i.e. untrusted input, and
keybindings are the channel a user employs to *interrupt* an agent and to *answer approval
prompts* that gate writes (ADR-001 / PRD trust requirement). `EffectiveConfig` is consumed by
`atelier --doctor` (`src/doctor/mod.rs`, `DoctorCheck`/`DoctorReport`) and `--print-config`.
The user chose **ignore-and-warn** for project-local `[keybindings]`.

## Decision

- **`ConfigLayer` marker.** Introduce `enum ConfigLayer { Builtin, Cli, Home, Local }`, threaded
  through `apply_config_file(..., layer)` into `apply_raw(..., layer)`. Existing sections keep
  applying on every layer (unchanged behavior).
- **Keybindings are user-scope only.** `apply_raw` applies `[keybindings]` only when
  `layer != Local`. When a `Local` layer carries `[keybindings]`, it is skipped and a warning
  is recorded on the merged/effective config (`keybinding_warnings: Vec<String>`) naming the
  file. Honored layers: `Home` and explicit `--config` (`Cli`). No per-key CLI flags in V1.
- **Validation severity split.** Keybinding overrides are parsed and validated during
  `load_effective_config` using the `keys` module + `KeyAction` registry (ADR-003):
  - **Hard-fail** (return `Err` with a precise `file + field + value` message; blocks startup):
    binding a **reserved key** (interrupt/quit), a **non-portable key** (outside the allowlist),
    an **unknown context** (e.g. `[keybindings.approval]` in V1), a **duplicate** (two actions
    resolving to the same key), or a **malformed key string**.
  - **Soft-fail** (drop the offending entry, keep the rest, record a warning): an **unknown
    action name** or an otherwise parseable-but-unsupported target.
- **Diagnostics surface.** Hard errors block load, so they appear identically on startup and
  under `--doctor` (which loads config first). Soft warnings + the local-layer-ignored warning
  ride on `EffectiveConfig.keybinding_warnings` and surface as a `config.keybindings`
  `DoctorCheck` (`status: Warn`) and a one-line TUI startup notice. `--print-config` emits the
  effective (post-merge) keybindings.
- **Portable allowlist.** Bindable keys: `Ctrl`+letter except `C/D/I/M/[` (reserved or terminal
  aliases), function keys `F1..F12`, arrows, `PageUp/PageDown/Home/End`. Everything else is
  rejected at load (no silent dead keys). `Alt`/`Super`/`Ctrl+digit`/`Ctrl+Shift+*` are out of
  V1 (need Kitty protocol).
- **Reserved set enforced structurally.** Consolidate the three current `Ctrl-C` branches
  (`src/tui/mod.rs:1070`, `1123`, `1394`) into a single guard at the top of
  `key_event_to_tui_command_with_ui` that returns the interrupt command for the reserved
  `KeyEvent` **before** any keymap lookup — so the kill-switch cannot be shadowed regardless of
  config. The keymap lookup is gated to the normal-input context, so it can never resolve while
  an approval/clarification/help modal owns input.

## Alternatives Considered

### Alternative 1: Strip `keybindings` from the local `RawConfig` inline

- **Description**: In `load_effective_config`, set `raw.keybindings = None` before applying the
  local layer.
- **Pros**: No new enum.
- **Cons**: Implicit; no clean place to attach the "ignored — move to home" provenance warning;
  doesn't generalize.
- **Why rejected**: The `ConfigLayer` marker is explicit, supports the warning, and is reusable
  if another section ever needs user-scope.

### Alternative 2: Hard-error on local `[keybindings]`

- **Description**: Refuse to start if project-local config contains `[keybindings]`.
- **Pros**: Loudest signal.
- **Cons**: A cloned repo could block the app from launching — a denial-of-service via committed
  config.
- **Why rejected**: User chose ignore-and-warn; safe by default without a DoS vector.

### Alternative 3: Validate only inside `--doctor`

- **Description**: Let any config load; report problems only in doctor.
- **Pros**: Never blocks startup.
- **Cons**: A reserved-key shadow or duplicate would silently take effect until the user runs
  doctor.
- **Why rejected**: Security-critical and structural errors must fail-fast at load (PRD).

## Consequences

### Positive

- Untrusted project config can never alter the user's control keys; the kill-switch is
  structurally unshadowable.
- One `ConfigLayer` change unlocks a clear, auditable trust model and the provenance warning.
- Severity split keeps a cosmetic typo from bricking the TUI while still fail-fasting the
  dangerous cases.

### Negative

- `apply_config_file`/`apply_raw` signatures gain a `ConfigLayer` parameter (mechanical churn at
  call sites).
- `EffectiveConfig` gains `keybinding_warnings`, a non-fatal-diagnostics carrier.

### Risks

- **Threading `ConfigLayer` through all call sites** could miss one → covered by a test that a
  local `[keybindings]` is ignored and warned.
- **Hard-fail blocks `--doctor` load** for the worst configs → acceptable; the precise load
  error is the diagnostic.

## Implementation Notes

`apply_config_file` is at `src/config/mod.rs:1713`; layer call sites are in
`load_effective_config` (`1654-1688`). Doctor check slots into `run_doctor`
(`src/doctor/mod.rs:55`). Reserved-key guard consolidates `src/tui/mod.rs:1070/1123/1394`.
