# ADR-001: V1 Scope for Config-Driven Keybindings

## Status

Accepted

## Date

2026-06-15

## Context

Every atelier keybinding is hardcoded in two pure functions —
`key_event_to_tui_command_with_ui` (`src/tui/mod.rs:1056`) and
`key_event_to_tui_command` (`1388`) — which map `(state, KeyEvent) -> Option<TuiCommand>`.
Keys route through a modal precedence cascade (help → clarification → approval →
`/agent:` → `/skill:` → `@` mention → command dropdown → queue → normal input).
Power users (vim/emacs muscle memory), users whose terminal/OS already claims a key
atelier uses (classic: `Ctrl-L`), and accessibility needs cannot remap anything.

A council session (pragmatic-engineer, architect-advisor, security-advocate,
product-mind, devils-advocate) stress-tested the proposal and surfaced four forces:

1. **The remappable surface is small.** Reading the routers, the cleanly remappable
   *normal-mode* actions are only ~5: `Ctrl-L → ToggleRoster`, `PageUp/PageDown → scroll`,
   `Home/End → scroll top/bottom`. The keys power users most want — `hjkl` list-navigation
   (lives in *fixed* modal/dropdown handlers) and emacs line-editing `Ctrl-A/E/K/W`
   (**do not exist as `TuiCommand` variants at all**) — are out of reach without expanding
   scope. So V1 mainly serves the *terminal-conflict victim* and light remappers, not yet
   the full muscle-memory power user.
2. **The on-disk schema is the only irreversible choice.** Code (the lookup) is free to
   refactor; a config format becomes a public contract the moment a user writes it. Every
   cited prior-art tool (Claude Code, helix, zellij, yazi, atuin) ships a **context/mode-scoped**
   keymap with merge-over-defaults from day one.
3. **Keys are a security control surface.** Approval prompts gate `WriteFile`/`ApplyPatch`/
   `RunCommand`; `Ctrl-C` (interrupt/quit) is the kill-switch. `Ctrl-C` currently routes
   *through* the pure function across three branches with no signal handler, so a config
   could shadow it. A local `./atelier.toml` ships inside any cloned repo (untrusted input).
4. **Terminal limits constrain what is bindable.** In legacy mode `Tab==Ctrl+I`,
   `Enter==Ctrl+M`, `Esc==Ctrl+[`; `Ctrl+digit`/`Ctrl+Shift+*`/`Cmd` are indistinguishable
   without the Kitty keyboard protocol (partial terminal support). A user can otherwise
   configure a binding the terminal can never deliver — a silent dead key.

## Decision

Ship the **Hybrid** of "Foundation + conflict relief" **plus composer line-editing**: a
keymap engine and a forward-compatible, **context-scoped** TOML schema (`[keybindings.normal]`),
with V1 wiring **only** the `normal` context, **and** a small set of new readline/emacs
line-editing actions added to the input composer so the muscle-memory power user is served
in V1 without touching the fixed modal handlers.

- **Override seam:** a keymap is consulted at the top of normal-input routing, before the
  hardcoded cascade. **Absent config → byte-for-byte identical defaults** (regression-tested).
- **Context-scoped schema now, normal-only wired:** the on-disk format is keyed by context
  (`[keybindings.normal]`) even though only `normal` is honored in V1, so V2 (modal contexts,
  presets) is **additive, never a format migration**. Writing a not-yet-supported context
  (e.g. `[keybindings.approval]`) is a precise load-time error, not a silent miss.
- **Bindable surface = portable allowlist:** Ctrl+letter (except `C/D/I/M/[`), function keys,
  arrows, `Page/Home/End`. Keys outside the allowlist are **rejected at load**. This designs
  out the undeliverable-key footgun rather than warning about it.
- **Action targets = existing remappable normal-mode `TuiCommand`s**, bound to names via an
  **exhaustive compile-checked match** so names cannot drift from the enum.
- **Composer line-editing (Hybrid slice):** add new normal-mode actions for readline/emacs
  editing in the input composer — `Ctrl-A` (line start), `Ctrl-E` (line end), `Ctrl-K`
  (kill-to-end), `Ctrl-U` (kill line), `Ctrl-W` (kill word). These are new `TuiCommand`
  variants + composer buffer logic, all within normal mode (no modal-handler or approval-key
  changes), and are remappable like any other binding. This is the slice of the "ambitious"
  vocabulary that fits the normal-mode charter.
- **Safety, structural:** consolidate the three `Ctrl-C` branches into a **single pre-lookup
  chokepoint**; quit/interrupt are structurally non-rebindable regardless of config; a config
  that *tries* to bind a reserved key is **hard-rejected** with a file/field/value error.
- **Approval accept/reject keys stay fixed** (out of scope) — reframed as a security feature.
- **Trust boundary = user scope:** keybindings load from **home/global config + CLI only**,
  not the local/project `./atelier.toml`. (Generalizable to a per-section trust policy later;
  YAGNI for V1.)
- **Validation posture (refines the original "fail-fast"):** **hard-fail** on security-critical
  or structural violations (reserved-key bind, malformed/unknown context); **fail-soft** on
  cosmetic mistakes (unknown action, unsupported key) — fall back to the default for that
  entry, collect all errors, and surface them via `atelier --doctor`. `--print-config` emits
  the effective keymap.
- **Discoverability:** the existing static help `Keys` tab (`keys_tab_lines`, `src/tui/mod.rs:3737`)
  becomes **data-driven**, rendering the active keymap with fixed/reserved keys visibly locked.

## Alternatives Considered

### Alternative 1: Flat global keymap

- **Description**: One un-scoped key→action map consulted before the cascade.
- **Pros**: Smallest possible schema; trivial lookup.
- **Cons**: Contradicts the modal cascade (routing is contextual); a "normal" binding could
  leak into the approval context (a security invariant break); reshaping to context-scoped
  later is a breaking change to a published config contract.
- **Why rejected**: The on-disk format is the irreversible artifact; a flat map calcifies the
  wrong shape. Context-scoping costs one serde nesting level now.

### Alternative 2: Presets + leader-key first (Product Mind)

- **Description**: Ship `vim`/`emacs` presets and an OpenCode-style leader-key escape hatch
  over the engine, defer per-key TOML to an evidence-driven V2.
- **Pros**: Arguably the cheaper learning loop for the power-user hypothesis; leader-key
  sidesteps terminal conflicts without per-key remapping.
- **Cons**: Credible presets are impossible without first **building the missing line-editing
  `TuiCommand`s and lifting `hjkl` nav out of the fixed modal handlers** — exactly the
  routing-core risk and scope creep this feature was chartered to avoid. A leader-key is a new
  modal input state. A preset of 5 scroll keys labeled "vim" is cargo-cult.
- **Why rejected for V1, adopted for V2**: Becomes a clean, additive surface over this schema
  once the action vocabulary exists. V1's shipped config is itself the instrument that earns it.

### Alternative 3: Ambitious — expand vocabulary + full context-scoped remapping

- **Description**: Add emacs line-editing actions, make `hjkl` list-nav remappable, and allow
  remapping modal/dropdown keys too.
- **Pros**: Actually serves the muscle-memory power user end-to-end.
- **Cons**: Large, risky, touches the well-tested modal handlers and the approval control
  surface; expands the security-critical reserved set; far beyond an "M".
- **Why rejected (mostly)**: Violates the near-zero-risk-to-routing-core charter. The one
  slice that *does* fit the charter — **composer line-editing**, which lives entirely in
  normal mode — was pulled into V1 as the Hybrid. The rest (modal-key remapping, `hjkl`
  list-nav, presets, leader-key) is sequenced as V2.

### Alternative 4: Honor the local layer / fail-fast everything

- **Description**: Merge `[keybindings]` through the full ladder including `./atelier.toml`;
  reject the whole config on any invalid entry.
- **Pros**: Ladder uniformity; simplest validation rule.
- **Cons**: Local layer is attacker-controlled (malicious-project-config class); fail-fast on a
  cosmetic typo can strand a user who cannot read the error (lockout).
- **Why rejected**: Security carve-out (user-scope) + nuanced validation (hard-fail critical,
  soft-fail cosmetic, surfaced via `--doctor`) are strictly safer at near-zero extra cost.

## Consequences

### Positive

- Removes a hard adoption blocker (terminal/OS key conflict, e.g. `Ctrl-L`) and lays a durable,
  forward-compatible foundation for presets/contexts/leader-key in V2.
- Near-zero risk to the well-tested routing core: defaults unchanged, lookup is consult-before-fallback.
- Safety is *strengthened* vs today (single Ctrl-C chokepoint; structurally unkillable quit;
  approval keys fixed; untrusted project configs can't touch keys).
- Single-sourced discoverability (live Keys tab + `--print-config`) that cannot drift.

### Negative

- The Hybrid's composer line-editing closes most of the muscle-memory gap (readline/emacs
  editing is the first thing such users reach for in a text input), but **list-navigation
  remapping** (`hjkl` over dropdowns/clarification) is still V2, so vim-style *navigation*
  users are only partially served in V1. Honest framing required in docs and the Keys tab.
- The line-editing slice adds ~5 `TuiCommand` variants + composer buffer logic + tests — a
  modest scope increase over the pure "Foundation + conflict relief" baseline.
- A `defaults-in-code / overrides-in-data` split is intentional debt until V2 data-fies the cascade.

### Risks

- **Audience mismatch** (power user underserved) → mitigate with explicit V1 framing + a V2 path;
  treat shipped configs as the demand instrument.
- **Action-name ↔ `TuiCommand` drift** → exhaustive compile-checked match + round-trip test.
- **Existing test churn** (`keys_tab_lines_contains_expected_keybindings` asserts hardcoded strings)
  → rewrite to assert "no config ⇒ byte-identical defaults".
- **Reserved-set enforcement must dominate all Ctrl-C branches** → consolidate to one chokepoint
  (do not patch three).
- **Schema lock-in** → version-tolerant, fail-soft schema; unknown keys fall back, never brick.

## Implementation Notes

- Add `keybindings: Option<RawKeybindings>` to `RawConfig` (`src/config/mod.rs:419`), applied in
  `apply_raw` (`909`) — but only from the home/global + CLI layers (user scope), not local.
- Centralize string↔`KeyEvent` parsing, the action-name↔`TuiCommand` match, the reserved set, the
  portable allowlist, and the Keys-tab display model in one module to contain the drift-prone seams.
- Consolidate `Ctrl-C` handling (currently `src/tui/mod.rs:1070`, `1123`, `1394`) into one pre-lookup
  guard.
- Wire keybinding diagnostics into `src/doctor/mod.rs` and emit the effective keymap via `--print-config`.
- Make `keys_tab_lines` (`src/tui/mod.rs:3737`) data-driven; keep all color in theme tokens
  (`colors_live_only_in_theme_module` test).
