# ADR-003: App-Owned Queue State And Replay

## Status

Accepted

## Date

2026-06-07

## Context

The queued follow-up inputs PRD requires explicit `/queue <message>` and `/q <message>` commands, visible queue state, cancellation before replay, FIFO replay after clean completed Runs, and paused replay after unsafe Run endings.

The existing codebase already centralizes Run lifecycle behavior in `App`. `App::submit_prompt` parses app-owned commands, rejects new normal prompts while a Run is active, records history events, updates `AppState`, and drives Runs. The TUI owns input editing, local help, rendering, and app-worker dispatch, but it should not own product lifecycle semantics. The existing worker channel can buffer events, but it is transport-level machinery, not user-visible queue state.

## Decision

Queued follow-up state and replay policy will be owned by `App`.

The implementation will:

- add queue item and queue view fields to `AppState`;
- parse `/queue <message>` and `/q <message>` in `App::submit_prompt` before unknown slash-command rejection;
- store each queued item with id, prompt text, created timestamp or sequence, status, and optional pause reason;
- record lightweight queue lifecycle history events and project them into Chat;
- replay at most one queued item after each clean completed Run;
- pause replay for failed, interrupted, limit-reached, approval-waiting, clarification-waiting, or otherwise non-clean endings;
- keep the TUI responsible for rendering queue state, exposing cancel/resume controls, and documenting commands in help and slash-command suggestions.

## Alternatives Considered

### Alternative 1: TUI-Local Queue State

- **Description**: Store queued items in `TuiUiState` and replay through the app worker when the TUI sees an idle state.
- **Pros**: Smallest initial code surface and strictly limited to the current TUI.
- **Cons**: Makes queued follow-ups terminal UI behavior instead of app behavior, complicates testing, and risks duplicate queue logic when replay edge cases or non-TUI surfaces appear.
- **Why rejected**: Queued follow-ups are app-visible user intent and must respect the same lifecycle rules as normal prompt submission.

### Alternative 2: Worker Channel As Queue

- **Description**: Let queued prompts accumulate in the existing app-worker channel while the active Run is busy.
- **Pros**: Minimal new state.
- **Cons**: Invisible, not cancellable, not statused, not auditable as product state, and vulnerable to surprising replay.
- **Why rejected**: The PRD explicitly requires visible queue state and cancellation before replay.

### Alternative 3: Duplicate Parsing In TUI And App

- **Description**: Parse `/queue` and `/q` in both TUI key handling and `App::submit_prompt`.
- **Pros**: TUI can provide immediate local feedback.
- **Cons**: Creates two command definitions that can drift and makes non-TUI submit paths inconsistent.
- **Why rejected**: The app already parses app-owned commands and unknown slash commands; a single command parser keeps behavior coherent.

## Consequences

### Positive

- Preserves the one-active-Run invariant at the same layer that starts Runs.
- Makes queue state testable without terminal event plumbing.
- Keeps history and Chat projection consistent with the rest of the app.
- Avoids treating transport buffering as user-facing behavior.
- Leaves runtime adapters unchanged.

### Negative

- Requires `AppState` and chat projection changes for a TUI-only MVP.
- Requires careful replay control to avoid recursive prompt submission bugs.
- Requires TUI changes to render queue controls even though queue ownership lives in `App`.

### Risks

- **Replay recursion or double-start**: Replaying from inside run completion could accidentally start multiple Runs. Mitigate by draining at most one queued item after a clean completion and by preserving active-run guards.
- **Paused state drift**: A queued item could remain paused after the user resumes or cancels if status updates are incomplete. Mitigate with focused queue state transition tests.
- **Command drift**: Help text, slash suggestions, and unknown-command guidance can diverge. Mitigate by centralizing command metadata where the existing slash-command dropdown work introduces it, or by updating every visible command list in the same change.

## Implementation Notes

- Add explicit queue events such as `follow_up_queued`, `follow_up_cancelled`, `follow_up_replay_started`, `follow_up_replay_paused`, and `follow_up_replay_resumed`.
- Project queue events as Chat diagnostic or prompt-adjacent items until a dedicated Chat item kind is justified.
- Keep queued prompts session-scoped; do not persist queue state for restart recovery in V1.
- Add app-level tests for command parsing, FIFO replay, cancellation, paused replay after non-clean endings, and active-run preservation.
- Add TUI tests for help text, slash suggestions, queue rendering, and cancel/resume command dispatch.
