# ADR-002: Select Explicit Queue-Next MVP For PRD

## Status

Accepted

## Date

2026-06-06

## Context

The queued follow-up inputs PRD needs a product approach that turns the approved idea into a clear MVP. The feature should optimize first for preventing lost follow-up intent for power TUI users running long agent tasks.

Clarification decisions established that V1 should:

- use explicit `/queue <message>` and `/q <message>` commands;
- preserve normal prompt submission behavior while a Run is active;
- replay queued items FIFO after clean completed Runs;
- pause blocked items with a visible reason plus resume and cancel controls;
- support viewing the queue and cancelling items in MVP;
- include `/queue` and `/q` in help text and slash-command suggestions.

## Decision

The PRD will use the Explicit Queue-Next MVP approach.

V1 will focus on explicit queue-next behavior: users can add queued follow-up Prompts through `/queue` or `/q`, inspect the pending list, cancel queued items before replay, and understand when replay is paused because the previous Run did not finish cleanly. The MVP will not include edit, reorder, persistence, automatic busy-send queueing, or mid-run steering.

## Alternatives Considered

### Alternative 1: Rich Queue Manager

- **Description**: Include edit and reorder controls in the MVP alongside queueing, viewing, cancellation, and replay.
- **Pros**: Closer to advanced competitor queue experiences and more flexible for power users.
- **Cons**: Expands MVP scope before validating the core queue-next behavior.
- **Why rejected**: The immediate product goal is preventing lost follow-up intent. View and cancel provide enough control for V1.

### Alternative 2: Minimal Hidden Queue

- **Description**: Add `/queue` with only a count or basic status, without a visible list or cancellation.
- **Pros**: Smaller visible product surface.
- **Cons**: Fails the selected control requirement, makes stale intent harder to manage, and risks recreating hidden buffering as product behavior.
- **Why rejected**: The user selected view and cancel controls during clarification, and the market research shows users expect queue state to be visible.

### Alternative 3: Automatic Busy-Send Queue

- **Description**: Treat normal prompt submission during an active Run as queued input.
- **Pros**: Very low friction and closer to some agent chat defaults.
- **Cons**: Changes existing prompt semantics, can surprise users, and weakens the clear distinction between immediate rejection, queued intent, and future steering modes.
- **Why rejected**: The selected V1 requires explicit command-only queueing.

## Consequences

### Positive

- Keeps the PRD focused on one user outcome: follow-up intent is not lost during long Runs.
- Preserves the current one-active-Run mental model.
- Gives users enough visibility and control to trust queued replay.
- Leaves room for future richer queue controls after the core behavior is validated.

### Negative

- Users who expect automatic queueing must learn `/queue` or `/q`.
- Users cannot edit or reorder queued items in V1.
- The PRD must define clear paused-queue UX so safe replay does not feel broken.

### Risks

- **Discoverability risk**: Users may not know `/queue` exists. Mitigate with help text and slash-command suggestions.
- **Adoption risk**: Some users may still paste follow-ups normally and hit the active-run rejection. Mitigate with clearer rejection guidance that points to `/queue`.
- **Trust risk**: Queued replay can feel surprising if not visible. Mitigate by showing queue state and paused reasons before replay.

## Implementation Notes

- The PRD should describe user-visible capabilities and outcomes, not internal implementation details.
- The TechSpec should later define exact command parsing, state shape, replay transitions, and test coverage.
