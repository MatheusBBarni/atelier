# ADR-001: Scope Queued Follow-Up Inputs V1

## Status

Accepted

## Date

2026-06-06

## Context

Atelier's TUI currently preserves a one-active-Run model. A normal submitted Prompt creates one Run, and `App::submit_prompt` rejects new prompts while the app is `Planning`, `Running`, or `WaitingForUser`, except for explicit clarification handling. This keeps orchestration clear, but it creates friction during long-running work: users often think of follow-up instructions while the harness is busy, and those instructions can be rejected, forgotten, or hidden in transport-level buffering.

The TUI already has local command handling for `/help` and `/reload:skills`, and the app already owns Run lifecycle state. The worker mpsc channel can buffer events, but that queue is not user-visible, not cancellable, and should not become product behavior.

Market patterns from Cursor, Claude Code, Codex, and adjacent agent tools show that users increasingly expect slash commands and queued or deferred inputs in long-running agent sessions. V1 should satisfy the core need without changing normal prompt semantics or weakening the one-active-Run invariant.

## Decision

Queued follow-up inputs V1 will add explicit TUI commands:

- `/queue <message>`
- `/q <message>`

Only those commands queue follow-up prompts. Normal sends keep current behavior and remain rejected while a Run is active.

The TUI is the only V1 surface for command entry and queue controls, but the App owns the queue state and replay policy. Each queued item has stable identity, visible order, and cancellable state. The TUI renders the queue count/list and exposes cancellation before replay.

Queued messages replay FIFO one at a time. Auto-replay occurs only after a clean completed Run and only when the app can start a new Run without unresolved user input. Failed, interrupted, limit-reached, approval-waiting, clarification-waiting, or otherwise non-clean endings pause the queue visibly until the user resumes or cancels.

Runtime adapters must not receive special queue semantics in V1. They continue to receive ordinary prompts only when the App starts a normal Run.

## Alternatives Considered

### Alternative 1: Implicitly queue every normal send while busy

- **Description**: Treat any prompt submitted during an active Run as a queued follow-up.
- **Pros**: Lowest friction and matches some agent UI defaults.
- **Cons**: Surprises users who expected immediate rejection or steering, blurs normal prompt semantics, and can accidentally chain stale instructions.
- **Why rejected**: The user explicitly selected explicit command-only queueing for V1, and council advisors agreed that normal sends should preserve current behavior.

### Alternative 2: TUI-only local queue state

- **Description**: Store queued items entirely in `TuiUiState` and replay through the app worker when the TUI observes idle state.
- **Pros**: Fastest narrow implementation and strictly scoped to the TUI.
- **Cons**: Makes queued prompts terminal-rendering behavior instead of app behavior, weakens testability, complicates lifecycle edge cases, and risks future duplication for any non-TUI surface.
- **Why rejected**: A queued follow-up is app-visible user intent. The TUI should expose commands and controls, while App should own queue state and replay.

### Alternative 3: Use the worker mpsc channel as the queue

- **Description**: Let submitted prompts accumulate in the existing TUI worker channel while the app is busy.
- **Pros**: Requires little new state.
- **Cons**: Invisible to users, not cancellable, not ordered as product state, and indistinguishable from transport buffering.
- **Why rejected**: This would reproduce the core problem under a different name and would not satisfy view/cancel requirements.

### Alternative 4: Full queue platform with edit, reorder, persistence, interrupts, and cross-surface support

- **Description**: Build a richer queue similar to Cursor, Augment, or Replit with editing, reordering, persistence, send-now, pause/resume, and interrupt modes.
- **Pros**: More complete and closer to advanced competitor behavior.
- **Cons**: Expands scope into prompt scheduling, replay safety, persistence, and interruption semantics before the core behavior is validated.
- **Why rejected**: Valuable later, but too broad for V1. The product need is explicit queue-next behavior, not a full task scheduler.

## Consequences

### Positive

- Preserves the one-active-Run invariant.
- Gives users a visible, cancellable place to put follow-up intent during long runs.
- Avoids hidden transport buffering as product behavior.
- Keeps runtime adapters generic and harness-owned lifecycle boundaries intact.
- Creates a clean foundation for future queue modes such as steer-now, side-question, or cancel-and-replace.

### Negative

- Requires App state changes even though the initial surface is TUI-only.
- Users who expect automatic busy-send queueing still need to learn `/queue` or `/q`.
- V1 will not support editing, reordering, persistence, or send-now controls.

### Risks

- **Stale queued intent**: A queued message may become wrong after the active Run changes files or fails. Mitigate by auto-replaying only after clean completion and pausing on non-clean endings.
- **Slash-command ambiguity**: `/q` must be recognized only as a slash command, while plain `q` remains normal input. Mitigate with command parsing tests.
- **Queue surprise**: Users may forget queued messages exist. Mitigate with persistent queue count/list and visible pause/cancel affordances.
- **State drift**: TUI help, slash-command suggestions, and unknown-command guidance can diverge. Mitigate by reusing shared command metadata where available.

## Implementation Notes

- Add queue-oriented App events or methods rather than overloading `PromptSubmitted`.
- Queue item fields should include at least id, prompt text, created order/time, and status.
- Parse `/queue <message>` and `/q <message>` before unknown slash-command rejection.
- Empty `/queue` or `/q` should show usage rather than queueing an empty prompt.
- Queue replay should dispatch only one prompt after each clean completed Run.
- Cancellation should be deterministic until the queued item begins replay.
- Help text and any slash-command dropdown metadata should include `/queue` and `/q`.
