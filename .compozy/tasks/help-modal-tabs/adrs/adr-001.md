# ADR-001: V1 Scope for the Tabbed Help Modal

## Status

Accepted

## Date

2026-06-12

## Context

The TUI help modal (`render_help_modal`, `src/tui/mod.rs:3085`) is today a single
scrollable overlay with two flat sections (TUI commands + CLI flags). The stated
user pain is "hard to scan." The product owner wants a **tabbed** help surface with
**more useful information**, including **live session data**, optimized for
**new/occasional users**.

A four-advisor council (`pragmatic-engineer`, `architect-advisor`, `product-mind`,
`devils-advocate`) stress-tested the scope against the codebase. Key constraints
surfaced:

- `render_help_modal(frame, &theme)` takes no state today, but both call sites
  (`src/tui/mod.rs:2026, 2068`) already sit inside `render(frame, &AppState, &mut TuiUiState)`,
  so `state.agents` (with `RuntimeAvailability`) and `ui_state.skill_suggestions` are
  already in scope — live Agents/Skills are a **signature change, not snapshot surgery**.
- The **Agent Roster** (`Ctrl-L`, `src/tui/mod.rs:1946`) is visible by default
  (`roster_visible: true`) and already renders live agents — a standalone "Agents &
  Runtimes" tab would duplicate it.
- **Approval mode** and **workspace read/write roots** are NOT in `AppState` (they live
  in `App.config`); surfacing them live requires extending the projected
  `ConfigStatusView` and its sync writer — the only genuine plumbing cost.
- The help modal blocks all keys except Esc/Ctrl-C; tab navigation and any filter input
  must be added to key routing. 8 tests encode help contracts (catalog-derived command
  rows, Esc-closes-only-when-visible, dropdown suppression, README-wording alignment).
- `src/tui/mod.rs` is the repo's most-contended file with adjacent WIP in flight
  (@-mention dropdown, agent-roster TUI, slash-command dropdown, broader TUI redesign).

## Decision

Ship a **keyboard-navigable tabbed help overlay** (Left/Right/Tab to cycle, Esc to close,
default tab = **Getting Started**) as V1, scoped as follows:

**Tabs (V1):**

1. **Getting Started** (default) — the prompt → orchestrator → named-agents mental model,
   a **compact live agent/runtime summary** (configured agents, model, runtime
   availability), and 2 copy-pasteable example prompts. Leads with examples (NN/G).
2. **Commands** — derived from `slash_commands::catalog()` (no drift), with a **substring
   filter line** (`contains()` over the catalog-derived lines).
3. **Keys** — keybindings reference.
4. **Skills** — **live** from `ui_state.skill_suggestions` (project + personal), with the
   "skills are guidance, don't bypass approvals" disclaimer.
5. **Approvals & Modes** — **static explanatory prose** for V1 (how yolo vs normal works,
   capabilities, read/write roots concept).
6. **CLI** — last, non-default tab; `atelier` flags for the operator/CI audience.

**Enablers / structure:**

- Change `render_help_modal` to consume `(&AppState, &TuiUiState)` (keep it a pure
  function of the snapshot — no reach into `App` internals).
- Factor a shared `agent_roster_items(state, theme)` builder reused by both the Roster
  and the Getting Started agent summary (zero data duplication).
- Represent tabs as a small `enum HelpTab` with per-tab pure `Vec<Line>` builders using
  theme tokens (respect `colors_live_only_in_theme_module`). Active-tab index lives in
  `TuiUiState` (ephemeral UI state — never in the event-sourced snapshot).
- Do **not** add a `category` field to `SlashCommandSpec`; tab taxonomy is a UI property.
  Derive any intra-Commands grouping from the existing `SlashCommandKind`.

**In-flow onboarding (V1 companion, confirmed by product owner):** an empty-state hint on
the input composer ("describe a task; it routes through an orchestrator to named agents —
`/help` for the map") and a one-line explainer at the first approval prompt. These *push*
surfaces point the confused newcomer at the help modal (the *pull* destination), reaching
the target persona at the moment of confusion rather than relying on them discovering
`/help`.

**Deferred to V1.5/V2:** live approval-mode/roots projection (`ConfigStatusView`
extension), and any live approval-mode display in the always-on footer.

**Sequencing:** land after the adjacent in-flight TUI branches to avoid merge conflict in
`src/tui/mod.rs`.

## Alternatives Considered

### Alternative 1: Literal "7 standalone tabs, all live" (the original ask as stated)

- **Description**: A dedicated "Agents & Runtimes" tab plus a fully **live** "Approvals &
  Modes" tab (live approval mode + read/write roots), alongside the other tabs.
- **Pros**: Maximally matches the literal request; every category is its own tab; all data
  is live.
- **Cons**: The standalone Agents tab duplicates the always-on Roster; live Approvals/roots
  requires extending the serialized `AppState` snapshot to feed an opt-in overlay.
- **Why rejected**: Lower marginal value for real plumbing cost. The agent value is
  captured by folding a live summary into Getting Started; the Approvals *content* is
  useful as static prose without the snapshot change.

### Alternative 2: "Search + adaptive footer, no tabs" (devil's-advocate leaner bet)

- **Description**: Skip tabs; add a fuzzy filter to the existing modal and an always-on
  adaptive footer showing keys valid for the current `RunState`.
- **Pros**: Targets the scanning problem directly; reaches users who never open `/help`;
  near-zero new state.
- **Cons**: Under-delivers the requested tabbed *organization* and the onboarding front
  door; the adaptive footer is a separate, larger concern.
- **Why rejected**: Doesn't satisfy the "separate each type of information into a tab"
  requirement. Its best insight — **search/filter** — is adopted into the tabbed design.

### Alternative 3: "Static tabs only, defer all live data" (pragmatic's opening)

- **Description**: Reorganize existing content into tabs with hand-written static text for
  the new tabs; no live data, no filter.
- **Pros**: Fastest; minimal risk; no signature change.
- **Cons**: Static agent/skill text drifts from reality (the exact failure the
  catalog-derived tests guard against); misses the "more useful information" value.
- **Why rejected**: Live Agents/Skills proved nearly free (signature change), so deferring
  them sacrifices the differentiator for almost no savings.

## Consequences

### Positive

- Delivers the tabbed organization and live data the user asked for, at low cost (most
  data already in the snapshot).
- A single signature change unlocks live Agents + Skills; a shared `agent_roster_items`
  builder is a net cleanup of code that is inline today.
- Single-sourced Commands tab (from `catalog()`) means help cannot drift.
- Scope is disciplined: the one genuinely-expensive piece (live approval/roots) is
  deferred without losing user-facing value (static Approvals prose).

### Negative

- A filter line introduces the modal's first input mode (query buffer + one key-routing
  branch) — small but net-new; it is the explicit cut-line if it proves messy.
- ~3 tests must be updated to select the Commands tab before asserting catalog-derived
  rows / README wording (these contracts must be preserved, not dropped).
- "Approvals & Modes" being static text is a minor inconsistency with the otherwise-live
  tabs until V2.

### Risks

- **Merge conflict** in the hot `src/tui/mod.rs` — *mitigation*: sequence after adjacent
  TUI branches; per-tab pure builders are new functions, minimizing edits to the render body.
- **Over-hiding behind tabs** (research anti-pattern) — *mitigation*: visible tab strip,
  Getting Started as the front door, filter for fast lookup.
- **Scope creep toward live Approvals / fuzzy search** — *mitigation*: this ADR fixes the
  V1 boundary; those are explicit V2 items.

## Implementation Notes

- Add `help_active_tab: HelpTab` (or `usize`) to `TuiUiState`, defaulting to Getting Started.
- Insert tab-cycling (Left/Right/Tab) into the help-visible branch of
  `key_event_to_tui_command_with_ui` (`src/tui/mod.rs:763`); Esc still closes from any tab.
- Keep the Commands tab body flowing through `slash_commands.rs` so single-sourcing holds.
