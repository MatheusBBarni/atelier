# ADR-002: V1 Ships the Full Faithful-Parity Recall Set in One Release

## Status

Accepted

## Date

2026-06-12

## Context

The idea and ADR-001 locked the V1 core: ↑/↓-only recall, per-project scope, a
read-only projection over the existing event log, with outcome-aware recall
committed to V2. The PRD must decide the **shape and phasing** of the first
release. Clarifying answers added three product decisions: recall is on by
default with a disable toggle; discoverability uses the existing contextual
hint line plus a `/help` entry; and recall surfaces all submitted inputs
(natural-language prompts and slash commands).

The council established that the full shell-parity behavior set
(collision-gating, draft-preservation, consecutive-dedup, size cap,
leading-space-skip) is collectively a small change but spans several distinct
user-facing behaviors. The open question: ship the full parity set at once,
phase it core-then-polish, or pull a sliver of the V2 differentiator forward.

## Decision

V1 ships the **complete faithful-parity recall experience in a single release**:
↑/↓ recall, collision-safe gating, draft-preservation, consecutive-dedup,
configurable size cap, leading-space-skip, on-by-default with a disable toggle,
hint-line + `/help` discoverability, recall of all submitted inputs, and
recalled-vs-fresh instrumentation. No outcome metadata in V1 (committed to V2 per
ADR-001 and the idea's hybrid direction).

## Alternatives Considered

### Alternative 1: Core-then-polish phased V1 (Approach B)

- **Description**: Ship recall + collision-gate + draft-preservation first;
  fast-follow the conventions (leading-space-skip, dedup, hint-line, toggle).
- **Pros**: Smallest first PR; fastest validation of the core habit; spreads risk.
- **Cons**: Ships below table-stakes parity briefly (no privacy escape hatch, no
  dedup); double-touches the hottest input keypath; release overhead
  disproportionate to the small full-set diff.
- **Why rejected**: The parity set is already small and cohesive; shipping it
  incomplete squanders the muscle-memory win and re-opens the riskiest keypath twice.

### Alternative 2: Recall + thin outcome marker (Approach C)

- **Description**: Approach A plus a minimal ✓/✗/interrupted marker on recalled
  entries from the originating run.
- **Pros**: Differentiates on day one; uses outcome data already recorded.
- **Cons**: Pulls V2 scope forward; adds render/UX surface; undoes the clean
  wedge/differentiator split; risks rushing the V2 design.
- **Why rejected**: The hybrid direction deliberately separates the recall wedge
  from the outcome-aware differentiator so each is designed well; pulling a sliver
  forward compromises both.

## Consequences

### Positive

- One cohesive, correct, table-stakes release; users get the full shell-parity
  experience at once.
- The hot input keypath is modified once, with the full collision/draft test
  matrix exercised in a single pass.
- The clean wedge/V2 boundary is preserved for a well-designed outcome-aware follow-up.

### Negative

- The first release is larger than a bare wedge (still small overall).
- No differentiation in V1 beyond the per-project default; outcome-metadata value
  waits for V2.

### Risks

- A larger single release concentrates the collision/draft correctness risk in
  one change → mitigate with the dedicated test matrix (recall into a wrapped
  line, cursor up/down across the wrap boundary, draft restore after recall).
- "On by default" surfaces past prompts more accessibly → mitigate with the
  disable toggle and leading-space-skip; the durable record is unchanged (already
  access-restricted and excluded from version control).

## Implementation Notes

- Delivery is a single release. The PRD's rollout plan maps Phase 1 = this full
  parity set, Phase 2 = outcome-aware recall, Phase 3 = reverse-search +
  cross-project scope-cycling.
