# ADR-003: Recall State in TuiUiState; Tag Submissions via Extended `AppEvent`

## Status

Accepted

## Date

2026-06-12

## Context

Prompt recall must (a) hold a navigable list of past prompts plus a cursor and a
saved in-progress draft, and (b) tag each submission as recalled-vs-fresh for the
"recall adoption" KPI (PRD Success Metrics). Input editing in `atelier` is already
UI-local: `AppState.input` is mutated TUI-side, and ↑/↓ map to `MoveInputCursor`
handled by `move_input_cursor_vertically` (`src/tui/mod.rs`). The submit path
dispatches `AppEvent::PromptSubmitted(String)` over the mpsc channel to the app
worker, which records the `prompt_submitted` event (`src/app/mod.rs`). We must
decide where recall state lives and how the recalled flag reaches the worker that
writes the event.

## Decision

- Recall state lives in `TuiUiState` as three fields: `prompt_history: Vec<String>`
  (timestamp-desc, deduped, capped), `prompt_history_cursor: usize`
  (0 = live draft; N = Nth-newest entry), and `prompt_history_draft: String`
  (the saved in-progress draft).
- Extend the submit event to carry provenance:
  `AppEvent::PromptSubmitted(String)` → `AppEvent::PromptSubmitted(String, PromptSource)`
  with `enum PromptSource { Fresh, Recalled }`. The TUI sets `Recalled` when the
  composition was seeded from a history entry; the worker writes `"source"` into
  the `prompt_submitted` payload.

## Alternatives Considered

### Alternative 1: No V1 instrumentation

- **Description**: keep state in `TuiUiState`; do not change `AppEvent` or the
  payload; drop the recalled/fresh tag.
- **Pros**: smallest diff; no worker/event change.
- **Cons**: forfeits the primary "recall adoption > 20%" KPI and the data behind
  the Phase-3 search widen-trigger.
- **Why rejected**: the metric is a core PRD goal and the governance trigger
  depends on it.

### Alternative 2: Worker-owned recall state

- **Description**: hold the recall ring in `AppState`; UI sends recall commands;
  the worker mutates input and tracks recalled-ness.
- **Pros**: the worker owns the tag natively.
- **Cons**: contradicts the established UI-local input-editing model; adds channel
  round-trips for a pure keyboard interaction; couples render latency to the worker.
- **Why rejected**: recall is a presentation concern; UI-local keeps it instant
  and isolated.

## Consequences

### Positive

- Recall is instant (no channel hop) and isolated to the render layer, consistent
  with cursor editing.
- A single authoritative provenance tag flows with the submit event; the payload
  gains one field.

### Negative

- `AppEvent::PromptSubmitted` is a widely-referenced variant; the signature change
  touches every match site (compile-time caught, mechanical).
- The TUI must define precisely when an edited-after-recall prompt counts as
  `Recalled` vs `Fresh`.

### Risks

- Mis-tagging if the "edited after recall" rule is fuzzy → define provenance by the
  cursor: a composition is `Recalled` iff `prompt_history_cursor != 0` at submit;
  entering history sets the cursor > 0 and edits keep it there (matching the KPI's
  "originate from a recalled entry, possibly edited"); clearing the input back to
  empty resets the cursor to 0 (→ `Fresh`). Covered by the test matrix.

## Implementation Notes

- Recall activates only when the live draft is empty (or the cursor is already in
  history mode) AND no dropdown / queue / clarification owns ↑/↓ — gated inside the
  existing top/bottom boundary branch of `move_input_cursor_vertically`.
- Backspacing the recalled text to empty resets `prompt_history_cursor` to 0, so a
  delete-all-then-retype is correctly tagged `Fresh`.
