# ADR-007: Dedicated Verdict Ledger + Coarse Task-Type Signature for Routing

## Status

Accepted

## Date

2026-06-19

## Context

ADR-004 makes V1 routing active: history of which runtime wins which kind of task selects the race roster. The history store (`history::read_events`) reads **one session's** `events.jsonl`, but routing needs a **cross-session** corpus that survives session compaction and aggregates quickly. ADR-004 also leaves the task-type signature as an Open Question that must be forward-compatible with the Phase 2 router.

## Decision

Persist verdicts in a dedicated, append-only **verdict ledger** at the workspace root, and key routing on a **coarse, versioned task-type signature**.

- **Ledger:** `.atelier/race/verdicts.jsonl`, one record per attempt:
  `{ schema_version, timestamp, run_id, task_signature, runtime, model, oracle_outcome, exit_code, won, cost_tokens }`.
  Append-only; cross-session by construction; independent of per-session history compaction. Per-run events are still emitted for the transcript (ADR-005's projection), but the ledger — not session logs — is the routing source of truth.
- **Task-type signature (v1):** a coarse, versioned tuple derived deterministically from the instruction + target files — `{ sig_version, primary_language, change_kind }`, where `change_kind` is a small closed set (e.g. `feature | refactor | bugfix | test | docs | config`). Kept coarse on purpose so early buckets accumulate enough samples; `sig_version` lets the Phase 2 router migrate without invalidating prior data.
- **Routing read:** aggregate the ledger by `(task_signature, runtime)` → win-rate; order the configured roster by win-rate; select the top `num_attempts`. Below `ensemble.min_route_samples` for a signature, race the **default roster** (cold start) and mark the read-back "still learning."
- **Read-back:** the win-rate aggregation feeds `/provider:status` (or a dedicated stats view), labeled as historical, workspace-local, sample-sized.

## Alternatives Considered

### Alternative 1: Derive from session event logs on demand

- **Description**: Scan every session's `events.jsonl`, filter `ensemble_attempt_verdict`.
- **Pros**: No new store.
- **Cons**: O(all history) per read; breaks if sessions are pruned/compacted; couples routing to transcript retention.
- **Why rejected**: Routing must not depend on transcript retention or pay a full-history scan per race.

### Alternative 2: Maintained rollup cache

- **Description**: Keep a pre-aggregated win-rate summary updated after each race.
- **Pros**: Fastest reads.
- **Cons**: Derived-state cache that can drift; needs rebuild/repair logic.
- **Why rejected**: Premature optimization; the append-only ledger aggregates fast enough at V1 volumes, and is the durable source a rollup could be rebuilt from later.

## Consequences

### Positive

- Routing is fast, durable, and decoupled from session-history lifecycle.
- The signature is forward-compatible (versioned) for the Phase 2 single-model router.
- The ledger doubles as the audit trail for win-rate read-back.

### Negative

- A second persistence artifact beyond session history (small, append-only).
- Signature derivation is a heuristic; mis-bucketing dilutes win-rate accuracy.

### Risks

- **Signature too coarse/fine** → start coarse, version it; revisit with real data in Phase 2.
- **Ledger growth** → records are tiny; add a compaction/rollup only if volume demands (the rollup alternative remains available).
- **Cold-start mislabel** → conservative `min_route_samples`; default roster below threshold.

## Implementation Notes

- The roster selector is a pure function `(task_signature, ledger_aggregate, default_roster, min_samples) -> ordered_roster` — trivially unit-testable and safe to fall back.
- Write the ledger record at the same point the per-run `ensemble_attempt_verdict` event is emitted, after grading each attempt.
