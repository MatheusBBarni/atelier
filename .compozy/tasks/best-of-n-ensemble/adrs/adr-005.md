# ADR-005: Dedicated `run_race_workflow` Runner (Not the DAG Scheduler)

## Status

Accepted

## Date

2026-06-19

## Context

`/race` runs the same instruction across N attempts and selects a winner. The harness already has three step-execution paths: single-agent, `run_parallel_group` (disjoint-scope children), and `run_execution_graph` (the DAG ready-set scheduler with dependency edges + disjoint-scope admission). The TechSpec had to decide whether the race reuses one of these or gets a dedicated runner.

A race has **no edges** and **no scope partitioning** — every attempt shares the same logical target and is isolated by scratch, not by disjoint write-sets. The DAG scheduler's core value (dependency ordering + disjoint-scope admission) is therefore unused, and its "scopes describe real-tree writes" invariant would have to be bent (pointing each node's `file_scope` at a scratch path). `/race` is also **user-invoked**, not an orchestrator decision, so it does not need to be an `OrchestratorDecision`/`DecisionNextStep` variant.

## Decision

Build a dedicated `run_race_workflow` runner, modeled on `run_council_workflow` (`app/mod.rs:5544`) for its workflow lifecycle and on `run_parallel_group` (`app/mod.rs:3391`) for concurrent spawn/await/cancellation.

- **Dispatch:** `/race <instruction>` is a built-in command handled in `App::submit_prompt`, alongside `/workflow`/`/subtask`. It opens a `RunDriveContext` carrying a `RaceRunContext { instruction, roster, num_attempts }` and drives one race step.
- **Execution:** the runner composes the attempt roster (ADR-007 routing), spawns N attempt agent steps concurrently (each on a distinct runtime, each in an `AttemptScope` — ADR-006), grades each via the existing oracle, selects deterministically + narrates (ADR-008), and promotes the winner.
- **Result:** a new `RunStepResult::Race { result: RaceResult }` variant is appended to `run.previous_results`, with a matching `ChatLifecycleKey`/`ChatItemKind` projection arm for the live panes + verdict card.

The DAG scheduler and `run_parallel_group` are left unchanged.

## Alternatives Considered

### Alternative 1: Reuse `run_execution_graph` (degenerate graph)

- **Description**: Model the race as an `ExecutionGraph` of N edge-less sibling nodes, each `file_scope` pointed at a scratch dir to keep scopes disjoint.
- **Pros**: No new scheduling loop; inherits cancellation/limits.
- **Cons**: Bends the DAG's real-tree-scope semantics; drags in ready-set/edge/scope-arbitration machinery a race never uses; verdict aggregation and live-pane UX would fight the graph result shape.
- **Why rejected**: Conceptual mismatch outweighs the code saved; the race is not a dependency graph.

### Alternative 2: Extend `run_parallel_group`

- **Description**: Generalize the parallel-group runner to allow same-instruction, scratch-isolated children.
- **Pros**: Reuses the closest concurrency primitive.
- **Cons**: Entangles best-of-N selection/promotion semantics into a path built for disjoint-partition work; risks regressing the existing parallel-group contract.
- **Why rejected**: Keep the proven primitive single-purpose; borrow its spawn plumbing without overloading its semantics.

## Consequences

### Positive

- Clean conceptual boundary; verdict aggregation, deterministic selection, and live-pane UX are first-class in the runner.
- Existing schedulers stay untouched — no regression surface in `run_parallel_group`/`run_execution_graph`.
- Reuses council's workflow lifecycle and parallel-group's spawn/cancel plumbing, so "new" code is mostly composition.

### Negative

- A fourth step-execution path to maintain.
- Some spawn/await/cancellation logic is structurally similar to `run_parallel_group` (mitigate by extracting a shared concurrent-spawn helper if duplication is real).

### Risks

- **Divergent concurrency handling** vs the existing parallel path → factor the shared spawn/await/cancel into a helper both can call.
- **Run-state/limits integration** (step counting, interrupts) must match council/DAG semantics → mirror `run_council_workflow`'s state advancement exactly.

## Implementation Notes

- New: `RunStepResult::Race { result: RaceResult }`; `RaceResult { status, summary, attempts: Vec<RaceAttemptRef>, winner: Option<…>, verdicts, changed_files }`; command registration in `slash_commands.rs` (`SlashCommandKind::AppCommand`).
- Reuse: `run_council_workflow` lifecycle, `run_parallel_group` spawn/await/cancel, `derive_grade_verdict` oracle.
