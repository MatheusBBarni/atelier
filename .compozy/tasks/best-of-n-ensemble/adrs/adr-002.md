# ADR-002: Frame the Feature Around a Learning Fleet Router; the Race Is the Data Engine

## Status

Accepted

## Date

2026-06-19

## Context

The opportunity-scan phase asked whether the council-refined V1 (opt-in `/race`, oracle-selected pick-one, cross-runtime) is the highest-leverage framing. As scoped, the race is a *one-time* improvement per invocation: it picks a winner and forgets everything. Its ceiling is "a better answer on the steps you opt into" — strong, but not compounding.

A more ambitious framing emerged: every oracle-graded race produces an objective, attributable verdict — *runtime R won on a task of shape S, proven by the project's own tests*. Accumulated, those verdicts are a **proprietary routing signal** grounded in the user's own codebase and test suite. No single-vendor tool can build it, because it requires racing across providers in the first place. This reframes the feature from a halo quality tool into a compounding moat: the harness learns which model to trust for which kind of work, and eventually routes without racing when confidence is high — which also makes "quality-at-any-cost" cheaper over time.

## Decision

Frame the idea's headline thesis around the **learning Fleet Router**, with the cross-runtime race positioned as its **data engine**:

- **V1 (foundation, this packet):** the opt-in `/race` defined in ADR-001 — oracle-selected pick-one, cross-runtime, fail-closed promotion — **plus a mandatory requirement that every attempt's outcome is recorded as structured, durable telemetry**: producing runtime/model, task-shape features (language, file kinds, change kind), oracle result (pass/fail + evidence), judge rationale, and won/lost. The race must be instrumented as a labeled-data generator from day one, even though V1 does not yet consume the data for routing.
- **V2+ (North Star):** a router that consumes the accumulated verdicts to (a) recommend which models to race for a given task shape, and (b) eventually route a single model without racing when historical confidence is high — turning the fleet from "race everything" into "race only where it pays."

The race's *selection and promotion* mechanics are unchanged from ADR-001; this ADR adds the telemetry obligation and sets the product narrative.

## Alternatives Considered

### Alternative 1: Keep the one-shot race framing (refined original)

- **Description**: Ship `/race` as a self-contained quality tool; no learning layer.
- **Pros**: Simplest narrative; nothing speculative.
- **Cons**: Non-compounding; ceiling is per-invocation; leaves the defensible asset (the user's own win/loss data) unbuilt; Defensibility stays "Strong" rather than "Must do."
- **Why rejected**: The compounding routing asset is the difference between a flashy halo feature and a durable moat, and it is cheap to enable *only if* V1 records verdicts from the start.

### Alternative 2: Build the router itself in V1

- **Description**: Ship the learning router as part of V1, not just the data engine.
- **Pros**: Delivers the compounding value immediately.
- **Cons**: A router needs a corpus of verdicts that does not exist yet (cold start); routing policy is unprovable without the race running first; massively expands V1 scope and risk.
- **Why rejected**: Sequencing — the router is worthless without accumulated data. V1 must generate the data; the router earns its way in once the corpus and the race's oracle-win metric have proven out.

## Consequences

### Positive

- Elevates the feature from "Strategic Bet" to a **compounding moat**: Defensibility becomes Must-do.
- The telemetry obligation is a small, well-bounded addition to V1 with outsized future leverage.
- Provides a credible, evidence-grounded story ("the harness learned from *your* tests which model to trust") that single-vendor tools structurally cannot tell.

### Negative

- Adds a telemetry/schema requirement to V1 that has no immediate user-facing payoff (a deferred-value cost).
- Risks over-promising the router vision before V1 ships; the idea must be explicit that V1 is the foundation, not the router.

### Risks

- **Telemetry schema churn** (early schema can't support later routing features) → design the verdict record around the task-shape + outcome dimensions the router will need, and version it.
- **Privacy/portability of accumulated verdicts** → keep verdicts local to the workspace's `.atelier/` history; treat them as workspace-scoped data, not a shared service (defer any cross-project aggregation).
- **Narrative outrunning delivery** → the idea and PRD must mark router behavior as explicitly V2+, not implied in V1.

## Implementation Notes

- Reuse the event-sourced `.atelier/` history for durable verdict storage; emit a structured `ensemble_attempt_verdict` event per attempt alongside the existing run events.
- The verdict record should capture: `runtime`, `model`, task-shape features, `oracle_result` (+ cited evidence ref), `judge_rank`/`rationale`, `won: bool`, `cost` (tokens/latency).
