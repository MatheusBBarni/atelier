# ADR-004: Minimal Routing in V1 — Route the Race Roster, Never Skip the Race

## Status

Accepted

## Date

2026-06-19

## Context

ADR-002 framed the feature around a learning Fleet Router and made V1 record structured oracle verdicts. During PRD clarification the user went further: V1 should **actively** use the accumulated verdicts, not merely record them. That choice is valuable (it makes the compounding moat real in V1) but introduces two hazards that must be bounded or the V1 risk balloons:

1. **Cold start.** A new workspace has no verdict history, so any routing policy has nothing to learn from on day one.
2. **Over-reach.** The full router vision — "trust one model and skip racing when confident" — replaces the quality mechanism (the race) with a prediction. If that prediction is wrong, the user loses the very safety the race provides, and there is no oracle-grounded selection to catch it.

The PRD needs a precise, bounded definition of what "minimal routing" means in V1 so the feature is shippable and safe.

## Decision

V1 routing **selects which runtimes enter the race**; it never replaces or skips the race.

- **What it does:** for a given task type (a coarse task-shape signature — e.g. language + change kind), the router orders the configured ensemble roster by historical oracle win-rate and selects the top N≤3 to race. Every run still races N attempts, still oracle-gated, still pick-one promoted.
- **Cold-start fallback:** when history for a task type is absent or below a minimum-sample threshold, race the **default roster** (the `[ensemble]` preset's members, up to N). The read-back view shows a "learning" state until the threshold is met.
- **Read-back:** accumulated per-runtime win-rates by task type are surfaced (e.g. in `/provider:status` or a stats view) so the user can see the router learning.
- **Explicitly NOT in V1:** routing a *single* model and skipping the race; cross-task-type generalization; any policy that promotes without an oracle-gated race. Those are V2+ (the full router).

The routing decision is advisory to roster composition only — it can never widen scope, bypass the oracle, or change the promotion path.

## Alternatives Considered

### Alternative 1: Telemetry-only (no active routing in V1)

- **Description**: Record verdicts; do not act on them until V2.
- **Pros**: Zero cold-start risk; smallest V1.
- **Cons**: The headline "router" value is invisible/inert in V1.
- **Why rejected**: The user explicitly chose active routing; bounding it to roster selection makes it safe enough to ship.

### Alternative 2: Full routing (skip the race when confident)

- **Description**: Use history to route a single trusted model and skip racing when confidence is high.
- **Pros**: The full compounding payoff — cheaper over time.
- **Cons**: Replaces oracle-grounded selection with prediction; a wrong prediction loses the race's safety with no fallback; needs a mature corpus and calibrated confidence that do not exist yet.
- **Why rejected**: Unsafe and premature for V1; this is the V2 North Star, gated behind a maturity criterion.

## Consequences

### Positive

- The compounding moat is genuinely active in V1, faithful to the user's choice.
- Bounded blast radius: routing only reorders/selects the roster; the oracle-gated race remains the safety mechanism on every run.
- Cold-start is handled gracefully (default roster + visible learning state) rather than failing or producing noise.

### Negative

- Until a workspace accumulates verdicts, routing is effectively the default roster — early value is modest.
- Introduces a task-shape signature and a win-rate store in V1 that must be designed for forward-compatibility with the V2 router.

### Risks

- **Task-shape signature churn** (V1 signature can't support V2 routing) → keep the signature coarse and versioned; treat it as an Open Question for the TechSpec.
- **Min-sample threshold mis-tuned** (routes too early on thin data) → conservative default threshold; race default roster below it.
- **User over-trusts the read-back** (reads win-rates as guarantees) → label them as historical, workspace-local, sample-sized observations.

## Implementation Notes

- Reuse `.atelier/` event-sourced history to store `ensemble_attempt_verdict` records; derive win-rates by task type on demand.
- The roster selector is a pure function of (task-shape signature, verdict history, default preset) → ordered roster; trivially testable and safe to fall back.
