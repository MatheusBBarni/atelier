# ADR-003: PRD Product Approach — Race-Led, Router-Active V1 (User-Invoked `/race`)

## Status

Accepted

## Date

2026-06-19

## Context

The `_idea.md` and ADR-001/ADR-002 established the technical shape (oracle-selected pick-one race; the race as the data engine for a learning router). The PRD phase had to choose how to **package and sequence** that into a shippable V1, given the user's clarification answers, which consistently favored the ambitious option:

- Trigger: user-invoked, opt-in `/race` (the first user-invokable cross-agent workflow after `/workflow`; council is orchestrator-routed only).
- No-oracle/tie case: auto-pick the judge's top with a low-confidence banner, then the normal approval gate.
- Presentation: a **live multi-pane** view of the N attempts while running, collapsing to a verdict card.
- Cost: announce N / runtimes / estimated multiplier in the race-started line, do not block (opt-in is consent).
- All-fail: promote nothing, surface each attempt's failures, offer retry/abort.
- Router: **active** minimal routing in V1, not just telemetry.

Three packagings were weighed: (A) ship the full race experience *and* active routing in V1; (B) ship the race now with routing as a visible read-back that becomes active as a fast-follow; (C) add an everyday confidence-signal surface to broaden reach.

## Decision

Adopt **Approach A — Race-led, router-active V1**. V1 delivers, as one release:

1. **Opt-in `/race <prompt>`** — a user-invoked workflow command (catalog entry alongside `/workflow`), gated by an `[ensemble]` config block (default off) and the existing parallel-capability feature flag.
2. **The race** — N≤3 attempts on *distinct* runtimes against the same instruction, each isolated in a per-attempt scratch scope, presented as a **live multi-pane** view that collapses to a **verdict card** (per-attempt oracle results, judge rationale, winning diff).
3. **Oracle-gated pick-one selection** — the project's compile/test/lint oracle disqualifies non-passing attempts; the independent judge tie-breaks survivors and narrates. No-oracle/tie ⇒ auto-pick top + low-confidence banner. All-fail ⇒ promote nothing, surface failures, offer retry/abort.
4. **Promotion** — the winning attempt's patch is re-validated as a fresh `ApplyPatch` through the existing scope fence + approval gate.
5. **Active minimal routing** — accumulated oracle verdicts inform *which* runtimes enter the race for a given task type, with a default-roster fallback on cold-start (see ADR-004 for the bounded scope).

Synthesize-merge and orchestrator auto-route remain V2+ (per ADR-001).

## Alternatives Considered

### Alternative 1: Approach B — Router as visible read-back, active routing as fast-follow

- **Description**: Ship the race in V1; record verdicts and *show* win-rates by task type, but defer *active* routing until a verdict corpus exists.
- **Pros**: Avoids cold-start entirely (never routes on empty data); smaller, safer V1; compounding value still visible.
- **Cons**: Partially walks back the user's explicit "build minimal routing" choice — the router shows but does not act in V1.
- **Why rejected**: The user chose active routing knowing the cold-start trade-off; ADR-004 bounds that risk (route the roster, never skip the race) so active routing in V1 is acceptable.

### Alternative 2: Approach C — Two surfaces (`/race` + everyday confidence signal)

- **Description**: Approach A plus a lightweight always-on confidence mode (2 background attempts on risky steps, show agreement) to lift reach/frequency.
- **Pros**: Attacks the feature's weakest scores (reach/frequency); more daily value.
- **Cons**: Much larger scope; pulls in the "consensus confidence" adjacent idea that was explicitly deferred to its own packet; dilutes a focused V1.
- **Why rejected**: Scope discipline — the confidence signal is a separate product with its own value model and should not ride on this V1.

## Consequences

### Positive

- Delivers the complete headline in one release: the cross-provider race *spectacle* plus the learning-router *payoff* — the differentiator and the moat, together.
- Faithful to every product decision the user made; no walk-backs.
- Reuses the `/workflow` command precedent, the council config shape, the existing approval gate, and the shipped oracle — most of V1 is composition, not invention.

### Negative

- Largest V1 in the packet's option space: live multi-pane streaming *and* a routing layer are both non-trivial lifts on top of the unavoidable scratch-isolation work.
- Active routing adds little user value until verdicts accumulate (cold-start), so early-adopter perception of the "router" depends on usage volume.

### Risks

- **Live multi-pane lift** — the TUI streams per-agent output to the Agent Roster today, not the transcript; a multi-pane race view is new UI surface → keep the verdict card as the durable artifact and treat live panes as progressive enhancement that can degrade to roster streams if needed.
- **Cold-start router confusion** — users may expect routing intelligence before data exists → default-roster fallback + a visible "learning" state in the read-back (ADR-004).
- **Scope creep into V2 features** — synthesize-merge / auto-route pressure → ADR-001 boundary holds; PRD Non-Goals restate it.

## Implementation Notes

- `/race` registers as a `SlashCommandKind::AppCommand` in `slash_commands.rs` (amend the frozen-V1 catalog ADR note + `FIXED_V1_LABELS` test).
- `[ensemble]` config mirrors `CouncilConfig` (`default_preset`, `timeout_seconds`, presets of runtime/model members), adding a parallel execution mode.
- Verdict card / live panes extend the chat projection (new `ChatItemKind` like `Plan`/`GradeLoop`, or an evolved `RunSummary`).
