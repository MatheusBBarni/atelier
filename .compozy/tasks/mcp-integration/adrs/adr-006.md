# ADR-006: Persist MCP trust and description pins in an app-managed `.atelier/` store

## Status

Accepted

## Date

2026-06-15

## Context

PRD CF3 requires durable, revocable per-server trust ("remember"); F6 requires pinning a hash of each tool's `(name + description + input schema)` and re-prompting on change. The existing approval flow is single-shot and in-memory (`App.pending_approval`); `atelier.toml` is hand-edited and read-only at runtime; and `validate_action_request_with_scope` must consult trust synchronously during validation.

## Decision

Store trust as an **app-managed JSON file under the workspace `.atelier/`** (e.g., `.atelier/mcp-trust.json`): per-server trust tier (`untrusted` / `trusted`) and the pinned `(name+description+inputSchema)` hash per tool. Promote/revoke **writes the file and records an event** (`mcp_server_trusted` / `mcp_server_revoked`); validation reads an in-memory cache loaded at startup. Trust is **workspace-scoped** (a server trusted in one project is not trusted elsewhere), consistent with `.atelier/` history scoping.

## Alternatives Considered

### Alternative 1: Store trust in `atelier.toml`

- **Description**: A `trusted` flag / trust list per server in the user's config.
- **Pros**: Transparent; user-editable.
- **Cons**: TUI promotion requires runtime write-back to config — a pattern atelier does not have today — and mixes machine-managed decisions into hand-edited config.
- **Why rejected**: Breaks the "config is read-only at runtime" invariant.

### Alternative 2: Session-only, event-sourced

- **Description**: Re-prompt on first contact each session; reconstruct trust from events within the session.
- **Pros**: Simplest; purely event-sourced.
- **Cons**: No cross-session "remember" — the user re-approves every new session.
- **Why rejected**: PRD CF3 explicitly wants remembered trust.

## Consequences

### Positive

- Durable, revocable "remember"; validation reads from a fast in-memory cache; promote/revoke is auditable via events; `atelier.toml` stays read-only at runtime.

### Negative

- A new on-disk state file with its own schema and migration concerns.

### Risks

- **File ↔ event divergence** — events are the audit trail; the file is a derived, queryable snapshot rebuildable from events.
- **Concurrent atelier instances** writing the same workspace file — last-writer-wins with a per-write lock; the file is workspace-scoped so cross-project contention does not arise.

## Implementation Notes

Record-time redaction (the new work identified in exploration) is applied where MCP results become events, before durable write — the trust store itself holds only hashes and server ids, no secrets.
