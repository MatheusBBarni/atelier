# ADR-003: Config-first MVP product surface for V1

## Status

Accepted

## Date

2026-06-15

## Context

The idea and ADR-001/002 fixed the *architecture* (harness-brokered MCP via the `ActionRequest` contract; stdio-first, HTTP/OAuth deferred to V1.1). The PRD must choose the V1 **product/UX surface**: how a solo power-user adds and manages servers, and how much governance UX ships in the MVP. Clarifying answers established the cross-cutting model: **per-server trust + read-only auto-allow** (revocable), **per-agent default-deny allowlist**, and **local-only, self-visible metrics**. Product/UX research showed atelier's users already hand-edit TOML for runtimes and agents, that approval fatigue and missing "remember" are the dominant MCP complaints, that "too many tools" measurably degrades agents, and that hosts surface almost nothing about a tool before approval.

Three approaches were considered: **A) Config-first MVP**, **B) Guided command surface** (`/mcp add|list|status|trust`), **C) Governance-forward** (per-tool globs + audit export in V1).

## Decision

Build V1 around **Approach A — Config-first MVP**:
- Servers configured via a `[mcp.servers.<name>]` **TOML** section, identical in idiom to `[runtimes.*]` / `[agents.*]`.
- **Trust + read-only auto-allow** delivered through the **existing normal-mode approval card**, extended to surface the tool's full description + server origin, with promote-to-trusted (revocable) and **hash-pin + diff-on-change re-prompt**.
- **Per-agent default-deny allowlist** governs which tools each agent sees (least privilege + bloat control).
- **`--doctor`** gains MCP health checks and a **cross-runtime parity matrix**; metrics are **local-only** via `--doctor --json`.
- stdio-only, behind a `features.mcp_enabled` flag.

A guided `/mcp` command surface (Approach B) is deferred to **Phase 2**, alongside the committed HTTP/OAuth bundle. Team governance — per-tool allowlist globs, audit export, curated catalog/RBAC (Approach C) — is deferred to **Phase 3 (V2+)**.

## Alternatives Considered

### Alternative 1: Guided command surface (Approach B)

- **Description**: Add `/mcp add|list|status|trust` slash commands modeled on `claude mcp add`, on top of A.
- **Pros**: Best onboarding/discoverability; CLI-add is the proven low-friction path.
- **Cons**: Requires a deliberate change to the governed slash-command catalog; meaningfully more build/test surface than the TOML-savvy solo persona needs for a first cut.
- **Why rejected**: Not required for the primary persona's first cut; folded into Phase 2 where it pairs with the HTTP/OAuth work.

### Alternative 2: Governance-forward (Approach C)

- **Description**: Add per-tool allowlist globs alongside per-server tiers, plus a one-command audit export, in V1.
- **Pros**: Strongest safety/governance story; closer to the team persona.
- **Cons**: Heaviest V1; partially duplicates the V2+ governed-catalog stretch the idea already banked; over-serves the solo user.
- **Why rejected**: Scope inflation against the solo-user MVP; deferred to Phase 3.

## Consequences

### Positive

- Consistent with every existing atelier UX idiom (TOML config, `--doctor`, in-chat approval cards) → predictable and discoverable for the target user.
- Ships the *differentiating* trust UX (description-at-approval, per-server trust, read-only tier, diff-on-change) without inflating scope.
- Leaves the governed command catalog untouched in V1.

### Negative

- No guided `/mcp add` in V1 — newcomers hand-write TOML.

### Risks

- TOML friction / silent config errors (a documented MCP onboarding failure mode) — mitigated by an `--init-config` example block and actionable `--doctor` diagnostics that distinguish real failure from noisy stderr.
- Where revocable per-server trust state is stored (config vs. session state) is a techspec question.

## Implementation Notes

Reuse the existing approval-card rendering, `--doctor` check framework, and `--print-config` redaction. The trust-promotion and diff-on-change flows emit events and project into chat like every other action.
