# ADR-001: Broker MCP through the harness ActionRequest contract

## Status

Accepted

## Date

2026-06-15

## Context

`atelier` is a multi-runtime harness: one config routes prompts across pluggable agent-CLI runtimes (Codex, Claude, Cursor, a Z.ai HTTP runtime, and a `fake` test runtime). Today it has **zero** access to the MCP (Model Context Protocol) tool ecosystem. The Claude runtime *deliberately* strips MCP (`--strict-mcp-config`, `--tools ""` in `src/runtime/claude.rs`) so the model cannot self-invoke tools and slip past the harness action boundary.

We want to give every runtime access to MCP servers (filesystem, git, GitHub, fetch, company tools). Three mechanisms are possible: (a) a harness-owned MCP client that brokers tool calls through the existing `ActionRequest` contract; (b) stop suppressing each runtime's *native* MCP and accept per-CLI config; (c) point users at an external MCP gateway in front of atelier. The council debated all three, with `devils-advocate` pressing hard that (b)/(c) are far cheaper and that (a) stakes parity on small models hand-emitting tool-call JSON.

## Decision

Build a **harness-owned MCP client**. MCP calls become first-class `ActionRequest`s that the harness brokers — the model returns the **same** `action_request` JSON contract it already uses, and the harness performs the actual MCP call through `validate_action_request_with_scope` → `ActionDecision` → (approval in Normal mode) → `execute_action_request` → recorded events → chat projection.

The decisive evidence (surfaced live from the codebase during the debate):
- **Native function-calling would *fork* the contract.** The Z.ai HTTP runtime and the `fake` runtime have no `tools` array wired; native FC is per-provider. Adopting it splits behavior into "native for codex/claude/cursor, brokered for zai/fake" — breaking the cross-runtime uniformity that is the entire point.
- **atelier already A/B-tested native tool exposure and rejected it.** The Claude strip exists *because* handing small models their full native tool surface measurably degraded contract adherence (malformed multi-action contracts, empty turns). Brokering, not native FC, is the path this project already validated.
- **Gateways are passive proxies the *model* self-invokes through.** They deliver "configure once" but no harness-owned approval/capability/audit at the call boundary, and add separate infra. The harness-owned invocation ("the harness, not the model, decides what runs") is the differentiator they structurally cannot offer.
- **Cross-runtime structured emission already ships in production.** All runtimes funnel output through one `parse_contract` path with a tested `ParseError` outcome and a same-model retry spine; MCP is incremental load on a proven mechanism.

## Alternatives Considered

### Alternative 1: Un-strip each runtime's native MCP

- **Description**: Stop suppressing MCP per-CLI; let each runtime use its vendor's hardened, constrained-decoding tool calling.
- **Pros**: Near-zero build cost; reuses labs' hardened function-calling; best raw emission reliability on each provider.
- **Cons**: Per-CLI config fragmentation (no "configure once"); no uniform harness gate/audit; behavior forks across runtimes; the Z.ai and `fake` runtimes cannot do it at all.
- **Why rejected**: Kills both moats (multi-runtime *and* harness-owned trust boundary) and cannot span all five runtimes.

### Alternative 2: External MCP gateway in front of atelier

- **Description**: Deploy McpMux / IBM ContextForge / similar; point each runtime's native MCP at the gateway URL.
- **Pros**: Configure-once + centralized governance for near-zero build; mature, maintained externally.
- **Cons**: Passive proxy — the *model* still self-invokes; no harness-owned approval/capability/audit at the action boundary; extra infra to stand up; undercuts the terminal-native, solo-user story.
- **Why rejected**: Does not deliver harness-mediated invocation, which is the defensible white space; relegates atelier to "renders approvals well."

## Consequences

### Positive

- Unlocks the full MCP ecosystem (~10k registry servers) for **every** runtime through one config.
- Third-party servers inherit approval gating, capability allowlists, and event audit **for free**, via the existing trust boundary.
- Uniform tool behavior and governance across all runtimes; no per-CLI drift.

### Negative

- The model must reliably emit well-formed `CallMcpTool` JSON for dynamic, server-defined tools — a real risk on small/cheap models (the Z.ai runtime), which is the runtime the North Star most needs to hold for.
- Reimplements connection/lifecycle plumbing that vendors maintain inside their CLIs.

### Risks

- **Small-model emission failure breaking parity** — mitigated by a **pre-build emission spike** on Z.ai's smallest model against a realistic high-tool-count server (measuring hallucinated-name / dropped-arg / wrong-server rates at p95 *including a structured repair round*), a harness-side **schema-validation + repair loop**, per-agent **tool-list scoping** to bound prompt bloat, and a per-runtime **"degrade-not-abandon"** capability flag. `devils-advocate`'s standing dissent: a spike on friendly servers manufactures false confidence — bind it to the long tail or the parity claim is unproven.
- The existing in-production emission record samples a *closed, hand-tuned* 7-action set; MCP is *open and untuned*, so the spike must exercise that distribution, not a friendly one.

## Implementation Notes

Reuse `validate_action_request_with_scope` (`src/actions/mod.rs:145`), the `execute_action_request` dispatch (`:278`), and `has_tool` / `has_capability` gating. Add new free-form event kinds `mcp_tool_called` / `mcp_tool_result` (event `kind` is a `String`, no enum change). Feature-flag the whole surface like the existing `features.parallel_step_groups`.
