# ADR-007: Read-only auto-allow via the protocol resource/tool split; server hints informational

## Status

Accepted

## Date

2026-06-15

## Context

PRD CF3 wants read-only tools to auto-allow (avoiding approval fatigue), but the council's security advisors were firm that **server-supplied data must not be a trust boundary**. `rmcp` exposes a `readOnlyHint` tool annotation, but it is optional and **set by the server** — a poisoned server could mark a destructive tool read-only to skip the gate.

## Decision

Auto-allow applies to MCP **resources** only: `ReadMcpResource` / `ListMcpResources` are read-class actions under the existing read capability and auto-allow. **All tools** (`CallMcpTool`, `Capability::McpTool`) pass the trust gate — prompt on first contact from an untrusted server, run quietly once the server is trusted. The server's `readOnlyHint` is **surfaced in the approval card as information** but never gates. This **refines PRD CF3**: read-only auto-allow means *resources*, not server-self-classified tools.

## Alternatives Considered

### Alternative 1: Honor `readOnlyHint` for auto-allow

- **Description**: A tool annotated `read_only_hint = true` auto-allows, even from an untrusted server.
- **Pros**: Lowest friction; matches CF3's literal wording.
- **Cons**: Makes a server-controlled field a security signal — a poisoned server bypasses the gate by lying.
- **Why rejected**: Violates "server data is not a trust boundary"; the per-agent allowlist contains blast radius but should not be the only line.

### Alternative 2: User-designated read-only in the allowlist

- **Description**: The per-agent allowlist tags specific tools as auto-allow (user-controlled).
- **Pros**: Safe (not server-controlled) and low-friction for chosen tools.
- **Cons**: More config surface.
- **Why rejected for V1**: Deferred as a possible enhancement; the resource/tool split covers the safe default without new config.

## Consequences

### Positive

- No server-controlled approval bypass; simplest model; maps cleanly onto the existing capability system.

### Negative

- A genuinely read-only *tool* prompts once until its server is trusted — slightly more first-contact friction than CF3 implied.

### Risks

- Minor expectation gap vs. PRD CF3 wording — documented here and surfaced in the spec.

## Implementation Notes

In `validate_action_request_with_scope`: `ReadMcpResource`/`ListMcpResources` → read capability, auto-allow; `CallMcpTool` → `Capability::McpTool` + per-`(agent, server, tool)` default-deny allowlist + trust-tier check (untrusted ⇒ `RequiresApproval` with the full description surfaced; description-hash change ⇒ `RequiresApproval`).
