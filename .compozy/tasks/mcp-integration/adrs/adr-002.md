# ADR-002: stdio-first V1; defer HTTP + OAuth as one bundle to V1.1

## Status

Accepted

## Date

2026-06-15

## Context

Given ADR-001 (harness-brokered MCP), how much transport/lifecycle/auth surface should V1 carry? The initial product choice was a "Complete" V1: stdio **and** Streamable HTTP transports, full lifecycle, with the OAuth-2.1 "server-as-Resource-Server" model designed-in. The council (pragmatic-engineer, architect-advisor) converged against this: HTTP and OAuth are pure new surface that contribute **nothing** to the North Star (cross-runtime parity is provable with stdio alone), and OAuth machinery (DCR, PKCE, token store, refresh, browser-launch consent) is security-sensitive code that **cannot be validated without a real remote server in hand**. A "design-in-but-defer" stub was named the worst outcome — you pay the abstraction cost now and still risk building the wrong seam.

## Decision

**V1 ships stdio transport only**, plus the full broker / governance / lifecycle spine. **HTTP + Streamable HTTP + OAuth are deferred as one coupled bundle to V1.1** (a committed next milestone, not "someday" — `HTTP-without-OAuth` is a useless half-thing, so the two ship together or not at all).

Three riders make V1.1 a strictly **additive drop-in** rather than a retrofit, and all three are free because stdio already exercises them:
1. **Transport-agnostic config** — `[mcp.servers.<name>]` carries `command`/`args`/`url`/`transport` from day one; only the stdio code path is wired.
2. **`McpSupervisor::connect` is `async` and its lifecycle is event-recorded/extensible** — stdio's own spawn + `initialize` handshake is already async; connect / initialized / crashed transitions are recorded events. Adding OAuth later means new lifecycle-event variants, not a reshaped connector.
3. **The governance taxonomy ships in V1** — per-server identity + a `Capability::McpTool` egress gate, exercised by a side-effecting *stdio* tool call exactly as by a remote one.

## Alternatives Considered

### Alternative 1: Complete V1 (stdio + Streamable HTTP + OAuth designed-in)

- **Description**: Ship both transports and the OAuth resource-server model in V1.
- **Pros**: Remote servers (a company's internal HTTP MCP tool) work immediately — the place governance matters most.
- **Cons**: OAuth machinery is unvalidatable with no remote server to test against → speculative; the "designed-in-but-deferred" stub pays abstraction cost without de-risking the seam; materially larger, slower, flakier V1.
- **Why rejected**: Spends the V1 budget on surface that adds zero parity and high unvalidated risk.

### Alternative 2: stdio-only, HTTP "on demand" (no committed milestone)

- **Description**: pragmatic-engineer's hardest line — ship stdio, don't even commit HTTP to a roadmap slot; earn it on concrete demand.
- **Pros**: Leanest possible V1.
- **Cons**: "Configure once, every runtime gets it" reads as false advertising when a user's org HTTP tool is unsupported indefinitely (product-mind's value objection).
- **Why rejected**: Remote-as-*never* is a value failure that undercuts the lead message; remote-as-*next* is fine.

## Consequences

### Positive

- Cleanest surface to prove the trust model end-to-end: local subprocess, local approval, no egress/credential story to get wrong first.
- Covers the primary persona's (solo power-user) local toolchain (filesystem, git, sqlite) — all stdio.
- HTTP/OAuth becomes an additive V1.1 drop-in, not a rewrite.

### Negative

- Remote / HTTP-only servers are unsupported in V1.

### Risks

- Users with remote tools are blocked until V1.1 — mitigated by the **committed** V1.1 milestone and transport-agnostic config that signals the roadmap in the schema itself.
- **Open**: the exact V1.1 trigger, and which MCP spec revision to pin (transports + auth were revised three times in 2025; pin and surface the version).

## Implementation Notes

Model transports behind a `Transport` trait with a single stdio impl; the Streamable HTTP impl is additive. Ship HTTP and OAuth together. The async, event-recorded `connect` lifecycle and the per-server-identity + `Capability::McpTool` taxonomy are V1 work even though only stdio uses them.
