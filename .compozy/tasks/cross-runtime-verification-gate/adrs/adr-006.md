# ADR-006: A structured `ReviewFinding` type carried in review events, rendered as one coalescing `ReviewRound` chat item

## Status

Accepted

## Date

2026-06-19

## Context

The PRD's finding anatomy requires severity, `file:line`, claim, rationale,
confidence, and provenance per finding. The probe found:

- `AgentResult.findings` is `Vec<String>` (`src/orchestrator/mod.rs:216`) — no
  structured finding/severity type exists.
- Multi-event chat items coalesce via a `ChatLifecycleKey` + an `apply_*`
  projection arm + `upsert`. `GradeLoop` is the exact analog:
  `ChatLifecycleKey::Grade { run_id }` (`src/app/chat/mod.rs:134`), `grade_key`
  (`src/app/chat/projection.rs:2514`), `apply_grade_round`
  (`projection.rs:1842`), `ChatItemKind::GradeLoop`. Council events today render
  as scattered diagnostics with no lifecycle key.

## Decision

1. **Add a structured `ReviewFinding` type** carried in the review event payloads,
   separate from `AgentResult.findings`. Fields: `severity` (an enum:
   `Important` / `Nit`), `file`, `line`, `claim`, `rationale`, `confidence` (an
   enum: `High` / `Medium` / `Low`). The reviewer returns these in its structured
   output; the harness records them as `review_finding` events. This keeps findings
   machine-readable for confidence-gating and the actioned-catch metric, and avoids
   parsing formatted strings.
2. **Render the review as one coalescing `ReviewRound` chat item.** Add
   `ChatItemKind::ReviewRound` and `ChatLifecycleKey::Review { run_id }` (with its
   `item_id()` arm), a `review_key` helper mirroring `grade_key`, dispatch arms for
   `review_started` / `review_finding` / `review_completed` in `apply_history_event`
   (`projection.rs:77`), and an `apply_review_round` arm mirroring
   `apply_grade_round` that appends each finding line and recomputes status/severity.
   The header carries the provenance line (reviewer family + producer-family set);
   findings render high-confidence-first with a leading tally; rationale is
   progressive-disclosure.
3. **Lightweight feedback** (👍/👎) attaches to a recorded finding and emits a
   `review_finding_rated` event for the precision metric — without re-running or
   mutating state.

## Alternatives Considered

### Alternative 1: Encode findings as formatted strings in `AgentResult.findings`

- **Description**: e.g. `"[Important] file.rs:42 — claim (confidence: high)"`.
- **Pros**: No new type; reuses the existing field.
- **Cons**: Parsing-fragile; can't gate/measure by confidence without re-parsing;
  weaker rendering; couples review output to the generic agent envelope.
- **Why rejected**: The PRD's confidence-gating and actioned-catch metric need
  structured fields; strings are a false economy.

### Alternative 2: Reuse `ChatItemKind::GradeLoop` for the review item

- **Description**: Render review rounds with the existing grade-loop item kind.
- **Pros**: No new item kind.
- **Cons**: Conflates the deterministic grade loop with the advisory review;
  different semantics (Pass/Fail verdict vs advisory findings), different header,
  different events.
- **Why rejected**: ADR-001/002 keep the two distinct; a dedicated `ReviewRound`
  keeps them legible and separately measurable.

## Consequences

### Positive

- Findings are machine-readable: confidence-gating, tally, and the actioned-catch
  metric all read structured fields.
- Review renders as one evolving item, matching `GradeLoop`/`Workflow` UX.
- Clear separation from the deterministic grading path.

### Negative

- New enums + a projection arm + lifecycle-key plumbing (item_id, key helper,
  drift tests) — a non-trivial but well-templated change.
- The reviewer's structured-output contract must express `ReviewFinding`, updating
  the runtime schema briefs.

### Risks

- **Reviewer returns malformed/garbage findings** → mitigation: validate the
  structured output; drop findings lacking a `file:line` (verify-before-surface);
  cap nit volume.
- **Variant drift tests** enumerate `ChatItemKind`/key variants → mitigation:
  update them in the same change.

## Implementation Notes

- `ReviewFinding` lives near the review module (or `src/orchestrator` alongside
  `AgentResult`); serialized into `review_finding` event payloads.
- Chat plumbing mirrors `apply_grade_round` / `grade_key` exactly
  (`src/app/chat/projection.rs:1842, 2514`; `src/app/chat/mod.rs:134, 248`).
