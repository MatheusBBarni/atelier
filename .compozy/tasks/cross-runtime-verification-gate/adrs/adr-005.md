# ADR-005: Model family is derived from `RuntimeKind → ProviderId`; the producer set is session-level; the reviewer is auto-selected; provenance is recorded on the step event

## Status

Accepted

## Date

2026-06-19

## Context

ADR-001 requires recording producer lineage and deciding diversity on model
family; ADR-003 defines independence over the producer-family *set* with a loud
SKIP. The probe established the constraints:

- The **only existing family signal is `RuntimeKind → ProviderId`**
  (`src/runtime/status.rs:66`: Claude/Codex/Cursor/HttpApi/Fake). There is **no
  model-string→family parser** anywhere, and the model string is never parsed.
- `agent_step_started` records **only `{agent: id}`** (`src/app/mod.rs:5841`); the
  resolved model (post-fallback) is not returned from the runtime layer
  (`src/runtime/mod.rs:510`).
- `AgentProfile` stores a runtime *id* string; the `RuntimeKind` must be resolved
  via `config.runtimes[runtime_id].kind`.
- Default config producers run on `codex` (Codex) and `http_api` (HttpApi); the
  default council preset is entirely HttpApi.

## Decision

1. **Family = `ProviderId` derived from the runtime kind.** Add a helper (next to
   `ProviderId` in `src/runtime/status.rs`) that maps an agent → its configured
   runtime → `RuntimeKind` → `ProviderId`. V1 does **not** parse model strings;
   family granularity is provider-level. (Distinguishing two model families on the
   same runtime, e.g. `glm-5.1` vs a future model on `http_api`, is deferred.)
2. **Producer-family set is session-level.** The set is the union of the families
   of every Edit-capable step executed in the current (or resumed) session. This
   is a conservative **superset** of the per-diff set: if a family wrote any code
   this session it is excluded, so the reviewer is never less independent than the
   exact rule would require. Hand-edits contribute no family (permissive, per
   ADR-003).
3. **Reviewer is auto-selected.** Scan enabled agents, derive each one's family,
   and pick one whose family ∉ producer-family set to run with the reviewer brief.
   If none is reachable, **SKIP loudly** with a message naming the producer set and
   guidance to add a different-family runtime. No new config section in V1.
4. **Provenance is recorded on the step event.** Extend the `agent_step_started`
   payload (and/or a `review_started` payload) to include the producing agent's
   `runtime` id and derived `family`, so a resumed session can reconstruct the
   producer-family set from history. V1 records the *configured* runtime (family is
   correct regardless of model fallback, since fallbacks stay within a runtime);
   plumbing the exact resolved model out of the runtime layer is deferred.

## Alternatives Considered

### Alternative 1: Parse the model string to derive family

- **Description**: Map `"claude-*"`/`"gpt-*"`/`"glm-*"` → family by prefix.
- **Pros**: Finer than provider; distinguishes families sharing a runtime.
- **Cons**: No such parser exists; brittle against aliases/new models; unneeded
  when each runtime currently fronts one family.
- **Why rejected**: YAGNI for V1; `RuntimeKind→ProviderId` is exact for today's
  runtimes. Revisit if one runtime fronts multiple families.

### Alternative 2: File-attributed producer set

- **Description**: Map `git diff --name-only` files to the steps that changed them.
- **Pros**: Precise to the actual diff.
- **Cons**: Needs file→step attribution and partial-overlap handling; marginal
  value when most sessions are single-producer.
- **Why rejected**: Session-level is a safe superset; precision deferred (ADR-003
  records the exact-set intent).

### Alternative 3: Plumb the resolved model out of the runtime layer now

- **Description**: Add a resolved-model field to `RuntimeStepResult`/`RuntimeOutput`.
- **Pros**: Exact model provenance.
- **Cons**: Touches the runtime return path; unnecessary because family (the
  decision input) is fallback-invariant within a runtime.
- **Why rejected**: Deferred; configured runtime is sufficient for the family
  decision.

## Consequences

### Positive

- Reuses the one existing family signal; no brittle string parsing.
- Session-level set is simple and never under-excludes (safe by construction).
- Auto-selection makes the feature "just work" with whatever runtime diversity the
  user configured (Mia's story), and the SKIP path nudges single-family users.
- Recorded provenance survives session resume.

### Negative

- Provider-level family can't tell apart two families behind one runtime — an
  over-coarse SKIP/independence call in that (currently nonexistent) case.
- Session-level set may SKIP when a file-attributed set would have allowed a
  reviewer (a family wrote unrelated code this session) — a conservative
  false-SKIP, surfaced clearly.
- Auto-selecting an arbitrary independent agent may pick a weaker model than a
  curated reviewer would; acceptable for the probe, revisited with the optional
  `[review]` override later.

### Risks

- **One runtime fronts multiple families in future** → provider-level family
  misclassifies. *Mitigation*: localize the helper so a model-string refinement
  can replace it without touching callers.
- **No independent family configured** → frequent SKIPs. *Mitigation*: the SKIP
  message is explicit onboarding toward adding a runtime.

## Implementation Notes

- Family helper in `src/runtime/status.rs`; resolve runtime kind through
  `EffectiveConfig`.
- Session producer-family set accumulated from Edit-capable step events; provenance
  fields added to `agent_step_started` payload construction
  (`src/app/mod.rs:5841` and siblings).
