# ADR-002: V1 ships as an on-request `/review` command — a single independent (different-family) reviewer over the working diff, advisory

## Status

Accepted

## Date

2026-06-19

## Context

ADR-001 fixed the cross-runtime feature as a lineage-based reviewer-diversity
policy: record producer lineage as fact, decide diversity on model family, ship
advisory and probe-first. This PRD-stage decision settles the **product shape** of
that probe: how a user invokes it, what it reviews, and what it returns.

Codebase research found that council is *orchestrator-routed only* (keyword
detection on the prompt/goal) with no user-facing `/review` or `/council`
command; council results render as separate diagnostic chat items with no
lifecycle coalescing; and there is no in-app "model family" concept today.
Market research found the closest analog is Claude Code's `/code-review`
(terminal, non-blocking, severity-tagged Important/Nit, effort-tunable, `file:line`,
👍/👎) combined with 2ndOpinion's explicit "a different model family reviewed
this" trust framing — together validating an on-request, advisory, severity-ranked,
provenance-labelled design.

Three approaches were weighed: (A) a single independent reviewer with a
research-backed findings list; (B) a 2–3 reviewer diverse panel with consensus and
disagreement foregrounding; (C) a minimal looks-good/has-concerns verdict.

## Decision

Ship V1 as a new **`/review`** slash command with this product shape:

1. **On-request only.** `/review` is the sole trigger. No auto-trigger on high-risk
   steps, no unattended surfacing, no auto-fixer in V1. The command is attended by
   definition, which sidesteps the "advisory output nobody reads" problem entirely
   for now.
2. **Target = the whole current uncommitted working diff** (mirrors Claude Code's
   `/code-review`). See ADR-003 for how independence is defined when the working
   diff has multiple or unknown producers.
3. **Single independent reviewer.** One council reviewer whose model family differs
   from the producer-family set of the diff (ADR-003); if none is reachable, **SKIP
   loudly** with a visible reason — never a same-family review presented as
   independent.
4. **Advisory, non-blocking.** Findings never block, gate, or mutate state. The
   run's status is untouched.
5. **Research-backed finding anatomy.** Each finding carries: severity class
   (Important / Nit), `file:line`, a one-line claim, expandable rationale, a
   suggested direction, a confidence level, and a prominent **provenance label**
   ("Reviewed by *<family>* — independent, advisory"). High-confidence findings are
   shown by default; an effort/`--all` knob widens recall.
6. **Verify-before-surface.** A finding must cite a real `file:line`, not an
   inference — to hold the false-positive rate down (the dominant abandonment
   driver).
7. **One evolving review item.** The review round renders as a single coalescing
   chat item (a new lifecycle key), not scattered diagnostics.

Approach **A** is chosen. Approach **B** (diverse panel) becomes the V2 stretch.

## Alternatives Considered

### Alternative 1: Approach B — diverse panel / consensus

- **Description**: Run 2–3 different-family reviewers in parallel, surface each plus
  a synthesized consensus, foreground where they disagree.
- **Pros**: Richest trust signal; disagreement-as-signal is the strongest
  differentiator; closest to 2ndOpinion's marketed value.
- **Cons**: Council executes **Serial-only** today — this needs a new parallel
  execution mode; 2–3× cost/latency; more findings to de-noise; premature before
  the single-reviewer probe proves users act on cross-family catches.
- **Why rejected**: Violates probe-first. Deferred to V2 once actioned-catch-rate
  justifies the added cost and the parallel mode.

### Alternative 2: Approach C — minimal verdict

- **Description**: A single cross-family looks-good / has-concerns verdict plus a
  short bullet list; no severity tiers, no confidence gating.
- **Pros**: Fastest to build; minimal UX surface.
- **Cons**: Research is explicit that un-tiered, unlocated, prose-only findings are
  the least actionable and the first to be tuned out; loses the finding-anatomy
  benefits; weak differentiation.
- **Why rejected**: Too thin to validate the premise; a noisy verdict torches trust
  with no way to gate it.

### Alternative 3: Invoke via council keyword routing instead of a command

- **Description**: Extend the orchestrator's council keyword trigger with phrases
  like "second opinion" so natural-language prompts route to a cross-family review.
- **Pros**: No new command; reuses existing routing.
- **Cons**: Undiscoverable; implicit; conflates "the orchestrator decided to
  review" with "the user asked for an independent review."
- **Why rejected**: An explicit, discoverable `/review` gives a far clearer mental
  model and a clean place to surface provenance and SKIP messaging.

## Consequences

### Positive

- Smallest credible probe: validates actioned-catch-rate before any auto-trigger,
  panel, or fixer cost is paid.
- Reuses council's serial dispatch and per-member runtime as-is — minimal new
  surface beyond the command, the finding model, and the chat item.
- The advisory/non-blocking, on-request posture means the worst case is observable
  transcript noise, which is exactly the data needed to earn V2.

### Negative

- A single reviewer is one independent opinion, not a panel — the disagreement
  signal (B's differentiator) is unavailable until V2.
- `/review` on the whole working diff inherits the multi-producer ambiguity that
  ADR-003 must resolve.
- A new lifecycle chat item and a new finding model are net-new UX surfaces to
  build and test.

### Risks

- **False-positive noise** erodes trust → confidence-gating (high-confidence
  default), verify-before-surface, nit caps.
- **Low actioned-catch-rate** would mean the premise doesn't pay off → the probe is
  explicitly instrumented to measure this before V2 is funded.

## Implementation Notes

- Add `/review` to the slash-command catalog (`src/slash_commands.rs`) as an app
  command; surface it in help and unknown-command guidance.
- Reuse `run_council_workflow` dispatch with a single member selected by the
  diversity policy (ADR-001 / ADR-003).
- Add a coalescing `ChatLifecycleKey` for the review round (parallel to
  `GradeLoop` / `Workflow`), upgrading council's current diagnostic-only rendering.
