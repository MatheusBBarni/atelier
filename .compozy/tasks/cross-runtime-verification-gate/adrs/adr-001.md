# ADR-001: Cross-runtime review is a lineage-based reviewer-diversity policy over council, advisory by default, grounded in recorded producer provenance

## Status

Accepted

## Date

2026-06-19

## Context

atelier already ships two review mechanisms: a deterministic **self-grading gate**
(reviewer profile runs the project's real tests/lint; verdict is machine-derived
from exit codes — `derive_grade_verdict`, `orchestrator/mod.rs:397`) and the
serial **council** review workflow (`run_council_workflow`, `app/mod.rs:5544`),
a routing target the orchestrator uses only on high-risk or explicitly-requested
steps. Council members already carry a per-member `runtime`, so dispatching a
review to a chosen runtime is a solved primitive.

The proposed "cross-runtime verification gate" adds the **judgment** layer the
deterministic gate cannot reach: on a high-risk diff, route a semantic review to
a model that does **not** share the producer's blind spots. The research premise
is strong — model similarity undermines AI oversight (arXiv:2502.04313), ~60%
error agreement when both models are wrong (arXiv:2506.07962), a 64.5%
self-correction failure rate (arXiv:2507.02778), and cross-family juries that are
both less biased and ~7–8× cheaper (arXiv:2404.18796) — but it is bounded by
frontier convergence (independence shrinks on the hardest diffs) and by LLM
false-positive rates (40–80% untuned; trust collapses above ~50%).

A five-advisor council debate surfaced two decisive corrections to the naive
framing ("extend council so the reviewer runs on a *different runtime*"):

1. **Runtime is a proxy for model lineage that can silently collapse to zero
   independence.** Two runtimes fronting the same model family (already plausible
   in this harness) would certify a same-lineage review as "diverse" — security
   theater exactly where stakes are highest.
2. **The producer's runtime/model is not recorded today** (`agent_step_started`
   stores only the agent id, `app/mod.rs:5844`). Selecting "different from the
   producer" by inferring from *current* config is a config-drift hazard, and the
   fact cannot be appended to an immutable event log after the fact.

## Decision

Ship the cross-runtime verification gate as a **lineage-based reviewer-diversity
policy that council consumes**, scoped as follows:

1. **Record producer provenance as an immutable fact.** Add the producer lineage
   triple `(provider, model_family, model)` to the dispatch/step event at
   production time. This is an additive, backward-compatible payload change and
   is the single load-bearing new primitive.
2. **Decide diversity on model family, not runtime kind.** The fire/SKIP rule is a
   named, testable predicate: if the candidate reviewer's `model_family` equals
   the recorded producer's `model_family`, **SKIP loudly** with a visible reason;
   otherwise fire. Runtime kind is a dispatch hint only. Prefer a different
   runtime kind for dispatch, but never let "different runtime, same family" pass
   as diverse, and never silently downgrade to a same-family reviewer to keep the
   feature "working."
3. **Boolean v1, score later.** Implement the predicate as a boolean on lineage.
   Defer any tunable independence / provenance-distance *score* and threshold
   until measured data justifies the calibration cost.
4. **Advisory by default; the fixer is earned.** Surfaced findings are advisory
   and non-blocking. The opt-in auto-fixer, any auto-trigger broadening, and a
   hard merge/ship gate stay gated on measured **actioned-catch-rate** and a
   false-positive precision floor — not shipped on optimism.
5. **Promise the floor, gate the ceiling.** The guaranteed value is *auditor
   independence* (the reviewer has no stake in the producer's diff, killing
   self-confirmation bias). Novel cross-family defect catch is the uncertain
   ceiling; instrument disagreement-rate per lineage-pair so correlated pairs can
   be demoted.
6. **Trigger stays narrow.** Fire only on council's existing high-risk /
   explicitly-requested trigger. Do not broaden the surface in v1.

The unattended-consumer question (does advisory output fire, or only silently
sample disagreement-rate, when no human is attached?) is left as an Open Question
with a config knob, not resolved here.

## Alternatives Considered

### Alternative 1: "Different runtime kind" selector (the original framing)

- **Description**: Select a reviewer whose `RuntimeKind` differs from the
  producer's; fall back to a different model on the same runtime; else SKIP.
- **Pros**: Smallest possible predicate; runtime kind is already resolved per
  agent profile.
- **Cons**: Runtime kind is not model lineage — two runtimes can front the same
  family, certifying a same-lineage review as diverse. The same-runtime fallback
  is usually the same family at a different size (weakest independence). Records a
  proxy, not the fact, into an immutable log.
- **Why rejected**: Sells an independence guarantee it cannot honor; the failure
  is silent and bakes a false negative into history. Council (Architect, Devil's
  Advocate, Thinker) converged against it.

### Alternative 2: Standalone `ReviewerDiversityPolicy` subsystem with an independence score

- **Description**: A reusable selector keyed on a scalar provenance-distance score
  (base-model lineage > corpus overlap > vendor > runtime), with a tunable
  fire/SKIP threshold, callable by council, the grading gate, and future jurors.
- **Pros**: Most correct long-term; reusable; models independence as a continuum.
- **Cons**: A threshold means a calibration problem, a config knob, and "why did
  it skip at 0.62" support burden — owned before a single data point exists.
- **Why rejected**: Speculative generality. The *fact* (lineage on the event) and
  the *boolean* (same-family SKIP) are v1; the *score* is deferred until measured
  false-positive data earns it. (Architect: "defer the score, never the fact.")

### Alternative 3: Auto-blocking forcing function in v1

- **Description**: Block the Completed status / mark the step unsafe automatically
  when the cross-family reviewer flags a concern.
- **Pros**: Closes the "advisory output nobody reads" gap for unattended runs.
- **Cons**: Wires an auto-blocker to a noise source whose FPR is unmeasured; the
  first false block trains the user to disable the feature, spending the one
  bullet.
- **Why rejected**: Premature. v1 adds at most a non-blocking
  `marked_for_human_review` flag for unattended runs; the hard gate is earned with
  precision data.

## Consequences

### Positive

- The feature's headline promise ("reviewed by a different mind") becomes
  *true and durable* rather than an inference that lies on config/fallback drift.
- The recorded lineage triple is reusable: the grading gate, a future jury, and
  even cost routing can consume it with zero new infrastructure.
- Advisory-default keeps the worst case to observable transcript noise — the exact
  data needed to earn the fixer.
- A guaranteed floor (auditor independence) means the feature has value even if the
  novel-catch rate proves low.

### Negative

- A new immutable field on a core event must be correct on day one and carried by
  every runtime's step path.
- Detecting `model_family` reliably across heterogeneous runtimes (Codex/Claude/
  Cursor/Z.ai, with fallback chains and aliased model names) is non-trivial.
- The feature fires only on a narrow, intermittent trigger for a multi-runtime
  subset of users — capped reach by design.

### Risks

- **Frontier convergence** — cross-family independence shrinks on the hardest
  diffs that trigger the gate. *Mitigation*: instrument per-lineage-pair
  disagreement-rate; auto-demote correlated pairs; promise the floor, not the
  ceiling.
- **False-positive noise** — untuned LLM reviewers run 40–80% FPR. *Mitigation*:
  advisory-only + a precision floor before any forcing function.
- **Write-only advisory on unattended runs** — findings no one reads cost tokens
  and poison the catch-rate metric. *Mitigation*: name the triage surface +
  segment the metric, or don't surface on unattended runs (Open Question).
- **Model-family detection gaps** — an unknown/unmappable family must SKIP loudly,
  never default to "diverse."

## Implementation Notes

- Add `(provider, model_family, model)` to the producer step event payload
  (`agent_step_started` or the step-completed event that carries the diff);
  ensure every runtime populates it.
- Express the predicate as a standalone, unit-tested function consumed by council
  dispatch — not an inline `if` inside `run_council_workflow`.
- Reuse `CouncilMemberProfile.runtime` for dispatch; the policy chooses *which*
  member/runtime satisfies the family-difference constraint.
- Surfacing: extend chat projection so a cross-runtime review round is visible
  (council events are diagnostic today, `app/chat/projection.rs:146`).
