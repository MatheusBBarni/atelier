# ADR-003: Harness-driven bounded grade→fix loop, exempt from the run step budget

## Status

Accepted

## Date

2026-06-15

## Context

ADR-001/002 committed to an externally-grounded, automatic, bounded grade→fix loop reusing the existing
machinery. The techspec phase had to choose how the loop is *driven* and *budgeted*. Codebase exploration
established the exact seams:

- `run_agent_step` (`src/app/mod.rs:3026-3095`) is the leaf executor; its `AgentResult` arm
  (`:3083-3092`) is where the producing agent's id and `changed_files` are available before the result is
  pushed into `run.previous_results`.
- `run_council_workflow` (`:3155-3323`) is a proven *virtual-workflow* template: a self-contained loop
  that runs sub-steps and pushes one synthesized result back, returning to the main drive loop.
- Council members run via `execute_runtime_step` with **actions stripped** (read-only advisory), so they
  cannot run commands; the action-executing path `execute_runtime_step_with_actions` (used by
  `run_agent_step` at `:3071`) is the one that runs `RunCommand` and records `command_completed` events.
- `run.step_count` is incremented by the *caller* (`run_agent_step:3055`, `run_council_workflow:3221`),
  and `max_agent_steps` (default 12) is checked against it — so a caller that does not increment
  `step_count` is automatically exempt.
- The existing reviewer→fixer cycle is **orchestrator-discretionary**; the orchestrator routinely skips
  routing a reviewer.

The PRD specifies "the **same** agent is re-dispatched with the concrete failures." The user selected a
harness-driven internal loop and exemption from `max_agent_steps`.

## Decision

Implement a dedicated harness executor `run_grading_workflow`, structurally modeled on
`run_council_workflow` but using the **action-executing** runtime path:

- **Trigger:** force-injected at the `run_agent_step` `AgentResult` arm (`src/app/mod.rs:3083`), gated by
  `grading.enabled` AND the producing agent has `Capability::Edit` AND `result.changed_files` is non-empty
  AND the step is a top-level single-agent step (not a subtask, not a parallel child, not the grader/fixer
  re-entry). The gate is computed *before* the result is moved into `previous_results` at `:3092`.
- **Loop:** for up to `grading.max_attempts`: dispatch the **grader** (the built-in `reviewer` profile —
  Read/Command/Verify, no Edit) via `execute_runtime_step_with_actions` so it runs the project checks;
  derive the verdict (ADR-004); on FAIL re-dispatch the **same producing editing agent** via the same
  action-executing path with the concrete failures appended; re-grade. Break on PASS or SKIP.
- **Budget exemption:** grade/fix sub-steps run via `execute_runtime_step_with_actions` **without**
  incrementing `run.step_count`, so they never count against `max_agent_steps`. The loop is bounded solely
  by `grading.max_attempts` plus the existing wall-clock guard (`wall_clock_limit_reached`) and the
  per-command timeout (`max_command_minutes`, default 10 min).
- **No recursion:** because sub-steps do not pass through the `run_agent_step` `AgentResult` arm, they do
  not re-trigger grading (the same reason council members are not auto-graded).
- **Exhaustion:** on FAIL after the last attempt, escalate to the user (ADR-001; reuses the clarification
  pause transport with accept/retry/abort), not a hard stop.

## Alternatives Considered

### Alternative 1: Orchestrator-routed grader (force-inject grader only; orchestrator routes the fix)

- **Description**: Inject only the grader step; let the existing orchestrator loop decide the fix, reusing
  and generalizing the `review_fix_cycle` bound.
- **Pros**: Less new code; reuses the routing loop and the cycle bound.
- **Cons**: The *fix* step stays orchestrator-discretionary (it may not route a fixer); the fixer (not the
  same agent) does the work, diverging from the PRD; requires generalizing the hardcoded
  `next_agent_id == "fixer"` cycle bound.
- **Why rejected**: Reintroduces the discretion the feature exists to remove; contradicts "re-dispatch the
  same agent."

### Alternative 2: Grade/fix sub-steps share the `max_agent_steps` budget

- **Description**: Increment `step_count` per grade/fix sub-step like council members.
- **Pros**: One budget; simplest accounting.
- **Cons**: A long task near its step limit can hit `max_agent_steps` mid-loop and stop with work
  unverified — the run-limit interrupts the loop, undercutting the guarantee.
- **Why rejected**: Verification is overhead, not user-requested work; it should not starve on the edit budget.

## Consequences

### Positive

- Deterministic: the fix always happens, bounded and self-contained; matches the PRD wording.
- Reuses the `run_council_workflow` template and the action-executing step path; no new runtime contract.
- Step-exemption falls out naturally (don't increment `step_count`); no recursion by construction.

### Negative

- A new executor (`run_grading_workflow`) plus the trigger gate is net-new code.
- Each grade is a real grader LLM turn (the cost the `max_attempts` cap bounds).

### Risks

- **Runaway cost** → bounded by `max_attempts` + wall-clock + per-command timeout; rounds shown with a counter.
- **Trigger over-firing** (subtasks, parallel children, grader/fixer re-entry) → the gate restricts to
  top-level single-agent Edit steps in V1; parallel-edit grading is deferred (PRD open question).
- **Step-exemption removes the original rationale** for extracting a shared `stop_for_agent_step_limit`
  helper (grading adds no 6th `max_agent_steps` copy). That refactor (ADR-001/002) is therefore
  **downgraded to optional adjacent cleanup**, out of this feature's MVP scope (YAGNI).

## Implementation Notes

`run_grading_workflow(&mut self, run, producing_agent_id, edited_changed_files)`; grader id is the
built-in `reviewer`; fixer is `producing_agent_id`. Use `execute_runtime_step_with_actions`
(`src/app/mod.rs:3071`) for every sub-step. Push the final grader result into `run.previous_results` and
return so the main `drive_run_inner` loop (`:1858`) re-enters the orchestrator (or pauses on escalation).
