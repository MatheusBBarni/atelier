# ADR-002: Phased delivery — agent-discovered verification in V1, config-asserted verification in Phase 2

## Status

Accepted

## Date

2026-06-15

## Context

ADR-001 committed to an externally-grounded auto-verification loop (the grader runs real
compile/test/lint; a PASS is emittable only with cited exit-0 evidence; no oracle → SKIP, never a
fabricated pass). The PRD phase had to decide *how* the verify command is determined and *how much*
lands in the MVP.

PRD-focused research surfaced a pivotal constraint and a greenfield gap:

- **The common case is already friction-free.** Canonical cargo commands (`cargo test`, `cargo clippy`,
  `cargo build`, `cargo fmt`) are on a hardcoded read-only allowlist and auto-approve in **both** yolo
  (the default) and normal mode — no prompt ever. Shell-chained (`&&`/pipes) or custom commands
  (`make test`) drop off the allowlist and prompt every time in normal mode, with no "remember."
- **Verify-command resolution is greenfield.** Nothing in atelier detects project type or runs a test
  command today; the built-in reviewer/fixer prompts mention `cargo test` only as an *example*, so
  verification is currently agent-discovered, not config-asserted. `--doctor` and `/config` are
  extend-by-append surfaces for later discoverability.
- **Benchmarks favor a single bounded pass** (+5–13pp pass@1, saturating after the first grounded
  iteration; ~2× cost vs 5–30× for unbounded loops).

The user selected: verify command **agent-discovered** for V1; loop rendered as **one evolving
transcript item with a retry counter**; approval behavior **inherited** (canonical commands silent,
custom/chained prompt in normal mode, documented). Delivery strategy: **lean grounded loop, phased.**

## Decision

Deliver in three phases, with the MVP scoped to the smallest *correct* grounded loop:

- **MVP (Phase 1):** The grounded loop with an **agent-discovered** verify command. The grader (built-in
  `reviewer`, no Edit) runs the check it chooses via `RunCommand`; the verdict is **derived from the real
  exit code** (PASS only on cited exit-0). When no real check runs, the step **SKIPs** (emits no verdict,
  proceeds as "done-unverified") — it never fabricates a pass. Bounded by `max_review_fix_cycles`; on
  exhaustion, escalate to the user (accept / retry / abort). Rendered as one evolving transcript item with
  a `retry N/max` counter. **Opt-in, default OFF.** Approval behavior is inherited and documented.
- **Phase 2 — authoritative grounding:** A configurable / auto-detected verify command so verification
  is reproducible and harness-asserted rather than agent-guessed, plus discoverability via a `--doctor`
  check and a `/config` status line/warning.
- **Phase 3 — trust + hardening:** Default-ON wherever an external check exists; "stuck / identical
  failure repeated" detection; and a user-extensible trusted-command list to remove normal-mode approval
  fatigue for custom commands.

This keeps ADR-001's grounding rule intact in V1 (agent picks the command, but the verdict is still
exit-code-derived; a no-check step SKIPs) and defers the authoritative config lever to Phase 2.

## Alternatives Considered

### Alternative 1: Authoritative grounding up front

- **Description**: Ship the configurable/auto-detected verify command in the MVP so verification is
  reproducible from day one (no agent guessing).
- **Pros**: Authoritative and reproducible immediately; closes the "two runs verify differently" gap.
- **Cons**: Bigger MVP and more config surface; reverses the user's choice; greenfield resolution
  (no cargo/npm detection exists) is real net-new work.
- **Why rejected**: The agent already tends toward canonical (allowlisted, friction-free) commands, so
  agent-discovery captures most MVP value at far lower cost; reproducibility is a fast Phase 2 follow-on.

### Alternative 2: Thin validation spike first

- **Description**: MVP strips to auto-firing the existing reviewer→fixer cycle on an exit-code gate — no
  typed verdict field, no new chat item, keep today's hard-stop (no escalation). Measure, then build.
- **Pros**: Cheapest to ship; fastest signal on whether grounded auto-verify reduces defects here.
- **Cons**: Defers the typed verdict, escalation, and evolving-item UX the council deemed minimum-correct;
  overloads `status`; thinner trust surface; likely rework to reach the real design.
- **Why rejected**: The minimum-correct representation (typed verdict, escalation, one evolving item) is
  cheap enough to include now and expensive to retrofit; a thin spike risks shipping a misleading metric.

## Consequences

### Positive

- Smallest correct MVP; reuses the `reviewer` profile, `max_review_fix_cycles`, and the existing path.
- Friction-free common case (yolo default + canonical cargo commands on the allowlist).
- A clean, motivated phasing story: agent-discovered → config-asserted → default-ON + hardening.

### Negative

- V1 verification is non-reproducible: two runs may verify differently, and the agent can SKIP by running
  no check (the accepted V1 trade-off, hardened in Phase 2).
- Custom/chained verify commands in `normal` mode prompt every time until Phase 3's trusted-command list.

### Risks

- **Agent skips verification** (runs no command, claims SKIP to avoid the loop) → V1 records SKIP honestly
  as "done-unverified" (no false pass); Phase 2's config verify command makes verification mandatory.
- **Normal-mode approval fatigue** for non-allowlisted commands → documented; recommend canonical commands;
  Phase 3 trusted-command list.
- **Discoverability of an opt-in default-OFF flag** → Phase 2 `--doctor`/`/config` surfacing.

## Implementation Notes

Agent-discovered command runs through `ActionRequest::RunCommand`, inheriting the canonical-cargo
auto-approval allowlist (`src/actions/mod.rs:448`) and `max_command_minutes`. The new `[grading]` config
section follows the `Features { parallel_step_groups }` opt-in precedent and must land with its `Raw`
mirror together (`#[serde(deny_unknown_fields)]`). Verdict derived from exit code; SKIP path emits no
verdict. See ADR-001 for the loop/verdict/escalation seams.
