# ADR-003: File-Index Acquisition via Background Worker Walk

## Status

Accepted

## Date

2026-06-12

## Context

The `@` dropdown needs a candidate list of repository files and folders. ADR-001
proposed a lazy, non-persistent walk on first `@`.

Codebase reality (verified against `src/tui/mod.rs`): the TUI render + input loop
is **synchronous** — a filesystem walk run inline in `render` or in a key handler
would stall the draw/input loop, and a re-walk on each dropdown open would stall
repeatedly on large repositories. However, the loop runs on a tokio
multi-thread runtime with an established **worker + channel** pattern
(`run_app_worker`, `mpsc` commands, `watch` state) and a 5-second background git
poller — the precedent for doing off-thread work and delivering results to the
TUI. Per-keystroke *filtering* is in-memory and cheap; only the *walk* is
expensive.

## Decision

Build the file index with a **background walk driven by the worker**: an initial
off-thread walk (`spawn_blocking`, since the `ignore`-crate walk is synchronous)
at startup, delivered to the TUI over a channel and cached in `TuiUiState`, plus
a **coarse periodic background refresh** (default ~15s, tunable) so files created
mid-session appear. Per-keystroke filtering runs in-memory over the cached list.

This **refines ADR-001**: "lazy on first `@`" becomes "background at startup +
periodic refresh," keeping every filesystem walk off the draw thread.

## Alternatives Considered

### Alternative 1: Synchronous one-shot at startup

- **Description**: Mirror the existing `load_skill_suggestions` loader — one
  synchronous walk after first paint, cached for the session.
- **Pros**: Simplest; most consistent with current code.
- **Cons**: A one-time startup stall on very large repos; no live refresh, so
  files created mid-session are missing until restart.
- **Why rejected**: The chosen approach reuses existing off-thread infra for
  marginally more code, avoids any stall, and supports refresh.

### Alternative 2: Lazy on first `@`, re-walk on reopen

- **Description**: Walk synchronously the first time `@` is used and on each open.
- **Pros**: Always fresh; zero startup cost.
- **Cons**: A synchronous re-walk stalls on each open for large repos.
- **Why rejected**: Violates the "never block typing" goal.

## Consequences

### Positive

- Never stalls input; the walk is always off the draw thread.
- Mid-session files appear via background refresh.
- Reuses the worker/channel and git-poller precedents.

### Negative

- Periodic re-walks consume background CPU.
- A brief window at startup before the first index arrives (the dropdown shows an
  empty/recents-pending state until ready).

### Risks

- Background re-walk cost on huge repos → mitigated by a coarse interval,
  off-thread `spawn_blocking`, and a capped result list; a future optimization is
  event-driven refresh after write actions complete.

## Implementation Notes

- Walk root = `ui_state.working_directory` (`Option<PathBuf>` from
  `config.working_directory`).
- Use the `ignore` crate; deliver `Vec<FileEntry>` over a channel; store it on
  `TuiUiState`.
- Refresh interval tunable and disable-able.
