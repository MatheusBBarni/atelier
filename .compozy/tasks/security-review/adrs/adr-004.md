# ADR-004: Findings cross the runtime boundary as formatted lines in the existing AgentResult envelope and are parsed app-side into shared Severity/Finding types; the rubric ships as the reviewer's built-in instructions

## Status

Accepted

## Date

2026-06-19

## Context

ADR-001 requires the security review to produce a typed event family carrying
`Vec<Finding>` with shared `Severity`/`Finding` leaf types (reusable by
`cross-runtime-verification-gate` in V2), while keeping the V1 mechanism runtime-
agnostic and YAGNI.

The codebase already defines the runtime result contract. A reviewer step returns
a `RuntimeOutput` (`runtime/mod.rs`), whose success variant is
`AgentResult { … findings: Vec<String>, summary, status, … }`
(`orchestrator/mod.rs:211`). All four runtimes (codex/claude/cursor/zai) and the
`fake` runtime already speak this envelope; the Claude runtime in particular is
deliberately stripped to a minimal structured-adapter brief, so teaching every
runtime a brand-new output schema is costly and cuts against runtime-agnosticism.

The self-grading gate set the precedent for a *typed verdict* (`GraderVerdict`,
`orchestrator/mod.rs:369`) recorded into a JSON event payload and projected into a
chat card — but that verdict is derived by app code from deterministic exit codes,
not parsed from free model output.

The methodology (vulnerability-class checklist, severity scale, confidence gate,
hard-exclusion list, untrusted-content framing) must reach the reviewer reliably.
ADR-001 framed this as a "security-review skill." Skills, however, are discovered
from filesystem roots (`.agents/skills`, `.claude/skills`); a built-in command
cannot depend on a skill file being present in the user's workspace.

## Decision

1. **Reuse the `AgentResult` envelope; parse findings app-side.** The reviewer
   returns the existing `AgentResult`. Its built-in instructions require each entry
   in `findings: Vec<String>` to be a single structured line of the form
   `[SEVERITY] <title> — <file:line> — <why exploitable> — <suggested fix>`. The
   app parses each line into a shared `Finding` (with a `Severity` enum), applies a
   **safe fallback** (an unparseable line becomes a `Finding` with `severity =
   Info`/`Medium` and the raw text preserved), then records the
   `security_review_completed` event with the structured `Vec<Finding>` payload.
   No new `RuntimeOutput` variant and no per-runtime schema change.
2. **Define `Severity` and `Finding` as shared leaf types** next to `GraderVerdict`
   in `orchestrator/mod.rs`, serde-serializable, with no coupling to any one
   workflow, so the cross-runtime gate can reuse them in V2.
3. **Ship the rubric as the reviewer's built-in inline instructions.** The
   `security-reviewer` agent profile carries the methodology as a built-in
   instruction constant (functionally the rubric ADR-001 called a "skill"), so the
   feature works with no filesystem skill present. A discoverable
   `/skill:security-review` may layer on later as optional manual augmentation.

## Alternatives Considered

### Alternative 1: New first-class `security_review` runtime output schema

- **Description**: Add a `RuntimeOutput::SecurityReview { verdict }` variant and a
  named output schema the reviewer must emit as validated JSON.
- **Pros**: Strongly typed end-to-end; no string parsing; matches the typed-verdict
  spirit of self-grading.
- **Cons**: Every runtime adapter (codex/claude/cursor/zai/fake) must learn the new
  contract; the minimal Claude adapter brief grows; more surface for a V1 advisory
  feature.
- **Why rejected**: Violates runtime-agnostic + YAGNI. The universal `AgentResult`
  envelope already crosses every runtime; parsing at the app boundary is the
  smaller, equally-runtime-agnostic change.

### Alternative 2: Keep findings as raw strings, no structured type

- **Description**: Render `findings: Vec<String>` as chat lines, inferring severity
  from a leading token for coloring only; no `Finding` struct.
- **Pros**: Least code.
- **Cons**: Drops the shared `Severity`/`Finding` leaf types ADR-001 mandates for
  V2 convergence; the event payload carries no structure for later consumers.
- **Why rejected**: Forecloses the V2 path for a trivial saving.

### Alternative 3: Rubric as a discovered skill file

- **Description**: Ship a `security-review` SKILL.md and rely on skill discovery to
  inject it.
- **Pros**: Literal reading of ADR-001; user-editable rubric.
- **Cons**: A built-in command would silently degrade if the skill file is absent
  or shadowed; couples a shipped feature to workspace filesystem state.
- **Why rejected**: Built-in reliability. Inline instructions guarantee the rubric
  is always present; an optional skill can still augment it.

## Consequences

### Positive

- No runtime-contract change; works identically across all runtimes.
- Shared `Severity`/`Finding` types satisfy ADR-001 and unblock V2 convergence.
- The rubric is always present regardless of workspace skill files.
- Reuses the established record-event → projection path used by the grade loop.

### Negative

- Parsing free-form model lines is inherently fragile; depends on the rubric's
  format discipline.
- The structured `Finding` is only as good as the model's adherence to the line
  format; malformed lines degrade to low-structure findings.

### Risks

- **Parser drift / malformed lines** — *Mitigation*: a tolerant parser with a safe
  fallback (preserve raw text, default severity) so a finding is never dropped, plus
  unit tests over representative and adversarial line shapes.
- **Severity inflation by the model** — *Mitigation*: the rubric's confidence gate +
  hard-exclusion list curate before emission (ADR-003 curation); the parser does not
  invent severity it cannot read.

## Implementation Notes

- `Severity` (Critical/High/Medium/Low/Info) + `Finding { severity, title, location,
  why, fix }` in `orchestrator/mod.rs`, both `Serialize`/`Deserialize`.
- The parser is a pure function `parse_finding_line(&str) -> Finding` — unit-tested
  in isolation, independent of any runtime.
- Built-in instructions live as a `const` referenced by the `security-reviewer`
  built-in agent profile in `config/mod.rs`.
