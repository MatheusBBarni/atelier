# ADR-003: Security review output is a read-only, scope-honest "security report" card, not a bare findings list or an interactive triage surface

## Status

Accepted

## Date

2026-06-19

## Context

ADR-001 fixed the V1 mechanism (a standalone, app-orchestrated advisory workflow
driving a read-only reviewer) and ADR-002 fixed the threat model. This ADR decides
the **product shape of the output the user actually sees** — a PRD-level (WHAT/WHY)
decision, not an implementation one.

Clarification answers locked four product constraints before this decision:

- **Read-only report** — no per-finding acknowledge/dismiss interaction in V1.
- **TUI only** — invoked via `/security-review` inside an interactive session; no
  non-interactive CLI/CI mode in V1.
- **Full finding content** — each finding shows severity, file:line location, a
  short why-it's-exploitable explanation, and an advisory suggested fix (never
  auto-applied).
- **Curated by default** — show only high-confidence findings (Claude's
  confidence-gate + hard-exclusion recipe); do not dump everything.

The research consensus is that LLM security review fails in two opposite
directions: **alert fatigue** (too much noise → ignored) and **false assurance**
(a clean report read as "secure"). atelier already ships UX primitives a security
report can reuse — an evolving single chat card (the self-grading "Verification"
item, `projection.rs:1842`), a severity color/label vocabulary
(`theme.rs`; `[LOW]/[MEDIUM]/[HIGH]` labels at `tui/mod.rs:2290`), a
findings-as-labeled-lines pattern (`append_string_array`), and one-time muted
disclaimer text (the first-approval explainer, `projection.rs:22`).

## Decision

Render the review as a **credible, scope-honest "security report" card**
(Approach B), read-only and TUI-only, with this user-visible shape:

1. **A one-line verdict header** summarizing the outcome (e.g. counts by severity),
   never a reassuring green "secure" affordance when zero findings are surfaced.
2. **An explicit scope/coverage statement** — what was reviewed (branch diff vs the
   default branch, file/hunk counts) and, by implication, what was not. This is the
   single device that fights both failure modes at once.
3. **Findings grouped by severity**, each carrying severity, location, a short
   why-it's-exploitable explanation, and an advisory suggested fix, reusing the
   existing severity vocabulary and findings-line pattern.
4. **The reviewing model named**, so the user knows whose judgment this is.
5. **A persistent, honest advisory disclaimer** (best-effort LLM review; absence of
   findings is not proof of security; coverage is the branch diff only and may be
   incomplete or evaded), reusing the one-time-disclaimer precedent.

The card is a single evolving chat item (Scanning → Completed), consistent with the
Verification card pattern.

## Alternatives Considered

### Alternative A: Minimal advisory card

- **Description**: A single read-only card containing just the curated findings list
  plus the disclaimer — the leanest faithful port of Claude's `/security-review`.
- **Pros**: Fastest to ship; least UI surface; fully satisfies the four locked
  constraints.
- **Cons**: A bare list reads as low-credibility, scales poorly when a diff yields
  many findings, and omits the explicit scope statement that inoculates against
  false assurance.
- **Why rejected**: The marginal cost of a verdict header + scope statement is tiny,
  and those are precisely the elements that protect trust — the feature's whole
  value. Minimalism here saves little and costs credibility.

### Alternative C: Report + reviewer transparency

- **Description**: Approach B plus per-finding confidence scores, an inline
  weak-model warning, and an explicit "what wasn't checked" enumeration.
- **Pros**: Most transparent about the reviewer's limits; maximizes honesty.
- **Cons**: Adds output surface and detail the user otherwise chose to keep lean
  (they declined interaction and CLI surface); per-finding confidence can read as
  false precision; risks clutter that itself causes fatigue.
- **Why rejected for V1**: The weak-model warning (F7) and the curated/“what wasn't
  checked” intent are already carried by Approach B's scope statement and disclaimer
  without per-finding confidence noise. The extra transparency is a candidate
  enhancement, not a V1 need.

## Consequences

### Positive

- Output reads as a credible security report, not a chat dump — supporting the
  "trust layer" positioning while staying read-only.
- The scope/coverage statement + honest disclaimer directly counter the documented
  false-assurance failure mode.
- Reuses existing chat-card, severity-vocabulary, findings-line, and disclaimer
  primitives, so UI work is composition, not invention.
- Scales gracefully to large diffs via severity grouping + the verdict header.

### Negative

- Slightly more rendering/projection work than a bare list (header + scope line +
  grouping).
- Naming the reviewing model and stating coverage adds fields the workflow must
  populate.

### Risks

- **Verdict header misread as a guarantee** — *Mitigation*: header states counts and
  scope, never "secure"; disclaimer always present.
- **Severity grouping hides a lone critical in a long report** — *Mitigation*: order
  groups Critical→Info; surface highest severity in the verdict header.

## Implementation Notes

- This ADR governs the *product shape*; the event/data model (the `SecurityReview`
  event family, `ChatLifecycleKey::SecurityReview`, shared `Severity`/`Finding`
  leaf types) is fixed by ADR-001.
- Reuse the Verification-card evolution pattern (`projection.rs:1842`) and the
  severity tokens in `theme.rs`; do not introduce new color literals
  (`colors_live_only_in_theme_module` guard).
