# ADR-001: Security review is a standalone read-only reviewer agent + skill rubric driven by an app-orchestrated diff-as-data workflow, advisory and diff-scoped, modeled as its own event family

## Status

Accepted

## Date

2026-06-19

## Context

atelier already ships review machinery that an LLM security review could be
naively folded into: the serial **council** workflow (`run_council_workflow`,
`app/mod.rs:5544`), which dispatches `CouncilMemberProfile`s and synthesizes a
plural deliberation, and the deterministic **self-grading gate**
(`self-grading-retry-loop`), whose typed verdict is machine-derived from real
test/lint exit codes. A pending sibling packet, `cross-runtime-verification-gate`,
adds an on-request advisory *correctness* review routed to a different model
family.

The feature under decision is a narrower, on-demand capability: the user invokes
a security review, it examines the **current branch git diff only**, and returns
an **advisory, severity-ranked findings report** in chat — a close port of Claude
Code's `/security-review`, runtime-agnostic, with atelier's value coming from its
local/in-session execution rather than fleet diversity (deferred to V2).

A five-advisor council debate (pragmatic-engineer, architect-advisor,
security-advocate, product-mind, devils-advocate) surfaced three decisive
corrections to the naive framings ("just reuse council" / "just inject a skill"):

1. **Council is the wrong home.** A single security reviewer is a degenerate
   council-of-one; routing it through `run_council_workflow` pollutes council's
   plural-deliberation + synthesis semantics. Security review answers "is this
   diff dangerous?" (static scan), not council's "is this work good?"
   (deliberation) — sibling concepts, not the same concept.
2. **The reviewer must not fetch its own diff.** The security advocate showed the
   reviewer ingests attacker-controlled content; letting it run `git diff` via the
   `RunCommand` action puts a general command capability within reach of a
   prompt-injection surface (see ADR-002). The diff must be gathered and redacted
   in app code and supplied as untrusted *data*.
3. **Neither existing finding shape fits.** `councillor_result` models one opinion
   per reviewer in a plural panel; the self-grading `verdict` models a single
   pass/fail of an agent's own output. A security review is one producer emitting
   **N ranked findings** — a distinct shape that should not be forced onto either.

## Decision

Ship security review as a **standalone, app-orchestrated advisory workflow**,
scoped as follows:

1. **Mechanism: read-only agent + skill rubric, driven by a thin app workflow.**
   A dedicated `[agents.security-reviewer]` profile (capabilities restricted to
   read/analysis; **no `Edit`, no general `Command`** — see ADR-002) carries
   execution; a `security-review` skill carries the methodology (vulnerability-class
   checklist, severity rubric, confidence gate, exclusion list). A thin app-side
   workflow gathers the branch diff, redacts it, and dispatches the reviewer with
   the diff injected as untrusted data. Reject the council-preset and skill-only
   alternatives.
2. **Diff-as-data, diff-scoped.** The workflow computes the diff against a single
   fixed base rule (merge-base with the default branch; not a config knob in V1)
   and supplies it to the reviewer. Findings are scoped to the diff; the reviewer
   may read referenced files **read-only** to confirm exploitability (a precision
   aid, not a scope expansion).
3. **Advisory and non-blocking.** Output is a severity-ranked report rendered in
   chat. Security review **does not** enter `RunState` transitions or orchestrator
   routing — it is a terminal advisory chat item, never a waited-on state and
   never a merge/commit gate.
4. **Own event family, shared leaf types.** Introduce `security_review_started`
   → `security_review_completed` events carrying `Vec<Finding>`, projected through
   a new `ChatLifecycleKey::SecurityReview` into one evolving chat card. Factor
   `Severity` (Critical/High/Medium/Low/Info) and `Finding`
   `{ severity, title, location, description, recommendation }` as **shared leaf
   value types**, deliberately reusable by `cross-runtime-verification-gate` so V2
   fleet diversity converges instead of duplicating concepts.
5. **Precision is the product.** The rubric adopts Claude's
   confidence-threshold (drop low-confidence findings) + hard-exclusion list
   (DoS/rate-limiting/open-redirect/already-secured-secrets/generic
   input-validation). **Finding-disposition instrumentation ships in V1** so the
   actioned-finding precision KPI is measurable from day one.
6. **Runtime-agnostic capability, sane default.** The reviewer runs on any
   configured runtime, but ships pointing at a capable default model and emits a
   visible warning when configured on a weak/uncalibrated model (a weak model
   emitting confident "HIGH" labels erodes trust in the whole harness).
7. **Surface entry.** Exposed as a `/security-review` built-in command (recorded
   as a slash-command catalog exception; the catalog is otherwise ADR-frozen).
   `/agent:security-reviewer` + `/skill:security-review` remains a valid manual
   path and the same-day fallback if the command wrapper slips.

## Alternatives Considered

### Alternative 1: `[council.presets.security-review]` (reuse council)

- **Description**: Add a security-focused council preset and route on-demand
  through `run_council_workflow`.
- **Pros**: ~80% plumbing reuse (lifecycle events, dispatch, projection);
  capability-restricted member gives structural read-only.
- **Cons**: A single reviewer is a degenerate council-of-one that pollutes
  council's plural-deliberation + synthesis semantics; couples an advisory static
  scan to a deliberation workflow; `councillor_result` is the wrong finding shape.
- **Why rejected**: Concept duplication / semantic mismatch (architect). Council
  ("is this good?") and security review ("is this dangerous?") must stay distinct
  siblings sharing only the severity vocabulary.

### Alternative 2: Skill-only (`/skill:security-review`)

- **Description**: Ship just a `SKILL.md` rubric injected into whatever agent is
  active; no new code path.
- **Pros**: Lowest effort; zero catalog/schema change; same-day shippable.
- **Cons**: Injects the rubric into a possibly Edit/Command-capable agent, so
  "advisory, read-only, diff-as-data" becomes a promise the harness does not
  enforce; no structured findings event; no finding-disposition instrumentation;
  the reviewer would fetch its own diff (ADR-002 hazard).
- **Why rejected**: "Advisory and read-only" must be a structural guarantee for a
  *security* feature, not a prose request. Retained only as the documented
  fallback.

### Alternative 3: Security lens on `cross-runtime-verification-gate`

- **Description**: Do not ship standalone; implement security review as a
  domain-narrowed lens over the pending cross-runtime gate, inheriting its
  provenance, family-diversity SKIP, and finding-disposition instrumentation.
- **Pros**: Maximum reuse; one measured review surface; review by a *different*
  model family (stronger independence) instead of self-review.
- **Cons**: Couples this packet's delivery to an unshipped sibling; pulls
  fleet-diversity (explicitly deferred) into V1; blocks the local/in-session wedge
  on the gate's broader machinery.
- **Why rejected for V1, adopted for V2**: The standalone local-private wedge is
  the differentiator users can have now; convergence with the gate is the V2 path,
  enabled by sharing the `Severity`/`Finding` leaf types from day one.

## Consequences

### Positive

- "Advisory and read-only" is a **structural** guarantee (capability set +
  diff-as-data), not a hope — the correct posture for a security feature.
- The new event family + shared leaf types keep council, the self-grading verdict,
  and security findings as three coherent, non-overlapping concepts while letting
  the cross-runtime gate reuse `Severity`/`Finding` for free.
- Finding-disposition instrumentation from day one turns the central risk
  (precision / alert fatigue) into a measured quantity rather than a guess.
- Local/in-session execution gives a wedge no cloud CI SAST can match (no diff
  egress; pre-PR timing).

### Negative

- A thin bespoke workflow + new event kinds + a new `ChatLifecycleKey` is more
  net-new code than skill-only or a council preset.
- Diff-only scope caps recall on cross-file source→sink vulnerabilities (Open
  Question; partially mitigated by read-only context reads).
- Runtime-agnostic means quality varies by configured model even with a sane
  default and a warning.

### Risks

- **Alert fatigue / low precision** — LLM review is high-recall, low-precision; a
  noisy first run causes abandonment. *Mitigation*: confidence gate +
  hard-exclusion list + finding-disposition metric + a wholesale-dismissal
  guardrail (<20%).
- **False assurance** — users read "no findings" as "secure." *Mitigation*: honest
  disclaimer; never render a green "0 findings = safe" (ADR-002).
- **Redundancy perception vs the cross-runtime gate** — *Mitigation*: shared leaf
  types + explicit V2 convergence path; distinct purpose (security scan vs general
  correctness) and rubric.
- **Catalog-exception creep** — adding `/security-review` reopens the frozen
  catalog. *Mitigation*: record the exception here; keep the command a thin wrapper
  over the `/agent:`+`/skill:` path.

## Implementation Notes

- Gather the diff in app code (extend the `git` subprocess pattern at
  `app/git.rs:42`), redact via the existing secret denylist (`file_index.rs:305`)
  and `config::to_redacted_toml` path, then inject as untrusted data.
- Model `Severity`/`Finding` as standalone shared value types, not nested inside a
  workflow-specific struct.
- Emit `security_review_started`/`security_review_completed` via `record_event`
  and add a `ChatLifecycleKey::SecurityReview` projection arm
  (`app/chat/projection.rs`).
- Declare `[agents.security-reviewer]` as a built-in profile mirroring the existing
  no-Edit reviewer template (`config/mod.rs:480`).
