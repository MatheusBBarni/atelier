# ADR-005: Security review runs as a self-contained async tracked flow with its own review id — merge-base-vs-default-branch diff, gathered-and-redacted as data, truncated-with-note when oversized, never touching RunState

## Status

Accepted

## Date

2026-06-19

## Context

ADR-001 fixed that the review is advisory, diff-scoped, and must not enter
`RunState` transitions or orchestrator routing, and that the diff is gathered and
redacted in app code (diff-as-data, ADR-002). This ADR pins the concrete execution
and scoping model the TechSpec builds on.

Relevant codebase facts:

- Built-in commands dispatch through the async `submit_prompt_with_source`
  (`app/mod.rs:1925`). Cheap synchronous commands use `handle_*_command(&self,
  &str) -> Result<bool>`, but a runtime call is async and long-running.
- The serial council (`run_council_workflow`, `app/mod.rs:5544`) and the grading
  loop (`run_grading_workflow`) are the precedents for dispatching agent steps and
  streaming deltas outside the orchestrator's main decision loop; both await the
  step and record lifecycle events under a run id.
- Chat items collapse by `ChatLifecycleKey` (`app/chat/mod.rs`); the grade loop uses
  `Grade { run_id }` to evolve one card in place.
- Git context is fetched via short-timeout `tokio::process::Command` subprocesses
  with `kill_on_drop` (`app/git.rs:42`); `git diff` exits 1 (not an error) when
  there are changes.

The review is initiated by a manual command and audits the *branch*, not a
specific prior run's output, so attaching it to an existing run's lifecycle would
be a category error.

## Decision

1. **Self-contained async flow with its own id.** `submit_prompt_with_source`
   matches `/security-review` and awaits a new `run_security_review_workflow`
   (sibling to `run_council_workflow`). The workflow mints a dedicated
   `review_id` used as the run-id field for its events and for a new
   `ChatLifecycleKey::SecurityReview { review_id }`. `RunState` is never read or
   mutated; the review is invisible to the orchestrator.
2. **Refuse to start while a run is active.** If an agent run is in flight
   (`RunState` is `Planning`/`Running`/`WaitingForUser`), the command declines with
   a clear message rather than racing the runtime; otherwise the user's input stays
   free — the review streams a "Scanning" card that completes in place.
3. **Diff = merge-base vs default branch + working tree.** Resolve the default
   branch (`origin/HEAD` → `main` → `master`), compute the merge-base with `HEAD`,
   and diff `merge-base…working-tree` so committed *and* uncommitted branch changes
   are covered. Fallback order for edge cases: no upstream/default → diff vs the
   repo's initial commit; detached HEAD or single commit → `git diff HEAD` (working
   tree); empty diff → a completed "no changes to review" card. Each fallback is
   stated in the card's scope line.
4. **Gather-and-redact as data.** The workflow runs the diff subprocess
   (5s timeout, `kill_on_drop`), redacts credential-shaped content
   (ADR-002), and embeds the result in the reviewer's prompt string before building
   the `RuntimeRequest`. The reviewer has `Capability::Read` only — no `Command`,
   no `Edit` — so it can optionally read referenced files to confirm a finding but
   can never fetch the diff itself or modify code.
5. **Truncate oversized diffs with an explicit note.** Cap the embedded diff at a
   configured byte budget; review what fits and record, in the scope line and
   verdict, that the diff was truncated and how many files/hunks were not reviewed.
   No silent truncation; no decline; no multi-call chunking in V1.

## Alternatives Considered

### Alternative 1: Blocking inline workflow (like council)

- **Description**: Await the review the way `run_council_workflow` blocks the
  session until completion.
- **Pros**: Simplest control flow; reuses the council await shape directly.
- **Cons**: Freezes input for up to ~90s on a manual, advisory action.
- **Why rejected**: A manual advisory check should not hard-freeze the session;
  a tracked flow that declines only when a real run is active is friendlier.

### Alternative 2: Attach to the current/last run context

- **Description**: Record review events under the most recent run's id instead of a
  dedicated one.
- **Pros**: Slightly less plumbing; no new lifecycle key.
- **Cons**: Couples an independent branch audit to an unrelated run's lifecycle;
  muddies the chat lifecycle key and the event stream.
- **Why rejected**: The review audits the branch, not a run; its own id keeps the
  concept and the chat card clean.

### Alternative 3: Working-tree-only diff (`git diff HEAD`)

- **Description**: Review only uncommitted changes.
- **Pros**: Always resolvable; trivial.
- **Cons**: Misses everything already committed on the branch — too narrow for the
  pre-PR review the PRD describes.
- **Why rejected**: Defeats the "everything this branch added" intent; retained only
  as a degraded fallback for detached HEAD / single-commit repos.

### Alternative 4: Per-file chunking / map-reduce for large diffs

- **Description**: Split a large diff across reviewer calls and merge findings.
- **Pros**: Best coverage on large branches.
- **Cons**: Multiplies cost/latency; adds merge/dedup complexity.
- **Why rejected**: Over-engineered for a V1 advisory feature; truncate-with-note
  preserves coverage honesty at a fraction of the cost.

## Consequences

### Positive

- The orchestrator and `RunState` are untouched — the review cannot destabilize a
  run, satisfying ADR-001's non-blocking requirement structurally.
- The merge-base diff matches the user's pre-PR mental model.
- Truncate-with-note guarantees a result while keeping coverage honest (ADR-003).
- Reuses the council/grade dispatch + git-subprocess + projection patterns.

### Negative

- Default-branch and merge-base resolution has several edge cases, each needing an
  explicit fallback and a scope-line message.
- A dedicated `review_id` plus a new lifecycle key is marginally more plumbing than
  reusing a run id.

### Risks

- **Base resolution wrong → misleading scope** — *Mitigation*: deterministic
  fallback order, the resolved base/scope always printed in the card, unit tests per
  edge case (detached HEAD, no default branch, first commit, no upstream).
- **Truncation hides the one critical finding** — *Mitigation*: state truncation
  prominently in the verdict; truncate at hunk boundaries; document the budget knob.
- **Review launched mid-run race** — *Mitigation*: the active-run guard rejects the
  command before any dispatch.

## Implementation Notes

- `run_security_review_workflow(&mut self) -> Result<()>` on `App`, awaited from
  `submit_prompt_with_source`; mirrors `run_council_workflow` structure.
- Extend `app/git.rs` with default-branch + merge-base resolution and a
  `git diff <base>` fetch following the existing subprocess pattern.
- `ChatLifecycleKey::SecurityReview { review_id }` + `ChatItemKind::SecurityReview`
  + `apply_security_review` projection arm, modeled on `apply_grade_round`.
- Diff byte budget is a named constant in V1 (no user config knob — ADR-001 cut
  scan-scope knobs from V1).
