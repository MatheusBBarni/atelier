# ADR-003: Roster View-Model Architecture and Render-Time Determinism

## Status

Accepted

## Date

2026-06-12

## Context

ADR-001 mandates a unified `RosterRow` view-model built in the app/projection layer, with the renderer staying a pure function. The TechSpec must decide exactly where the view-model is built, how the `agents`↔`live_steps` join happens, and — because ADR-002 adds coarse elapsed and a `Stalled` state — how time-dependent values are computed without making the `TestBackend` snapshot tests flaky.

Codebase exploration (verified) established:
- The render path is **genuinely time-independent today** — there is no `Instant::now()` anywhere in `render`/`render_chat`/`render_footer`; the working spinner is a per-frame counter (`tui/mod.rs:3486`). Introducing a render-time clock would newly break snapshot determinism.
- `AgentView` (`app/mod.rs:59`, canonical order from `build_agent_views` at `4940`) and `LiveStepView` (`app/mod.rs:92`, in `AppState.live_steps`) only co-exist on `App.state`.
- `publish_state` (`app/mod.rs:4050`) clones `AppState` and is the single egress called by every mutator. It is invoked on **every stream delta** (via `set_agent_status` inside `push_live_stream_content`), so anything hooked there runs very frequently.
- The repo already has a deterministic time-offset test pattern: `Instant::now() - Duration::from_secs(61)` (`app/mod.rs:10416`).

## Decision

1. **Define the view-model in the app layer.** Add `ActivityState` (`Active | NeedsInput | Stalled | Idle`) and `RosterRow` to `src/app/mod.rs` next to `AgentView`/`LiveStepView`, and a field `pub roster_rows: Vec<RosterRow>` on `AppState`.
2. **Build via a pure function with an injected clock.** `fn build_roster_rows(agents, live_steps, timing, now: Instant) -> Vec<RosterRow>` performs the join, classifies `ActivityState`, resolves the identity accent (ADR-005), formats coarse elapsed, and applies the `NeedsInput` pin-sort. **`now` is an explicit parameter** — production passes `Instant::now()`; tests pass a fixed `Instant`.
3. **Pre-format all time-dependent values into the row.** Each `RosterRow` carries finished strings (`elapsed: Option<String>`, `current_step: Option<String>`) and the final `ActivityState`. The renderer iterates `state.roster_rows` and prints these directly — **it never reads a clock**, preserving the `(AppState, TuiUiState) -> frame` purity contract and snapshot determinism.
4. **Rebuild centrally.** A `rebuild_roster_rows(&mut self)` runs inside `publish_state` so every existing mutator refreshes rows automatically and rows never drift from `agents`/`live_steps`.

## Alternatives Considered

### Alternative 1: Compute elapsed/`Stalled` at render time

- **Description**: Keep raw timestamps on the row (or read `state.live_steps`) and compute elapsed + stall in `render()` using `Instant::now()`.
- **Pros**: No new `AppState` field; no app-layer rebuild.
- **Cons**: Reintroduces a render-time clock → every roster snapshot becomes flaky; violates the pure-renderer contract (CLAUDE.md, ADR-001 item 6); re-runs the O(agents×steps) join every ~50 ms frame.
- **Why rejected**: Directly breaks the verified time-independence of the render path.

### Alternative 2: Thread a `now` parameter into `render()`

- **Description**: Pass wall-clock into the renderer and all its helpers.
- **Pros**: Keeps the value injectable for tests.
- **Cons**: Leaks wall-clock into a pure function; every render helper and existing snapshot test must thread `now`; large blast radius.
- **Why rejected**: The app-layer builder achieves the same injectability with a far smaller surface.

### Alternative 3: Build in `src/app/chat/projection.rs`

- **Description**: Reuse the chat projection module for the roster join.
- **Pros**: Co-located with another projection.
- **Cons**: That module owns `ChatItemView` only and has no natural hook on the `agents`+`live_steps` pair; mixes responsibilities.
- **Why rejected**: Wrong single-responsibility boundary.

## Consequences

### Positive

- Snapshot tests stay deterministic; `build_roster_rows` is unit-testable with a fixed `now`.
- The renderer reads one coherent vec and stays pure.
- One rebuild site (`publish_state`) guarantees rows never drift.

### Negative

- A new `AppState` field that is cloned on every publish (existing clone cost, slightly larger payload).
- The join runs on every publish — mitigated by ADR-004's change-gate and small N (handful of agents/steps).

### Risks

- **Publish-frequency cost** (verified PARTIAL: `publish_state` fires on every stream delta) → keep `build_roster_rows` allocation-light and rely on ADR-004's change-gate so the 1 Hz path does not add a publish storm; the per-delta rebuild is bounded by small agent/step counts.

## Implementation Notes

- `RosterRow` derives `Serialize/Deserialize` for parity with the other view structs; the internal `StepTiming` map (ADR-004) is **not** serialized.
- Tests construct `AppState` with hand-built `agents` + `live_steps` + a `StepTiming` map and call `build_roster_rows(..., fixed_now)` directly.
