# ADR-002: PRD Product Approach — Progress-Confident Roster with a First-Class Stalled State

## Status

Accepted

## Date

2026-06-12

## Context

PRD clarification fixed two things that reshape V1 scope:

1. **Primary persona = the daily driver** — the person watching live multi-agent runs, not the screenshot evaluator.
2. **#1 success signal = "trust the run is progressing"** — the user's most important outcome is distinguishing an agent that is *actively working* from one that is *stuck/hung*, with confidence.

This collides with a deferral in ADR-001. ADR-001 chose coarse elapsed time computed off existing render passes and **deferred any periodic "ticking" refresh to V2**. But a genuinely hung agent **stops emitting events** — which is exactly the failure the user most wants to catch — and with no events there is no redraw, so elapsed can freeze and the "idle vs. stalled" distinction becomes invisible. Research corroborates this as a documented, recurring failure mode in Codex, OpenCode, and Claude Code ("looks idle but isn't / hangs silently"), and the design guidance is explicit: keep the active indicator animated (a frozen one reads as a hung app), track last-activity, and after a no-progress threshold surface a distinct stalled cue with a next action.

Two further research findings constrain the visual design: status today is conveyed by **color only** with no fallback under `NO_COLOR`/colorblind/missing-glyph conditions, and the glyph `⏸` (and other emoji-presentation symbols) is **not column-safe** in a fixed-width TUI.

The user selected **Approach A (Progress-Confident Roster)** over B (elapsed-only) and C (phased).

## Decision

Adopt **Approach A**. V1 of the Agent Roster comprises the full live board from ADR-001 — stable canonical order, weight-driven activity, the `NeedsInput` top-pin, the thin summary header, accent-by-identity, and the unified `RosterRow` view-model — **plus** the following progress-confidence additions:

1. **First-class `Stalled` activity state.** Extend `ActivityState` to `Active | NeedsInput | Stalled | Idle`. A row flips to `Stalled` after a no-activity threshold during an otherwise-active step.
2. **Coarse elapsed on active rows.** Render `now − start` at human, low-frequency granularity (whole seconds → `1m 20s` → minutes; correct pluralization; never a fast-ticking sub-second counter).
3. **Bounded periodic refresh.** Introduce a small periodic refresh (target ~1 Hz) that runs **only while a run is active**, so elapsed stays current and stalls are detected even when no other events arrive. This **amends ADR-001 decision item 7.**
4. **Animated active indicator.** The working indicator must move; a frozen indicator is reserved to read as "stalled."
5. **Glyph + label accessibility.** Every state is legible from a portable glyph **and** a short text token alone; color only reinforces. Honor `NO_COLOR`. Use only portable BMP glyphs (Geometric Shapes / Dingbats such as `● ◐ ○ ◔ ▶ ✓ ✕`); **ban `⏸` and other emoji-presentation / double-width symbols** from load-bearing status; provide an ASCII-safe rendering.

## Alternatives Considered

### Alternative 1: Approach B — Elapsed-only, infer stuck

- **Description**: Live board + coarse elapsed computed off existing render passes; no periodic tick, no explicit `Stalled` state.
- **Pros**: Cheapest; no new redraw cadence; matches ADR-001 unchanged; smallest test surface.
- **Cons**: Under-delivers the user's #1 signal — a hung agent stops emitting events, so elapsed can freeze and nothing flags the stall; the user must infer "stuck" from a number that may itself be frozen.
- **Why rejected**: Fails the explicitly-chosen success criterion (trust the run is progressing).

### Alternative 2: Approach C — Progress-core first, polish later

- **Description**: Phase 1 = states + elapsed + stalled + pin + accessibility; Phase 2 = summary header + width resilience.
- **Pros**: Fastest route to the success signal; smaller first increment.
- **Cons**: The board looks incomplete until Phase 2 (no at-a-glance summary header); mild rework risk splitting tightly-coupled row work across two phases.
- **Why rejected**: The summary header and width handling are cheap and part of the same row pass; splitting them adds coordination cost for little gain. (Phasing is still expressed in the PRD's rollout plan, but within a single V1 deliverable.)

## Consequences

### Positive

- Directly delivers the daily driver's #1 outcome: confident "working vs. stuck" reading.
- Closes the existing `NO_COLOR`/colorblind status-legibility gap while these rows are already being rewritten.
- Portable-glyph + ASCII-safe rule prevents tofu/column-misalignment regressions.
- The `RosterRow` view-model and `ActivityState` enum absorb the new `Stalled` state and the refresh cleanly, keeping the renderer pure.

### Negative

- Introduces a bounded periodic redraw (a new moving part ADR-001 explicitly tried to avoid) and amends a prior accepted ADR.
- More user-facing states to design, label, and snapshot-test (now including `Stalled` and its ASCII/`NO_COLOR` renderings).

### Risks

- **Idle-time CPU/battery from the tick** → mitigation: the refresh runs only during active runs and pauses when the run is `Idle`/`Completed`.
- **Stalled false positives** (slow models legitimately think for a while) → mitigation: a conservative threshold, an animated working indicator that keeps reassuring during normal slow work, and "stalled?" phrased as a question, not a failure.
- **Competitive overlap** (Zed Parallel Agents, Cline Kanban shipped multi-agent panels in 2025/26) → mitigation: atelier's niche is an always-on, in-terminal, single-orchestrator roster with live-activity-first weighting and an explicit progress-confidence (stalled) angle those panels do not foreground.

## Implementation Notes

- Extend the `ActivityState` enum and `RosterRow` view-model (ADR-001) rather than adding a parallel path for `Stalled`.
- Drive the refresh from the existing app/TUI loop, gated on run activity; do not introduce a free-running timer when idle.
- Keep all styling in `theme.rs` tokens; state must survive `theme.is_monochrome()` via glyph + label.
