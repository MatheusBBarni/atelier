# ADR-005: Accent-by-Identity Decoupling

## Status

Accepted

## Date

2026-06-12

## Context

ADR-001 (constraint 1, item 5) requires that each agent's accent color be stable under the `NeedsInput` pin and consistent between the roster and the chat transcript. The TechSpec must decide the stable key the accent derives from and confirm every surface reads it.

Codebase exploration (verified) established that accents are **positional** today and resolved at render time through exactly **three** surfaces, all via `theme.accent_for(roster_index)`:
1. **Roster** — `agents.iter().enumerate()` index (`tui/mod.rs:2131`).
2. **Chat** — `agent_index_for_title` → `agents.iter().position(...)` (`tui/mod.rs:3108/3122`).
3. **`/agent:` dropdown** — `agents.iter().position(|a| a.id == suggestion.id)` (`tui/mod.rs:2488`).

An adversarial search confirmed there is **no fourth** per-agent accent surface (approval, clarification, footer, and status styling do not apply per-agent accents). `AgentView.id` (`app/mod.rs:60`) is the stable unique key; the canonical sort order is `orchestrator`-first then alphabetical (`app/mod.rs:4962`, `agent_roster_rank`). The accent pool (`theme.rs:110`) excludes red (ADR-006 of the redesign) and is unchanged. Two tests pin the contract: `roster_names_carry_same_accents_as_chat` (`tui/mod.rs:8828`) and `agent_dropdown_ids_carry_same_accents_as_roster` (`tui/mod.rs:8870`).

Because the `NeedsInput` pin reorders a row, a positional accent would recolor that agent and break both tests — so the index must be anchored to identity, not display position.

## Decision

1. **Resolve accent once, in the app layer, from canonical order.** Compute each agent's `accent_index` from its position in the canonical (sorted) `agents` vec and store it on `RosterRow` (`accent_index: usize`, used with `theme.accent_for`). Because the index is keyed to canonical identity, pinning a row to the top moves the row but **not** its `accent_index`.
2. **Repoint all three surfaces to the identity index.** Change the roster render to use `row.accent_index` instead of the enumerate index; change `item_agent_accent`/`agent_index_for_title` (`tui/mod.rs:3115`) and the dropdown lookup (`tui/mod.rs:2488`) to resolve the accent by agent identity through the same canonical index.
3. **Strengthen the contract tests.** Update `roster_names_carry_same_accents_as_chat` and `agent_dropdown_ids_carry_same_accents_as_roster` to assert accent **follows identity under a pinned-reorder fixture** (an agent pinned to the top keeps its canonical accent, not `accent_for(0)`).

## Alternatives Considered

### Alternative 1: Hash `agent.id` into the accent pool

- **Description**: `accent_index = hash(id) % pool_len`.
- **Pros**: Stable per identity without an ordering dependency.
- **Cons**: Changes every agent's *current* color (regresses both tests' fixed `accent_for(0)`/`accent_for(1)` expectations); risks collisions in a 5-slot pool (two agents same color).
- **Why rejected**: Needless visible churn and collision risk; canonical-order index preserves today's colors exactly.

### Alternative 2: Keep render-time enumerate index, skip pinned rows when indexing

- **Description**: Special-case the pinned row so the remaining rows keep their enumerate index.
- **Pros**: No new stored field.
- **Cons**: Brittle special-case duplicated across all three render sites — exactly the positional drift ADR-001 item 5 wants to eliminate.
- **Why rejected**: Re-creates the coupling in three places instead of removing it.

## Consequences

### Positive

- The `NeedsInput` pin (and any future reorder) is color-safe by construction.
- One canonical source feeds all three surfaces; the two contract tests become stronger (identity, not position).
- Existing agent colors are preserved (canonical order == today's display order when nothing is pinned).

### Negative

- Three call sites change to read the identity index; the two accent tests must be updated to the pinned-reorder fixture.

### Risks

- **A future fourth accent surface deriving accent independently would silently break the contract** (verified as the one standing vulnerability) → document the single-source rule in code comments at the three sites and keep the contract tests as the guard.

## Implementation Notes

- `accent_index` is computed in `build_roster_rows` (ADR-003) from the canonical order before the `NeedsInput` pin-sort, so the pin never perturbs it.
- Use `title_cell_fg` (`tui/mod.rs:8593`) for cell-level color assertions in the updated tests (robust to multi-byte glyphs).
