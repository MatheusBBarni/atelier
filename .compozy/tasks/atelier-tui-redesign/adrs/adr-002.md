# ADR-002: Unified Single-Release Rollout for the TUI Visual Identity

## Status

Accepted

## Date

2026-06-11

## Context

The idea phase (ADR-001) fixed the V1 scope and technical sequencing: theme seam ships with the welcome screen, full color migration in the same window, subprocess git context, live-orchestration identity. The PRD phase had to decide the release packaging: one unified release versus splitting welcome/theme and footer/orchestration into separate releases. PRD research added a constraint: market evidence shows screenshots that contradict the live product ("branded splash over unbranded UI") read worse than no branding, and the council had flagged the same risk.

## Decision

Ship the entire visual identity as one coherent release (Approach A) with three internal phases inside the ~1-week timebox:

1. Theme foundation + branded welcome screen (replacing the skill-loading screen).
2. Persistent footer + git context.
3. Per-agent orchestration accents + README asset refresh (welcome screenshot + live-orchestration GIF).

The README refresh lands only when every surface matches the screenshots — one before/after launch moment.

## Alternatives Considered

### Alternative 1: Welcome-first, two releases (Approach B)

- **Description**: Welcome + theme migration ships in ~3 days; footer, git context, and per-agent accents follow in a second release.
- **Pros**: Visible value sooner; smaller PRs to review.
- **Cons**: An interim period where the splash promises a polish level the live app does not deliver — the exact "screenshot becomes a lie" failure the council warned about; two release coordination overheads.
- **Why rejected**: The interim inconsistency damages the asset the effort exists to create.

### Alternative 2: Orchestration-first (Approach C)

- **Description**: Per-agent accents, progress views, and footer lead; welcome screen ships second.
- **Pros**: The differentiating parallel-agents GIF becomes possible earliest; daily drivers benefit first.
- **Cons**: Inverts the user's originating request (the wordmark/welcome screen); the live view is harder to style before the theme vocabulary the welcome screen establishes exists.
- **Why rejected**: Sequencing friction and misalignment with the primary ask, for no offsetting gain in the single-release model.

## Consequences

### Positive

- One coherent launch story; screenshots and the live product agree from day one.
- Matches ADR-001's technical sequencing without renegotiation.

### Negative

- Longest time until any user-visible change ships (~1 week).
- All-or-nothing exposure if the timebox slips; mitigated by ADR-001's kill-switches (git context cut at >0.5 day) and the phase ordering placing the highest-value items first.

### Risks

- Timebox slip delays the entire release — mitigation: internal phase boundaries are also valid stopping points; phases 1+2 alone constitute a shippable (if not announceable) state.

## Implementation Notes

Internal phase boundaries map to the PRD's Phased Rollout Plan; they gate announcement (README refresh), not merge.
