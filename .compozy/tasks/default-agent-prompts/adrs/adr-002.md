# ADR-002: Contract-First Default Agent Prompt Reliability

## Status

Accepted

## Date

2026-06-13

## Context

The default-agent-prompts PRD is being created for the multi-agent harness structured runtime adapter. Repository discovery found an existing idea document for concise role contracts across orchestrator, explorer, fixer, reviewer, oracle, and consul agents, with emphasis on action-request discipline, blocker handling, completion evidence, and avoiding prompt drift between built-in defaults and starter prompt files.

The user clarified that V1 should focus on Runtime reliability, specifically Contract violations, for the Workflow operator persona. The selected product approach is Contract-first reliability.

Workflow operators need agent outputs that consistently honor the harness contract. When agents return prose, malformed JSON, unsupported action shapes, or unclear completion evidence, the workflow becomes harder to run, recover, and trust.

## Decision

V1 will prioritize Contract-first reliability for default agent prompts.

The product will focus default agent prompt requirements on preventing malformed runtime outputs by making each role contract explicit, narrow, and evidence-driven. Each default role should make it clear what the agent is responsible for, when it must request an action instead of acting directly, what completion evidence is required, and how blockers must be reported.

This approach optimizes for workflow operators who need fewer contract violations and more predictable multi-agent runs. Prompt consistency and handoff quality remain important, but they are supporting outcomes under the primary goal of contract-compliant runtime behavior.

## Alternatives Considered

### Alternative 1: Operator Handoff Quality

- **Description**: Focus V1 on clearer blockers, stop conditions, and completion evidence so operators can recover faster when agents make mistakes.
- **Pros**: Improves recovery paths, makes failures easier to triage, and supports better operator confidence.
- **Cons**: Does not directly reduce malformed JSON, unsupported actions, or prose responses that violate the runtime contract.
- **Why rejected**: The user's highest-priority failure mode is contract violations. Recovery quality matters, but V1 should first reduce the violations that create many handoff problems.

### Alternative 2: Prompt Consistency Baseline

- **Description**: Focus V1 on keeping built-in defaults and generated starter prompt files aligned to reduce prompt drift.
- **Pros**: Creates a cleaner authoring baseline and reduces confusion across prompt surfaces.
- **Cons**: Alignment alone does not guarantee agents will obey the structured runtime contract or produce valid action/result envelopes.
- **Why rejected**: Prompt consistency is necessary but not sufficient for the selected reliability outcome. It should be included as a supporting requirement, not the primary product approach.

## Consequences

### Positive

- Workflow operators should see fewer malformed outputs and unsupported action attempts from default agents.
- Agent roles become easier to reason about because responsibilities, boundaries, and evidence expectations are explicit.
- Future prompt updates can be evaluated against a clear product goal: contract-compliant runtime behavior.
- Prompt consistency work has a concrete purpose instead of becoming general wording cleanup.

### Negative

- V1 scope is narrower than a broad prompt-quality overhaul.
- Some usability improvements around handoffs may be deferred unless they directly support contract reliability.
- Product language must stay focused on user outcomes even though the feature sits close to technical runtime behavior.

### Risks

- **Risk**: Over-specifying prompts could make agents rigid or verbose.
  **Mitigation**: Keep V1 requirements concise and role-specific, with only the evidence needed for reliable operation.
- **Risk**: Focusing on contract compliance could miss prompt-drift issues between built-in and starter prompts.
  **Mitigation**: Treat consistency as a supporting requirement for all role contracts.
- **Risk**: The PRD may drift into implementation details.
  **Mitigation**: Reserve runtime wiring, validation mechanics, and code structure for the later TechSpec.

## Implementation Notes

The PRD should describe user capabilities and product outcomes only. It should avoid implementation details such as specific files, APIs, validation code, prompt storage, or test strategy. Those details belong in the follow-up TechSpec.

The PRD must not be saved to `.compozy/tasks/default-agent-prompts/_prd.md` until the user approves the full draft.
