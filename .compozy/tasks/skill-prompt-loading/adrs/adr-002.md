# ADR-002: Select Deterministic Common Flow For PRD

## Status

Accepted

## Date

2026-06-06

## Context

The idea-stage ADR already selected app-owned skill prompt loading as the V1
boundary. During PRD clarification, the user confirmed the product behavior that
V1 must describe:

- every `/skill:name` occurrence should invoke a skill;
- successful loading should record a concise run/history note listing loaded
  skill names and sources;
- missing, invalid, or ambiguous loading should fail before run creation with a
  clear diagnostic and suggested matches;
- project skill roots should beat personal skill roots;
- within the same scope, `.agents/skills` should beat `.claude/skills`;
- aliases should include both frontmatter `name` and directory name.

The PRD needs one product approach that captures those decisions without
expanding into a full skill platform or shrinking to a one-skill MVP.

## Decision

Use the Deterministic Common Flow approach for the PRD.

The PRD will describe V1 as a predictable user workflow where explicit skill
references always resolve before run creation, loaded skills are visible in
concise run/history feedback, duplicate skill content is injected once, and
failure cases stop the run before the model receives an incomplete prompt.

## Alternatives Considered

### Alternative 1: Minimal Explicit Loader

- **Description**: Load only straightforward `/skill:name` tokens and skip
  broader alias, precedence, propagation, and feedback requirements.
- **Pros**: Smaller immediate surface area and fewer edge cases to document.
- **Cons**: Contradicts the selected behavior and leaves users with unresolved
  ambiguity around common prompts.
- **Why rejected**: The user selected the common-flow scope and explicitly
  answered the product questions that the minimal loader would avoid.

### Alternative 2: Skill Platform Foundation

- **Description**: Expand the PRD to include a skill registry, trust view,
  preview UX, implicit matching, and future platform-level skill management.
- **Pros**: More strategic and closer to mature agent-tool platforms.
- **Cons**: Expands V1 beyond the core user problem: `/skill:` appears to work
  but does not load prompt context.
- **Why rejected**: The PRD should fix explicit invocation first and defer
  registry, trust, and implicit matching features.

## Consequences

### Positive

- Aligns the PRD with the accepted idea and clarified user decisions.
- Keeps V1 user-visible and testable through clear success, failure, and
  history behaviors.
- Avoids over-scoping into a skill-management platform.

### Negative

- Requires the PRD to define more edge behavior than a one-skill loader.
- Makes failure behavior stricter, so users will see diagnostics instead of
  best-effort runs when skill references cannot resolve.

### Risks

- Users may be surprised that every `/skill:name` mention invokes a skill.
  Mitigation: include clear non-goals and open questions around literal mention
  ergonomics for future refinement.
- Users may expect a visual skill preview once loading becomes explicit.
  Mitigation: keep V1 feedback concise and reserve preview/registry surfaces for
  later phases.

## Implementation Notes

This ADR records product behavior only. Technical implementation details belong
in the follow-on TechSpec.
