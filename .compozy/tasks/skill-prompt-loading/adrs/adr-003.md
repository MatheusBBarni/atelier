# ADR-003: Shared Skill Resolver With Runtime-Time Prompt Rendering

## Status

Accepted

## Date

2026-06-06

## Context

The PRD requires every `/skill:name` occurrence to resolve before run creation,
load each resolved skill once, record concise audit metadata, and propagate the
explicit skill context into derived prompts. The current app stores a single
`RunDriveContext.prompt` string, records the raw `prompt_submitted` event before
driving the run, and builds runtime prompts through the shared
`runtime_request` function.

The current TUI discovers skill suggestions from project and personal roots,
but that code is autocomplete-only. It does not provide an authoritative
resolver with exact file identity, alias indexing, precedence handling,
frontmatter parsing, content loading, or audit metadata.

The selected technical design must keep runtime adapters generic. V1 should
deliver skill context through the existing runtime prompt text, not teach Codex,
Claude, Cursor, Z.ai, or Fake runtimes to interpret `/skill:` syntax.

## Decision

Implement skill loading through a shared `src/skills/mod.rs` module and render
full skill prompt text only when constructing `RuntimeRequest` values.

The shared skills module will own:

- `/skill:<id>` reference parsing;
- project/personal and `.agents/skills`/`.claude/skills` root ranking;
- YAML frontmatter parsing for skill metadata;
- directory-name and frontmatter-name alias indexing;
- canonical identity and ambiguity detection;
- skill content loading and validation;
- duplicate removal by canonical identity;
- prompt-section rendering helpers for V1 text delivery;
- suggestion data used by the TUI cache.

The app will store normalized prompt data and a `SkillPromptContext` on
`RunDriveContext`. The run context will keep full skill content available for
runtime rendering, but history and run records must persist metadata only.

The app will record a separate `skills_loaded` history event after a successful
resolution and before runtime work starts. That event will include loaded skill
names, requested aliases, source origins, canonical identities, and load
reasons, but not full `SKILL.md` bodies.

Skill prompt rendering will happen in the `runtime_request` path so
orchestrator, specialized agent, parallel child, council member, and subtask
requests receive the same explicit skill context exactly once. Runtime adapters
remain unchanged.

For YAML frontmatter, add a Serde-compatible YAML parser dependency. The
implementation should prefer a currently maintained parser such as
`serde_norway` and should not use crates with active unsoundness or maintenance
advisories.

## Alternatives Considered

### Alternative 1: Compile Full Skill Text Into `run.prompt`

- **Description**: Replace `RunDriveContext.prompt` with the full rendered
  System/Skill/User prompt before run creation.
- **Pros**: Simple data flow and no extra prompt rendering step.
- **Cons**: Leaks full skill text into prompt history, user prompt chat, run
  records, and derived prompt strings. It also makes it harder to distinguish
  the submitted prompt from the runtime prompt.
- **Why rejected**: V1 requires audit metadata without storing full skill
  bodies in history.

### Alternative 2: Add Structured Skill Fields To `RuntimeRequest`

- **Description**: Extend `RuntimeRequest` with structured skill context and
  serialize it separately in the prompt envelope.
- **Pros**: Clearer runtime envelope shape and future adapter-specific
  rendering path.
- **Cons**: Broadens the runtime contract immediately and requires updating
  request fixtures across adapters even though V1 can render text.
- **Why rejected**: V1 should keep runtime adapters generic and avoid a wider
  contract change until runtime-native skill support exists.

### Alternative 3: Keep TUI Discovery Separate

- **Description**: Leave skill discovery in `src/tui/mod.rs` and add a second
  app resolver for runtime loading.
- **Pros**: Minimizes TUI churn.
- **Cons**: Creates two sources of truth for roots, aliases, precedence, and
  metadata parsing.
- **Why rejected**: Autocomplete and runtime loading need the same canonical
  skill resolution rules.

## Consequences

### Positive

- Keeps the app as the owner of prompt compilation and audit metadata.
- Preserves runtime adapter compatibility.
- Prevents full skill bodies from being persisted in history.
- Gives the TUI and app a shared source of truth for skill discovery and
  precedence.
- Makes derived prompt propagation testable through one run-context field.

### Negative

- Adds a new shared module and a YAML parser dependency.
- Requires replacing the existing raw `/skill:` app test with compiled-prompt
  behavior.
- Introduces a new history event kind and chat projection handling.

### Risks

- **YAML dependency risk**: Some Rust YAML crates have maintenance or security
  concerns. Mitigation: choose a maintained Serde-compatible parser and run
  dependency review before implementation.
- **Prompt leakage**: Full skill text could accidentally enter persisted
  events. Mitigation: keep `skills_loaded` metadata-only and add regression
  tests.
- **Double rendering**: Derived prompts could include skill sections twice.
  Mitigation: carry `SkillPromptContext` separately and render once per
  runtime request.
- **Resolver drift**: TUI and app behavior could diverge. Mitigation: source
  both from `src/skills/mod.rs`.

## Implementation Notes

- Resolve skills in `submit_prompt` before creating `run_id` for normal runs.
- Resolve skills in `/subtask` task text before `start_subtask`.
- Do not resolve new skill references inside clarification answers in V1.
- Add `SkillPromptContext` to `RunDriveContext`.
- Keep normalized user prompt text separate from rendered runtime prompt text.
- Record `skills_loaded` after `run_started` and before the first runtime
  request.
- Update chat projection to show a concise loaded-skills item.
- Keep TUI cache advisory; runtime loading reads and validates fresh skill
  files before run creation.
