# ADR-002: Runway-First Provider Usage Status

## Status

Accepted

## Date

2026-06-12

## Context

The Provider Usage Status PRD needs a V1 product approach after clarification. The target users are solo heavy users who want to track remaining provider usage before or during long Atelier sessions. The selected user outcome is practical runway: users need to know whether they can safely continue a long coding session, should switch providers, should reduce scope, or should check an official provider account page.

The existing scope decision in ADR-001 requires truthful provider status and exact quota only when a documented provider integration exposes exact usage data. Repository exploration found no existing quota, subscription, remaining-credit, or usage telemetry surface, so V1 should not depend on a broad usage dashboard already existing in Atelier.

The product approach must therefore make practical remaining-usage guidance useful even when exact provider quota is unavailable, while keeping unsupported quota states explicit and avoiding inferred numbers.

## Decision

V1 will use a runway-first status approach.

The provider usage status command will prioritize a practical readiness and runway answer for each supported provider:

- Whether the provider appears usable for a long solo coding session.
- Whether remaining usage is sufficient, constrained, blocked, unknown, or unsupported based on provider-returned data and local status signals.
- Exact remaining quota only when the provider exposes reliable, documented usage data.
- Clear unsupported or unavailable states when exact remaining usage cannot be retrieved.
- Reset timing, account guidance, or official provider usage-page links when those are the most actionable next step.
- Provider-specific diagnostics that separate usage runway from authentication, billing, rate-limit, model availability, local command, and recent error states.

The command should not position V1 as a full exact-quota dashboard. It should answer the user's immediate workflow question first: can I keep working with this provider right now, and what should I do next if not?

## Alternatives Considered

### Exact quota dashboard

- **Description**: Prioritize numeric remaining messages, credits, requests, percentages, and reset timing as the main V1 surface.
- **Pros**: Directly matches the literal desire to track remaining usage and can be highly useful when providers expose exact data.
- **Cons**: Risks sparse or misleading output when providers do not expose exact quota, and may create a product promise Atelier cannot satisfy for Claude or Codex subscriptions.
- **Why rejected**: ADR-001 established that exact quota must be capability-gated. Making exact quota the primary V1 promise would overstate feasibility.

### Readiness troubleshooting

- **Description**: Prioritize whether each provider can be used now and what to fix, with usage runway treated as secondary.
- **Pros**: Strong at diagnosing local configuration, auth, billing, model availability, and recent provider errors.
- **Cons**: Underserves the clarified user need to track remaining usage and plan practical session runway.
- **Why rejected**: The user selected remaining usage and practical runway as the core V1 value, so troubleshooting should support that outcome rather than replace it.

## Consequences

### Positive

- Solo heavy users get an actionable status before starting or continuing long Atelier sessions.
- V1 remains truthful when exact quota is unsupported, unavailable, stale, or provider-specific.
- The product can still deliver value through readiness, local status, recent errors, and official guidance even without exact provider quota.
- The approach fits future providers because each adapter can expose different usage and readiness capabilities.

### Negative

- Users who expect exact numeric quota for every provider may see unsupported or unknown states in V1.
- Product copy must be precise enough to distinguish practical runway from exact remaining quota.
- Some runway labels may be less satisfying than numeric answers when provider APIs do not expose exact usage.

### Risks

- **Risk**: Users interpret practical runway labels as estimates of exact quota.
  **Mitigation**: Label every status with source and freshness, and avoid inferred numbers.
- **Risk**: Unsupported quota states feel like product failure.
  **Mitigation**: Make unsupported states first-class, explain provider limitations, and link to official account or usage pages.
- **Risk**: Provider semantics differ enough that a single runway label becomes ambiguous.
  **Mitigation**: Preserve provider-native meanings and separate subscription quota, API billing usage, rate limits, auth state, and local runtime health.

## Implementation Notes

Keep the PRD business-focused. Technical details such as adapter interfaces, storage, command routing, or provider API design belong in the TechSpec.
