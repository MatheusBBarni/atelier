# ADR-005: DAG user-surface integration — enable flag, single evolving Plan item, plan-item approval

## Status

Accepted

## Date

2026-06-15

## Context

The TechSpec must choose the config gating, the live-run chat surface, and the
plan-approval mechanism. Code facts (verified):

- Feature flags live on `Features` with matching `RawFeatures` (`#[serde(deny_unknown_fields)]`) + an `apply_raw` merge arm (`src/config/mod.rs:196,447,938`). `limits.max_parallel_agent_steps` is a `u32` with `0 = disable` (`:179`). `/config` renders only sources/preset/warnings (`ConfigStatusView`, `src/app/mod.rs:192`) — it shows **neither** approval mode nor the parallel flags.
- `ChatLifecycleKey` and `ChatItemKind` are exhaustive, `Ord`-derived enums (`src/app/chat/mod.rs:115,25`). `apply_history_event` has a `_ => {}` catch-all (`src/app/chat/projection.rs:110`) that **silently drops** unregistered kinds. `upsert` (`:1339`) replaces an item's body wholesale and caps it at 12 lines.
- The clarification pause-and-choose surface (`PendingClarificationView` `src/app/mod.rs:211`; `apply_clarification_requested` `:1214`) supports a recommended default + a custom free-text answer. The per-action approval slot `state.pending_approval` is shared with the serial/parallel paths.
- Each running node also emits a `LiveStepView` → a per-node `AgentProgress` chat item (`apply_live_steps`, `:121`).
- `HistoryEvent.schema_version` is pinned to 1; readers reject ≠ 1.

## Decision

**Enable flag.** Add `features.execution_graph: bool` (default `false`); add the field
to `Features`, `RawFeatures` (`Option<bool>`, required by `deny_unknown_fields`), and an
`apply_raw` merge arm. **Reuse `limits.max_parallel_agent_steps`** (u32, `0 = disable`)
as the concurrency ceiling unchanged. It **coexists** with `parallel_step_groups` (a
separate gate; flat groups are unaffected). Surface the DAG enable-state, ceiling, and
`approval_mode` in `/config` by extending `ConfigStatusView` + `build_config_status` +
`config_status_display`.

**Events (additive at schema_version 1).** Add `#[serde(default)] graph_id: Option<String>`
to `HistoryEvent` (threaded through `new_with_group` and the hand-built `append_debug_event`
JSON), duplicated into payloads (mirroring `group_id`). New event kinds, each **explicitly
registered** in `apply_history_event`:
- `execution_graph_proposed` — the full typed `ExecutionGraph` (nodes, typed edges, per-node scope);
- `execution_graph_approved` / `execution_graph_rejected` (normal mode; reject carries the reason);
- node lifecycle: `node_pending` / `node_ready` / `node_running` / `node_succeeded` / `node_failed` / `node_skipped` / `node_cancelled`, keyed by `node_id` within `graph_id`;
- `execution_graph_completed` — a typed `ExecutionGraphResult` (modeled on `ParallelGroupResult`).

**Chat — one evolving Plan view.** Add `ChatLifecycleKey::Plan { graph_id }` (+ `item_id`
arm) and `ChatItemKind::Plan` (+ `slug` arm). A single **durable** handler
`apply_execution_graph` re-renders the **whole** graph into the one Plan item on every
graph/node event (each event carries the full graph snapshot, because `upsert` replaces
the body wholesale). Node states map to `ChatItemStatus` (waiting/ready→`Pending`,
running→`Running`, done→`Completed`, failed→`Failed`, skipped→`Skipped`); large graphs
collapse to a per-state counts line under the 12-line cap. **Suppress** the per-node live
`AgentProgress` chat items for graph nodes — per-node detail stays in the Agent Roster
(Ctrl-L).

**Approval — on the Plan item.** In `normal` mode the Plan item itself enters
`WaitingApproval`, showing the graph plus accept/reject, resolved through the **clarification
answer channel** (a stable `question_id` derived from `graph_id`; accept is the recommended
default; reject carries a free-text reason that returns the plan to the orchestrator to
re-propose). `yolo` auto-accepts. The plan gate uses its **own** state field — it does not
reuse the per-action `state.pending_approval` slot. Fail-closed holds in both modes.

## Alternatives Considered

### Alternative 1: Reuse `parallel_step_groups` as the DAG flag
- **Why rejected** (ADR-003 Q1): silently changes approval/failure behavior for existing flat-group users; DAG's binary-plan-approval + fail-closed semantics differ.

### Alternative 2: Keep per-node live items in chat during a run
- **Why rejected** (ADR-003 Q3): floods the chat with N concurrent items — the documented "lose track past 3–5" failure. Detail belongs in the roster.

### Alternative 3: A separate approval item (clarification item or binary y/n prompt)
- **Why rejected** (ADR-003 Q4): splits review and decision across two items, or (y/n) makes the reject-reason awkward and risks colliding with the per-action approval slot.

### Alternative 4: Bump `HistoryEvent.schema_version` for the DAG
- **Why rejected**: readers reject ≠ 1, which would break replay of every existing session. DAG is additive — new kinds + serde-default fields only.

## Consequences

### Positive
- One coherent, in-place evolving Plan view; reuses the clarification surface and the projection upsert machinery.
- Closes the `/config` visibility gap (approval mode + concurrency settings become user-visible).
- Backward-compatible event log; old and new runs coexist in one `events.jsonl`.

### Negative
- The emitter must snapshot the **full** graph state on each event (delta-only events are insufficient given wholesale body replacement).
- The 12-line body cap forces large-graph summarization.
- Suppressing live-step projection for graph nodes is a new conditional on the live path.

### Risks
- **Durable vs transient**: the Plan item must be built from `apply_history_event` and must never enter `live_keys`/`pending_key`, or a sync would delete it. *Mitigation*: explicit durable handler + test.
- **Forgotten registration**: an unregistered new kind produces no chat output silently. *Mitigation*: register every kind and assert in tests.
- **Config golden tests**: extending `ConfigStatusView` / `config_status_display` and the `config_viewed` payload will require test updates.
