# ADR-001: V1 scope — one ExecutionGraph IR + ready-set scheduler, scope-derived arbitration, typed directed edges

## Status

Accepted

## Date

2026-06-14

## Context

`atelier` already runs **flat parallel groups**: `ParallelGroupPlan` spawns one tokio
task per child over an mpsc channel, with per-node `ParallelFileScope` whose disjoint
`write_files` are validated at decision time (`src/orchestrator/mod.rs:527`) **and**
enforced at runtime — `validate_action_scope` hard-denies any write "outside this
parallel step's exact write_files" (`src/actions/mod.rs:218`, `:768`) and rejects
non-read-only commands. The feature ships behind `parallel_step_groups` (default OFF)
with `max_parallel_agent_steps` (default 2). Children cannot depend on each other and
all spawn at once (no ready-set scheduling).

The "Sub-task DAG execution" idea adds dependency structure so the orchestrator can
propose a plan, the user approves it, and a scheduler runs independent nodes
concurrently while respecting ordering and avoiding conflicts. Chosen KPIs are
**wall-clock speedup, zero conflict regressions, higher effective concurrency**;
plan-quality / plan-edit-rate was explicitly **not** chosen. Ambition framing:
Strategic Bet (a clean foundation for later autonomy).

A 5-advisor council (pragmatic-engineer, architect-advisor, security-advocate,
devils-advocate, the-thinker) debated the scope. Two findings reshaped it:

1. **Scope overlap is symmetric; ordering is directed.** Scope-derived mutual
   exclusion answers "may A and B run together?" but never "must A precede B?".
   Real cases cross *disjoint* write-scopes: B writes `client.rs` but reads
   `api.rs` that A writes; a `cargo test` node depends on a prior edit. A missing
   ordering edge yields disjoint scopes, **zero conflict alarms, and a silently
   wrong result** — a conflict/correctness regression (a chosen KPI), not a
   plan-quality concern. So directed edges earn their place, but free-form
   LLM-authored *mutex* edges do not.
2. **The runtime write fence already exists** (`validate_action_scope`). Scope
   enforcement is not prompt-trusted, so "schedule-time scope disjointness" is a
   near one-line generalization of code that ships today, and the genuinely novel,
   *unverifiable* surface is precisely the LLM-inferred directed edges + the
   output handoff between nodes.

## Decision

V1 builds **one canonical `ExecutionGraph` IR** that `SingleAgent` (1 node / 0 edges)
and `ParallelGroup` (N nodes / 0 edges) lower onto as degenerate cases, executed by
**one ready-set scheduler** (retiring the all-spawn-at-once path). Specifically:

- **Structural scope arbitration, always on.** Generalize the existing decision-time
  disjoint-write check into a **schedule-time admission** rule: a node becomes
  runnable only when no concurrently-running node shares its write scope. Conflict
  freedom is by construction; the existing runtime fence stays as the enforcement
  boundary and the measurement instrument.
- **Minimal, explicitly-typed directed edges** authored by the orchestrator only for
  ordering *not reducible to scope*: `data_dependency` (B consumes A's output) and
  `semantic_gate` (e.g. design-before-implement, review-before-merge). Readiness =
  (all explicit predecessors complete) AND (no scope conflict with the running set).
  No free-form mutex edges.
- **Durable, opaque `node_id` + event-sourced node lifecycle** (Pending → Ready →
  Running → Succeeded / Failed / Skipped / Cancelled) and a `graph_id` sibling to the
  existing `group_id`. This is the "shape"; the *mechanism* of re-planning/resume is
  deferred.
- **Approval authorizes structure.** Whole-plan approval ratifies which nodes run,
  in what order, at what concurrency, and each node's declared touch-set — and
  **waives per-action prompts for in-scope writes**. The runtime fence stays always
  on (silent deny on escape); `RunCommand` and out-of-scope escalations remain gated
  in `normal` mode; `yolo` stays fast.
- **Fail-closed.** On a node failure, descendants are poisoned and cancelled; writes
  use atomic temp+rename so cooperative cancellation cannot leave torn files.
- **Phase 0 instrumentation first/alongside.** Flip the flag, raise the cap, and
  instrument *effective concurrency*, *conflict-deny events*, and *"ordering the
  orchestrator wanted but could not express"* on flat groups — to validate that real
  prompts decompose enough to pay, and to right-size the rest before over-investing.

V1 ships behind the existing `parallel_step_groups` flag (default OFF) so user-facing
blast radius stays zero.

## Alternatives Considered

### Alternative 1: Free-form LLM-authored DAG with whole-plan approval (original framing)

- **Description**: Orchestrator emits arbitrary nodes + LLM-authored dependency edges; user approves the whole graph; new executor path.
- **Pros**: Maximally expressive; matches the literal "DAG" mental model.
- **Cons**: Edges become an unchecked LLM guess; spurious edges over-serialize (taxing the speedup KPI), missing edges cause silently-wrong results; whole-plan approval of abstract edges is hard for a human to evaluate (rubber-stamp risk); a second execution path to maintain.
- **Why rejected**: Puts correctness on the layer no validator can check and no user can meaningfully approve; conflicts with the speed KPI and the zero-conflict KPI at once.

### Alternative 2: Scope-serializable scheduler only — no explicit edges (the-thinker, simplest)

- **Description**: Generalize disjoint-scope checking to schedule-time admission; derive all ordering from read/write scope overlap; no authored edges.
- **Pros**: Conflict-free by construction; maximally concurrent; tiny delta over existing code; nothing for the user to approve beyond today's gate.
- **Cons**: Scope overlap is symmetric — it cannot express *required direction* (read-after-write across disjoint write-scopes, test-after-edit, scaffold→implement); `cargo test` nodes have unbounded undeclarable read scope, forcing either over-serialization or unsafe under-declaration.
- **Why rejected (as a complete answer)**: Adopted as the *default* (derive mutual exclusion from scope), but insufficient alone — directed edges are still needed for the residual ordering cases, which are correctness-relevant.

### Alternative 3: Measure first — do not build the DAG yet (devils-advocate)

- **Description**: Flip `parallel_step_groups`, raise `max_parallel_agent_steps`, instrument flat groups, and let field data decide before building any graph IR.
- **Pros**: Cheapest possible experiment; tests the gating hypothesis (decomposition pays) with no new architecture; zero foundation commitment.
- **Cons**: Flat sibling groups structurally cannot express dependency-shaped decompositions, so they under-measure the *ordering* value; delays a foundation that is ruinous to retrofit.
- **Why rejected (as the whole plan)**: Folded in as **Phase 0** rather than rejected — the measurement runs first/alongside and gates the depth of the rest, but the IR's shape (node_id, lifecycle) is committed because retrofitting it later is the one genuinely expensive reversal.

## Consequences

### Positive

- One IR + one scheduler removes the divergent SingleAgent/ParallelGroup/Dag paths and makes flat groups a degenerate special case.
- Conflict freedom is structural (scope-derived), so the speed and zero-conflict KPIs are served by construction rather than by an LLM's edge guess.
- The runtime fence already exists, so the safety differentiator is real and *measurable* (denied-escape events make "zero conflict regressions" falsifiable).
- Durable node_id + event-sourced lifecycle make V2 (dynamic re-planning, resumable DAGs) a *policy relaxation*, not a rewrite.
- Phase 0 data right-sizes the investment and de-risks the Amdahl/low-decomposition objection.

### Negative

- More up-front modeling than a thin "edges bolt-on": the IR, lifecycle events, and a richer chat projection key (`Node` alongside `Step`) are real work even though OFF by default.
- Typed edges (`data_dependency` / `semantic_gate`) add orchestrator-contract surface and validation (cycle detection, edge-vs-scope reconciliation).

### Risks

- **Missing-edge silent-wrong-result** — the new failure class. *Mitigation*: derive mutual exclusion from scope so independence is structural; require typed directed edges only for genuine producer→consumer / gate orderings; instrument "serialized-but-should-have-pipelined" cases.
- **Read scope is coarse today** (`read_roots` are directories) — read-after-write detection needs finer modeling or an explicit `data_dependency` edge. *Mitigation*: prefer explicit edges for cross-file data deps until read-scope granularity improves.
- **Amdahl / low decomposition** — narrow/serial tasks pay planning + approval overhead for little gain. *Mitigation*: Phase 0 gate; single-agent fallback when no wide independent fan-out exists.
- **Approval theater** — abstract graphs are hard to evaluate. *Mitigation*: approval enumerates per-node files and commands (informed consent), authorizes structure only, and the fence + `RunCommand` gating enforce regardless.
- **Dissent (devils-advocate, preserved):** do not commit the IR/foundation until flat-group field data clears all three gates — (a) ≥~30-40% of eligible runs emit 3+ children with genuinely disjoint write scopes, (b) measured wall-clock speedup clears ~30% even at cap=2, (c) recurrent cases where the orchestrator wanted ordering it could not express. If decomposition is rare, speedup is marginal, or only linear A→B→C chains emerge, the DAG is ceremony.

## Implementation Notes

- Add `DecisionNextStep::Dag(ExecutionGraph)` as a **new** schema variant; never retrofit edges into the persisted `ParallelGroup` wire format (event-sourced history must deserialize forever).
- Lower `SingleAgent` and `ParallelGroup` onto the same `ExecutionGraph` so there is one scheduler, not two.
- Move disjointness from "all children disjoint at decision time" to "no two *concurrently-runnable* nodes share write scope at admission time."
- Reuse as-is: tokio/mpsc coordination, cancellation tokens, per-child limits, the approval queue, the `WorkflowTarget` ledger, event sourcing (`group_id`/`graph_id`), and `validate_action_scope` (the fence).
- Add a `ChatLifecycleKey::Node` (durable `node_id`) so projection neither fragments one node across items nor collapses distinct nodes.
