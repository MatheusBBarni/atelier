# ADR-003: V1 product shape — cohesive full-DAG MVP with a normal-mode binary plan-approval gate

## Status

Accepted

## Date

2026-06-14

## Context

`_idea.md` and ADR-001/ADR-002 fixed the architecture (one `ExecutionGraph` IR +
ready-set scheduler, structural scope arbitration, typed directed edges, durable
`node_id`, fail-closed) and the commitment to ship the **full static DAG in V1**. PRD
brainstorming resolved the remaining **user-facing product shape** through five
clarifications, grounded in fresh research:

- **Codebase (user-facing):** no whole-plan approval exists today — approvals are
  per-action and surfaced one at a time; parallel groups have no group-level gate. The
  pending-approval prompt is 1–3 lines; the **clarification composer** (numbered
  options, ★ recommended default, per-row descriptions, custom free-text, keyboard
  nav, auto-grow) is the richest pause-and-choose surface to extend. Chat is a flat
  scrolling list with **no Plan/DAG lifecycle key**. The slash-command catalog is
  **frozen** (ADR-001). `/config` does not even show approval mode or the parallel
  flags; the feature is **OFF by default**.
- **Market/UX:** approval fatigue is solved by **batching consent at the right
  altitude** (review one coherent plan once vs a stream of per-action prompts). The
  **enforced write-fence is a trust feature competitors lack** (Claude Code plan mode
  is advisory, not enforced). Users want **legible per-node visibility** (ready /
  running / blocked / done), lose track past 3–5 concurrent items, and expect a sane
  concurrency ceiling (~5–7). Speed is real but bounded (~1.8–3.7×).

## Decision

V1 delivers the complete static DAG as **one MVP** (Approach A) behind the default-off
flag, with these binding product decisions:

1. **Trigger.** The orchestrator **auto-proposes** a DAG when a prompt benefits; there
   is no per-prompt gesture. DAG planning has a **visible enable/disable state**
   surfaced in-app (closing today's `/config` visibility gap).
2. **Approval gate.** Shown **only in `normal` mode**: a **binary accept/reject** of
   the whole plan; reject may carry a free-text reason that returns the plan to the
   orchestrator to re-propose. **`yolo` (the default) auto-approves and runs
   immediately.**
3. **Plan legibility.** The approval presents the nodes, typed ordering edges, each
   node's agent, and each node's **file scope (touch-set)** so consent is informed;
   modeled on the existing clarification composer.
4. **Execution visibility.** A single persistent, **evolving "plan" view** shows the
   whole graph with per-node status (waiting / ready / running / done / failed), the
   dependency a node is blocked on, and its file scope, updating in place.
5. **Safety guarantee.** The enforced runtime **write-fence** — "two nodes can never
   write the same file" — is a promised, user-facing guarantee, not advisory text.
6. **Failure UX.** **Fail-closed report-and-stop**: mark the failed node, auto-skip /
   cancel its dependents, show clearly what completed vs what was skipped and why, and
   end the run; the user re-prompts. Retry/resume is deferred to V2.

## Alternatives Considered

### Alternative 1: De-risked two-step within V1 (Approach B)

- **Description**: MVP ships the scheduler + write-fence + evolving plan view + accept/reject with scope-derived ordering only; typed `data_dependency` edges + output handoff land in a fast Phase 2.
- **Pros**: Reaches a provably-safe concurrency win sooner; validates the plan UX before the unverifiable handoff surface.
- **Cons**: Less differentiated MVP; softens ADR-002's "full DAG now."
- **Why rejected**: The product owner wants the differentiated ordering capability in V1 and reaffirmed the full-DAG commitment.

### Alternative 2: Approval-surface platform (Approach C)

- **Description**: Build the plan-consent gate + evolving plan view as a reusable surface that also retrofits today's flat parallel groups, then layer DAG edges on top.
- **Pros**: Maximum consistency/reuse across the harness.
- **Cons**: Widest scope; slowest path to the DAG itself.
- **Why rejected**: Over-scoped for V1; the DAG is the priority, not a harness-wide approval refactor.

## Consequences

### Positive

- One coherent release; the trust (enforced fence) and visibility (evolving plan view) expectations from the research are answered in V1.
- Honors ADR-002 and all five clarifications; no internal contradiction across artifacts.
- Reuses the clarification composer vocabulary and the event-sourced projection model, lowering UX-build risk.

### Negative

- Largest single MVP in the roadmap.
- The output-handoff (the council's sharpest risk) ships in the first cut, so handoff correctness and the missing-edge failure class must be carried as **accepted risks** with mitigations.

### Risks

- **Approval fatigue re-emerging** — if mid-run prompts creep in (re-approvals, per-node clarifications), the feature reintroduces the fatigue it was meant to kill. *Mitigate*: keep interruptions rare and high-signal; fail-closed report-and-stop; no per-node mid-run prompts in V1.
- **Over-parallelization inverts the benefit** — beyond ~5–7 concurrent nodes, supervision and review costs eat the gains. *Mitigate*: a sane concurrency ceiling; present speedup honestly (bounded, not unbounded).
- **Plan illegibility for large graphs** — oversized plans get rubber-stamped or rejected wholesale. *Mitigate*: show per-node scope; right-size guidance; legible node/edge/status model.
- **Discoverability / teachability** — the new approve-the-plan gesture and the enable state must be taught. *Mitigate*: help-overlay update + visible enable state in `/config`.
- **Handoff / missing-edge silent-wrong-result** (from ADR-002) — *Mitigate*: independence derived structurally from scope; informed-consent approval enumerating scopes/edges/handoff sources; optional verify node carried as an Open Question.

## Implementation Notes

- Net-new user surfaces: a plan-approval view richer than today's per-action prompt (model on the clarification composer); a new evolving "plan" chat lifecycle surface; a visible enable state in `/config`; help-overlay teaching of the plan gate + write-fence guarantee.
- The slash-command catalog stays frozen; if a command is later deemed necessary it is its own scope change (ADR-001).
