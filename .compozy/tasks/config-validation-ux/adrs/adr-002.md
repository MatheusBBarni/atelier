# ADR-002: Atomic V1 delivery for config validation UX

## Status

Accepted

## Date

2026-06-15

## Context

The feature scope is fixed by ADR-001 (opt-in `--strict` gate, reserved `0/1/2` exit contract emitting `0/1`, unconditional-chain runtime elevation, additive typo hint, discovery nudge). The remaining product decision is *delivery strategy*: ship the five capabilities together, or stage them. The feature is sized "M" in the roadmap and the primary consumer is CI/CD.

A delivery choice matters because the capabilities are not equally valuable in isolation. The council established that the runtime elevation is what makes the strict gate *trustworthy* — a gate that exits 0 while a required runtime is missing reproduces the `flutter doctor` / `npm doctor` anti-pattern (exits cleanly but does not catch the real problem), which trains operators to ignore it.

## Decision

Ship all five capabilities plus their documentation as a single **atomic V1 release**: the `--doctor --strict` gate, the reserved exit-code contract, unconditional-chain runtime elevation, the additive typo hint, the default-doctor stderr discovery nudge, and the README CLI Notes + copy-paste CI snippet. The Phased Rollout Plan is therefore V1 (this complete set) → V2 (the named successors from ADR-001: emitting exit `2`, the phantom-entry doctor Warning, JSON Schema export, and model-fallback / cross-preset coverage).

User-facing product decisions confirmed alongside this: the typo hint uses the friendly "did you mean `codex`?" phrasing (git/cargo/kubectl convention); V1 scope includes the README CLI Notes entry and a copy-paste CI example so the primary consumer self-serves.

## Alternatives Considered

### Alternative 1: Two-phase, gate-first

- **Description**: Phase 1 = gate + contract + nudge + docs; Phase 2 = elevation + typo hint.
- **Pros**: Ships the headline CI capability fastest; lets adoption be validated before investing in elevation.
- **Cons**: Phase 1's gate fails only on pre-existing Error checks; a missing in-use runtime stays `Warn`, so the gate ships with a known blind spot the council called "a flag worth ignoring."
- **Why rejected**: The integration cost of bundling is ~zero (one shared doctor/config/CLI surface), so staging buys nothing while shipping a weaker, less trustworthy MVP.

### Alternative 2: Gate-only MVP

- **Description**: Ship gate + contract + nudge + docs; defer both elevation and the typo hint.
- **Pros**: Smallest possible change.
- **Cons**: Same missing-runtime blind spot as Alternative 1, plus no typo ergonomics.
- **Why rejected**: This is the "simpler essence" cut already rejected at the idea stage; it under-delivers on the trustworthy-signal thesis.

## Consequences

### Positive

- The strict gate is trustworthy from day one because elevation ships with it — no interim blind-spot window.
- One coherent release and one documentation pass; no re-touching the same surface across phases.
- Clean V1/V2 boundary inherited from ADR-001.

### Negative

- Slightly larger single release than a gate-only MVP (mitigated by the shared surface and existing machinery).

### Risks

- Bundling could obscure that the capabilities are independently testable — mitigated by per-feature acceptance criteria and the KPI table.

## Implementation Notes

Sequence within the single release is a techspec concern, but the natural order is: relocate `edit_distance` → add the typo hint → add `--strict` flag + gate + nudge → add `referenced_runtime_ids()` + elevation → docs + dogfood CI step.
