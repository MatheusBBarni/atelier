# ADR-003: Orchestrator-only runtime elevation, decoupled from `--strict`

## Status

Accepted

## Date

2026-06-15

## Context

ADR-001 scopes runtime elevation to "the primary runtime of an agent the default orchestrator chain resolves unconditionally," with the invariant that every runtime elevated to `Error` is one whose absence *guarantees* the next run fails (closing false CI failures by construction). The TechSpec codebase exploration resolved what that set is concretely:

- Only the **orchestrator** agent is invoked unconditionally on every prompt-driven run (`run_orchestrator_step` at app/mod.rs:1811,1859). It is identified by the well-known id `orchestrator`.
- All specialized agents (explorer, fixer, reviewer, oracle, consul, librarian, designer) are *dynamically routed* by the orchestrator's per-prompt `OrchestratorDecision`; none is guaranteed to run.
- Council is invoked only for high-risk or explicit-review prompts (orchestrator/mod.rs:713).
- `EffectiveConfig.runtimes` and `.agents` are `BTreeMap`s; `AgentProfile` exposes `runtime: String`, `model_fallbacks: Vec<String>`, and `enabled: bool`. Runtime availability currently maps both `Unavailable` and `Unknown` to `Warn` (doctor/mod.rs:67-71).
- `EffectiveConfig.active_preset` means the merged config already reflects the invocation's preset selection.

## Decision

**In-use set = the orchestrator agent's primary runtime only.** Under elevation, an orchestrator runtime that is **`Unavailable`** is reported as `Error`. `Unknown` (probe inconclusive) and all non-orchestrator / council / inactive-preset / model-fallback runtimes stay `Warn`.

**Elevation is decoupled from `--strict`.** `run_doctor` always marks an unavailable orchestrator runtime as `Error` in the report. `--strict` only decides whether that error fails the process: the exit code is a pure function of the report's max severity (`DoctorReport::has_errors()`), so `run_doctor` never needs to know about the flag.

**Owned derivation.** Add `EffectiveConfig::required_runtime_ids() -> BTreeSet<&str>` returning the runtime ids that must be available (V1: the orchestrator's). A guardrail unit test asserts the default config yields exactly the orchestrator's runtime, so the set cannot broaden silently.

Because the merged config already reflects the active preset, `--strict` validates whatever preset/flags it is invoked with — operators validate with the same invocation context they deploy with.

## Alternatives Considered

### Alternative 1: All enabled agents' runtimes elevate

- **Description**: Elevate the primary runtime of every `enabled` agent profile.
- **Pros**: Broader coverage; catches a missing runtime for any agent that could be routed to.
- **Cons**: A run that never routes to that agent would fail `--strict` on a runtime it did not need — a false CI failure, the exact failure mode the council closed.
- **Why rejected**: Breaks the "absence guarantees failure" invariant; trains adopters to disable the flag.

### Alternative 2: Elevate only under `--strict` (strict-gated severity)

- **Description**: Apply the Warn→Error elevation only when `--strict` is set, leaving default `--doctor` output byte-for-byte unchanged.
- **Pros**: Preserves exact current default rendering.
- **Cons**: Threads the flag into severity computation; the same config shows different severity depending on the flag; exit code is no longer a clean function of the report.
- **Why rejected**: Decoupling is simpler and more honest; the report should reflect true severity regardless of how the process is invoked.

## Consequences

### Positive

- Zero false CI failures: the single elevated runtime's absence is a certain, not probable, failure.
- `run_doctor` stays flag-agnostic; exit code = function of report severity.
- The orchestrator runtime is the highest-value check — its absence breaks everything.

### Negative

- A missing runtime used only by a conditionally-routed agent stays `Warn` (a defensible false-pass; still visible). Broader coverage is a named V2 item.
- Default `--doctor` now renders an unavailable orchestrator runtime as `ERROR` rather than `WARN` (exit code unchanged). Existing doctor unit tests whose fixtures leave the orchestrator runtime unavailable may need status-assertion updates.

### Risks

- The set silently broadening → mitigated by the `required_runtime_ids()` guardrail test.
- Elevation keying on the literal id `orchestrator` → mitigated by treating it as the same well-known id the orchestrator step already resolves.

## Implementation Notes

- Elevation lives in the runtime-availability loop in `run_doctor` (doctor/mod.rs:65-99): if `runtime.id == required` and availability is `Unavailable`, set status/severity `Error`.
- `--strict` gate lives in the `cli.doctor` dispatch: after rendering, `if cli.strict && report.has_errors() { return Err(...) }` → `main.rs` exit 1.
