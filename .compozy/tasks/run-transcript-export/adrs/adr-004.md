# ADR-004: Tiered secret scan (single-source) with fail-closed CLI enforcement

## Status

Accepted

## Date

2026-06-19

## Context

ADR-001 requires tiered, detect-don't-mutate redaction that gates on
high-confidence secrets and treats entropy as advisory. Codebase exploration
found two *divergent* secret passes: the history write-time pass
(`runtime::http_util::redact_sensitive_text`, only `Bearer` + `sk-`/`zai-`/`or-`/`ov-`)
and a richer detector `runtime::status::looks_like_secret` (9 provider prefixes +
sensitive-`key=value` + a ≥20-char entropy heuristic). A prior repo ADR mandates
secret logic stay single-source so it "cannot silently diverge." Both existing
APIs return `bool`/`String` — neither yields the findings, spans, or confidence
the gate needs. Three more constraints shape enforcement: there is **no
structured exit-code convention** (`main` maps any `Err` → exit 1); `--yes` is
**hard-gated to `--clean-sessions`**; and **no gitignore-membership predicate
exists** anywhere in `src/`.

## Decision

1. **One scanner, extending `runtime::status`.** Add
   `pub fn scan_secrets(text: &str) -> Vec<SecretFinding>` that reuses/refactors
   the existing `looks_like_secret` + `key_is_sensitive` classification, so the
   export, the status redactor, and the history pass share one secret definition.
   `SecretFinding { category, span, confidence }` with
   `confidence ∈ { Deterministic, Advisory }`.
2. **Two tiers.**
   - **Deterministic (gates):** known provider prefixes — the existing nine
     plus AWS `AKIA…`, Stripe `sk_live_`/`pk_live_`, Google `AIza…`, JWT `eyJ…`,
     Slack `xapp-`, GitLab `glpat-`, and PEM `-----BEGIN … PRIVATE KEY-----` —
     **sensitive `key=value`**, and **credential-file bodies** (file names via
     `file_index::is_secret_name`: `.env*`/`*.pem`/`*.key`/`id_rsa*`), whose body
     is redacted wholesale (path kept).
   - **Advisory (warns, never gates):** the ≥20-char entropy heuristic, which
     fires on git SHAs/base64/UUIDs and so must not block CI.
3. **Detect, don't mutate the narrative.** Findings are redacted by labelled
   placeholder (reusing the `<redacted>` convention); the scan never rewrites kept
   diffs/commands/reasoning except a credential file's body. Spans are surfaced in
   the artifact and the gate.
4. **Risk-adaptive gate.** Interactive clean export → `y`/`yes`; interactive
   flagged export → type `approve` (the high-tier approval token). Non-interactive
   `--yes`: write only when there is no Deterministic finding; otherwise **fail
   closed** — `bail!` (→ exit 1) with a stderr nudge *"N secret(s) flagged; re-run
   with --allow-flagged to override,"* mirroring `--doctor --strict`. No new exit
   code (YAGNI). `--allow-flagged` proceeds and records a categorized override.
5. **Relax CLI guards.** Admit `--export-session` in the `--yes` guard and the
   `--update` mega-exclusion in `src/cli.rs`.
6. **Egress warning.** Shell out to `git check-ignore <target>` (copying the
   500ms-timeout, `kill_on_drop` subprocess pattern in `src/app/git.rs`); warn when
   the target is not ignored or sits inside the repo working tree. Default target
   `.atelier/exports/<session>-<timestamp>.md` (owner-only, under the
   already-ignored `.atelier/`).

## Alternatives Considered

### Alternative 1: A dedicated export-only secret scanner

- **Description**: New detector independent of `runtime::status`.
- **Pros**: Export owns its own rules.
- **Cons**: Creates a third secret definition that drifts from the other two,
  violating the single-source ADR.
- **Why rejected**: Divergent secret logic is exactly the failure the repo's ADR
  forbids.

### Alternative 2: Reuse `looks_like_secret` as-is (bool)

- **Description**: Call the existing `bool` detector at the gate.
- **Pros**: Zero new surface.
- **Cons**: No spans, categories, or confidence — can't drive a risk-adaptive gate,
  highlight flagged spans, or separate gating from advisory tiers.
- **Why rejected**: Insufficient for the gate; a findings type is unavoidable.

### Alternative 3: A dedicated "secrets found" exit code

- **Description**: Add e.g. exit 2 for fail-closed.
- **Pros**: CI could distinguish leak-block from other failures.
- **Cons**: `main.rs` maps every `Err` → 1; a typed exit code means changing the
  process-exit mapping for the whole binary.
- **Why rejected**: YAGNI; `bail!` → exit 1 + a distinct stderr message is enough
  to fail CI and is the established `--strict` pattern.

## Consequences

### Positive

- One secret definition across export, status, and history; extends coverage for
  everyone.
- Deterministic-gates / entropy-advises keeps CI from flaking on hashes while still
  failing closed on real credentials.
- Fail-closed `--yes` makes automated provenance safe by construction; overrides
  are logged.

### Negative

- Extending `runtime::status` couples export to a runtime module (acceptable: it is
  the secret single-source).
- The deterministic ruleset is a maintained list; new token shapes need additions.

### Risks

- **False negative on a novel secret** (irreducible) → the human gate, the
  advisory entropy tier, the "rotate touched credentials" notice, and the
  seeded-corpus recall test (≥99% on the deterministic class) backstop it.
- **`--allow-flagged` overused** → recorded as a categorized override in the audit
  event; loud stderr.

## Implementation Notes

- `scan_secrets` is `pub` in `runtime::status`; the recall test seeds a corpus of
  `(input, expected_findings)` next to the existing redaction tests there.
- `git check-ignore` returns exit 0 when ignored; treat non-zero / no-repo as
  "not ignored → warn."
