# ADR-002: V1 product experience — CLI-first export, lean review artifact, risk-adaptive review gate

## Status

Accepted

## Date

2026-06-19

## Context

ADR-001 set the V1 scope and security architecture (CLI-first, tiered
detect-don't-mutate redaction, tiered fail-closed, quarantine egress). This ADR
records the **product-experience** decisions made during PRD brainstorming: the
delivery surface, the shape of the exported artifact, the confirmation
experience, and how overrides and false positives are handled.

PRD-phase research added decisive evidence on *how such a feature is adopted or
rejected*:

- **The accepted-gate model is GitHub push protection:** block + inline
  remediation + a **logged, categorized override** (not silent, not free-text).
- **Precision beats recall** for interactive flags — false positives are the #1
  adoption killer; alert fatigue drives blanket bypass.
- **Rubber-stamping is the dominant failure** of mandatory human review; a single
  "Confirm" on a wall of text is reflexively pressed. The counter is a *minimal
  active decision* plus *risk-based tiering* so the gate does not cry wolf.
- **Reviewers want a short intent summary that maps to the diff**, plus the
  execution trail — not a chain-of-thought dump. Message↔code consistency is
  load-bearing (mismatched PRs see 51.7% lower acceptance, 3.5× slower merge).
- atelier already owns the matching vocabulary: `--doctor --json`,
  `--doctor --strict` ("re-run with --strict to fail CI"), a `--yes` precedent,
  and the approval-modal `y/n/t` tokens and `<redacted>` labels.

## Decision

Adopt **Approach A: a CLI-first export with an inline, risk-adaptive review
gate**, producing a **lean review artifact**, with **logged overrides and
per-export false-positive dismissal**.

1. **Surface — CLI first.** Ship `atelier --export-session <id>` (with run
   scoping and a file/stdout target). The in-TUI `/export` is **deferred to V2**
   as a thin follow-on over the proven serializer and the existing preview modal.
2. **Artifact — lean review artifact.** Summary-first: a TL;DR + a redaction
   summary (counts by category) lead the file; verbose file-reads and tool output
   are collapsed/elided; flagged spans are surfaced. The structured audit-artifact
   ("AIBOM") shape is the V2+ north star, not V1.
3. **Review gate — risk-adaptive.** A clean export (no high-confidence secret
   hits) passes with a lightweight single-key confirm. A flagged export requires
   the user to acknowledge the flagged count/categories before the file is
   written. The gate escalates friction only when there is something to decide.
4. **Non-interactive mode — fail closed.** `--yes` runs without prompting and
   fails closed (non-zero exit, no file) on any deterministic high-confidence hit;
   override only via an explicit, loudly-logged `--allow-flagged`.
5. **Overrides & false positives.** Every override (interactive bypass or
   `--allow-flagged`) is recorded to the `session_exported` audit event with a
   category. A false-positive flag can be dismissed for the current export only;
   a persistent "not-a-secret" baseline is **deferred to V2**.

## Alternatives Considered

### Alternative 1: In-session TUI `/export` first (Approach B)

- **Description**: Ship the in-TUI `/export` with the rich preview modal first;
  CLI follows.
- **Pros**: Best review ergonomics (visual highlighting, scroll); most in-flow for
  a user finishing a session in the TUI.
- **Cons**: TTY-only, so it misses the CI/scripting job where the provenance value
  lives; mutates the deliberately-fixed slash-command catalog and key-routing
  precedence; proves the Markdown format in the harder-to-test surface.
- **Why rejected**: The primary job (attach provenance to a PR, including from
  hooks/CI) is non-interactive. CLI-first validates the format where it matters
  and is TTY-free testable; the TUI becomes a clean V2 follow-on.

### Alternative 2: Both surfaces in V1 (Approach C)

- **Description**: Ship the CLI and `/export` together.
- **Pros**: Most complete day-one experience; no one waits for their surface.
- **Cons**: Doubles the gate/confirm test surface and re-expands the scope ADR-001
  disciplined to CLI-first, before the format is validated on a real PR; a
  wrong-first-cut format then has to be fixed in two places.
- **Why rejected**: Front-loads cost the evidence says to defer; sequencing
  CLI → TUI is cheaper and lower-risk.

### Alternative 3: Always-active acknowledgment (gate variant)

- **Description**: Require acknowledging the redaction summary on every export,
  clean or not.
- **Pros**: Most consistent and conservative.
- **Cons**: Adds friction to clean exports and trains users to dismiss the gate
  reflexively — the rubber-stamping failure mode.
- **Why rejected**: Risk-adaptive tiering preserves safety on flagged exports
  while keeping clean exports frictionless, so the gate earns trust.

## Consequences

### Positive

- Serves the PR/CI provenance job directly; scriptable and TTY-free testable.
- Reuses atelier's established CLI, confirm, and redaction-label vocabulary, so the
  feature feels native.
- The risk-adaptive gate + logged overrides convert "mandatory review" from
  security theater into an accountable, low-cry-wolf control.
- Lean summary-first artifact maps to what reviewers actually read, improving the
  odds the transcript is used rather than ignored.

### Negative

- The inline terminal gate cannot highlight spans as richly as a TUI modal; review
  is summary + flagged-list driven in V1.
- TUI `/export`, the change digest, and a persistent FP baseline all slip to later
  phases.

### Risks

- **False-positive fatigue** → precision-first flagging; the fuzzy/entropy class is
  advisory, never a gate.
- **Rubber-stamping on flagged exports** → require an active acknowledgment of the
  count/categories, not a bare key.
- **`--allow-flagged` becomes a copy-paste incantation** → loud logging; recorded
  as a categorized override; must be explicit.
- **Low adoption** → instrument attach-and-repeat with pre-committed kill/scale
  thresholds; the V2 digest attacks the "unread transcript" risk.

## Implementation Notes

- Mirror `--doctor`/`--print-config` parsing and the `--yes` precedent in
  `src/cli.rs`; reuse `--strict`-style "fail CI" messaging for `--allow-flagged`.
- Reuse the `<redacted>` label convention and the approval-modal `y/n` vocabulary
  for the gate.
- The lean artifact serializes the existing `ChatItemView`s; collapsing verbose
  spans is a rendering choice over the same projected items.
