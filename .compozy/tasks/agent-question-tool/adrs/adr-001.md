# ADR-001: Scope Clarification Select UI

## Status

Accepted

## Date

2026-06-06

## Context

The harness already has `Clarifying Question`, `WaitingForUser`, `pending_clarification`, `HistoryEvent`, `ChatProjection`, and TUI dropdown mechanics, but the current clarification flow is free text. When a run reaches ambiguity, the orchestrator can pause with one string question, and the next submitted prompt becomes the answer.

The feature idea is to add an OpenCode-like question tool where the Input Composer becomes a select input with a short title, recommended options, and a final custom answer option. The primary V1 goal is to prevent stalled runs for the human TUI operator while making common answers faster.

The council recommended preserving a future-compatible question protocol, but the opportunity scan surfaced a simpler direction: upgrade the existing free-text clarification path first. The user selected the simpler clarification select UI direction. V1 should prove the operator flow before widening the runtime or agent contract.

## Decision

V1 will implement a focused Clarification Select UI for the existing orchestrator-owned `pending_clarification` flow.

The V1 user flow includes:

- one active question at a time;
- short question title/header and full question text;
- recommended answer options with one default/recommended selection;
- final custom text option;
- answer or interrupt handling, with no separate skip action in V1;
- compact Chat and Session History events for requested and answered questions;
- run resume after the answer is recorded.

The first implementation should avoid unnecessary protocol expansion. It may keep the data model close to the existing `clarifying_question` and `pending_clarification` structures as long as the UI flow is complete and the history events are explicit enough to debug what happened.

## Alternatives Considered

### Alternative 1: Orchestrator-specific UI patch

- **Description**: Add a TUI select widget only for the current `pending_clarification` string and keep the rest of the model orchestrator-specific.
- **Pros**: Fastest implementation and smallest immediate code surface.
- **Cons**: Treats durable orchestration state as a renderer concern and risks a future migration when non-orchestrator agents need to ask questions.
- **Why accepted with constraints**: The user selected the simpler opportunity. V1 should still record explicit lifecycle events and keep the UI as a projection of app state rather than pure renderer-local state.

### Alternative 2: Any-agent question tool in V1

- **Description**: Allow any specialized agent or runtime step to emit question requests immediately.
- **Pros**: Matches the broadest interpretation of OpenCode and Claude-style question tools.
- **Cons**: Expands policy, authorization, spam control, concurrent waiting behavior, resume logic, and runtime contracts before the base operator flow is proven.
- **Why rejected**: It widens the behavioral surface before the project has stable question ownership, cancellation, and replay semantics.

### Alternative 3: Generic protocol with orchestrator-only V1 policy

- **Description**: Model questions generically but permit only the orchestrator to produce them in V1.
- **Pros**: Keeps the shipped behavior focused while preserving a future path to agent-originated questions.
- **Cons**: Requires slightly more careful naming and event modeling than a direct `pending_clarification` patch.
- **Why rejected for V1**: It is architecturally cleaner, but broader than the chosen simple clarification-select direction.

## Consequences

### Positive

- Reduces stalled runs without widening runtime and agent contracts in V1.
- Gives the TUI a complete operator decision loop instead of a partial primitive.
- Keeps question state auditable through Session History and visible through Chat.

### Negative

- V1 does not let specialized agents ask questions directly.
- A later any-agent question tool may require a model and history migration.
- Headless and non-interactive behavior still needs explicit product decisions before PRD completion.

### Risks

- **Question spam**: Mitigate by permitting only orchestrator-originated questions in V1 and one active question at a time.
- **Ambiguous defaults**: Mitigate by requiring recommended options to be explicit and recording whether the user chose a recommended option or custom text.
- **History noise**: Mitigate by recording compact lifecycle events rather than verbose UI state.
- **Approval confusion**: Mitigate by keeping Action Approval and Clarifying Question as separate Chat item kinds and run states.

## Implementation Notes

- Treat the TUI select input as a projection of existing pending clarification state, not the source of truth.
- Reuse existing dropdown navigation patterns where practical, but add a distinct pending-question mode so arrow keys select options instead of moving the text cursor.
- Store selected recommended answers by stable option identity or label, and store custom answers as text values.
- Preserve the existing app-owned lifecycle boundary: runtimes return structured contracts; the app owns run state, history, answer application, cancellation, and resume.
