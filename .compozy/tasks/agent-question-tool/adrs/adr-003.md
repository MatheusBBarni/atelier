# ADR-003: Implement Clarification Select As Structured Orchestrator State

## Status

Accepted

## Date

2026-06-07

## Context

The PRD requires the existing orchestrator Clarifying Question flow to render as a select-style Input Composer with 2-4 recommended answers plus custom text. V1 excludes any-agent question requests and skip actions. Current code stores only a free-text `clarifying_question` on `OrchestratorDecision`; the app keeps `pending_clarification` private and resumes by treating the next `PromptSubmitted` as the answer. Chat currently renders clarification waits with approval-oriented status.

The technical design must preserve the existing app-owned lifecycle while making question state explicit enough for TUI rendering, answer handling, Chat projection, and Session History.

## Decision

V1 will implement clarification select through structured orchestrator-owned state:

- Extend `OrchestratorDecision` with structured `clarifying_options` and `recommended_option_id` fields.
- Add `PendingClarificationView` to `AppState`.
- Add a dedicated `AppEvent::ClarificationAnswered` answer path.
- Add dedicated Chat semantics through `ChatItemKind::Clarification` and `ChatItemStatus::WaitingForUser`.
- Keep the custom answer text field visible below the recommended option list.
- Verify the feature with layered unit tests for schema validation, app flow, Chat projection, and TUI key/render behavior.

## Alternatives Considered

### Alternative 1: Derive options inside the app

- **Description**: Keep `clarifying_question` as a string and let the app generate or infer options.
- **Pros**: Avoids changing runtime prompt contracts.
- **Cons**: The app cannot reliably infer product-specific answer choices and would hide model intent.
- **Why rejected**: The PRD requires recommended answers, and those should come from the orchestrator decision.

### Alternative 2: Reuse `PromptSubmitted` for answers

- **Description**: Continue treating the next submitted prompt during `WaitingForUser` as the answer.
- **Pros**: Minimal app event changes.
- **Cons**: Cannot distinguish selected option versus custom text, weakens history payloads, and makes TUI behavior implicit.
- **Why rejected**: V1 needs explicit answer source tracking and a separate composer mode.

### Alternative 3: Reuse approval Chat semantics

- **Description**: Keep rendering clarification waits as approval-like Chat items with different wording.
- **Pros**: Smallest Chat change.
- **Cons**: Conflicts with the PRD requirement to distinguish Clarifying Questions from Action Approval.
- **Why rejected**: Clarification and approval are different user decisions and need distinct visible states.

## Consequences

### Positive

- Makes question state explicit across orchestrator, app state, TUI, Chat, and history.
- Preserves the app-owned lifecycle boundary.
- Keeps V1 scoped to orchestrator Clarifying Questions while enabling robust UI behavior.

### Negative

- Requires runtime prompt-contract updates across Codex, Claude, Cursor, fake, and orchestrator guidance.
- Adds a new app event and public pending view.
- Adds new Chat enum variants and corresponding projection/rendering tests.

### Risks

- **Contract drift across runtimes**: Mitigate with prompt snapshot or parser tests for each runtime adapter that embeds the orchestrator decision schema.
- **Custom text ambiguity**: Mitigate by recording `answer_source = "custom"` versus `answer_source = "recommended"` in history.
- **Approval confusion**: Mitigate with dedicated Chat kind/status and separate TUI copy.
