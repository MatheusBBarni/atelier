# ADR-001: Workflow Command Uses One Evidence-First Run

## Status

Accepted

## Date

2026-06-06

## Context

The proposed `/workflow <prompt>` feature should help a solo developer hand a broad engineering prompt to the Harness and receive decomposed specialized-agent work, validation, and one consolidated answer. Market references from Claude Code Dynamic Workflows, Cursor multitask agents, and OpenAI Codex show strong demand for multi-agent orchestration, but also create expectations around parallel work, review, and evidence.

The existing `multiagent-harness` domain model already treats a Prompt as one Run guided by one Orchestrator-owned Run Plan. It also has Parallel Step Groups, Parallel Group Results, Chat, Agent Roster, Harness Actions, Action Approval, action policy, and Session History boundaries. Adding a separate workflow scripting engine in V1 would create a second control plane before the existing Run model has proven workflow-mode behavior.

## Decision

V1 will define `/workflow <prompt>` as a workflow-mode entry point into one normal Run. The command should bias the Orchestrator toward decomposition, safe specialized-agent work, validation, and final synthesis while preserving the existing Run, Run Plan, Parallel Step Group, Harness Action, approval, cancellation, and history boundaries.

Workflow mode must be evidence-first. A completed workflow run should make the plan, scope boundaries, child outcomes, validation evidence, skipped checks, and unresolved risks visible enough that the user can understand what happened and what remains uncertain.

## Alternatives Considered

### Alternative 1: Separate workflow scripting engine

- **Description**: Add a workflow runtime or DSL that can spawn and coordinate agents independently of the normal Run loop.
- **Pros**: More closely resembles Claude Dynamic Workflows and could support reusable scripts, advanced fan-out, and custom control flow.
- **Cons**: Creates new persistence, debugging, authorization, recovery, cancellation, and documentation surfaces.
- **Why rejected**: Too much boundary expansion for V1. The existing Run model should prove workflow-mode orchestration first.

### Alternative 2: Saved reusable workflows in V1

- **Description**: Let users save workflow definitions or templates immediately.
- **Pros**: Increases repeatability and competitive parity with workflow libraries.
- **Cons**: Introduces versioning, portability, trust, prompt-injection, and lifecycle questions before the core command is validated.
- **Why rejected**: Useful later, but premature until users prove that `/workflow` improves broad task completion quality.

### Alternative 3: Direct specialized-agent delegation

- **Description**: Let Specialized Agents spawn or delegate directly to other Specialized Agents.
- **Pros**: More autonomous and potentially more dynamic.
- **Cons**: Bypasses Orchestrator-owned Run Plan semantics and weakens policy, review, and history clarity.
- **Why rejected**: The Orchestrator must remain the owner of decomposition and next-step selection in V1.

### Alternative 4: Worktree or background execution in V1

- **Description**: Run workflow children in isolated worktrees or continue work in autonomous background sessions.
- **Pros**: Better isolation and stronger parallelism for large changes.
- **Cons**: Adds merge, cleanup, branch, approval, recovery, and resource-management complexity.
- **Why rejected**: Valuable future direction, but not required for the first reliable local workflow command.

## Consequences

### Positive

- Preserves the accepted one-Prompt, one-Run product model.
- Reuses existing Parallel Step Group, Chat, Agent Roster, action policy, approval, and history primitives.
- Keeps V1 smaller while still giving users a visible workflow-shaped experience.
- Makes trust and verification central to the feature instead of treating speed as the main value.

### Negative

- V1 will not match every Claude Dynamic Workflows capability.
- Workflow behavior may initially depend on Orchestrator prompt quality and existing parallel-group readiness.
- Users who expect reusable scripts, worktrees, or background autonomy will need a later phase.

### Risks

- **Overpromising**: The `/workflow` name may imply stronger determinism than V1 can guarantee. Mitigate with explicit plan, evidence, skipped-check, and residual-risk reporting.
- **Scope ambiguity**: Broad prompts can produce unclear file scopes. Mitigate by asking clarifying questions or falling back to sequential steps.
- **Cost and latency**: Workflow mode can consume more runtime work than normal prompts. Mitigate with conservative default parallelism and visible limits.
- **Policy bypass pressure**: More autonomous behavior can tempt shortcuts around Harness Actions. Mitigate by keeping every file edit, command, approval, and VCS action under existing app-owned enforcement.

## Implementation Notes

- Parse `/workflow <prompt>` before unknown slash-command rejection.
- Start one normal Run with a workflow-mode prompt envelope.
- Fail with a clear workflow-specific message when `features.parallel_step_groups` is disabled, because V1 workflow mode is defined as executing decomposed specialized-agent work rather than producing a planning-only fallback.
- Respect `limits.max_parallel_agent_steps`.
- Prefer Parallel Step Groups only when file scopes are exact, disjoint, and safe.
- Record or surface enough workflow-specific evidence for plan, child work, validation, skipped checks, and unresolved risk.
- Keep saved workflows, workflow scripts, worktrees, direct agent delegation, and background autonomy out of V1.
