# ADR-003: Unified GovernanceDecision data model + single pending_governance_decision state

## Status

Accepted

## Date

2026-06-15

## Context

The spine must formalize a governance-pause surface that both siblings already approximate: `approval-trust-list` "reuses the clarification options-list pattern" and `subtask-dag-execution` resolves whole-plan approval "through the clarification channel" via its own `pending_plan_approval`. The codebase expresses pauses as concrete `Pending*` structs + per-kind projection arms (no trait indirection), and PRD Q1/Q2 chose a shared concrete data model held in one unified state.

## Decision

Define a concrete **`GovernanceDecision`** view type — action/intent, fully-qualified target/scope, blast-radius/reversibility, plain-language reason, an explicit risk label, and clearly-separated decision affordances — plus **one shared event kind** (`governance_decision_requested` / `_resolved`), **one shared projection arm**, and a **`ChatLifecycleKey::GovernanceDecision`**. Hold it in a single **`App.pending_governance_decision`** field that rides the existing clarification pause/resume transport (`RunDriveContext` capture + `drive_and_replay`) but is distinct from `pending_clarification`. Consumers **populate** the type. The early-abort is the V1 consumer; the siblings migrate `pending_plan_approval` and the rich per-action approval onto it in Phase 2. The type carries an optional structured **plan payload** so a single-agent intent echo and (later) a DAG `ExecutionGraph` view render through the same arm.

## Alternatives Considered

### Alternative 1: A trait consumers implement

- **Description**: `GovernanceDecision` as a Rust trait each gate implements.
- **Pros**: Extensible, polymorphic.
- **Cons**: Indirection the codebase's concrete-struct style avoids; only one V1 implementer.
- **Why rejected**: Over-abstraction for the current need.

### Alternative 2: Per-consumer pending states / convention-only

- **Description**: Each gate keeps its own `pending_*`; the contract is documentation.
- **Pros**: Smallest immediate change.
- **Cons**: No unification — drifts, and forces a double refactor when siblings adopt anyway.
- **Why rejected**: Undercuts the spine's whole purpose.

### Alternative 3: Overload `pending_clarification`

- **Description**: Add a governance variant to the existing clarification state.
- **Pros**: Least new state.
- **Cons**: Conflates free-text clarification with structured governance decisions; muddies key-routing/projection.
- **Why rejected**: The architect explicitly warned against it.

## Consequences

### Positive

- One governance surface with consistent projection + key-routing; siblings converge onto it incrementally.

### Negative

- Defining a generic shared type up front for a single V1 consumer; sibling migration is deferred work.

### Risks

- The shared type must be a **superset** of the siblings' needs (`RiskNote`, `ExecutionGraph` view) — design it as an envelope with an optional structured-plan payload and an open `risk` label, validated against both sibling techspecs.

## Implementation Notes

Reuse the clarification *transport* (capture + `drive_and_replay`), not the clarification *type*. Slot a new `pending_governance_decision` branch into the TUI key-routing precedence between clarification and approval.
