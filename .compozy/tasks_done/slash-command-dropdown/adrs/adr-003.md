# ADR-003: Use Shared Metadata-Only Slash Command Catalog

## Status

Accepted

## Date

2026-06-06

## Context

The slash command dropdown needs one visible source of command names, inserted text, usage hints, and descriptions. Today, command guidance is duplicated across the TUI help modal, README, and app-level unknown-command guidance. Command execution is intentionally split: the TUI handles `/help` and `/reload:skills`, the app handles `/goal`, `/config`, and `/subtask`, and `/agent:` plus `/skill:` remain prompt prefixes.

The PRD requires metadata alignment without changing command semantics or broadening V1 into a command platform.

## Decision

Add a shared metadata-only module at `src/slash_commands.rs`.

The module will define the fixed V1 command catalog for:

- `/help`
- `/goal`
- `/goal clear`
- `/config`
- `/subtask`
- `/agent:`
- `/skill:`
- `/reload:skills`

The catalog will expose command labels, insertion text, usage text, descriptions, and command kind/category as static metadata. The TUI will consume it for the slash-command dropdown and help text. The app will consume it for unknown-command guidance. Existing execution ownership remains unchanged.

## Alternatives Considered

### Alternative 1: Full Shared Command Registry With Dispatch

- **Description**: Move both metadata and command execution into a central registry.
- **Pros**: Stronger centralization and fewer execution-boundary differences.
- **Cons**: Larger refactor, higher regression risk, and broader scope than the PRD requires.
- **Why rejected**: V1 only needs aligned visible metadata; command execution already works and should stay stable.

### Alternative 2: TUI-Local Metadata

- **Description**: Keep the dropdown command list in `src/tui/mod.rs` and update app error text separately.
- **Pros**: Fastest implementation path.
- **Cons**: Adds another source of truth and preserves the drift problem.
- **Why rejected**: The core technical requirement is reducing metadata drift across visible command surfaces.

### Alternative 3: App-Scoped Metadata Module

- **Description**: Put metadata in `src/app/slash_commands.rs` and export it for TUI use.
- **Pros**: Keeps app command guidance close to app handlers.
- **Cons**: Makes TUI rendering depend on app internals for metadata that is not app-owned execution state.
- **Why rejected**: A top-level module better reflects the shared, metadata-only boundary.

## Consequences

### Positive

- Keeps visible command metadata aligned across TUI and app surfaces.
- Avoids a risky command-dispatch refactor.
- Gives the dropdown a stable catalog while preserving existing command owners.
- Makes `/reload:skills` available to unknown-command guidance through the same catalog.

### Negative

- Adds a top-level module for a small fixed catalog.
- Metadata and execution can still drift semantically if command behavior changes without catalog updates.
- README remains documentation and may still need manual updates when command behavior changes.

### Risks

- **Catalog grows into a dispatch registry by accident**: Keep the module metadata-only in V1.
- **Descriptions become stale**: Route help and unknown-command guidance through the catalog so tests catch drift.
- **Kind/category overdesign**: Keep fields limited to what the dropdown, help, and app guidance need.

## Implementation Notes

- Export a static slice or function returning `&'static [SlashCommandSpec]`.
- Keep fields narrow: label, insert text, usage, description, and kind.
- Avoid runtime state, callbacks, closures, or dispatch functions in the catalog.
- Update `src/lib.rs` or module declarations so both `src/tui/mod.rs` and `src/app/mod.rs` can import the catalog.
