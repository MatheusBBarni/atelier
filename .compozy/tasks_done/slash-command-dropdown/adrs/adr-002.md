# ADR-002: Choose Error-Reduction Product Approach

## Status

Accepted

## Date

2026-06-06

## Context

The slash command dropdown PRD needs a product approach that translates the approved idea into user-facing requirements. The primary target user is a new or occasional Atelier user. The selected success signal is fewer unknown-command submissions, not maximum command-entry speed or a larger onboarding surface.

The approved V1 scope already constrains the feature to a fixed command set, text insertion only, Tab and Enter acceptance, and the same interaction approach as the existing `/agent:` and `/skill:` dropdowns.

## Decision

Use the Error-Reduction MVP approach for the PRD.

The PRD will optimize V1 around preventing invalid slash-command submissions by:

- Showing the fixed V1 command set when the user types `/`.
- Filtering the list as the user types.
- Showing a compact empty state when no commands match.
- Inserting selected command text only, without submitting.
- Preserving raw input until the user explicitly accepts a suggestion with Tab or Enter.
- Keeping the dropdown scoped to new and occasional user discoverability rather than broader onboarding or power-user speed.

## Alternatives Considered

### Alternative 1: Discovery-First Onboarding

- **Description**: Make the dropdown more explanatory with richer command guidance and onboarding copy.
- **Pros**: Helps users learn what each command does.
- **Cons**: Adds copy density, layout pressure, and more metadata to maintain.
- **Why rejected**: The primary target is reducing invalid submissions, and V1 should stay compact.

### Alternative 2: Speed-First Command Entry

- **Description**: Optimize the dropdown for shortest-path keyboard insertion for users who already know the command set.
- **Pros**: Useful for frequent users and can make command entry feel faster.
- **Cons**: Does less for new or occasional users and can over-index on ranking or shortcuts.
- **Why rejected**: The selected persona and metric prioritize fewer unknown commands over power-user speed.

### Alternative 3: Passive Help Improvements

- **Description**: Improve `/help` and unknown-command error text without adding an in-composer dropdown.
- **Pros**: Lowest interaction risk and simplest product surface.
- **Cons**: Users still only learn commands after seeking help or making a mistake.
- **Why rejected**: The dropdown should prevent errors before submission, not merely explain them afterward.

## Consequences

### Positive

- Aligns the PRD around a measurable user outcome.
- Keeps V1 small enough to validate quickly.
- Reduces accidental invalid command submissions at the moment users are composing input.
- Preserves existing command execution behavior because suggestions insert text only.

### Negative

- The dropdown will not fully explain every command in V1.
- Power-user acceleration features are deferred.
- The empty state needs to be concise enough not to distract from normal text entry.

### Risks

- **Overfitting to one metric**: Unknown-command reduction may miss broader usability issues. Mitigation: include qualitative usability feedback and first-run discovery signals in success metrics.
- **Passive users may still miss commands**: A user must type `/` to see the dropdown. Mitigation: keep `/help` and documentation aligned with the same command metadata.
- **Empty-state friction**: A no-match state could feel noisy. Mitigation: keep it compact and never mutate or block raw input.

## Implementation Notes

- This ADR defines product scope, not implementation details.
- V1 acceptance should insert command text only and should not automatically submit no-argument commands.
- The fixed command set remains `/help`, `/goal`, `/goal clear`, `/config`, `/subtask`, `/agent:`, `/skill:`, and `/reload:skills`.
