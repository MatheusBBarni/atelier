# ADR-005: Skill correctness via lightweight Rust tests + an enum/TOML drift guard

## Status

Accepted

## Date

2026-06-15

## Context

The deliverable is Markdown (no executable skill code), yet correctness is binary: the config loader
uses `deny_unknown_fields`, so any documented key or enum value that is wrong makes a generated
config fail. The PRD targets ≥ 90% first-attempt validity and 0 unknown keys, and the schema must not
drift from `src/config/mod.rs`.

## Decision

Guard correctness with **fast, deterministic Rust tests** (no LLM in CI), in a new
`tests/atelier_config_skill.rs`:

1. **Discoverability** — the skills module loads `atelier-config-setup` from a discovery root with
   valid `{name, description}` frontmatter; canonical alias resolves to `atelier-config-setup`.
2. **Enum-coverage drift test** — every serde variant name of `RuntimeKind`, `ApprovalMode`,
   `AgentEffort`, `Capability`, `ToolName` appears in `references/config-schema.md`, with **no stray
   variant strings**; assert the documented `schema_version == 1`.
3. **TOML-block load test** — extract every ` ```toml ` fenced block from the skill (`SKILL.md` +
   `references/`, including the named presets) and assert each **loads via the config loader**
   (`RawConfig` parse / `load_effective_config`). This catches unknown keys and bad enum values.
4. **Mirror equality** (shared with ADR-004) — each discovery-dir mirror equals the canonical source.

A **manual eval checklist** (in the skill's docs) covers the interactive wizard behavior. A full
**LLM eval harness** is deferred; if added, it is env-gated and `#[ignore]`d like
`tests/runtime_integration.rs`.

## Alternatives Considered

### Alternative 1: Generate the schema reference from Rust types

- **Pros**: eliminates drift at the source.
- **Cons**: this is the larger `--emit-config-schema` work the PRD deferred to V2.
- **Why rejected**: out of V1 scope; the drift test gives most of the benefit cheaply.

### Alternative 2: LLM eval in CI

- **Pros**: highest fidelity to the 90% metric.
- **Cons**: slow, flaky, costly.
- **Why rejected**: not CI-friendly; deferred behind an ignore flag.

### Alternative 3: Discoverability test only

- **Pros**: minimal.
- **Cons**: misses schema/preset correctness — the core risk.
- **Why rejected**: too weak.

## Consequences

### Positive

- Deterministic CI guarantee that the skill's schema and every shipped preset are valid and in sync.

### Negative

- The TOML-extraction test couples to the fenced-block convention (documented in the skill).

### Risks

- The four enums lacking iteration need a small, localized change (add `strum::EnumIter` or an
  `all()`); `ToolName::all()` already exists. Free-form `String` fields (e.g. `model`) load
  regardless, so model strings are not asserted — the skill guides users to pick a real model.

## Implementation Notes

- Reuse the existing config loader and skills-discovery module; no new runtime code.
