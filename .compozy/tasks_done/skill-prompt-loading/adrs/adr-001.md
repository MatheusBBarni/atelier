# ADR-001: Scope Skill Prompt Loading V1

## Status

Accepted

## Date

2026-06-06

## Context

Atelier already recognizes `/skill:<name>` as a valid prompt prefix and offers
TUI completion for discovered skills, but the app currently submits the prompt
unchanged. This creates a mismatch between the composer affordance and runtime
behavior: users can select a skill, but the selected `SKILL.md` content is not
loaded into the model context.

The current TUI scans project and personal skill roots, including
`.agents/skills`, `.claude/skills`, `~/.agents/skills`, and `~/.claude/skills`.
That discovery path returns suggestion metadata for autocomplete. It is not a
complete app-level resolver for aliases, duplicate skill names, exact file
identity, ambiguity handling, prompt provenance, or validation evidence.

External agent tools now treat skills as reusable workflow units. Codex, Claude
Code, and Cursor all support explicit skill invocation, and the Agent Skills
standard recommends progressive disclosure: load skill metadata broadly, then
load full `SKILL.md` instructions only when activated. Security research also
shows that skill metadata and instructions are operational text, not passive
documentation, so V1 must avoid blind string injection.

The main constraints are:

- Harness Actions must remain the only execution boundary for file edits,
  shell commands, VCS actions, approvals, and cleanup.
- Runtime adapters should not learn `/skill:` syntax in V1.
- Skill loading must work for every submit path, not only the TUI.
- Missing, ambiguous, unreadable, or invalid skills must fail before runtime
  dispatch.
- V1 must not support shell expansion, dynamic commands, or skill-granted
  capabilities.

## Decision

Build V1 as an app-owned skill prompt loading pipeline.

V1 will:

- Parse multiple `/skill:<name>` references from a submitted prompt.
- Treat `/skill:<name>` references as valid anywhere in the submitted prompt,
  subject to a documented grammar that avoids accidental matches in literals
  where possible.
- Resolve aliases to canonical skill identities through a shared app-level
  resolver, not through the TUI suggestion cache.
- Prefer project skill roots over personal skill roots when the same skill name
  exists in both scopes.
- Dedupe repeated references by canonical skill identity while preserving the
  first-use order.
- Validate every resolved skill before a run is created.
- Fail closed with clear diagnostics for unknown, ambiguous, invalid,
  unreadable, or unsupported skill references.
- Compile the runtime prompt into explicit sections:
  - `System Prompt`
  - one ordered `Skill: <name>` section per resolved skill, including source
    and load-reason metadata
  - `User Prompt`
- Record selected skill name, canonical identity, source path or origin, and
  load reason in session history or diagnostics.
- Keep runtime adapters generic; they receive a composed prompt instead of
  interpreting `/skill:` syntax.
- Propagate compiled skill context into derived child prompts, council prompts,
  and subtasks so delegated work keeps the user's explicit workflow context.

Resolution and rendering must be separate internal concerns. The resolver owns
canonical identity, precedence, ambiguity, validation, and provenance. The
renderer owns the V1 text prompt shape. This keeps the door open for future
adapter-specific rendering if a runtime gains a first-class skill context.

## Alternatives Considered

### Alternative 1: Leave `/skill:` As A Raw Prompt Prefix

- **Description**: Keep current behavior where `/skill:<name>` is allowed and
  submitted unchanged.
- **Pros**: No implementation cost and no new trust surface.
- **Cons**: The UI implies a behavior that does not happen. Users must hope the
  model infers the intended skill, and missing skills never fail clearly.
- **Why rejected**: Explicit skill invocation is now a baseline expectation in
  agent CLIs. The current behavior is misleading and weakens correctness.

### Alternative 2: Runtime-Specific Skill Handling

- **Description**: Teach each runtime adapter to interpret `/skill:` and load
  skill context in the adapter.
- **Pros**: Could eventually exploit runtime-native skill APIs or role
  separation.
- **Cons**: Couples skill semantics to every runtime, duplicates parsing and
  validation, and risks inconsistent behavior across Codex, Claude, Cursor,
  Z.ai, and Fake runtimes.
- **Why rejected**: V1 needs deterministic shared behavior. Runtime-native
  rendering can be added later behind a normalized `SkillInvocation` contract.

### Alternative 3: Full Agent Skills Platform

- **Description**: Implement implicit skill matching, scripts, supporting
  resources, tool grants, dynamic context expansion, and runtime-specific skill
  capabilities.
- **Pros**: More complete parity with mature agent tools.
- **Cons**: Expands the execution surface and security model far beyond the
  requested bug/UX fix.
- **Why rejected**: V1 should solve explicit loading first. Scripts, dynamic
  resources, and implicit matching require separate trust, permission, and
  context-budget decisions.

## Consequences

### Positive

- Makes `/skill:<name>` deterministic and inspectable.
- Aligns TUI discovery with app behavior.
- Keeps skill loading consistent across all execution runtimes.
- Preserves the Harness Actions boundary.
- Creates a shared resolver that future TUI, CLI, and runtime rendering paths
  can reuse.

### Negative

- Adds prompt compilation complexity before run creation.
- Requires a precise grammar for skill references.
- Introduces new failure cases users will see before a run starts.
- Needs careful prompt framing so skill text cannot counterfeit provenance or
  section boundaries.

### Risks

- **Ambiguous identity**: Multiple roots can contain the same skill name.
  Mitigation: prefer project roots over personal roots, fail as ambiguous within
  the same precedence tier, and record the exact resolved source.
- **Prompt injection**: A skill can instruct the model to ignore Harness policy.
  Mitigation: frame skill content as loaded workflow guidance, keep Harness
  Actions as enforcement, and never let skill text grant capabilities.
- **Stale discovery**: TUI suggestions and app resolution may disagree.
  Mitigation: use a shared resolver contract and treat the cache as advisory.
- **Grammar surprises**: Literal text, code blocks, punctuation, or quoted
  `/skill:` strings may be parsed incorrectly. Mitigation: specify and test the
  reference grammar.
- **Future runtime capabilities**: Text-only rendering may become limiting.
  Mitigation: separate normalized resolution from V1 text rendering.

## Implementation Notes

- Prefer a new shared skill module over expanding TUI-only discovery helpers.
- Define canonical identity using enough provenance to distinguish roots and
  exact `SKILL.md` files.
- Treat aliases as resolver input, not prompt-rendering behavior.
- Apply skill resolution anywhere `/skill:<name>` appears in a submitted prompt,
  while documenting the escaping or literal-text behavior for examples that
  mention `/skill:` without intending invocation.
- Preserve user prompt text after removing or normalizing skill directives.
- Carry compiled skill context forward into child/council/subtask prompt
  construction.
- Do not execute shell substitutions or scripts from `SKILL.md` in V1.
- Add table-driven tests for parsing, aliases, duplicate handling, ambiguity,
  unreadable files, prompt framing, section delimiter escaping, and history
  metadata.
- Add regression coverage that slash-prefixed clarification answers such as
  `/tmp/project` are not treated as skill invocations.
