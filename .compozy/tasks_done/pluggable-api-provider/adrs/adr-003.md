# ADR-003: Extract Shared HTTP Utilities into http_util.rs

## Status

Accepted

## Date

2026-06-17

## Context

The codebase has 6 duplicated functions across `runtime/mod.rs` and `runtime/zai.rs`: `redact_bearer_tokens`, `redact_sensitive_text`, `redact_raw_secret_tokens`, `next_raw_secret_prefix`, `is_secret_token_character`, and `parse_runtime_output`. Additionally, `codex.rs` has its own private copy of `parse_runtime_output`. These duplications exist because each runtime module was developed independently, and security-relevant code (secret redaction) has silently diverged between copies.

As we generalize `ZaiRuntime` into a configurable `HttpApi` runtime, more providers will hit these code paths. Divergence in redaction logic is a secret-leak risk. The duplication must be consolidated before adding new providers.

## Decision

Extract all duplicated HTTP utility functions into a new `src/runtime/http_util.rs` module. The canonical copies of `redact_sensitive_text`, `redact_bearer_tokens`, `redact_raw_secret_tokens`, `next_raw_secret_prefix`, `is_secret_token_character`, and `parse_runtime_output` move to `http_util.rs`. All other modules (`mod.rs`, `codex.rs`, `http_api.rs`) import from `http_util`.

## Alternatives Considered

### Alternative 1: Keep in mod.rs, Import from super

- **Description**: Keep the canonical copy in `mod.rs` (it's already `pub(crate)`), have `codex.rs` and `http_api.rs` import via `super::`
- **Pros**: Minimal file changes; no new module to manage
- **Cons**: `mod.rs` is already large (~800 lines); mixing Runtime trait definition with HTTP utility functions muddies responsibilities; `parse_runtime_output` is not conceptually part of the Runtime trait
- **Why rejected**: Separation of concerns — `mod.rs` owns the Runtime trait and dispatch; `http_util.rs` owns HTTP-specific utilities.

### Alternative 2: Keep Duplicated, Add Comments

- **Description**: Leave copies in place, add comments noting the duplication
- **Pros**: Zero risk of regression
- **Cons**: Secret redaction divergence risk grows with each new provider; maintenance burden doubles with every change
- **Why rejected**: Unacceptable security risk — redaction code must have a single source of truth.

## Consequences

### Positive

- Single source of truth for secret redaction — prevents divergence
- `parse_runtime_output` is shared by all runtimes that produce JSON output (codex, http_api, and any future HTTP-based runtime)
- `mod.rs` becomes focused on the Runtime trait and dispatch logic
- Easier to add new redaction patterns (e.g., new provider key prefixes) in one place

### Negative

- New module to maintain (`http_util.rs`)
- Import paths change in `mod.rs`, `codex.rs`, and `http_api.rs`

### Risks

- **Refactor breaks existing behavior** — Mitigate with full test suite before merge; the functions are pure (no side effects) so the refactor is mechanical
- **Visibility mismatch** — `redact_sensitive_text` is `pub(crate)` in `mod.rs` but private in `zai.rs`; the shared copy must be `pub(crate)` to remain accessible from hooks modules

## Implementation Notes

1. Create `src/runtime/http_util.rs` with all 6 functions
2. Update `mod.rs` to re-export from `http_util` (preserves `pub(crate)` visibility for hooks)
3. Update `codex.rs` to import `parse_runtime_output` from `super::http_util`
4. Update `http_api.rs` (renamed from `zai.rs`) to import all utilities from `super::http_util`
5. Remove duplicated function definitions from `mod.rs`, `codex.rs`, and `http_api.rs`
6. Expand `SECRET_PREFIXES` from `["sk-", "zai-"]` to `["sk-", "zai-", "or-", "ov-"]`
