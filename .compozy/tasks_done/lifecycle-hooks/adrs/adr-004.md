# ADR-004: Handler-array config schema and a normalized, versioned cross-runtime payload contract

## Status

Accepted

## Date

2026-06-15

## Context

Hooks need to support **multiple actions on the same event** (e.g. notify *and* append-to-audit on `run_completed`). The payload must be **uniform across runtimes** (PRD) and **decoupled from the internal event taxonomy** — atelier's ~50 stringly-typed `kind` values with free-form payloads (`src/history/mod.rs`) must stay refactorable, so hooks cannot pin internal kinds directly (the architect's concern, ADR-001). `atelier --events follow` must emit the *same* shape a hook receives, to serve as a faithful dry-run harness.

## Decision

**Config schema — handler array.** Hooks are a flat array of handlers:

```toml
[[hooks.handler]]
on = "run_completed"            # a public event name, or a list
notify = true                   # built-in notifier (ADR-005)

[[hooks.handler]]
on = ["run_completed", "run_failed"]
command = "cat >> ~/atelier-audit.jsonl"
```

Each handler declares `on` (one public event name or a list; exact match — glob/regex deferred) and exactly one action: `notify` (built-in) or `command` (shell). `payload = "metadata" | "full"` is per-handler, defaulting to `metadata`.

**Public event vocabulary.** A curated, stable set of public names maps to internal kinds, decoupling the contract from internals:

| Public name | Internal kind |
|---|---|
| `run_started` | `run_started` |
| `step_started` | `agent_step_started` |
| `action_requested` | `action_requested` |
| `approval_required` | `approval_requested` |
| `clarification_required` | `clarification_requested` |
| `file_edited` | `file_edit_applied` |
| `run_completed` | `run_completed` |
| `run_failed` | `run_failed` |
| `run_limit_reached` | `run_limit_reached` |
| `run_interrupted` | `run_interrupted` |

Events outside the vocabulary (incl. `hook_started`/`hook_completed`, `runtime_stream_delta`) never trigger hooks.

**Normalized payload.** A versioned struct, atelier's own stable JSON — standards-aligned in spirit (who/what/when/outcome + correlation) but not bound to an evolving upstream spec: `schema_version`, `event` (public name), `time` (RFC3339), `session_id`, `run_id`, `step_id`, `actor { agent, runtime }`, optional `target`, optional `outcome`. A single pure `normalize(event, actor_ctx) -> HookPayload` is shared by the live tap and the `--events follow` reader (which reconstructs `actor_ctx` by folding the session's own run/step events). Payload is **metadata-only by default**; opt-in `full` includes bodies; `redact_sensitive_text` (`src/runtime/mod.rs:704`) runs before any payload reaches stdin.

## Alternatives Considered

### Alternative 1: Per-event single table (`[hooks.run_completed]`)
- **Description**: One config block per event.
- **Pros**: Simplest; matches the original `[hooks.<event>]` phrasing.
- **Cons**: One action per event — cannot notify *and* audit the same event.
- **Why rejected**: Fails the core multi-action requirement.

### Alternative 2: Expose raw internal event kinds
- **Description**: Let `on` reference internal `kind` strings directly.
- **Pros**: No mapping layer.
- **Cons**: Pins ~50 internal kinds + free-form payloads as a public API; every refactor risks breaking user hooks.
- **Why rejected**: Calcifies internal plumbing into a contract (ADR-001 architect concern).

### Alternative 3: Full OpenTelemetry GenAI / CloudEvents conformance
- **Description**: Emit `gen_ai.*` + CloudEvents field names for zero-mapping SIEM ingestion.
- **Pros**: Drops into observability pipelines with no mapping.
- **Cons**: Heavier; tracks a spec still marked "Development, names may change."
- **Why rejected**: Deferred in the PRD (pragmatic stable schema chosen); revisit for the V3 integration hub.

## Consequences

### Positive
- N handlers per event; drop-in-familiar shape.
- Public contract is refactor-safe; internal kinds stay free to evolve.
- One `normalize()` makes `--events follow` a faithful preview of hook stdin.
- Designed decision-first: the V2 veto adds a *return* field, not a payload redesign.

### Negative
- A mapping + normalization layer to maintain.
- The follow-path actor reconstruction is best-effort for events emitted before the agent is known in-stream (actor `null`/orchestrator).

### Risks
- **Secret leakage** via `full` payload or audit egress → metadata default, stdin-only (no argv interpolation), hardened redaction, documented leak path.
- **Public-vocabulary drift** → start minimal; additions are deliberate, versioned changes.

## Implementation Notes

`HookHandler` / `HooksConfig` join the config ladder via `RawConfig.hooks` and `apply_raw` (`src/config/mod.rs:909`); the **Local (`./atelier.toml`) layer's hooks are dropped** (ADR-001 security posture) by skipping `raw.hooks` when the source is the project layer (`src/config/mod.rs:1680`). The `normalize` function and `HookPayload` live in a new `src/hooks/` module.
