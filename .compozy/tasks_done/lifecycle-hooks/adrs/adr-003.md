# ADR-003: Off-funnel hook dispatch with enrich-at-tap actor resolution

## Status

Accepted

## Date

2026-06-15

## Context

`record_event_with_group` (`src/app/mod.rs:4215`) is the single, synchronous write path for every event. It runs on the app-worker thread (`run_app_worker`, `src/tui/mod.rs:957`) and fires for *every* event, including each `runtime_stream_delta` token. Codebase verification surfaced two constraints:

1. **Runtime + agent identity is not in scope at the call sites.** `ActiveStep` (`src/app/mod.rs:372`) holds only the agent **id** (a `String`), not the `AgentProfile` or `RuntimeKind`. The uniform cross-runtime *actor* field the payload contract requires (ADR-001) must therefore be resolved, not read directly.
2. **The path is synchronous and on the hot thread.** Any blocking work (a subprocess spawn, an `.await`) at the write site would stall the worker/render loop — and at per-token frequency it would be catastrophic.

## Decision

Dispatch happens **off the event funnel**, with the payload **enriched at the tap**:

- Immediately after the durable `append_event` inside `record_event_with_group`, and only when hooks are configured, the app **maps the internal event kind to a public event name** (ADR-004) and, if a configured handler matches, **resolves the actor** cheaply via `self.active_step.agent → self.agent(id) → profile.runtime`. It builds the normalized `HookPayload` and `try_send`s it onto a **bounded `mpsc` channel** (`App` gains a `hook_sender: Option<mpsc::Sender<HookPayload>>` field, set at construction). `try_send` is non-blocking: when the queue is full it **drops** and increments a counter surfaced in `--doctor`.
- A **long-lived dispatcher task** (spawned in `run_tui` alongside `run_app_worker`) drains the channel and executes each matched handler as a subprocess, reusing the established idiom (`tokio::process::Command` + `kill_on_drop(true)` + `select!` timeout; payload written to stdin — `src/app/git.rs:72`, `src/runtime/claude.rs:174`). The dispatcher holds no `&App`.
- Each execution is recorded back as `hook_started` / `hook_completed` events (for transcript transparency, ADR-004). These are **not in the public event vocabulary**, so they can never re-trigger hooks — recursion is prevented structurally.

## Alternatives Considered

### Alternative 1: Inline subprocess spawn at the write site
- **Description**: Spawn the hook process directly inside `record_event_with_group`.
- **Pros**: No channel; simplest control flow.
- **Cons**: Fork/exec on the hot worker thread per event — including per stream-delta token; blocks rendering.
- **Why rejected**: A non-starter at the funnel's frequency.

### Alternative 2: Thread `AgentProfile` through all record sites
- **Description**: Add an actor parameter to `record_event_with_group` and its ~100 call sites.
- **Pros**: Actor available without a lookup.
- **Cons**: Large, invasive, breaking change touching every call site.
- **Why rejected**: The enrich-at-tap lookup is cheap and local; threading is disproportionate.

### Alternative 3: Dispatcher resolves actor itself (holds config/`&App`)
- **Description**: Send the raw event; let the off-thread task resolve actor.
- **Pros**: Tap does less.
- **Cons**: The dispatcher would need `App`/`active_step`, which is only authoritative on the worker thread; couples the task to app state.
- **Why rejected**: `active_step` is the authoritative actor source and lives on the worker; resolving at the tap keeps the task app-free.

## Consequences

### Positive
- The write path never blocks; per-event cost is one map + one lookup, gated behind an "any hooks configured" check (zero cost when none).
- The dispatcher is self-contained (no `&App`), easy to test in isolation.
- Recursion and replay double-fire are closed structurally (hook events excluded from the public vocabulary; dispatch only on live tap, never on projection replay).

### Negative
- Delivery is **best-effort** under burst (drop-on-full), not guaranteed — acceptable for observer hooks, and the drop count is observable in `--doctor`.
- Adds a channel, a task, and one `App` field.

### Risks
- **Queue saturation** under a storm of events → bounded channel + drop + visible counter; tune capacity in testing.
- **Lookup correctness** when `active_step` is absent (pre-agent events) → actor is `null`/orchestrator for those events (ADR-004).

## Implementation Notes

Tap insertion point: `src/app/mod.rs:4232` (immediately after `append_event`). Dispatcher spawn: `run_tui` (`src/tui/mod.rs`), mirroring `spawn_parallel_runtime_task` (`src/app/mod.rs:5803`). Per-hook execution mirrors `run_git` (`src/app/git.rs:72`).
