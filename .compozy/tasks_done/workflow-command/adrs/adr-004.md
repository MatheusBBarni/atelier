# ADR-004: Workflow Events Carry Workflow-Specific Completion Status

## Status

Accepted

## Date

2026-06-07

## Context

The PRD requires `/workflow <prompt>` to preserve the user-visible command, execute through a workflow-specific prompt envelope, record `workflow_started`, and distinguish completed-with-issues from plain success. The current app state model has `RunState::Completed` and `RunState::Failed`, but no `CompletedWithIssues`. Chat projection currently renders `run_completed` as success and `parallel_group_joined` with `completed_with_issues` as warning.

Adding a new app-level run state would affect the TUI, history interpretation, tests, and any code that treats completion as terminal success. The workflow-specific status is important, but it does not need to become a global run state in V1.

## Decision

Workflow mode will preserve the original `/workflow <prompt>` text in `prompt_submitted`, pass a workflow-specific prompt envelope to the Orchestrator runtime path, and emit dedicated `workflow_started` and `workflow_completed` history events. `workflow_completed.status` will carry `completed`, `completed_with_issues`, or `failed`.

`completed_with_issues` will keep `RunState::Completed` so the existing run lifecycle stays stable. Chat projection will render `workflow_completed.status = completed_with_issues` as a warning and show unfinished targets, skipped checks, verification evidence, and residual risks.

## Alternatives Considered

### Alternative 1: Store Only the Transformed Prompt

- **Description**: Store the workflow prompt envelope as the user prompt in history.
- **Pros**: Simplifies runtime and history consistency.
- **Cons**: Hides the exact user command and makes history harder to read.
- **Why rejected**: The user-visible command should remain auditable.

### Alternative 2: Add `RunState::CompletedWithIssues`

- **Description**: Add a first-class run state for workflows with unfinished targets.
- **Pros**: Makes the app state directly reflect warning completion.
- **Cons**: Broadens the state machine and affects unrelated run consumers.
- **Why rejected**: V1 can carry workflow-specific status in `workflow_completed` without a global state-machine change.

### Alternative 3: Use Only `run_completed`

- **Description**: Add workflow fields to `run_completed` and make ChatProjection payload-aware.
- **Pros**: Avoids another event kind.
- **Cons**: Mixes generic run lifecycle with workflow-specific evidence and risks success styling regressions.
- **Why rejected**: A dedicated event keeps workflow evidence explicit and easier to project.

## Consequences

### Positive

- History remains readable because the original command is preserved.
- Runtime behavior can be workflow-specific without changing global Orchestrator defaults.
- Workflow completion can show warning status without changing `RunState`.
- Chat projection can render workflow evidence explicitly.

### Negative

- The app records both generic run completion and workflow completion evidence.
- Consumers need to understand `workflow_completed` for workflow-specific status.

### Risks

- Duplicated terminal events can confuse users if Chat renders both with equal prominence. Mitigate by making `workflow_completed` the evidence-rich workflow summary and keeping generic `run_completed` compact.
- The runtime prompt envelope must not leak into the user-visible prompt item.

## Implementation Notes

- Add `handle_workflow_command` before unknown slash-command rejection.
- Preflight Parallel Step Groups before `run_started`; do not record workflow history on prerequisite failure.
- Record `workflow_started` after `run_started` and before or near `prompt_submitted`.
- Store the original command text and extracted workflow prompt in `workflow_started`.
- Add ChatProjection handling for `workflow_started` and `workflow_completed`.
