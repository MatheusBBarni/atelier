# ADR-002: Evidence-First Executing Workflow Approach

## Status

Accepted

## Date

2026-06-06

## Context

The PRD needs a product approach for `/workflow <prompt>`. The idea phase established that the feature must execute work, not only plan it, while remaining inside one normal Run. Clarification confirmed the primary V1 outcome is trustworthy completion, the main journey is broad implementation or refactor work, existing user controls are enough for V1, and unfinished planned file-edit targets should produce a completed-with-issues result when each unfinished target is explicitly accounted for.

## Decision

Use an evidence-first executing workflow approach for V1. `/workflow <prompt>` starts one workflow-mode Run that decomposes broad implementation or refactor work, executes scoped Specialized Agent steps, validates outcomes, and returns one consolidated answer with plan evidence, child outcomes, completed targets, unfinished targets, skipped checks, and remaining risks.

## Alternatives Considered

### Alternative 1: Plan-Gated Workflow

- **Description**: Require the user to approve the Run Plan before execution starts.
- **Pros**: Gives the user more control before any work begins and can reduce surprise.
- **Cons**: Adds friction to the main workflow and turns a broad execution command into a multi-step approval ritual.
- **Why rejected**: Existing Action Approval, Clarifying Questions, and run interrupt are enough for V1. The product should first prove trustworthy completion without adding plan approval ceremony.

### Alternative 2: Investigation-First Workflow

- **Description**: Limit V1 to read-heavy codebase investigation, audit, or review workflows.
- **Pros**: Lower risk and easier to explain.
- **Cons**: Misses the user's explicit requirement that `/workflow` execute implementation or refactor work.
- **Why rejected**: The chosen V1 journey is broad implementation/refactor work, with evidence and completion accounting to preserve trust.

## Consequences

### Positive

- Matches the user-selected V1 outcome of trustworthy completion.
- Keeps the feature differentiated from ordinary prompts by executing decomposed work and exposing evidence.
- Preserves existing user control surfaces instead of adding a new approval flow.
- Gives the PRD a concrete main journey for broad implementation and refactor work.

### Negative

- Workflow runs may consume more time and runtime work than normal prompts.
- Users who want mandatory plan approval must wait for a later phase.
- Completion semantics for planned file-edit targets need careful definition in the TechSpec.

### Risks

- A completed-with-issues result could feel like success even when important targets are unfinished. Mitigate with prominent unfinished-target status and reasons.
- Users may expect workflow mode to work without Parallel Step Groups enabled. Mitigate with a clear failure message.
- Evidence may be too verbose if every child detail is surfaced equally. Mitigate by prioritizing plan, target status, verification, and residual risk.

## Implementation Notes

- Record `workflow_started` so workflow-mode Runs are distinguishable in Session History.
- Use completed-with-issues when unfinished planned file-edit targets are explicitly marked skipped, blocked, or failed.
- Keep existing Action Approval, Clarifying Questions, and run interrupt as the only V1 user-control surfaces.
- Define precise target accounting and final-summary evidence requirements in the TechSpec.
