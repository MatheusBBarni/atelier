# ADR-003: App-Owned Workflow Target Ledger

## Status

Accepted

## Date

2026-06-07

## Context

The PRD requires workflow completion to account for every planned file-edit target as completed, skipped, blocked, or failed. The existing parallel execution model already requires edit-capable parallel children to declare exact `ParallelFileScope.write_files`, and the app owns Parallel Step Group execution, Harness Actions, approvals, history, and joined results.

Relying only on `changed_files` would undercount targets because it records what happened after an action, not what the workflow promised to address. Relying only on the Orchestrator final summary would make completion evidence prompt-dependent and harder to verify.

## Decision

Workflow mode will add an app-owned `WorkflowRunContext` to the active run driver. The context will maintain a workflow target ledger derived from `ParallelChildStepPlan.file_scope.write_files` when a Parallel Step Group starts. The app will update target status as child results and joined group results arrive, then use the ledger to produce the terminal `workflow_completed` event.

Read-only parallel children with empty `write_files` do not create file-edit targets.

## Alternatives Considered

### Alternative 1: Orchestrator-Only Target Summary

- **Description**: Require the Orchestrator final summary to describe completed and unfinished targets.
- **Pros**: Minimal app changes and no new app state.
- **Cons**: Makes completion accounting prompt-dependent and hard to validate.
- **Why rejected**: The product goal is trustworthy completion, which needs app-owned evidence.

### Alternative 2: Extend Only `ParallelGroupResult`

- **Description**: Add target accounting only to joined group results and avoid run-level workflow state.
- **Pros**: Keeps accounting close to the existing group join boundary.
- **Cons**: Cannot easily summarize targets across multiple groups or later sequential follow-up steps.
- **Why rejected**: Workflow completion is run-level evidence, not only group-level evidence.

## Consequences

### Positive

- Planned targets come from declared scopes rather than post-hoc changed files.
- Completion evidence survives prompt quality variation.
- The final workflow summary can distinguish completed, skipped, blocked, and failed targets.

### Negative

- Adds a small run-level state structure.
- Requires careful mapping from child results to target outcomes.
- Requires explicit handling for read-only children and no-change outcomes.

### Risks

- Target status can drift if a child edits a file outside the declared scope. Existing Harness Action enforcement mitigates this.
- A no-change result can be ambiguous. The TechSpec must define when `NoChanges` counts as completed versus skipped.

## Implementation Notes

- Add `WorkflowRunContext` and `WorkflowTarget` near `RunDriveContext` in `src/app/mod.rs`.
- Derive planned targets from `ParallelChildStepPlan.file_scope.write_files`.
- Key targets by normalized path and source step identity.
- Update targets after child terminal results are recorded.
- Do not count read-only reviewer scopes as file-edit targets.
