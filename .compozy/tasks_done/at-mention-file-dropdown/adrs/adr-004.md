# ADR-004: Fuzzy Matching via nucleo-matcher with a Ranking Blend

## Status

Accepted

## Date

2026-06-12

## Context

ADR-001 chose `nucleo` for fuzzy matching. nucleo ships in two layers: the
high-level `nucleo` worker (its own thread pool, streaming, for very large
live-updating lists) and the low-level `nucleo-matcher` (a one-shot `Matcher` +
`Pattern` that also returns matched-character indices). The `@` dropdown filters
an already-in-memory, capped candidate list per keystroke — no streaming or
worker thread pool is needed.

## Decision

Use **`nucleo-matcher`** (the matcher-only crate) for one-shot fuzzy scoring of
the cached file list on each keystroke. Rank as:

- **Empty query** (bare `@`): most-recently-modified first, then shallower path,
  then alphabetical.
- **Non-empty query**: nucleo score descending, tie-broken by shallower path,
  then most-recently-modified, then alphabetical.

Show up to `DROPDOWN_MAX_ITEMS` (6) rows. The matcher's matched-character indices
drive highlighting. A non-empty query with zero matches renders the "No matching
files" row.

## Alternatives Considered

### Alternative 1: Full `nucleo` worker

- **Description**: Use the high-level streaming matcher with its thread pool.
- **Pros**: Built for massive, live-updating candidate streams.
- **Cons**: Overkill for a 6-row, capped, in-memory popup; more surface and
  lifecycle.
- **Why rejected**: The matcher-only crate fits the synchronous per-keystroke
  model exactly.

### Alternative 2: Substring matching (`.contains`)

- **Description**: The council's leaner option — case-insensitive substring, as
  the existing `/agent:`/`/skill:` dropdowns use.
- **Pros**: Zero new matcher dependency.
- **Cons**: Cannot match non-contiguous abbreviations (`@rcm` →
  `src/runtime/claude.rs`).
- **Why rejected**: The product owner chose true fuzzy in V1 (ADR-001).

### Alternative 3: `fuzzy-matcher` / skim

- **Description**: The older fuzzy crate.
- **Pros**: Established.
- **Cons**: Slower, ASCII-only bonus system; superseded by nucleo.
- **Why rejected**: nucleo is the current best practice.

## Consequences

### Positive

- fzf-grade matching plus highlight offsets with minimal surface.
- Synchronous; fits the per-keystroke in-memory filtering model.

### Negative

- Adds the `nucleo-matcher` dependency.
- The ranking blend (weights of score vs. depth vs. recency) needs tuning — a
  known open item.

## Implementation Notes

- Reuse a single `Matcher` instance across keystrokes.
- If the candidate list is very large, apply a cheap prefilter before scoring.
- Keep matching behind a `FileIndex::query` method so the scorer can be swapped.
