# ADR-003: Enforce floor + trust at the single enforcement point via a structured risk assessment

## Status

Accepted

## Date

2026-06-15

## Context

The PRD requires a catastrophic floor (always-prompt, even in `Yolo`), a gray-area floor (warn-only by default, opt-in enforce), a rich decision-support modal (tier, reason, resolved command, diff, boundary crossed), and exact-target session trust. The existing architecture has a **single enforcement point**, `validate_action_request_with_scope` (`src/actions/mod.rs`), called inside the free function `execute_action_request`; it returns `ActionDecision { Allowed | RequiresApproval(String) | Denied(String) }`. `decision_for_command` already classifies commands into three tiers via `classify_command` → `CommandClassification { Allow | Approve | Deny }`. The TUI renders purely from an `AppState` snapshot and cannot read the filesystem, so any data the modal shows must be precomputed app-side.

We must decide where the floor and trust list are applied and how the tier/target/reason reach the modal, without creating a second enforcement site or coupling the pure actions layer to mutable session state in an unprincipled way.

## Decision

Keep gating in the single enforcement point and enrich its inputs and outputs.

- Add a pure `assess_risk(request, context) -> RiskNote` in `src/actions/mod.rs` that computes `tier` (Low/Medium/High), a `catastrophic` flag, a one-line `reason`, and the `target` (the trust key, or `None` when catastrophic). Command classification normalizes `~`/`~user` and `$HOME`/`${HOME}`/`$PWD` before matching the catastrophic set; command substitution/pipes/redirects continue to be handled by the existing `has_shell_control_syntax` (they never reach the `Allow` tier).
- Extend `ActionExecutionContext` with `floor: FloorPolicy` (`Warn | Enforce`, gray-area posture) and `trusted_targets: Arc<TrustSet>` (a per-action snapshot of the session trust list).
- Enrich `ActionDecision` to carry structured outcomes: `Allowed`, `AllowedByTrust(TrustTarget)`, `AllowedWithWarning(RiskNote)`, `RequiresApproval(RiskNote)` (was `String`), `Denied(String)` (unchanged). `validate_action_request_with_scope` keeps its existing hard checks (schema/tool/capability/path/VCS → `Denied`) and then applies: catastrophic → `RequiresApproval` (ignores mode); trusted non-catastrophic → `AllowedByTrust`; gray-area → `RequiresApproval` in `Normal`/`Enforce`, `AllowedWithWarning` in `Yolo`+`Warn`; safe tier → `Allowed`.
- `execute_action_request` stamps the outcome onto `ActionResult` (new `risk: Option<RiskNote>` + `gate_outcome: GateOutcome`) so the App records the correct events (`approval_requested`, `approval_auto_resolved`, `floor_warned`) and builds the rich modal.

No new package or directory: the assessment lives beside the existing classifier in `src/actions/mod.rs`; the App owns trust state and event recording.

## Alternatives Considered

### Alternative 1: App-level gate wrapper

- **Description**: Keep `src/actions` pure/unchanged; the App computes the gate before calling `execute_action_request`.
- **Pros**: Actions layer stays free of trust/floor state.
- **Cons**: Creates a second enforcement site beside `validate_action_request`, so the "single enforcement point" invariant is lost and the two can drift.
- **Why rejected**: The invariant is load-bearing for safety; one place to get the catastrophic override right is safer.

### Alternative 2: Hybrid (pure assessor + context floor, App owns trust)

- **Description**: Split — assessor in actions, catastrophic override via context, trust matching in the App.
- **Pros**: Keeps trust state fully in the App.
- **Cons**: Gating logic spread across two layers; easy to apply the catastrophic override inconsistently with trust matching.
- **Why rejected**: Cohesion — all gate logic in one function is easier to reason about and test.

### Alternative 3: Literal / tilde-only classification (no env expansion)

- **Description**: Match the literal or tilde-only command string.
- **Pros**: Simplest.
- **Cons**: Misses `$HOME`-disguised home deletion, which under `Yolo`+`Warn` would run silently.
- **Why rejected**: The `rm -rf ~`/`$HOME` class is the canonical incident; conservative env expansion closes it with false positives that merely re-prompt.

## Consequences

### Positive

- One source of truth for gating; the modal's tier/reason/target come straight from the decision.
- The floor's catastrophic override and the trust short-circuit are decided in the same place, so they can't disagree.
- Reuses the existing classifier and `has_shell_control_syntax`; the net new surface is small.

### Negative

- `ActionDecision`, `ActionResult`, and `ActionExecutionContext` gain fields; `ActionResult` is serialized into the event log, so the additions need `#[serde(default)]` for back-compat.
- The pure validation function now receives a trust snapshot (still pure — passed in, not read from global state).

### Risks

- The enforcement function grows. *Mitigation*: extract `assess_risk` and a `match_trust` helper so `validate_action_request_with_scope` stays a thin dispatcher.
- Catastrophic-set completeness is safety-critical (an escape runs under `Yolo`+`Warn`). *Mitigation*: keep the set small/high-precision and cover it with table-driven + adversarial-variant tests (tilde/`$HOME`/quoting/spacing).

## Implementation Notes

`FloorPolicy` comes from a new `[approval] floor = "warn" | "enforce"` config (default `warn`); the catastrophic core is not configurable off. `approval_mode` (`Yolo`/`Normal`) is unchanged; `floor` only changes how `Yolo` handles the gray-area tier. The enforcement matrix: Allow→run; Catastrophic→prompt (any mode); Gray-area→prompt in `Normal`/`Enforce`, warn-and-run in `Yolo`+`Warn`; Trusted non-catastrophic→run (auto-approved, logged).
