# ADR-002: Phased floor rollout with a non-bypassable catastrophic core

## Status

Accepted

## Date

2026-06-14

## Context

ADR-001 set the V1 scope: a fail-closed destructive floor, a rich decision-support modal, and a minimal exact-target session-trust entry. The remaining product decision is the **rollout and enforcement posture** for the floor, where two well-supported forces pull against each other:

- **The council position:** the floor's entire value is that it protects users *even in `Yolo`* (the default) — that is the only mechanism delivering "fewer risky auto-approvals" to the majority. Claude Code's precedent of circuit-breaking `rm -rf /` even in bypass mode supports enforcing catastrophic actions regardless of mode.
- **The rollout norm:** silently changing the behavior of an auto-approve mode invites backlash (e.g., the copilot-cli silent breaking change). The canonical safe path is opt-in/preview → warn-only/audit → default-on with a loud changelog and first-run notice, with conservative, configurable defaults.

Three clarifying decisions were also made during brainstorming: trust is inspected/revoked via a `/trust` command plus inline chat feedback; the changed behavior is introduced with a one-time first-run notice (reusing the ADR-004 latch) plus an updated Approvals help tab; and a denial is **deny-and-continue** (the agent receives a structured reason and may try a narrower path), with no automatic runaway backstop in V1.

## Decision

Adopt a **two-tier floor** for V1:

1. **Catastrophic core — enforce immediately, even in `Yolo`, non-bypassable.** A small, high-precision set of clearly irreversible or cross-boundary actions (`rm -rf /` & `~`, `git push --force`, secret-file exfiltration, `curl|bash` and other fetch-and-run) always raises the approval modal, in every mode, with no config escape hatch. Classification runs on the post-shell-expansion string.
2. **Gray-area floor — warn-only/audit by default in V1.** The broader "auto-run only the provably-safe; everything unknown re-prompts" logic ships in **warn-only** mode by default: in `Yolo` it surfaces the risk and records a "would have blocked" chat annotation but does not block. A config setting (`floor = "enforce"`) lets users opt into blocking now; a later release flips the default to `enforce`.

The **rich decision-support modal**, the **`/trust` list-and-revoke command** with inline trust feedback, and **deny-and-continue** are all active in V1. A **first-run notice** plus the **Approvals help tab** introduce the changed behavior.

## Alternatives Considered

### Alternative 1: Full enforce from V1

- **Description**: Both the catastrophic core and the gray-area floor block by default in `Yolo` from day one.
- **Pros**: Delivers the complete "fewer risky auto-approvals" benefit to 100% of users immediately; ships the product the council described in one step.
- **Cons**: Changes `Yolo` behavior on day one — effectively a breaking change to an "I turned safety off" mode — with backlash risk if false positives are high; demands a strong provably-safe allowlist and high classifier confidence out of the gate, before any field calibration.
- **Why rejected**: Too risky to change a default-mode behavior without a calibration phase; the phased path reaches the same destination with far less workflow disruption.

### Alternative 2: Opt-in preview (all flags default off)

- **Description**: The entire feature (floor, modal, trust) ships behind config flags that default to off; the default flips in a later release.
- **Pros**: Lowest risk; cleanest beta; zero surprise for any user.
- **Cons**: Almost no one experiences it by default, so the safety benefit reaches ~nobody and validation is slow — the "empty room" problem the idea already flagged.
- **Why rejected**: Defeats the core goal of protecting the default (`Yolo`) user; provides no day-one safety value.

## Consequences

### Positive

- 100% of users get **day-one catastrophic protection**, even on the `Yolo` default.
- The gray-area floor is **calibrated against real false positives** before it ever blocks, so the eventual enforce-by-default lands with confidence.
- No silent breaking change: the behavior shift is announced via first-run notice + changelog, with an opt-in to enforce early and a documented escape hatch.
- The complete `Normal`-mode experience (modal, `/trust`, deny-and-continue) ships in V1, validating the differentiated parts immediately.

### Negative

- Gray-area auto-approvals still happen by default in `Yolo` until Phase 2, so the "fewer risky auto-approvals" outcome is only **partially** realized for the gray-area set in V1.
- Two-tier behavior (always-enforce core vs. warn-only gray area) is more to explain to users.
- A second rollout event (the Phase 2 default-flip to `enforce`) must itself be announced.

### Risks

- **Defining the catastrophic core precisely** — it must stay small and high-precision (post-expansion, low false-positive) so the non-bypassable tier never blocks legitimate work. *Mitigation*: start with the canonical irreversible/cross-boundary set; everything uncertain goes to the gray-area (warn-only) tier, not the core.
- **Warn-only annotations going unnoticed** — if the "would have blocked" signal is invisible, no one opts into enforce and Phase 2 lands blind. *Mitigation*: make the annotation a clearly styled chat item and surface a per-session count.
- **Phase-2 default-flip backlash** — flipping gray-area to enforce is itself a default change. *Mitigation*: announce with changelog + first-run notice + the already-shipped escape hatch.

## Implementation Notes

Build on `classify_command()` / `is_vcs_mutation()`; the catastrophic core is a high-precision subset evaluated even under `ApprovalMode::Yolo`. Warn-only emits an audit event + chat annotation rather than pausing. A `[approval]`-style config controls the gray-area tier (`warn` default, `enforce` opt-in); the catastrophic core is not configurable off. The `/trust` command and deny-and-continue (structured denial reason returned to the orchestrator) are V1. Detailed mechanism belongs in the TechSpec.
