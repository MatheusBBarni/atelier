# ADR-001: V1 scope — fail-closed destructive floor, decision-support modal, and minimal floor-anchored session trust

## Status

Accepted

## Date

2026-06-14

## Context

`atelier` gates write/command actions only in `Normal` mode, as a **binary** approve/deny prompt over a one-line summary (`PendingApprovalView` → `ApprovalHandle::answer(bool)`). The only escape from repeated prompts is `Yolo` mode, which auto-approves everything — and `Yolo` is the **default**. The user's framing is that approval fatigue pushes people to `Yolo`; their explicit success signals are **faster, confident decisions** and **fewer risky auto-approvals** (not "fewer prompts," and *not* changing the `Yolo` default).

Market research validates the problem as a *security* issue: Anthropic reports ~93% of permission prompts are approved (habituation), so the value of the gate is the ~7% that should be "no." A real incident (`rm -rf ~` firing because `~` expanded unquoted) shows classification must run on the post-shell-expansion string. Competitors converged on allowlist + denylist + sandbox/classifier + a Yolo escape; Claude Code circuit-breaks `rm -rf /` even in bypass mode.

A five-advisor council (pragmatic-engineer, security-advocate, product-mind, devils-advocate, the-thinker) debated scope. Two positions moved materially: pragmatic-engineer went from "cut the trust list" to "accept a minimal trust scope anchored to the floor stop," and security-advocate withdrew the "denylist theater" charge once the floor was reframed as **fail-closed**.

## Decision

Ship V1 as three layers, sequenced floor → modal → trust:

1. **Fail-closed destructive floor (the core).** Reuse/extend the existing 3-tier `classify_command()` so only *provably safe* actions auto-run; anything not proven safe re-prompts (`unknown → Approve`, never silent-allow). A hard, **non-bypassable** core set re-prompts **even in `Yolo`**: `rm -rf /` & `~`, `git push --force`, `sudo`, `chmod -R 777`, `curl|bash` and other fetch-and-run, writes/reads crossing the configured write/read roots, and secret-file reads. Classify on the **post-shell-expansion** string at execution time. Floor items are never trustable and never auto-cleared from a parallel queue.

2. **Rich decision-support modal.** Surface the resolved/expanded command, a diff for `ApplyPatch`/`WriteFile`, affected paths relative to write-roots, which capability/root is being crossed, a one-line risk rationale, and a risk tier (green/yellow/red derived from the classifier). The red tier must break muscle memory: Enter does not default to approve, and "approve" never shares a keystroke with "approve-and-trust."

3. **Minimal, floor-anchored session trust.** Exactly one scope — "trust this **exact resolved target** for the rest of this session" — offered at the approval/floor stop. In-memory only (dies with the process), revocable via a list-and-revoke panel, never written to disk. No wildcards, patterns, action-types, or per-agent trust. Every trust grant and every auto-approval it produces is recorded as an event and projected to chat.

The north star is reframed from raw speed to **decision quality on the dangerous tail** (catch rate on genuinely risky actions; absence of later regret), with speed/confidence as guardrails, not goals.

## Alternatives Considered

### Alternative 1: Full multi-granularity trust list (once / exact / pattern / action-type), keyed to `(agent, action-class, root)`, as the headline

- **Description**: The original idea — a rich trust list with several scopes the user picks per approval, keyed by agent identity.
- **Pros**: Most flexible; strongest differentiation vs. competitors; fewest repeat prompts.
- **Cons**: action-type/pattern trust is "scoped invisible Yolo"; per-agent trust rests on agent identity, which is hijackable via prompt injection; the broadest rung has the largest blast radius and the UI's gravity pulls tired users toward it; serves the de-prioritized "fewer prompts" goal.
- **Why rejected**: Footgun-heavy and works against success signal #2 (fewer *risky* approvals). Richer keying deferred to V2 with an explicit prompt-injection caveat.

### Alternative 2: Denylist-based floor (enumerate destructive commands)

- **Description**: Maintain a list of dangerous command patterns that always re-prompt.
- **Pros**: Simple; matches the existing Deny list.
- **Cons**: Denylists fail *open*; shell evasions are infinite (`find -delete`, `dd`, `git clean -fdx`, `> file`, `python -c`, `base64|sh`); a leaky guard manufactures false comfort that keeps users in Yolo until the missed spelling burns them.
- **Why rejected**: Replaced by a **fail-closed** shape (auto-run only the provably-safe set; unknown re-prompts), which makes an honest safety claim instead of "we block `rm`."

### Alternative 3: Reversibility-first (snapshot + undo) instead of a floor

- **Description**: Don't gate reversible work; auto-checkpoint so anything can be reverted (Aider-style).
- **Pros**: Works *with* the 93%-approve reality; great for local-filesystem mistakes; NN/g-endorsed (undo over confirm).
- **Cons**: Undo goes blind on exactly the irreversible/cross-boundary surface — network POSTs, secret exfil, `git push`, package publish, DB drops — which is the surface the floor exists for. Undo and an exec-floor fail on the *same* correlated region.
- **Why rejected as a substitute**: Retained as a **V2 complement** (defense-in-depth for the reversible local-fs class), not a replacement for the floor.

### Alternative 4: Sandbox-first containment (remove prompts structurally)

- **Description**: Contain actions by default (read-only / workspace-write, network off); escalate to a human only when an action leaves the box (Codex/Cursor-style).
- **Pros**: Removes the prompt rather than improving it; the human gate becomes rare and meaningful.
- **Cons**: Bigger lift; atelier's read/write roots are policy, not an OS sandbox, and `RunCommand` can spawn a shell that escapes app-level containment.
- **Why deferred**: V2+ direction worth pursuing to shrink the Approve-tier stream; out of V1 scope.

## Consequences

### Positive

- The floor protects **100% of users**, including the `Yolo` default — directly delivering "fewer risky auto-approvals" without changing the default or reducing routine prompts.
- The safety claim is honest (fail-closed: "we never silently run what we can't prove safe"), not the false-comfort claim a denylist makes.
- The modal reuses the existing classifier and action data, so "faster confident decisions" is cheap to deliver.
- Trust is footgun-bounded (exact target, in-memory, revocable) and every auto-approval is auditable through the event log — even Yolo becomes auditable.

### Negative

- A fail-closed floor re-prompts more often, so it depends on a good provably-safe allowlist (`cargo build`/`test`, `git status`, `ls`, `rg`, reads within roots); without it, re-prompting itself induces rubber-stamping.
- The rich modal and trust list mainly serve the opt-in `Normal` minority; the majority on `Yolo` only ever experiences the floor.
- Power-user ergonomics (pattern/per-agent trust) are deferred to V2.

### Risks

- **Reflexive Enter / habituation** — a prettier modal can manufacture confidence. *Mitigation*: red tier requires a deliberate non-default keystroke; consider polymorphic dangerous-tier prompts; separate "approve" from "approve-and-trust" keys.
- **`RunCommand` opacity** — semantic effect-classes are crisp for path-bearing actions but decay to name-matching for arbitrary exec (`python script.py`, `make deploy`). *Mitigation*: fail-closed default (unknown → re-prompt) + full audit.
- **Parallel-queue decision-laundering / TOCTOU** — a batch could mix one benign exemplar with dangerous siblings. *Mitigation*: trust applies only to *future* actions; never retro-flush a queued batch without showing the full set and a count; floor items are re-classified at exec time and never auto-cleared.
- **Unmeasured Approve-tier histogram** — whether the trust list is valuable or noise depends on how repetitive Approve-tier actions actually are. *Mitigation*: instrument the histogram from the event log before investing in richer trust.

## Implementation Notes

- Build on `classify_command()`, `is_vcs_mutation()`, `vcs_action_explicitly_requested()` (`src/actions/mod.rs`); reframe the classifier output as provably-safe (Allow) vs. must-confirm (everything else), and add the non-bypassable core that ignores `ApprovalMode::Yolo`.
- Trust state is in-memory on `App`, surfaced to the renderer through the `AppState` snapshot (the TUI cannot read app internals or the FS). The "pick scope" affordance can reuse the clarification options-list pattern.
- Record `trust_granted` and trust-driven auto-approvals as events so `src/app/chat/projection.rs` can show them; reuse the ADR-004 `.atelier/ui_state.json` latch pattern only for a one-time modal explainer, not for trust persistence.
- Resolve the allow-once vs. session-persist seam in favor of **session-persistent exact-target** trust (single-use "allow once" is just today's approve and adds no value).
