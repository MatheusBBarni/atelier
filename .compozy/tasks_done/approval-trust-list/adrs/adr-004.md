# ADR-004: In-memory exact-target session trust, keyed by command/path, never covering the catastrophic core

## Status

Accepted

## Date

2026-06-15

## Context

ADR-001 scoped trust to a single, footgun-bounded form: "trust this exact resolved target for this session," in-memory and revocable, never covering catastrophic actions. The PRD adds that commands and file writes are the trustable kinds, that trust is inspected/revoked via a `/trust` command with inline audit feedback, and that "approve" must never share a keystroke with "approve-and-trust." Today the approval answer is a bare `bool` (`ApprovalHandle::answer(bool)` → `ApprovalSignal { sequence, approved }`), and `resolve_pending_approval` re-runs the action by temporarily setting `approval_mode = Yolo`. A "session" is one app process; cross-session UI state lives in `.atelier/ui_state.json`.

## Decision

- **Data model.** `TrustTarget` is an enum: `Command(String)` (the exact resolved command, normalized identically to classification) and `WritePath(PathBuf)` (the exact target path of `WriteFile`/`ApplyPatch`). A `TrustStore` holds an in-memory `HashSet<TrustTarget>` on `App`; it is never written to disk and dies with the process. A per-action `Arc<TrustSet>` snapshot is passed into `ActionExecutionContext` (ADR-003) for matching at the enforcement point.
- **Granting.** Replace the boolean approval answer with `ApprovalResolution { Deny | ApproveOnce | ApproveAndTrust }` carried on `ApprovalSignal`. `resolve_pending_approval` inserts the pending action's `TrustTarget` into the `TrustStore` only on `ApproveAndTrust`, and only when the action is non-catastrophic (catastrophic assessments expose no target, so the "approve-and-trust" affordance is hidden for them).
- **Managing.** A `handle_trust_command(&mut self, prompt) -> Result<bool>` app command (registered in `src/slash_commands.rs`, dispatched beside `handle_goal_command`/`handle_config_command`): `/trust` lists active entries with human-readable scope ("this session only"); `/trust revoke <n>` removes one; `/trust clear` empties the store.
- **Auditing.** Every grant, trust-driven auto-approval, and revoke is recorded via `record_event` (`trust_granted`, `approval_auto_resolved`, `trust_revoked`, `trust_cleared`) and projected to chat, so trust is always visible.

## Alternatives Considered

### Alternative 1: Commands-only trust

- **Description**: Only `RunCommand` is trustable.
- **Pros**: Smallest surface; unambiguous key.
- **Cons**: Misses edit-heavy `Normal` sessions, where most prompts are file writes — the repeat-collapse KPI would barely move there.
- **Why rejected**: Per PRD clarification, writes are a dominant gated type.

### Alternative 2: Persisted / cross-session trust

- **Description**: Store trust in `.atelier/ui_state.json` so it survives restarts.
- **Pros**: Fewer prompts across sessions.
- **Cons**: The "approve once, exploit forever" failure mode — invisible, accreting standing consent.
- **Why rejected**: PRD non-goal; session scope is the safety feature.

### Alternative 3: Keep the boolean answer; infer trust elsewhere

- **Description**: Avoid changing `ApprovalSignal`; add a side channel for the trust choice.
- **Pros**: No change to the existing approval signal.
- **Cons**: Splits one user decision across two signals; risks the "approve" and "approve-and-trust" keys getting coupled.
- **Why rejected**: A single explicit resolution enum is clearer and enforces the distinct-keystroke requirement.

## Consequences

### Positive

- Trust is bounded (exact match), ephemeral (session), fully visible and revocable — directly answering the "approve once, exploit forever" risk.
- Catastrophic actions can never be trusted away, by construction (no target exposed).
- Reuses the established app-command and event-projection patterns; no new persistence.

### Negative

- The approval answer signal changes from `bool` to an enum, touching the TUI key-routing and the `app` resolution path together.
- `TrustTarget` needs `Hash`/`Eq` and a stable normalization shared with classification to avoid match misses.

### Risks

- Normalization drift between "what we classify" and "what we store/match" would silently break trust matching. *Mitigation*: a single shared normalization helper used by both `assess_risk` and `TrustTarget` construction, covered by tests.
- Distinct keys for approve vs approve-and-trust add UI surface. *Mitigation*: document the mapping in the Approvals help tab; default focus never lands on a trusting/destructive choice.

## Implementation Notes

`/trust` revoke targets a 1-based index from the most recent `/trust` listing for ergonomics. The TUI maps: a normal key → `ApproveOnce`, a separate key → `ApproveAndTrust` (hidden for catastrophic), and `n`/other → `Deny`; high-tier prompts require a deliberate non-default keystroke (and type-to-confirm for the catastrophic core) per the PRD. Trust matching happens before the modal is raised, so a trusted action never reaches `PendingApprovalView`.
