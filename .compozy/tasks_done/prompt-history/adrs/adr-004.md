# ADR-004: Asynchronous Background History Projection

## Status

Accepted

## Date

2026-06-12

## Context

Per ADR-001, recall is a read-only projection over `prompt_submitted` events
across this project's `.multiagent/sessions/*`. There is no cross-session reader
today: `HistoryStore` reads only the active session, and `clean_sessions` globs
the sessions directory solely to delete it. We must decide how to discover and
read those files, how to order / dedup / bound the result, and when to run the
load so it never blocks the UI (PRD: history available < 300ms, non-blocking;
each ↑/↓ step < 16ms).

## Decision

- Add a free function
  `history::list_session_event_paths(multiagent_root: &Path) -> Result<Vec<PathBuf>>`
  that enumerates `sessions/*/events.jsonl`. This is the only new history
  primitive, and is reusable by future Ctrl-R / scope-cycling / outcome views.
- Build the recall list in a **detached background task at startup**, mirroring the
  file-index refresh: after the first frame, `tokio::spawn` a `spawn_blocking`
  closure that (1) lists session event files, (2) reads each via the existing
  `read_events_from_path`, **tolerating and skipping** unreadable or
  legacy-schema files, (3) keeps `prompt_submitted` entries and drops
  leading-space prompts, (4) sorts by event `timestamp` (RFC3339 millis, lexically
  sortable) descending, (5) applies consecutive-dedup, (6) truncates to
  `prompt_history_max`. Deliver the `Vec<String>` over a
  `watch::Sender<Vec<String>>`; the render loop syncs it into
  `TuiUiState.prompt_history` when ready.
- The whole load is gated behind `ui.prompt_history_enabled`.
- The **current session's** submissions are prepended to the in-memory
  `prompt_history` on submit (consecutive-dedup, respect cap), so recall reflects
  this session without re-reading disk.

## Alternatives Considered

### Alternative 1: Blocking load after first frame (skill-suggestions pattern)

- **Pros**: simplest control flow; no extra channel.
- **Cons**: a 10–50ms stall before the UI is interactive on large histories; cost
  scales with session count.
- **Why rejected**: violates the non-blocking constraint; the detached pattern
  already exists and is proven (file-index walk).

### Alternative 2: Lazy load on first ↑

- **Pros**: zero startup cost; only pays if used.
- **Cons**: first-recall stutter on large histories; needs a loading guard and a
  re-entrancy story.
- **Why rejected**: degrades the first recall — the highest-value moment — to save
  a startup cost the background task already eliminates.

### Alternative 3: Bounded read (newest sessions first, early-exit)

- **Pros**: bounds read cost, not just output size.
- **Cons**: ULID≈timestamp approximation; early-exit complexity; premature
  optimization.
- **Why rejected**: output is already capped and the read is off-thread; revisit
  only if measured load exceeds the latency target.

## Consequences

### Positive

- Paint is never blocked; the first ↑ is correct once the (fast) background load
  completes.
- One small, reusable reader primitive; ordering is correct (true timestamp sort)
  and the result is bounded.
- Reuses an established channel/task pattern; no new infrastructure.

### Negative

- Reads all session files once per launch (cost proportional to total history
  size); acceptable off-thread and capped, but an unbounded read on pathological
  histories.
- A brief window after launch where history is empty (load in flight); the hint
  only appears once loaded, so there is no broken affordance.

### Risks

- Large or corrupt event files slow or break the load → per-file error tolerance
  (skip on parse error) plus the output cap; if load latency becomes a problem,
  adopt Alternative 3's bounded read.
- The live session writes concurrently → the disk read is a snapshot; new prompts
  from the current session are merged in memory on submit, so no reload is needed.

## Implementation Notes

- `read_events_from_path` currently returns an error on `schema_version != 1`; the
  loader must wrap each file in a tolerant match and skip on error, so one bad file
  cannot empty all recall.
- Leading-space-skip is applied at read time (the prompt is still present in the
  durable event log — recall is a filter, not a deletion).
