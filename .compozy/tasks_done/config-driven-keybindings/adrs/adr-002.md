# ADR-002: Parity-First, Two-Wave Delivery

## Status

Accepted

## Date

2026-06-15

## Context

The PRD's chosen north star is **native input feel + unblocking terminal conflicts** (a broad,
adoption-agnostic outcome), not power-user customization adoption. Two research findings shape
delivery:

1. **Readline parity is table-stakes, not a power feature.** `Ctrl-A/E/K/U/W` are universal
   shell/REPL defaults; their absence reads as "broken." This value is broad and needs **no
   config**.
2. **Customization is opt-in and low-adoption** (<5% of users change any setting), and atelier
   has **no usage telemetry** to observe adoption. Excellent defaults must precede customization.

The feature is sized **M**, and the charter requires near-zero risk to the well-tested routing
core. The customization machinery (config schema, validation, user-scope loading, unbind) is the
"bulk of the effort"; the parity layer is independent of it.

## Decision

Deliver in two sequenced waves plus a deferred V2, rather than one cohesive drop:

- **Wave 1 (MVP) — broad parity, no config dependency:** add the composer line-editing default
  actions (`Ctrl-A/E/K/U/W`); consolidate the three `Ctrl-C` branches into one pre-lookup safety
  chokepoint; make the help `Keys` tab **data-driven**, rendering the *default* keymap. Delivers
  native input feel to every user and de-risks the routing core. No `[keybindings]` schema yet.
- **Wave 2 — the remap layer:** the keymap override engine + context-scoped `[keybindings.normal]`
  schema (user-scope only), portable-allowlist validation, **unbind**, severity-split validation
  surfaced via `atelier --doctor`, and the Keys tab now reflecting customizations
  (`--print-config` emits the effective keymap). Serves conflict victims and power-user customizers.
- **Phase 3 / V2 (deferred):** modal/dropdown-context remapping over the context schema,
  `vim`/`emacs` presets, leader-key, `hjkl` list-navigation, Kitty-protocol chords, a
  "customized vs default" Keys-tab marker, and an optional discovery nudge.

Note: the two waves are a sequencing/de-risking strategy and MAY land in the same release cycle;
the value is that Wave 1 ships broad parity independent of the customization machinery.

## Alternatives Considered

### Alternative 1: Single cohesive V1 (Approach B)

- **Description**: Ship engine + config + line-editing + Keys tab + unbind + `--doctor` together.
- **Pros**: Cleanest "config-driven keybindings" narrative; one decision; no half-shipped state.
- **Cons**: The broad table-stakes parity value is held hostage to the customization machinery;
  any slip delays everything; larger single review surface against the hot `src/tui/mod.rs`.
- **Why rejected**: Couples broad value to opt-in value and contradicts "excellent defaults first."

### Alternative 2: Remap engine first, parity as fast-follow (Approach C)

- **Description**: Ship remapping + config + Keys tab + unblock-conflicts first; line-editing later.
- **Pros**: Fixes the original conflict-victim hard blocker soonest; leads with the headline.
- **Cons**: Contradicts the chosen north star (native input first); ships the low-adoption opt-in
  layer before the broad parity layer — the inverse of the research guidance; the composer still
  "feels broken" at launch for the broadest audience.
- **Why rejected**: Misorders broad vs niche value and fights the chosen north star.

## Consequences

### Positive

- Broad "native input feel" reaches all users in Wave 1, independent of the config machinery.
- Routing-core risk is isolated and validated early (chokepoint + defaults-byte-identical) before
  the schema lands.
- The Keys tab is built once (Wave 1) and extended (Wave 2), avoiding rework.

### Negative

- The conflict-victim's hard-blocker fix (remap/unbind) lands in Wave 2, not Wave 1.
- Two success gates instead of one add light process overhead for an M-sized feature.

### Risks

- **Wave 2 slips, leaving only parity** → acceptable degraded state (parity is real value); keep
  Wave 2 in the same release cycle and tracked.
- **Perceived as incomplete at Wave 1** → docs frame Wave 1 as "better defaults," with remapping
  announced as imminent.

## Implementation Notes

Product-level only (HOW belongs in the TechSpec): Wave 1 carries no config-schema dependency;
Wave 2 introduces the `[keybindings]` ladder section applied from user-scope layers exclusively.
