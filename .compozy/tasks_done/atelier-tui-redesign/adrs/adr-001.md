# ADR-001: V1 Scope and Sequencing for the Atelier TUI Visual Identity

## Status

Accepted

## Date

2026-06-10

## Context

Atelier (v0.1.1, solo maintainer, public/open-source audience) has no visual identity: no welcome screen, the product name appears once in a transient loading box, and 88 inline `Color::` literals are scattered through `src/tui/mod.rs` (~2,000 lines of render code plus 66 `TestBackend` tests) with yellow overloaded across four unrelated meanings. Market research shows the README screenshot is the primary distribution unit for terminal dev tools; the palette space copper+verdigris/teal is unclaimed in the agent-CLI category (orange = Claude Code, blue/purple = Gemini CLI, pink = Charm/Crush); and no ratatui-based agent ships a theme system. The user requested a Claude Code-style welcome screen (ASCII "Atelier" wordmark, version/session info, tips, project/git context), an own-brand palette, and consistent polish across status bar, borders/panels, agent output views, and dialogs/dropdowns.

A four-advisor council (pragmatic-engineer, architect-advisor, product-mind, devils-advocate) debated scope, sequencing, technical approach, and measurement.

## Decision

Ship a one-week timeboxed V1 in this order:

1. **Semantic-token theme module first** (`theme.rs`): a single const `Theme` struct with 10-15 semantic tokens (e.g., `accent`, `surface`, `text_muted`, `border_focused`, `agent_active`, `status_warning`) whose vocabulary is derived from the brand spec. Color *definition* is separated from color *resolution*: a resolution layer handles `NO_COLOR`, truecolor detection via `COLORTERM`, and 256-color fallback. This layer is a hard V1 dependency — introducing brand RGB values means owning degradation behavior that today's ANSI-named colors get for free. The struct is serde-ready but no user-facing config file ships in V1.
2. **Welcome screen as the theme's first consumer**: `tui-big-text` 0.7.x wordmark (pinned for ratatui 0.29) with per-row gradient, bordered info panels (version via `CARGO_PKG_VERSION`, session/model info, tips, project/git context, agent roster), and a width-responsive degradation ladder (full banner → compact → plain text below ~80/60/40 columns). The welcome screen writes zero inline `Color::` literals.
3. **Git context via subprocess only**: one function returning `Option<GitContext>` from `git rev-parse` with a short timeout; any non-zero exit, timeout, or missing binary renders graceful omission. The persistent status-bar footer (repo + branch) is the primary consumer; the welcome panel is the second consumer of the same value. A debounced refresh policy is specified up front (capture-once is not acceptable for a widget meant to prevent wrong-branch agent runs). Kill-switch: if this exceeds half a day, it is cut from V1.
4. **Full migration of all 88 inline literals** to theme tokens in the same release window, enforced by a CI-checkable invariant (grep: zero `Color::` literals outside the theme module).
5. **Restyle remaining surfaces** (status/input bar, dropdowns, dialogs, agent output views) using tokens.
6. **README screenshot/GIF refresh** as the actual distribution asset.

Measurement: the originally proposed +25% star-velocity KPI is dropped as unfalsifiable at this project stage; star counts are pre-registered as non-evidence for or against this work. Success signals are qualitative: the screenshot travels (reshares/comments reference the look), startup overhead stays under 150ms, and the CI color invariant holds.

## Alternatives Considered

### Alternative 1: Screenshot-first, defer the theme refactor until adoption signal

- **Description**: Ship welcome screen + palette in days; migrate the 88 literals opportunistically later (Product Mind's opening position).
- **Pros**: Fastest visible value; no refactor cost before the brand hypothesis shows signal.
- **Cons**: Adds literals #89+ to the pile; runs two color systems indefinitely; brand RGB without a resolution layer renders wrong on 256-color/`NO_COLOR` terminals — the screenshot becomes a lie; "migrate opportunistically" is how the 88 literals accumulated originally.
- **Why rejected**: The resolution layer is a hard dependency of shipping any brand color honestly, and the token extraction is too cheap (one file, test-covered, 1-2 days) to justify forking the color system.

### Alternative 2: Full OpenCode-style user-facing theme system in V1

- **Description**: 62-slot JSON themes, dark/light per-color variants, OSC terminal-background detection, community theme loading.
- **Pros**: Best-in-class differentiation; no ratatui-based agent ships this; compounds via community contributions.
- **Cons**: A configurable theme system is a support surface, not a feature, for a solo maintainer at v0.1.1; months of maintenance against a "Maybe" defensibility score.
- **Why rejected**: Deferred to V2+. The serde-ready semantic-token struct keeps it a weekend follow-up rather than a quarter.

### Alternative 3: git2 crate for git context

- **Description**: Link libgit2 for branch/repo introspection.
- **Pros**: No subprocess management; structured API.
- **Cons**: Heavy native C dependency; build-time pain on every contributor machine, forever, to display a branch name.
- **Why rejected**: Subprocess `git rev-parse` collapses the entire edge-case surface (bare repos, worktrees, detached HEAD, submodules) into one fallback contract. Raw `.git/HEAD` file reads were also rejected — `.git` is a file in worktrees/submodules and detached HEAD yields a raw SHA.

### Alternative 4: Cut git context entirely from V1

- **Description**: Devil's Advocate's opening position — git context is scope creep decorating a 2-second splash.
- **Pros**: Smallest scope; zero new failure surface.
- **Cons**: Overrides an explicit user requirement; the persistent footer placement converts it from decoration to an instrument (prevents wrong-branch agent runs — a real footgun for a multi-agent harness).
- **Why rejected**: The advocate conceded once the implementation collapsed to ~50 lines + one test with graceful omission, under his own "defer until a user asks" standard — a user asked.

## Consequences

### Positive

- A permanent theme boundary and the first extraction out of the monolithic `tui/mod.rs`, valuable even if the brand bet flops.
- CI-enforceable styling invariant (zero inline colors) prevents regression.
- `NO_COLOR` and 256-color correctness from day one — table-stakes conventions users expect.
- The welcome screen positions Atelier as a multi-agent harness (agent roster on splash) — no competitor communicates this.
- Claimable visual identity (copper + verdigris/teal) in screenshots, the category's primary distribution unit.

### Negative

- ~1 week of solo-maintainer time displaced from harness capability work.
- `tui-big-text` couples the welcome module to the ratatui version line; isolated behind the welcome module so a future ratatui bump can swap it out.
- Owning color degradation behavior permanently (previously delegated to the user's terminal theme).

### Risks

- **Refactor regression in the render module** — mitigated by the 66 existing `TestBackend` tests and behavior-preserving mechanical extraction; risk budget goes to tests first.
- **"Polished but flaky" perception** — a beautiful splash over an unstable harness reads as abandoned-after-the-redesign (Devil's Advocate dissent, preserved); mitigation: timebox enforcement, no structural refactors beyond `theme.rs` extraction.
- **Palette degradation on non-truecolor terminals** (macOS Terminal.app) — mitigated by the resolution layer and manual verification on 3 terminals.
- **Scope creep mid-implementation** (the 3,900-line file invites "fixing" things) — mitigation: extract `theme.rs`, touch nothing else structurally.

## Implementation Notes

- Pin `tui-big-text = "0.7"` (0.8.x requires the ratatui 0.30 line).
- Sub-cell `PixelSize` variants (Sextant/Quadrant) give a crisper wordmark than the chunky Full size everyone copies from Claude Code, but require Unicode-capable fonts — provide an ASCII-only degradation path.
- Gradient lettering: render each banner row with its own interpolated RGB `Style`; quantize to 256-color via nearest match.
- Semantic helpers already exist (`status_style`, `severity_badge_style`, `availability_style`) — repoint them at theme tokens rather than replacing them.
