# ADR-004: Theme Module Architecture — Resolved Token Struct Threaded via TuiUiState

## Status

Accepted

## Date

2026-06-11

## Context

ADR-001 mandated a semantic-token theme with color definition separated from color resolution (NO_COLOR, truecolor→256 fallback). The codebase threads all render state functionally — `render(frame, &AppState, &mut TuiUiState)` with no globals — and all 88 inline `Color::` literals live in `src/tui/mod.rs`. The TechSpec phase had to fix where the theme lives, how it reaches ~40 render helpers, and which dependency renders the wordmark.

## Decision

1. **Location**: new module `src/tui/theme.rs`, co-located with rendering concerns.
2. **Shape**: a plain `Theme` struct of named `ratatui::style::Color` fields (semantic tokens, e.g. `accent`, `text`, `text_muted`, `border`, `border_focused`, `status_ok`, `status_warn`, `status_error`, `agent_accents: [Color; N]`). Tokens are **resolved at startup**: `Theme::resolve(caps: TerminalCaps)` takes detected capabilities (NO_COLOR env, COLORTERM truecolor check) and produces final `Color` values — RGB brand values from the web palette, quantized to ANSI-256 indices when truecolor is absent, or terminal-default/monochrome styles when NO_COLOR is set. Render code never branches on capabilities.
3. **Threading**: `Theme` becomes a field on `TuiUiState`, which is already passed to every render helper. No new parameters, no globals; tests construct `TuiUiState` with any theme variant.
4. **Wordmark dependency**: `tui-big-text = "0.7"` (the ratatui-0.29-compatible line), isolated inside the welcome renderer so a future ratatui upgrade can swap or drop it without touching other code.

## Alternatives Considered

### Alternative 1: Global `OnceLock<Theme>`

- **Description**: Resolve once at startup into a static; render code calls `theme()`.
- **Pros**: Zero signature or struct changes.
- **Cons**: Breaks the codebase's functional-state convention; per-test theme variants (NO_COLOR tests) require static juggling.
- **Why rejected**: Testability and convention consistency outweigh the small wiring saving.

### Alternative 2: Explicit `&Theme` parameter on every render helper

- **Description**: Add a parameter to ~40 functions.
- **Pros**: Maximally explicit dependency.
- **Cons**: Large mechanical diff for no behavioral gain over the `TuiUiState` field; `TuiUiState` is already the UI context object.
- **Why rejected**: Same capability at a fraction of the churn.

### Alternative 3: Runtime-branching colors (no resolution step)

- **Description**: Render code checks `NO_COLOR`/`COLORTERM` at each style decision.
- **Pros**: No startup resolution machinery.
- **Cons**: Scatters capability logic across the render module — the same disease as the 88 literals.
- **Why rejected**: ADR-001 explicitly separates definition from resolution.

## Consequences

### Positive

- One file owns every color; CI grep invariant (`Color::` only in `theme.rs`) is enforceable.
- NO_COLOR/256-color behavior is decided once, testable as pure functions.
- Test suites exercise themes by constructing `TuiUiState` variants — no env-var manipulation inside tests.

### Negative

- `TuiUiState` grows a field whose mutation is never needed (read-only theme on a `&mut` struct) — a minor modeling impurity.
- Capability detection at startup cannot react to runtime terminal changes (e.g., COLORTERM changing mid-session) — acceptable; no terminal does this.

### Risks

- ANSI-256 quantization of the web palette may land on muddy indices — mitigated by hand-picking the 256-color fallback index per token rather than algorithmic nearest-match where the result looks wrong.

## Implementation Notes

- `TerminalCaps::detect()` reads `NO_COLOR` (any non-empty value → monochrome) and `COLORTERM` (`truecolor`/`24bit` → RGB allowed; else 256-fallback).
- Per-token definition: `(rgb: Color::Rgb, ansi256: Color::Indexed, mono: Style modifier)` resolved into the final `Theme`.
- Existing semantic helpers (`status_style`, `severity_badge_style`, `availability_style`) keep their signatures but read tokens from the threaded `ui_state.theme`.
