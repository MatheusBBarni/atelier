# ADR-005: Welcome Screen as Synthetic Chat Item

## Status

Accepted

## Date

2026-06-11

## Context

PRD F1 requires the welcome content to render on every startup and persist in scrollback with the input anchored beneath it (Claude Code model). In the TUI's layout, the chat `Paragraph` is the only scrollable region; chat content is a `Vec<ChatItemView>` rendered by `chat_item_lines()`. The welcome screen also replaces the current blocking "Loading skills..." screen.

## Decision

Implement the welcome screen as a **synthetic `ChatItemView` with a new `ChatItemKind::Welcome`**, injected as the first chat item during app initialization. `chat_item_lines()` dispatches `Welcome` items to a dedicated renderer that draws the adaptive wordmark (tui-big-text, width-laddered) and the facts box (version, working directory, repo+branch, agents summary, preset, warnings count, `/help` hint). The item:

- scrolls naturally with chat history (true scrollback persistence),
- replaces the "No chat yet." empty state,
- is suppressed/reduced by config (`[ui] hide_banner`) and capability context (NO_COLOR/screen-reader → facts as plain text, no wordmark),
- carries no lifecycle key and never updates after creation (git facts at startup time; the live footer owns freshness).

Wordmark width adaptation happens at render time (terminal width from the layout area), not at item-creation time, so resizing re-adapts.

## Alternatives Considered

### Alternative 1: Fixed header layout region

- **Description**: A dedicated constraint area above the chat that shrinks or disappears after the first prompt.
- **Pros**: Always visible until dismissed.
- **Cons**: Does not persist in scrollback (PRD requirement); adds layout-state machinery; steals vertical space from chat.
- **Why rejected**: Fails the persistence requirement directly.

### Alternative 2: Pre-TUI terminal print

- **Description**: Print the welcome to the normal terminal buffer before entering the alternate screen.
- **Pros**: Native terminal scrollback.
- **Cons**: Invisible the moment the alternate screen activates; lost on exit; cannot be styled consistently with the TUI theme.
- **Why rejected**: The user never sees it while using the app.

## Consequences

### Positive

- Zero layout changes; reuses scroll, follow, and wrap machinery.
- Welcome content is testable through the existing `render_to_text` helpers like any chat item.
- The "Loading skills..." interstitial disappears; skill loading proceeds behind the already-rendered welcome frame.

### Negative

- `ChatItemKind` gains a variant that is not an orchestration event — a small semantic widening of the chat model.
- Render-time width adaptation makes the welcome item's height dynamic, which the wrapped-line scroll accounting must handle (it already recomputes per frame).

### Risks

- Chat projection code that iterates items assuming orchestration events must ignore `Welcome` (audit `ChatProjection` consumers) — low risk, single match arm additions.
