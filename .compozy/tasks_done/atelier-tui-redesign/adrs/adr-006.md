# ADR-006: Polled Git Context Refresh and Round-Robin Agent Accents

## Status

Accepted

## Date

2026-06-11

## Context

PRD F3 requires the footer's repo+branch to reflect mid-session branch switches ("the footgun is starting a run on the wrong branch"), with graceful omission outside git repos. ADR-001 fixed the mechanism (subprocess `git rev-parse`, `Option<GitContext>`, half-day kill-switch) but left the refresh cadence open. PRD F4's open question: how per-agent accent colors are assigned from the palette's accent set.

An event-driven-only design (refresh at startup/prompt/run-end) was initially selected, then revised by user decision: branch switches made outside Atelier must appear in the footer promptly, not only at the next interaction.

## Decision

1. **Git context is polled.** A background tokio interval task (default every 5 seconds) runs `git rev-parse --abbrev-ref HEAD` (plus repo-name resolution at startup) through the established `tokio::process::Command` pattern with a short timeout. The result is compared to the last known `Option<GitContext>`; **state updates and a footer redraw occur only when the value changes**. An immediate refresh also runs at startup and on prompt submission, so the wrong-branch decision moment never waits for the next tick. Any failure (non-zero exit, timeout, missing binary, not a repo) yields `None` → footer segment omitted, poller keeps running (a repo can appear later, e.g., `git init`).
2. **Per-agent accents assign by roster order, round-robin** over a fixed accent sequence from the theme (`agent_accents` array, excluding error-red). Adjacent agents are guaranteed distinct up to the sequence length; assignment is a pure function `accent_for(index)` — no persistence, no config surface.

## Alternatives Considered

### Alternative 1: Event-driven only (startup, prompt submission, run completion)

- **Description**: Refresh git context only at interaction moments; no idle polling.
- **Pros**: Zero idle subprocess cost; freshness exactly at decision moments.
- **Cons**: A branch switched externally while Atelier idles shows stale in the footer until the next interaction — the footer silently lies during exactly the contemplation period before the user acts.
- **Why rejected**: User decision — the footer must track external branch changes promptly; a stale ambient indicator undermines trust in it. (`git rev-parse` is sub-10ms; a 5s poll is negligible cost.)

### Alternative 2: Filesystem watch on the git directory

- **Description**: Watch `.git/HEAD` (resolved via `git rev-parse --git-dir`) for modification and refresh on change.
- **Pros**: Near-instant updates, no polling subprocesses.
- **Cons**: New file-watcher dependency (`notify`); worktree/submodule layouts complicate which path to watch — the same edge-case family the council eliminated by choosing subprocess-only.
- **Why rejected**: Reintroduces the complexity ADR-001 paid to remove, to improve on a 5-second latency nobody perceives as slow.

### Alternative 3: Name-hash stable agent colors

- **Description**: Hash agent name into the accent list so colors survive config reordering.
- **Pros**: Reorder-stable.
- **Cons**: Two agents can collide on one color with no recourse; rosters are small and stable, making reorder-stability low-value.
- **Why rejected**: Distinctness beats reorder-stability for the traceability goal.

### Alternative 4: Explicit per-agent color config

- **Description**: Optional `color` key per agent profile, falling back to round-robin.
- **Pros**: Full user control.
- **Cons**: New config surface, validation, and documentation V1 does not need.
- **Why rejected**: YAGNI; round-robin is the fallback such a key would use anyway, so it can be added compatibly later.

## Consequences

### Positive

- Footer reflects any branch change within ~5 seconds, regardless of how it happened (Atelier agent, another terminal, IDE).
- Change-detection gating means idle polling causes zero redraws and no visible churn when nothing changes.
- Agent color assignment is deterministic, testable, and dependency-free.

### Negative

- A subprocess spawn every 5 seconds while idle — negligible (`git rev-parse` is sub-10ms), but nonzero battery/process noise; interval is a single constant if it ever needs tuning.
- Agent colors shift if the configured roster order changes — accepted for small stable rosters.

### Risks

- Poll task must not outlive the TUI session — tie the interval task to the worker lifecycle (abort on shutdown, as existing background tasks do).
- Slow filesystems (network mounts) could make `git rev-parse` exceed the timeout intermittently — treated as `None`-then-recover; change-gating prevents footer flicker because consecutive `None`s produce no update, though a `Some→None→Some` flap on a flaky mount would briefly hide the segment.
