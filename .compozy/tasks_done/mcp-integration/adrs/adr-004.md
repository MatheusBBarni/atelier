# ADR-004: Adopt the official `rmcp` Rust SDK for the MCP client

## Status

Accepted

## Date

2026-06-15

## Context

ADR-001 commits to a harness-owned MCP client. The crate currently has **no** JSON-RPC or MCP dependency (`Cargo.toml`: tokio 1, serde/serde_json, anyhow, async-trait, tokio-util). The official Rust SDK, `rmcp` (`/modelcontextprotocol/rust-sdk`, v0.5.0, High reputation), is tokio-native and provides: the `initialize` handshake, JSON-RPC request/response correlation, a `TokioChildProcess` stdio transport (and a Streamable HTTP transport for V1.1), typed `Tool` / `CallToolRequestParam` / resource models, and tool annotations. atelier's dependency tree is deliberately lean, so a new dependency is a real cost.

## Decision

Add `rmcp` as a dependency and use its client role (`().serve(TokioChildProcess::new(Command))` → a running client) for stdio in V1, with `list_all_tools` / `call_tool` / resource reads. **Wrap the rmcp client behind a thin internal `McpClient` trait** (`call_tool`, `list_tools`, `read_resource`, `shutdown`) so the supervisor depends on atelier's seam, not rmcp's surface — this trait is the boundary the in-repo fake server and unit mocks implement. Pin the `rmcp` version.

## Alternatives Considered

### Alternative 1: Hand-rolled minimal JSON-RPC client

- **Description**: Build a small client over the existing `cursor.rs` subprocess+stdio pattern.
- **Pros**: Zero new dependencies; full control; no pre-1.0 churn.
- **Cons**: Reimplements the handshake, id-correlation, content/schema/annotation types, and tracks MCP spec changes by hand; HTTP/OAuth for V1.1 would be entirely bespoke.
- **Why rejected**: Commodity plumbing the council explicitly warned against rebuilding; more surface and ongoing maintenance.

### Alternative 2: Generic JSON-RPC crate + custom MCP types

- **Description**: Use a generic JSON-RPC library and hand-model MCP semantics on top.
- **Pros**: Some reuse of transport/correlation.
- **Cons**: Still hand-builds all MCP-specific types, capabilities negotiation, and transports.
- **Why rejected**: `rmcp` provides the whole protocol, including the V1.1 HTTP transport, for less work.

## Consequences

### Positive

- Handshake, transports, typed models, and annotations for free; the Streamable HTTP transport is ready when V1.1 needs it (supports ADR-002's "additive" promise).

### Negative

- A new, pre-1.0 dependency enters a deliberately lean tree.

### Risks

- **`rmcp` API/version churn** — mitigated by pinning the version and by the internal `McpClient` trait wrapper, which localizes any future SDK change to one adapter and keeps the supervisor/tests decoupled.

## Implementation Notes

The `McpClient` trait is the test seam (ADR-008 testing strategy). The real implementation adapts `rmcp`'s `RunningService<RoleClient>`; the fake implementation is the in-repo stdio fixture server.
