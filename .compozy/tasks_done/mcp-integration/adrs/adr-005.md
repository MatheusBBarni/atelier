# ADR-005: `McpSupervisor` as a supervisor actor with a command channel

## Status

Accepted

## Date

2026-06-15

## Context

MCP servers are long-lived, stateful connections, unlike atelier's runtimes which spawn on-demand. `execute_action_request` is a free `async fn(agent, context, request) -> ActionResult` with no access to any connection owner today. ADR-002 requires the connection lifecycle to be **async and event-recorded**, owned outside `App` so network state does not bleed into the deterministic, event-sourced core.

## Decision

Introduce a dedicated **`McpSupervisor`** task that owns every connection and its lifecycle (spawn / `initialize` / health / timeout / reconnect / kill). It exposes a cheap, cloneable **`McpHandle`** (an mpsc command sender) carried on `ActionExecutionContext`. Commands: `CallTool`, `ListTools` / `SnapshotCatalog`, `ReadResource`, and lifecycle (`Connect`, `Health`, `Shutdown`); each carries a `oneshot` reply. The supervisor owns the connection map and lifecycle, but **dispatches each tool call concurrently** onto its connection (rmcp clients are `Send + Sync` and self-correlate) rather than serializing all calls through one loop.

## Alternatives Considered

### Alternative 1: Shared `Arc<RwLock<HashMap<server, client>>>`

- **Description**: `execute_action_request` holds an `Arc` and calls the rmcp client directly under a read lock.
- **Pros**: Simpler call path; no channel hop.
- **Cons**: Reconnect/health/timeout logic spreads across call sites; the async, event-recorded connect lifecycle has no single owner.
- **Why rejected**: ADR-002 wants lifecycle centralized and event-recorded; a lock-map scatters it.

### Alternative 2: Spawn a connection per call

- **Description**: Open a fresh stdio connection for each tool call.
- **Pros**: No lifecycle state to manage.
- **Cons**: Defeats long-lived sessions; pays the `initialize` handshake every call.
- **Why rejected**: Negates the point of persistent MCP sessions.

## Consequences

### Positive

- Centralized, event-recorded lifecycle; matches atelier's existing mpsc/watch idiom; one place to fake/mock for tests; lifecycle transitions are serialized and observable.

### Negative

- One channel hop per call; a new long-lived task to own and shut down with `App`.

### Risks

- **Head-of-line blocking** if all tool calls funnel through a single actor loop — mitigated by dispatching each call concurrently per connection (the actor owns the map + lifecycle, not a global call mutex).
- **Backpressure / shutdown ordering** — bounded command channel; supervisor drains and kills children on `Shutdown`, with `kill_on_drop` as the backstop.

## Implementation Notes

The catalog snapshot (ADR-001/F5) is produced by the supervisor and recorded as an event at run/planning entry; the prompt builder reads the snapshot, never the live handle.
