# ADR-006: Sequencing Relative to the atelier-tui-redesign Effort

## Status

Accepted

## Date

2026-06-12

## Context

The idea, PRD, and TechSpec all flagged an open sequencing risk: this roster reflow and the `atelier-tui-redesign` F5 ("live-orchestration identity": per-agent accent colors in the roster, run-summary restyle, working indicator) both touch the roster render block (`src/tui/mod.rs:2114-2177`). If both were in flight, they would collide on the same code.

Investigation of the actual repository state resolves the risk:

- `atelier-tui-redesign/_tasks.md` shows tasks **01–08 `completed`**; only **task 09 is `blocked (manual)`**.
- The redesign code is **landed on `origin/main`**: `src/tui/theme.rs` and `src/tui/welcome.rs` exist on `main`, and `theme.accent_for(...)` is already used by the roster (`tui/mod.rs:1963`), chat (`tui/mod.rs:2950`), and `/agent:` dropdown (`tui/mod.rs:2321`) — i.e. F5 / task_07 (per-agent accents) is merged.
- Task 09 is the **only** outstanding redesign item and is a content/verification deliverable: capturing the README welcome screenshot + the parallel-agent GIF and running the 3-terminal / `NO_COLOR` visual check. It edits no roster render code.

Therefore there is no live code-level conflict: the roster reflow is a successor to F5, building on the theme/accent seam it produced. The TechSpec was authored against this post-redesign `main` (it depends on `theme.accent_for`, the three accent surfaces, and the `roster_names_carry_same_accents_as_chat` / dropdown contract tests — all F5 output).

## Decision

1. **Branch the roster work from `main`.** It inherits the full theme seam and per-agent accents; no rebase against an in-flight F5 is required.
2. **No merge sequencing constraint against redesign code** — all redesign code (tasks 01–08) is already merged.
3. **Land the roster reflow BEFORE redesign task 09's manual asset capture.** The reflowed roster (states, glyphs, summary header, live-activity weighting) is visible in both the welcome panel and the live GIF, and is precisely the "live show" F5/F8 intend to showcase. Capturing the README GIF / welcome screenshot / 3-terminal + `NO_COLOR` verification *after* this work lands yields stronger assets and avoids redoing them.
4. **Standard rebase hygiene against other in-flight branches.** Other open branches (`feat/claude-integration`, `fix/chat-user-prompt-above-run-summary`, `fix/questioning-tool-and-chat-scrollbar`) each modify `src/tui/mod.rs` for unrelated reasons; they are not roster-render conflicts but warrant ordinary rebase care since this work also edits that file.

## Alternatives Considered

### Alternative 1: Merge the roster reflow into the redesign packet / branch

- **Description**: Treat this as additional redesign scope and ship under that effort.
- **Pros**: Single coherent visual-identity release.
- **Cons**: The redesign is already complete and merged; reopening it adds no value and re-entangles a closed effort. This work has its own PRD/TechSpec/ADRs and a distinct (information-architecture + progress-confidence) thesis.
- **Why rejected**: Nothing to merge into — the redesign code is done; this is net-new follow-on work.

### Alternative 2: Hold the roster work until redesign task 09 is captured

- **Description**: Capture the README GIF/screenshots first, then do the roster reflow.
- **Pros**: Unblocks the redesign's marketing deliverable sooner.
- **Cons**: The captured assets would immediately be stale (they would show the old flat roster), forcing a recapture after this lands.
- **Why rejected**: Wastes the asset-capture effort; the reflow is the thing worth showcasing.

## Consequences

### Positive

- The original "parallel collision" risk is eliminated, not merely mitigated — there is no concurrent F5 code.
- Sequencing becomes a synergy: this work strengthens the redesign's still-pending GIF/screenshot deliverable.
- The TechSpec's assumptions (already written against post-redesign `main`) are validated.

### Negative

- Redesign task 09's manual capture is intentionally deferred until this work lands (a scheduling dependency, not a code one).

### Risks

- **Other in-flight branches editing `tui/mod.rs`** could create textual merge conflicts → low risk (different regions); resolve by branching from latest `main` and rebasing before merge.

## Implementation Notes

- Cut the implementation branch from latest `origin/main`.
- When the roster reflow merges, notify the redesign task 09 owner that asset capture is unblocked and should use the new roster.
