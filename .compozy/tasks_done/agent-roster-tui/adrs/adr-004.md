# ADR-004: Refresh Cadence and Stall-Detection Mechanism

## Status

Accepted

## Date

2026-06-12

## Context

ADR-002 requires coarse elapsed on active rows and a first-class `Stalled` state driven by a bounded ~1 Hz refresh that runs only during active runs. The TechSpec must decide (a) where the refresh timer lives and (b) what signal detects a stall, both grounded in the actual event loop.

Codebase exploration (verified) established:
- The app-worker `tokio::select!` (`tui/mod.rs:731-756`) already hosts a command-receiver arm plus two gated pollers — git (5 s) and file-index (15 s, with `set_missed_tick_behavior(Skip)`). Adding a third poller is the established in-repo pattern.
- `set_git_context` (`app/mod.rs:4056`) uses a **value-change gate** before publishing — the existing idiom for avoiding redundant publishes.
- `push_live_stream_content` (`app/mod.rs:4320`) is the **single chokepoint** for stream arrivals: a grep confirmed it is the only writer of `live_step.streams` and the only path that sets status to `Streaming`. No external code advances visible output without routing through it.
- "Run active" is knowable from `RunState` (`work_indicator_active` mirrors `Planning|Running`, `tui/mod.rs:3419`).
- Adversarial review (PARTIAL) on a `select!` arm: under heavy streaming a 1 Hz arm could miss ticks. Counter-point established in the same review: under heavy streaming, stream deltas already rebuild the roster constantly (event-driven), so the timer only has to fire when an agent is **quiet** — exactly the stall case — when the loop is uncontended.

## Decision

1. **Refresh = a 4th arm on the app-worker `select!`** (`tui/mod.rs:731`). Create `tokio::time::interval(Duration::from_secs(1))` with `set_missed_tick_behavior(Skip)`; its tick calls a new `app.refresh_roster_tick()`.
2. **Gate the work, not the timer.** `refresh_roster_tick()` returns early unless `work_indicator_active(&self.state)`. When active, it rebuilds `roster_rows` with a fresh `now`, recomputes `Stalled`, and **publishes only if any row's activity or elapsed-bucket changed** (change-gate, mirroring `set_git_context`). Idle cost is one no-op tick per second, no publish.
3. **Stall signal = elapsed-since-last-activity.** Maintain an internal `BTreeMap<String /*step_id*/, StepTiming { started_at, last_activity }>` on `App`. Stamp both in `set_active_step_with_metadata` (`app/mod.rs:3246`); bump `last_activity` in `push_live_stream_content` (`4320`) and on status transitions in `set_live_step_status` (`4362`); clear on `clear_active_step`.
4. **Classification.** A row is `Stalled` when its step is in `Running`/`Streaming` **and** `now - last_activity >= STALL_THRESHOLD`. `const STALL_THRESHOLD: Duration = Duration::from_secs(30)`.
5. **Elapsed** is `now - started_at`, formatted coarse (whole seconds → `1m 20s` → minutes), shown on active rows only.

## Alternatives Considered

### Alternative 1: Dedicated `tokio::spawn` timer task

- **Description**: A separate task drives the refresh, fully independent of command/stream throughput.
- **Pros**: Bulletproof tick timeliness even under saturation.
- **Cons**: Another task plus a shared-state access path to trigger the rebuild/publish; more moving parts than the proven poller pattern.
- **Why rejected**: The select-arm's missed-tick risk is self-mitigated (events refresh under load; the timer fires uncontended when quiet); YAGNI favors matching the existing git/file-index pollers. Retained as the escalation path if stress testing shows missed ticks.

### Alternative 2: `biased!` select ordering to prioritize the timer

- **Description**: Check the timer branch first to guarantee servicing.
- **Pros**: Single loop; guarantees the tick.
- **Cons**: Reorders fairness for all branches, including command processing.
- **Why rejected**: Unnecessary given the self-mitigation; changes global loop fairness for one branch.

### Alternative 3: Stall from elapsed-since-step-start (not since-activity)

- **Description**: Flag stall when total step time exceeds a threshold.
- **Pros**: No `last_activity` tracking.
- **Cons**: A legitimately long step false-positives; contradicts ADR-002's "slow models legitimately think" mitigation.
- **Why rejected**: A hung agent stops emitting chunks; since-activity is the correct signal.

### Alternative 4: Serialize `last_activity` onto `LiveStepView`

- **Description**: Put the timestamp on the public/serialized view.
- **Pros**: Simpler to read at render.
- **Cons**: Pollutes the durable history record and forces a `SystemTime` in the hot stream path.
- **Why rejected**: An internal `Instant` map keeps wall-clock out of the event stream.

## Consequences

### Positive

- Minimal, idiomatic change (a third gated poller) delivering timely stall detection — the PRD's #1 success signal.
- `push_live_stream_content` as the single activity chokepoint means no path can falsely keep an agent "fresh."
- Negligible idle cost via the active-runs gate + change-gate.

### Negative

- One new internal map to keep in sync across step lifecycle transitions (start / stream / status-change / clear).
- A fixed 30 s threshold (configurability deferred per PRD Non-Goals).

### Risks

- **Missed ticks under saturation** (verified PARTIAL) → self-mitigated by event-driven refresh under load; if a stress test shows drift, escalate to Alternative 1 (dedicated task).
- **`StepTiming` leak** if a clear path is missed → clear on `clear_active_step` and on terminal status; covered by unit tests.
- **Stall false positives** on slow models → 30 s conservative default + animated indicator reassurance + "stalled?" phrased as a question.

## Implementation Notes

- Reuse `set_missed_tick_behavior(Skip)` exactly as `file_index_poll` (`tui/mod.rs:728`).
- The change-gate compares the freshly built `roster_rows` (activity + elapsed bucket) against the current ones before publishing.
- `work_indicator_active` is the single source of "run active"; pause the work when `RunState` is `Idle`/`Completed`/`WaitingForUser`.
