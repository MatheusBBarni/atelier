# ADR-006: Session adoption via a single `adopt_session()` swap + exhaustiveness test

## Status

Accepted

## Date

2026-06-15

## Context

ADR-003 requires adopting a different session at runtime by building a fresh session-state value and swapping it atomically — explicitly leaving the *enforcement* mechanism open (the "T3 nuance"). Codebase facts:

- `App` (src/app/mod.rs:316) owns the session-scoped state by value: `history: HistoryStore`, the session subset of `state: AppState` (`session_id`, `run_state`, `active_run_id`, `session_goal`, `chat_items`, `pending_*`), `chat_projection`, `pending_approval`, `pending_clarification`, `active_step`/`active_steps`, `follow_up_queue`. `self.history` and friends are referenced across hundreds of call sites (e.g. `record_event` at :4164).
- The worker thread (`run_app_worker`, src/tui/mod.rs:957) is the **sole owner** of `App`; the UI only observes `AppState` via a `watch` channel. So any swap performed on the worker thread is already atomic from the UI's perspective.
- The project already enforces a cross-cutting invariant with a test (`colors_live_only_in_theme_module`, src/tui/mod.rs:9200).

A full "named `ActiveSession` handle" refactor would touch every `self.history` / `self.state` access site — large and risky. The council's Architect conceded that a *mechanically enforced* exhaustiveness check makes a field swap operationally equivalent to a named boundary.

## Decision

Keep `App`'s current field layout. Funnel **all** session adoption/reset through one private method:

```rust
struct LoadedSession {
    history: HistoryStore,        // via HistoryStore::open(root, session_id)
    projection: ChatProjection,   // ChatProjection::rebuild(&events)
    session_goal: Option<String>,
    run_state: RunState,          // reconciled to Idle (dangling run -> Interrupted event)
    // ... every other session-scoped field, reset to its adopted value
}

impl App {
    fn adopt_session(&mut self, loaded: LoadedSession) { /* reassign ALL session-scoped fields here, then broadcast */ }
}
```

`adopt_session` is the single swap point: it reassigns every session-scoped field and triggers one `watch` broadcast. The **heavy disk read** (enumerating + reading `events.jsonl`) runs off-thread using the existing `spawn_file_index_refresh` watch-channel pattern; the cheap in-memory **fold (`rebuild`) + swap** runs on the worker thread inside `adopt_session`.

A unit test enforces **exhaustiveness**: it constructs an `App`, mutates every session-scoped field to a sentinel, calls `adopt_session`, and asserts each field was replaced — so a future session-scoped field added to `App` without being handled in `adopt_session` fails CI.

## Alternatives Considered

### Alternative 1: Named `ActiveSession` struct threaded through `App`

- **Description**: Group all session-scoped fields into one `active_session` value; `App` holds only that.
- **Pros**: Strongest compile-time boundary; new session state forced into the struct.
- **Cons**: Rewrites hundreds of call sites (`self.history` → `self.active_session.history`), including `record_event` and the whole run loop.
- **Why rejected**: Large, risky churn for a property the swap method + exhaustiveness test already deliver.

### Alternative 2: Inline field reset at the resume call site

- **Description**: Reassign fields where resume happens.
- **Pros**: Smallest code.
- **Cons**: A future field silently won't be reset → stranded modal/queue state.
- **Why rejected**: The piecemeal partial-reset the council rejected.

## Consequences

### Positive

- One audited swap point; no partial-reset surface.
- Minimal churn; reuses the proven off-thread watch-channel pattern for the disk read.
- The swap is atomic to the UI because the worker owns `App`.

### Negative

- The exhaustiveness guarantee is test-time, not compile-time.

### Risks

- A developer could bypass `adopt_session` and reset fields elsewhere. *Mitigation:* `adopt_session` is the only non-`create` constructor of session state; the test documents the invariant.

## Implementation Notes

`HistoryStore::open(root, session_id)` (new) loads metadata + validates `schema_version`. Reading the log off-thread yields `Vec<HistoryEvent>` (Send); `ChatProjection::rebuild` runs on the worker. The read-only preview uses the same off-thread read + a throwaway `rebuild` whose `items()` are rendered directly (no live-step/approval/welcome overlays).
