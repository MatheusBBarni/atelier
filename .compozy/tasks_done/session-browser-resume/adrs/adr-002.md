# ADR-002: Append-in-place resume with explicit lifecycle events

## Status

Accepted

## Date

2026-06-15

## Context

Resuming a session writes new prompts/events somewhere. The user chose **append-in-place** (continue the SAME durable log) over fork or snapshot-first, because crash recovery means "it's the same session, just keep going."

The council (Architect, Security Advocate, Devil's Advocate) flagged that naive append-in-place is unsafe in two ways:

- A session that crashed mid-run leaves a **dangling, non-terminal run** in the log. If the run's end is only applied as in-memory state (not written), the **next replay cannot tell the run ended** — the activated production fold (ADR-003) would render a lie.
- Append-in-place mutates what was an append-only record, so the **pre-resume end-state must remain reconstructible** for forensics and to detect tampering.

A second-source-of-truth hazard also exists: if `metadata.json` (goal/outcome) is written independently, a crash between the metadata write and the log write makes the list show an outcome the transcript contradicts.

## Decision

Resume **appends into the same `events.jsonl`**, and the lifecycle is recorded **as events**:

1. On resume, any dangling/in-flight run is closed by appending a **terminal `run_interrupted` event** (reconcile-to-Idle is a written transition, not just in-memory state).
2. A **`session_resumed` boundary event** is appended capturing: resume timestamp, resume cwd, git HEAD + dirty flag, the capability/approval context being re-adopted, the prior end-state, and a hash/offset of the pre-resume tail (tamper-evident; see ADR-004).
3. After that, the session opens **Idle**, awaiting a new prompt. No automatic re-execution of the interrupted step in V1.
4. `metadata.json` `{goal, outcome}` is a **derived cache**, not a source of truth. The event log is authoritative; the cache is rebuilt by folding the log and is **self-healing** on next browse.

## Alternatives Considered

### Alternative 1: Fork into a new linked session

- **Description**: Copy the session into a fresh one linking back to the original; original stays immutable.
- **Pros**: Original preserved as a distinct artifact; clean audit.
- **Cons**: Two artifacts and a "which is current?" question; contradicts the "same thread, keep going" mental model of the anchor.
- **Why rejected**: Misaligned with crash-recovery UX; the boundary event achieves forensic preservation more cheaply.

### Alternative 2: Snapshot the original before appending

- **Description**: Continue in place but first write an immutable snapshot of the pre-resume log.
- **Pros**: Full recoverability of the original.
- **Cons**: Extra machinery and storage; duplicates data.
- **Why rejected**: The `session_resumed` boundary event + immutable append already preserve the prior end-state and a tail hash at far lower cost.

## Consequences

### Positive

- Replay stays correct and forensic: every transition is in the log.
- `metadata.json` can never permanently diverge — it's regenerable.
- One continuous append-only chain; no fork/merge semantics.

### Negative

- Replay is O(total history) per open, which grows with very long sessions.

### Risks

- Log bloat on long-lived sessions → **snapshot/compaction is named as a future ADR**, not V1 scope.

## Implementation Notes

`run_interrupted` and `session_resumed` are additive event variants; they must round-trip through the fold (ADR-003). Emit them at the `HistoryStore::open()`/replay boundary so adoption and event-emission share one seam.
