# TechSpec: Default Agent Prompts

Date: 2026-06-13
Status: Draft

## Overview

This TechSpec defines the implementation plan for improving the six core structured-runtime agent prompts: `orchestrator`, `explorer`, `fixer`, `reviewer`, `oracle`, and `consul`.

The implementation will make the default prompts contract-first role contracts, keep built-in defaults and generated starter instruction files aligned through a single Rust source of truth, and add focused tests that fail when prompt surfaces drift.

## Source Inputs

- PRD: `.compozy/tasks/default-agent-prompts/_prd.md`
- ADR-001: `.compozy/tasks/default-agent-prompts/adrs/adr-001.md`
- ADR-002: `.compozy/tasks/default-agent-prompts/adrs/adr-002.md`
- User clarification: use centralized Rust constants with focused drift tests.

## Goals

1. Rewrite the six core prompts as concise, contract-first role contracts.
2. Centralize prompt text in Rust constants so built-in runtime defaults and starter instruction files reuse the same source.
3. Preserve existing runtime JSON schemas, action contract shapes, permissions, and protocol mechanics.
4. Add focused tests that verify built-in prompt defaults and generated starter prompt files remain aligned.
5. Keep prompt text concise enough for routine runtime use while explicitly covering role boundaries, harness action discipline, completion evidence, and blockers.

## Non-Goals

- No JSON schema or action contract changes.
- No runtime validator, scheduler, or planner redesign.
- No new agent roles.
- No configurable prompt profiles.
- No broad prompt evaluation suite beyond focused alignment and behavior-shape tests that fit the repository test style.
- No standardization of disabled or non-core bundled agents in V1.

## Current Implementation Context

Repository discovery identified `src/config/mod.rs` as the relevant implementation area. It contains:

- Built-in agent defaults defined through `insert_builtin_agent(...)`.
- Generated starter configuration text through `starter_config_text`.
- Generated starter instruction file contents through `starter_instruction_files`.

The current risk is prompt drift: implicit built-in agents and freshly initialized projects can receive different prompt guidance if inline built-in defaults and generated starter files are updated separately.

## Design Decision

Use centralized Rust constants as the single source of truth for the six core role prompts.

Both prompt consumers must reuse these constants:

- Built-in runtime defaults for `orchestrator`, `explorer`, `fixer`, `reviewer`, `oracle`, and `consul`.
- Starter instruction files generated by the init flow for the same six roles.

Add focused tests that prove the two surfaces are aligned and that the generated starter output contains the expected role contract language.

## Prompt Contract Requirements

Each core prompt must instruct the agent to obey the runtime-requested structured output contract. The prompt must explicitly forbid prose outside the requested JSON envelope when the runtime demands structured output.

Each core prompt must cover:

- Role ownership: what the agent is responsible for.
- Role boundaries: what the agent must not do.
- Harness action discipline: file reads, commands, edits, and verification must be requested through harness actions when unavailable directly.
- Result discipline: completion fields must contain factual findings, changed files, commands, verification, and blockers as applicable.
- Blocker handling: blockers must identify the missing data, permission, command result, file, action result, or user decision.
- Stop condition: the agent should stop when its assigned step is complete, blocked, failed, or requires a harness action.

## Role Contracts

### Orchestrator

Owns planning, routing, clarification, and delegation decisions.

Required behavior:

- Return only the requested orchestrator decision contract.
- Choose the next specialist agent based on the current stop condition and available capabilities.
- Ask one targeted user question when a decision cannot be made safely.
- Define the next step, required capabilities, reason, and stop condition clearly.

Forbidden behavior:

- Do not edit files, run commands, inspect the repository, or perform specialist work directly.
- Do not embed action descriptors inside orchestrator decisions.
- Do not route work to unavailable agents or unavailable capabilities.

### Explorer

Owns read-only repository and context discovery.

Required behavior:

- Request read, list, search, or safe inspection actions when repository data is needed.
- Return factual findings with file paths, observed behavior, and uncertainty labels where applicable.
- Identify the next useful files, commands, or decisions if discovery is incomplete.

Forbidden behavior:

- Do not edit files.
- Do not run modifying commands.
- Do not propose unverified conclusions as facts.

### Fixer

Owns scoped implementation changes and targeted verification.

Required behavior:

- Request reads before editing when file context is missing.
- Request edits through harness actions.
- Request commands for formatting, tests, or verification when needed.
- Report changed files, commands, verification, and residual blockers in the proper result fields.

Forbidden behavior:

- Do not claim direct tool access.
- Do not perform unrelated refactors.
- Do not mark completion without either verification evidence or a specific blocker explaining why verification could not run.

### Reviewer

Owns risk-first review of completed work.

Required behavior:

- Review for bugs, regressions, missing tests, incomplete requirements, and verification gaps.
- Lead with findings ordered by severity.
- Reference files and evidence when available.
- State when no issues are found and name residual risk or test gaps.

Forbidden behavior:

- Do not edit files.
- Do not take over implementation.
- Do not report vague concerns without concrete evidence or an explicit uncertainty label.

### Oracle

Owns focused advisory answers from available evidence.

Required behavior:

- Answer narrow questions using provided context and requested reads or searches.
- Label uncertainty and identify missing evidence.
- Keep answers scoped to the question.

Forbidden behavior:

- Do not pretend to have unseen repository, web, or command data.
- Do not edit files or execute implementation steps.
- Do not overrule runtime constraints.

### Consul

Owns adversarial critique, trade-off analysis, and assumption testing.

Required behavior:

- Challenge plans, risks, and assumptions.
- Identify decision trade-offs and failure modes.
- Recommend adjustments without taking over execution ownership.

Forbidden behavior:

- Do not edit files.
- Do not execute the plan.
- Do not create unnecessary process overhead when the path is already clear and low risk.

## Implementation Plan

### 1. Introduce Central Prompt Constants

Add centralized constants near the existing config default definitions in `src/config/mod.rs`, or a nearby Rust module if the file is already too large for maintainability.

Suggested shape:

- `DEFAULT_ORCHESTRATOR_INSTRUCTIONS`
- `DEFAULT_EXPLORER_INSTRUCTIONS`
- `DEFAULT_FIXER_INSTRUCTIONS`
- `DEFAULT_REVIEWER_INSTRUCTIONS`
- `DEFAULT_ORACLE_INSTRUCTIONS`
- `DEFAULT_CONSUL_INSTRUCTIONS`

If a helper map or function better matches existing code style, it may wrap these constants, but the prompt body should still have one canonical Rust source.

### 2. Reuse Constants For Built-In Defaults

Update the `insert_builtin_agent(...)` definitions for the six core agents to reference the centralized constants instead of inline prompt literals.

Acceptance criteria:

- Each core built-in agent uses the centralized prompt for its role.
- Non-core and disabled agents are left unchanged unless a compile-time dependency requires a small mechanical adjustment.
- Existing agent capabilities, model defaults, runtime settings, and enablement behavior remain unchanged.

### 3. Reuse Constants For Starter Instruction Files

Update `starter_instruction_files` so generated starter prompt files for the same six roles use the same centralized constants.

Acceptance criteria:

- Freshly initialized projects receive the same role contract text as built-in runtime defaults.
- Starter generation keeps the existing file naming and directory structure.
- The generated starter config remains compatible with existing init behavior.

### 4. Preserve Existing Runtime Protocol

Do not alter:

- Agent schema definitions.
- Action request schema definitions.
- Agent result schema definitions.
- Orchestrator decision schema definitions.
- Harness permission enforcement.
- Runtime parsing, validation, scheduling, or retry mechanics.

The prompt update should improve model behavior without depending on protocol changes.

## Testing Plan

Add focused tests in the repository's existing Rust test style.

### Alignment Tests

Tests should prove that built-in defaults and generated starter instruction files share the same prompt text for all six core roles.

Recommended assertions:

- The built-in `orchestrator` instructions equal the generated starter `orchestrator` instruction file content.
- Repeat for `explorer`, `fixer`, `reviewer`, `oracle`, and `consul`.
- The set of tested roles is explicit so adding or removing a core role requires intentional test updates.

### Prompt Content Tests

Add lightweight assertions that each core prompt contains key contract language. These tests should avoid brittle full-text snapshots unless the repo already uses snapshot testing.

Recommended assertions:

- Each core prompt mentions the requested JSON or structured contract requirement.
- Each core prompt mentions harness actions for unavailable file, command, edit, or verification operations where relevant.
- Each core prompt mentions blocker reporting.
- Role-specific prompts include their defining boundary, such as explorer read-only, reviewer no edits, fixer verification evidence, and orchestrator no direct implementation.

### Init Surface Tests

If existing init tests already cover starter file generation, extend them to assert that the generated files contain the centralized prompt constants. If not, add a small test around the starter instruction generation helper rather than a broad end-to-end init test.

## Verification Commands

Use the repository's normal Rust verification flow. The expected targeted verification is:

- `cargo fmt --check`
- `cargo test` or the narrower package/module test command if the repo has a more focused config test target.

If the repository requires an `rtk` wrapper for local commands, run the same commands through that wrapper.

## Migration And Compatibility

This change should be backward-compatible because it changes default prompt text only.

Existing project-owned instruction files should not be rewritten automatically. The new prompts apply to:

- Built-in defaults used when no project override is present.
- Newly generated starter instruction files after the change.

Existing user-edited instruction files remain under user control.

## Rollout Plan

1. Land centralized constants and update the two prompt consumers.
2. Land focused alignment and prompt-content tests.
3. Run targeted verification.
4. Use representative structured-runtime scenarios to confirm that agents request harness actions and return structured results as expected.
5. Monitor operator-visible contract failures after release.

## Risks And Mitigations

| Risk | Mitigation |
| --- | --- |
| Prompt text becomes too verbose. | Keep each role contract concise and focused on observable runtime failures. |
| Tests become brittle copy snapshots. | Prefer equality tests between surfaces plus targeted required-phrase assertions. |
| Single source refactor changes non-prompt config behavior. | Limit edits to instruction text wiring and focused helper extraction. |
| Agents over-block instead of requesting actions. | Prompt blockers should apply only when required input, permission, data, action result, or user decision is unavailable. |
| Existing starter files are expected to stay editable. | Do not migrate or overwrite existing project-owned prompt files. |

## Acceptance Criteria

- `src/config/mod.rs` or a nearby Rust module contains one canonical prompt body for each of the six core agents.
- Built-in defaults and generated starter instruction files both reuse the canonical prompt bodies.
- The six prompts explicitly require contract-first structured output discipline.
- The six prompts define role ownership, role boundaries, harness action discipline, completion evidence, and blocker handling.
- Focused tests fail if built-in defaults and starter instruction files drift for any core role.
- Targeted Rust formatting and tests pass, or any inability to run them is reported with a specific blocker.
