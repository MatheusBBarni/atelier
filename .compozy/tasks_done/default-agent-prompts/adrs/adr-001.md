# ADR-001: Improve Default System Prompts for Core Runtime Agents

## Status

Accepted

## Date

2026-06-13

## Context

atelier ships default agent definitions for the structured runtime. The current core agent system prompts are concise but too high-level to reliably teach the runtime protocol, capability boundaries, handoff discipline, blocked-state reporting, and role specialization expected by structured multi-agent workflows.

The core runtime agents in V1 scope are `orchestrator`, `explorer`, `fixer`, `reviewer`, `oracle`, and `consul`. Codebase exploration found two default-text touchpoints that must stay aligned:

- Built-in agent defaults in `src/config/mod.rs`, where `insert_builtin_agent(...)` defines inline instructions.
- Generated starter instruction text from the init flow in `src/config/mod.rs`, including `starter_config_text` and `starter_instruction_files`.

If only one touchpoint changes, implicit built-in agents and freshly initialized projects can drift. This feature should therefore treat prompt changes as runtime quality infrastructure, not cosmetic copy editing.

## Decision

Rewrite the default system prompts for the six core runtime agents as concise role contracts.

Each role contract should define:

- The agent's purpose in the structured runtime.
- The work it should perform and the work it should avoid.
- The capability boundary for the role.
- The requirement to request harness actions instead of using unavailable tools directly.
- The evidence or handoff details expected when completing work.
- How to report blockers.
- The stop condition for the agent's step.

The V1 scope is limited to:

- `orchestrator`: routing, planning, clarification, and delegation decisions.
- `explorer`: read-only repository and context discovery.
- `fixer`: scoped file edits, commands, and verification evidence.
- `reviewer`: risk-first review of completed work without edits.
- `oracle`: focused research and advisory answers from available context.
- `consul`: challenge, trade-off analysis, and decision pressure-testing.

Built-in defaults and starter instruction files must be kept intentionally aligned. V1 should either use a shared source of truth for prompt bodies or add focused alignment/snapshot tests that make divergence visible and deliberate.

## Alternatives Considered

### Improve only generated starter files

Rejected. Freshly initialized projects would improve, but implicit built-in agents would keep the weaker behavior.

### Improve only inline built-in defaults

Rejected. Runtime defaults would improve, but initialized projects would continue receiving weaker editable templates.

### Add one large shared policy prompt to every agent

Rejected. A shared policy would increase token cost, blur role boundaries, and make agents less specialized.

### Rely entirely on runtime validation

Rejected. Validation catches malformed outputs after the fact, but it does not guide agents toward correct handoffs, capability discipline, or blocker reporting.

### Expand V1 to every bundled or disabled agent

Deferred. The user clarified core runtime agents, and limiting the blast radius keeps V1 focused on active default behavior.

## Consequences

Positive consequences:

- Agents should produce fewer malformed structured-runtime responses.
- Agents should make fewer capability-boundary mistakes, such as attempting unavailable tools or forbidden edits.
- Orchestrator routing should become clearer because each core agent has a sharper responsibility.
- Fixer and reviewer handoffs should include more consistent changed-file, command, verification, finding, and blocker evidence.
- Fresh projects and implicit built-ins should behave consistently when defaults are aligned.

Negative consequences and risks:

- Prompt text becomes a maintained runtime surface that must evolve with contract or schema changes.
- Overly verbose prompts could increase token overhead and reduce adaptability.
- Overly narrow role wording could cause agents to refuse reasonable adjacent work or require unnecessary re-delegation.
- Prompt improvements do not replace runtime validation; long-context failures and malformed responses can still happen.

## Out of Scope for V1

- Changing runtime JSON schemas or action contract mechanics.
- Adding telemetry dashboards, even though telemetry would help measure long-term success.
- Redesigning the full agent roster or adding new agents.
- Standardizing disabled or non-core bundled agents.
- Building a comprehensive prompt evaluation suite beyond focused alignment or snapshot tests that fit the repository's existing test style.

## V2 Stretch Goal

Add a small prompt conformance evaluation suite with seeded structured-runtime scenarios covering parse errors, denied capability attempts, handoff completeness, and role-routing ambiguity.
