# ADR-002: Phased Delivery Approach for the Tabbed Help Modal

## Status

Accepted

## Date

2026-06-12

## Context

ADR-001 settled the *scope* of the tabbed help modal (tabs, live Agents/Skills via a
render-signature change, static Approvals prose, deferred approval/roots plumbing, plus an
in-flow onboarding hint). The PRD must choose a *delivery phasing*.

Clarifying decisions made during PRD brainstorming constrain the phasing:

- **Primary success signal (north-star):** faster **time-to-first-successful-run** for new
  users — a locally-measurable outcome derivable from the event-sourced history.
- **In-flow onboarding for MVP:** the **empty-state hint only** (extending the existing
  welcome facts box, which already shows "type /help for commands"). The first-approval
  explainer is deferred because the app has no first-run / show-once tracking today, and
  research warns of hint fatigue.
- **Getting Started emphasis:** lead with a one-line routing **mental model**, then 2
  runnable **example prompts**.
- **Filter behavior:** a **Commands-tab-only** substring filter (not cross-tab search,
  which is the deferred V2 palette).

The target file (`src/tui/mod.rs`) is the repo's most-contended, with adjacent TUI work in
flight, so minimizing per-ship surface area is valuable.

## Decision

Adopt **Approach A — Lean onboarding MVP, enrich in Phase 2**.

**MVP (Phase 1):**

- Tabbed help overlay + keyboard navigation (cycle tabs, Esc closes from any tab), default
  tab = Getting Started.
- Getting Started tab: routing mental model → 2 runnable example prompts → a compact
  **live** agent/runtime summary.
- Reference tabs built from existing content: Commands (catalog-derived), Keys, CLI.
- Approvals & Modes tab: **static** explanatory prose.
- **Live Skills tab** (reads the already-cached skill suggestions — nearly free).
- **Empty-state onboarding hint** in the welcome/empty-chat area.

**Phase 2:**

- Commands-tab substring **filter** (the modal's first in-place input mode).
- **First-approval explainer** (requires introducing show-once / first-run tracking).

**Phase 3 / V2 (stretch):**

- Live approval-mode/roots data (`ConfigStatusView` projection), fuzzy command palette
  across commands/agents/skills, context-adaptive (RunState-aware) help, recency ranking.

## Alternatives Considered

### Alternative 1: Approach B — Full V1 single ship

- **Description**: Ship the entire MVP above **plus** the Commands filter in one release.
- **Pros**: One complete experience; nothing deferred except true stretch items.
- **Cons**: Adds the net-new in-modal input mode and a larger review surface to the
  contended file in a single change; slower first merge, higher conflict risk.
- **Why rejected**: The filter is the only genuinely net-new interaction; isolating it into
  a fast-follow shrinks the first ship without delaying any north-star value.

### Alternative 2: Approach C — Structure-first, two-step enrich

- **Description**: MVP reorganizes only existing content into tabs (no live data, no hint,
  no filter); live agent summary, Skills tab, and the hint arrive in Phase 2.
- **Pros**: Lowest-risk first ship; validates the tab UX before adding live data.
- **Cons**: Delays the differentiator (live, agent-aware help) and the new-user value — the
  exact thing the north-star measures — to Phase 2.
- **Why rejected**: Optimizes for caution over the stated primary goal; the live tabs proved
  nearly free (a render-signature change), so deferring them buys little.

## Consequences

### Positive

- The MVP delivers the north-star value (faster first successful run) and the live
  differentiator immediately.
- Per-ship footprint in `src/tui/mod.rs` stays small; the one net-new interaction (filter)
  is isolated into Phase 2.
- The empty-state hint reuses an existing surface (the welcome facts box), so it's low-risk
  and self-gating.

### Negative

- Two ships instead of one; requires fast-follow discipline so Phase 2 isn't dropped.
- The Approvals tab is static prose until the V2 live-data work.
- No in-help filter until Phase 2 — power users wait a release for fast lookup.

### Risks

- **Phase 2 slips** and the filter never lands — *mitigation*: keep Phase 2 small and
  explicitly tracked; the filter reuses the established type-to-filter pattern.
- **Hint fatigue** if the empty-state hint feels naggy — *mitigation*: it only renders on an
  empty chat and disappears once the user types (self-gating, no latch needed).

## Implementation Notes

Deferred to the TechSpec. The MVP is sequenced to land after the in-flight TUI branches
(@-mention dropdown, agent-roster, slash-command dropdown) to avoid merge conflict, per
ADR-001.
