# ADR-003: Tabbed Help Modal — Technical Architecture

## Status

Accepted

## Date

2026-06-12

## Context

ADR-001 fixed the feature scope and ADR-002 the delivery phasing. This ADR records the
*implementation architecture* for the tabbed help modal, grounded in the current code:

- `render(frame, state: &AppState, ui_state: &mut TuiUiState)` (`src/tui/mod.rs:2085`) already
  holds both `state` and `ui_state` at the two `render_help_modal` call sites (`:2194`,
  `:2236`), so passing live state into help is a pure signature change, not new plumbing.
- `render_help_modal(frame, &Theme)` (`src/tui/mod.rs:3257`) is currently stateless and builds
  one `Vec<Line>` from `slash_commands::help_command_lines()` plus literal key/CLI rows
  (`:3277`, `:3290`).
- The help-visible key branch (`key_event_to_tui_command_with_ui`, `:790`) returns `None` for
  every key except Esc (→ `ToggleHelp`) and Ctrl-C, so tab-navigation keys are free to bind.
- `colors_live_only_in_theme_module` forbids inline `Color::` literals outside `theme.rs`.
- The agent roster builds 3-line-per-agent items inline in `render` (`:2120`) from
  `state.agents`.
- Three tests assert Commands-tab content with `help_visible: true`
  (`renders_help_modal_commands` `:4588`, `help_modal_command_rows_are_catalog_derived`
  `:4624`, `readme_skill_command_wording_matches_help_language` `:4658`).

## Decision

**Tab model.** Introduce `enum HelpTab { GettingStarted, Commands, Keys, Skills, Approvals,
Cli }` with `ALL`, `title()`, `next()`, `prev()`. Store ephemeral `help_active_tab: HelpTab`
in `TuiUiState` (default `GettingStarted`), reset on close. It is **UI state — never added to
the event-sourced `AppState` snapshot.**

**Render.** Change `render_help_modal(frame, &Theme)` →
`render_help_modal(frame, state: &AppState, ui_state: &TuiUiState, theme: &Theme)`. It draws a
theme-token tab strip (active tab highlighted via existing tokens — no `ratatui::Tabs`) and the
active tab's body. Each tab body is a **pure builder** returning `Vec<Line>`:
`getting_started_lines`, `commands_tab_lines` (from `catalog()`), `keys_tab_lines`,
`skills_tab_lines` (from `ui_state.skill_suggestions`), `approvals_tab_lines` (static prose),
`cli_tab_lines`.

**Shared roster builder.** Extract the inline roster loop into
`agent_roster_items(theme, agents, style: RosterRowStyle)` where `RosterRowStyle` is `Full`
(3 lines, used by the Ctrl-L roster) or `Compact` (1 line, used by Getting Started). One data
path, two presentations — no duplication.

**Key routing.** Add `TuiCommand::HelpNextTab` / `HelpPrevTab`. In the help-visible branch,
bind Right + Tab → `HelpNextTab`, Left + Shift-Tab → `HelpPrevTab`; Esc still closes. The
handlers mutate `ui_state.help_active_tab` via `HelpTab::next/prev`.

**Empty-state hint.** Render-time line(s) in `welcome.rs::facts_lines` beside the existing
"type /help for commands" cue — no events, no persistence, self-gating (welcome only renders
on an empty chat).

**Phase 2 filter.** A dedicated `help_filter: String` in `TuiUiState` with a `.contains()`
filter over the Commands rows (mirroring `skill_suggestions` filtering at `:2067`), driven by
new `TuiCommand::HelpFilterCharacter(char)` / `HelpFilterBackspace`. It does **not** mutate the
composer `state.input`.

## Alternatives Considered

### Alternative 1: ratatui built-in `Tabs` widget

- **Description**: Use `ratatui::widgets::Tabs` for the tab strip.
- **Pros**: Less custom code for the strip.
- **Cons**: Styling requires `Color` values, risking the `colors_live_only_in_theme_module`
  test; less control over interleaving live per-tab content.
- **Why rejected**: A theme-token strip is only a few lines and keeps all color in `theme.rs`.

### Alternative 2: Stateful Tab component / struct

- **Description**: A `HelpTabs` object owning tab state and its own render method.
- **Pros**: Encapsulation.
- **Cons**: Introduces a stateful UI object at odds with the render-from-snapshot discipline;
  more edits to the hot render body.
- **Why rejected**: YAGNI. An enum + pure per-tab builders matches the existing pattern and
  minimizes churn in `src/tui/mod.rs`.

### Alternative 3: `category` field on `SlashCommandSpec` to drive tabs

- **Description**: Tag each command with a tab category in the catalog.
- **Pros**: Direct command→tab mapping.
- **Cons**: Leaks UI taxonomy into the frozen command source of truth; Keys/CLI/Getting Started
  aren't commands.
- **Why rejected**: Per ADR-001 — the Commands tab derives from `catalog()`; Keys/CLI stay
  literal; any grouping derives from the existing `SlashCommandKind`.

### Alternative 4: Reuse the composer input for the Phase-2 filter

- **Description**: Type the filter into the live `state.input` composer.
- **Pros**: No new field.
- **Cons**: Entangles help with the live prompt; risks submitting filter text as a prompt.
- **Why rejected**: A self-contained `help_filter` buffer is cleaner and safer.

## Consequences

### Positive

- Live data reaches help via one signature change; the shared roster builder is a net cleanup
  of code that is inline today.
- All color stays in `theme.rs`; tab state stays out of the serialized snapshot.
- Pure per-tab builders are independently testable and minimize edits to the contended render
  body.

### Negative

- Three tests must select the Commands tab before asserting (contracts preserved, not dropped).
- New `TuiCommand` variants and a net-new tab strip render path.

### Risks

- **Merge conflict** in `src/tui/mod.rs` — *mitigation*: sequence after the in-flight TUI
  branches (per ADR-001/002); per-tab builders are new functions, not edits to existing bodies.
- **Tab-nav keys leaking** to the base handler — *mitigation*: handle them entirely within the
  help-visible branch, which already returns `None` for unhandled keys.
