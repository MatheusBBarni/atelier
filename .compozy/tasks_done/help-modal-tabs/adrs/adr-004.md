# ADR-004: Show-Once Latch for the First-Approval Explainer

## Status

Accepted

## Date

2026-06-13

## Context

Phase 2 of the tabbed help modal (ADR-002) introduces a one-line **first-approval
explainer**: the first time a user ever hits an approval prompt, a muted line explains that
an agent is requesting a gated action and how to approve/deny it. The PRD requires it to be
shown **at most once per user** (`≤ 1 impression`), and ADR-002 explicitly deferred it
because *"the app has no first-run / show-once tracking today."*

The relevant facts in the current code:

- `HistoryStore` (`src/history/mod.rs`) owns the `.atelier/` data root. Each launch creates a
  **fresh** per-session directory under `.atelier/sessions/<id>/`; nothing is read back from
  prior sessions, so there is no existing first-run signal.
- `clean_sessions` deletes only `.atelier/sessions/` and `.atelier/runs/` — a file at the
  `.atelier/` **root** survives session cleanup.
- `AppState` is the only channel from `App` to the pure render path (`watch<AppState>`); the
  renderer never reaches into `App` internals or the filesystem.
- The approval surface renders in two places: the projected `ChatItemKind::Approval`
  (`src/app/chat/projection.rs`, the live surface) and a defensive fallback in
  `src/tui/mod.rs` that only fires when `chat_items` is empty (unreachable in the running app
  because `sync_chat_items` always prepends a welcome item — exercised only by a unit test).

"At most once per user" is cross-session, so the latch cannot live in per-session history or
ephemeral UI state — it must be a small persisted flag outside the session directory.

## Decision

**Storage.** Persist the latch in a single small JSON file at the data-root level:
`.atelier/ui_state.json`, holding `{ "first_approval_explainer_shown": true }`. This mirrors
the existing `metadata.json` convention (serde struct + pretty JSON + `0o600` private
permissions via `write_private_file`). It lives at the root (not under `sessions/`), so it is
shared across all sessions and survives `clean_sessions`. A JSON object (rather than a bare
marker file) is chosen so future show-once UI flags can be added without a new file each time;
all fields use `#[serde(default)]` so the file format is forward-compatible.

**Read/write API.** Add two methods to `HistoryStore`:
- `first_approval_explainer_shown() -> bool` — reads the flag; missing/unparseable file ⇒
  `false` (treated as not-yet-shown; never errors the run).
- `mark_first_approval_explainer_shown() -> Result<()>` — idempotently sets the flag (no-op if
  already set).

**Gating + render.** Add `show_first_approval_explainer: bool` to `AppState`
(`#[serde(default)]`, default `false`). When `App` creates a pending approval, it consults the
latch exactly once: if unset, it sets `show_first_approval_explainer = true` **and** persists
the latch; otherwise it sets the flag `false`. The render path stays pure — both the projected
approval body and the fallback append the explainer line only when the flag is `true`, using
the existing muted theme token (`ChatLineStyle::Muted` / `theme.text_muted`); no inline
`Color::` literals, no change to approve/deny semantics.

## Alternatives Considered

### Alternative 1: Bare marker file (presence = shown)

- **Description**: Touch `.atelier/.first_approval_explainer_shown`; existence is the latch.
- **Pros**: Absolute minimum code; no serde.
- **Cons**: Not extensible — each future show-once flag needs its own file; no room for
  versioning or related state.
- **Why rejected**: A single JSON object costs almost nothing more and consolidates future UI
  latches in one forward-compatible place.

### Alternative 2: Store the latch inside per-session history

- **Description**: Record an event / write the flag under `.atelier/sessions/<id>/`.
- **Pros**: Reuses the per-session event stream.
- **Cons**: A fresh session dir is created every launch and prior sessions are not read back,
  so the explainer would re-show on every launch — violating "at most once per user".
- **Why rejected**: Fails the core cross-session requirement.

### Alternative 3: Decide show/suppress in the render layer (read the file at render time)

- **Description**: Have the renderer read the latch and decide.
- **Pros**: No `AppState` field.
- **Cons**: Breaks the render-from-snapshot discipline (render would do filesystem I/O and
  could not write the latch); the "set exactly once" write has no clean home.
- **Why rejected**: The App owns side effects; the renderer is a pure function of the snapshot.

## Consequences

### Positive

- Introduces the first cross-session show-once primitive with minimal, reusable surface area.
- Render stays pure; the latch write happens once, in `App`, at approval-creation time.
- The flag survives `clean_sessions`, so the explainer never re-shows after the first time.

### Negative

- Adds one `AppState` field (touches every `AppState` literal in tests) and one root-level
  file to the `.atelier/` layout.
- Two approval render surfaces must each gate on the flag (kept in sync).

### Risks

- **Stale/corrupt `ui_state.json`** — *mitigation*: read errors degrade to `false` (explainer
  may show once more) rather than failing the run.
