# ADR-004: Harness-derived verdict from canonical-check exit codes

## Status

Accepted

## Date

2026-06-15

## Context

ADR-001 requires PASS to be grounded in a real executed check, never the agent's self-judgment.
Codebase exploration confirmed the mechanism is feasible and pinned the exact data flow:

- `execute_run_command` (`src/actions/mod.rs:947-993`) captures ground truth: `exit_code =
  output.status.code()` and `ActionStatus::Completed/Failed` strictly from `output.status.success()`,
  embedding `{command, exit_code, stdout, stderr}` in `ActionResult.content`.
- The harness records a durable `command_completed` event `{action_id, command, status, exit_code,
  diagnostic}` (`record_command_completed_with_group`, `src/app/mod.rs:4753-4801`), readable via
  `history.read_events()`. The in-memory `request.action_results` (`:4059`) hold the same ground truth.
- **The verdict is NOT grounded today:** `AgentResult.status` and `AgentResult.verification` are
  model-controlled (reconstructed by `parse_agent_result`, `src/orchestrator/mod.rs:297-312`), so a grader
  could emit `status: completed`, `verification: ["cargo test passed"]` having run nothing.
- The harness already authors deterministic results (`failed_agent_result`, `limit_reached_agent_result`,
  `src/app/mod.rs:5976-6004`) — the same seam a derived verdict uses.
- Per ADR-002, V1 has no configured verify command; the command is agent-discovered. The read-only
  auto-approval allowlist `is_default_read_only_command` (`src/actions/mod.rs:443-484`) already enumerates
  the canonical checks: `cargo test/check/build/clippy/fmt`.

## Decision

Compute a **harness-owned `GraderVerdict`** deterministically from the grade sub-step's recorded command
results, never from the grader's self-attested `AgentResult`:

- **Canonical-check match:** the verdict considers only commands whose (trimmed, lowercased) text matches
  a canonical verification prefix (`cargo test`, `cargo check`, `cargo build`, `cargo clippy`,
  `cargo fmt`), reusing the existing allowlist set as the single source of "a real check."
- **Outcome:**
  - **PASS** — at least one canonical command ran in the grade step AND every canonical command it ran
    exited 0.
  - **FAIL** — at least one canonical command ran and any of them exited non-zero (carry the failing
    command, exit code, and a short failure excerpt as the critique fed to the fixer).
  - **SKIP (done-unverified)** — no canonical command ran (or the command was denied/never executed).
    Never a fabricated PASS; never a punitive FAIL.
- **Representation:** a small harness-constructed struct, kept out of the model-filled contract, emitted
  as a `grader_verdict` history event for durability/observability. `AgentResult.status`/`verification`
  are never consulted for the gate.
- **Runtime briefs untouched:** because the verdict is derived from `command_completed`, the
  codex/claude/cursor agent-result schema briefs need **no** change in V1.

## Alternatives Considered

### Alternative 1: Trust the grader's `AgentResult.status` / `verification`

- **Description**: Gate on the model-reported status/verification strings.
- **Pros**: Zero new derivation code.
- **Cons**: Fully self-attested; the documented failure mode (self-preference bias passes own buggy code).
- **Why rejected**: Violates ADR-001's grounding rule.

### Alternative 2: Any command, all-zero

- **Description**: PASS iff ≥1 command ran and all exited 0, regardless of which command.
- **Pros**: Simplest rule; works for any toolchain.
- **Cons**: Gameable — a passing `echo`/`ls` satisfies the gate; weak grounding.
- **Why rejected**: Reopens the self-attestation hole through the back door.

### Alternative 3: Grader declares its verification command

- **Description**: The grader reports which command is "the verification"; harness grounds on its exit code.
- **Pros**: Supports non-cargo projects in V1.
- **Cons**: Thin self-attestation (the agent chooses *which* command to point at).
- **Why rejected (for V1)**: Revisit in Phase 2 via a configured/auto-detected command (ADR-002), which is
  the authoritative answer to non-cargo projects.

## Consequences

### Positive

- Strong grounding with no config and no contract change; a fabricated `status: completed` is non-load-bearing.
- Reuses the existing allowlist as the canonical-check definition.

### Negative

- V1 is cargo-centric: a non-cargo project's grade SKIPs (done-unverified) until Phase 2's configured command.
- Lint/build that exit 0 with *warnings* count as PASS (an Open Question for Phase 2 to refine).

### Risks

- **Denied/approval-gated command** (e.g. chained `&&`, or normal mode + custom command) → no
  `command_completed` for it → treated as SKIP, not PASS (fail-safe).
- **Grader runs no canonical command** → SKIP, surfaced honestly in chat; Phase 2's configured command makes
  it mandatory.

## Implementation Notes

`struct GraderVerdict { outcome: GradeOutcome (Pass|Fail|Skip), command: Option<String>,
exit_code: Option<i64>, critique: Option<String> }` near `AgentResult` in `src/orchestrator/mod.rs`.
Derive from the grade sub-step's `action_results` / `command_completed` events filtered by the grader
`step_id`, matching commands via the canonical prefix set (factor a shared predicate out of
`is_default_read_only_command`, `src/actions/mod.rs:443`). Emit `grader_verdict` via `record_event`.
