# Atelier — Feature Roadmap

Candidate new features for the `atelier` harness, generated from a multi-agent audit of the
codebase (2026-06-14). Each idea is grounded in atelier's three structural assets:

1. A single capability/approval-gated **action chokepoint** (`src/actions/mod.rs`).
2. An **event-sourced spine** — everything is recorded and projected (`record_event_with_group` → chat projection).
3. A **pluggable `Runtime` trait** behind a `RuntimeKind` dispatch.

Features are organized so new power (cost metering, MCP tools, foreign runtimes, hooks, DAGs)
routes *through* those seams, inheriting atelier's multi-runtime / multi-agent / approval-gated guarantees.

> Status: proposal / backlog. Effort: S (hours) · M (days) · L (1–2 weeks) · XL (multi-week).
> This is an idea catalog, not committed scope — promote items to `.compozy/tasks/<slug>/` to execute.

### Extensibility & Ecosystem

#### MCP tools as a harness-level, capability-gated action surface (refines the empty mcp-integration packet)  _(XL)_

- **Problem:** The mcp-integration packet (.compozy/tasks/mcp-integration/adrs/) is an empty placeholder with no PRD. Meanwhile atelier deliberately strips MCP from the Claude runtime (--strict-mcp-config, --tools "" in src/runtime/claude.rs) so models cannot self-invoke tools. The result: atelier has zero access to the entire MCP tool ecosystem (filesystem servers, GitHub, Postgres, web fetch, company-internal tools) that Claude Code/Cursor users already depend on.
- **What:** Add a harness-owned MCP client (not per-CLI) configured via a new [mcp.servers.<name>] config section (command/args/url/transport). At startup atelier connects, lists tools, and advertises them to the orchestrator prompt. Crucially, an MCP tool call is NOT a runtime side-channel: it becomes a new ActionKind::CallMcpTool with params {server, tool, args}, so the model returns the SAME action_request JSON contract it already uses, and the harness brokers the actual MCP call. The call flows through validate_action_request → ActionDecision → (approval in Normal mode) → execute_action_request, is recorded as events, and projected into chat like every other action.
- **Value:** Unlocks the whole MCP tool ecosystem for EVERY runtime at once (codex, cursor, zai, claude) instead of per-CLI — atelier's multi-runtime nature turns one MCP integration into N runtimes' worth of capability. Because tools route through the existing trust boundary, third-party MCP servers inherit approval gating, capability allowlists, and event auditing for free — a governance story no raw MCP host offers.
- **Fit:** New ActionKind::CallMcpTool variant (src/actions/mod.rs:29) + a base-validation arm in validate_action_request_with_scope (~L176) + executor dispatch in execute_action_request (~L334) + a new Capability::McpTool and ToolName mapping (src/config/mod.rs:28/41/64) so per-agent allowlists govern which tools each agent may call. New [mcp.servers] Raw*/Merged*/final structs through the config ladder (apply_raw mod.rs:909, into_effective mod.rs:1302) and into PrintableConfig redaction. build_orchestrator_prompt (src/orchestrator/mod.rs:672) advertises the live tool list. New event kinds (mcp_tool_called/result) recorded via record_event_with_group and an apply_* arm in projection.rs. Connection lifecycle owned alongside App, parallel to runtimes. ListMcpResourcesTool/ReadMcpResourceTool already exist in the host env as a reference shape.
- **Risks:** MCP servers can return huge/secret payloads — must reuse redact_sensitive_text and the 8KB content-preview caps in projection. Tool schemas are dynamic, so capability mapping needs a sane default-deny policy. Server process lifecycle (spawn/health/timeout/kill) adds the same hung-process latency concern already noted for runtimes. Largest scope item here; should ship behind a feature flag like parallel-groups.

#### External process runtime adapter (BYO agent CLI plugin SDK)  _(L)_

- **Problem:** Adding a new agent CLI today requires forking the repo: a RuntimeKind variant plus editing two closed match arms (check_runtime_availability src/runtime/mod.rs:422-450 and execute_runtime_step_once ~545-578) plus status.rs. There is no way for a user to wire up Gemini CLI, aider, opencode, or an in-house agent without a Rust PR — a hard ceiling on the runtime ecosystem.
- **What:** Add a generic RuntimeKind::External (a.k.a. Process) whose behavior is fully data-driven from [runtimes.<id>] config (command, args, prompt_mode, env passthrough, availability probe args). It reuses the EXISTING structured-adapter protocol the codebase already speaks to codex/cursor: write the prompt_envelope_json with JSON_START/JSON_END delimiters to stdin, stream stdout deltas through the RuntimeEventSink, and parse the result via the shared parse_runtime_output. This is the documented, stable subprocess contract that turns 'add a runtime' from a code change into a config change.
- **Value:** Opens the runtime layer to the broader agent-CLI ecosystem declaratively. Combined with atelier's model-fallback/retry executor and approval gating, any conformant CLI instantly gets retries, parallel-group eligibility, council membership, and action governance. Also collapses today's near-duplicate codex/cursor adapters toward one shared, documented protocol — paying down the triplicated-dispatch and duplicated-prompt-brief smells the brief flags.
- **Fit:** One RuntimeKind::External variant (src/config/mod.rs:251) + one ProcessRuntime impl of the Runtime trait (src/runtime/mod.rs:398) wired into the two dispatch matches, replacing N bespoke arms with one configurable adapter. Reuse prompt_envelope_json + parse_runtime_output (mod.rs:650) and the cursor-style line-aligned BufReader streaming. To participate in retry/fallback it must return RuntimeProviderError::retryable/non_retryable (the codex 'no classification' smell is the cautionary example). Extend From<RuntimeKind> for ProviderId + provider_capabilities in status.rs for /provider:status coverage.
- **Risks:** A user-supplied command is a code-exec vector — must run under the same protected-args validation philosophy as claude/cursor and never inherit unrestricted env/secrets. Protocol versioning matters: a stable, documented envelope/contract version is needed so external adapters don't silently break on schema bumps (note schema_version is currently a 63x-hardcoded magic number). Non-conformant CLIs will surface as ParseError; needs the existing one-shot repair retry.

#### Lifecycle hooks system (observe + optionally veto, over the event spine)  _(L)_

- **Problem:** There is no way to react to what the harness does — no notification when a run pauses for approval while the user is away from the terminal, no audit export, no lint-on-edit, no policy gate beyond the built-in command classifier. Teams adopting agent tooling increasingly require exactly these org-level guardrails and integrations.
- **What:** A [hooks.<event>] config mapping lifecycle events (run_started, step_started, action_requested, approval_required, file_edit_applied, run_completed/failed) to shell commands. Each hook receives the event payload as JSON on stdin. Two tiers: (1) fire-and-forget observers (notifications, audit shipping, lint), dispatched right where events are already recorded; (2) blocking PreAction hooks that can return a veto, feeding the SAME ActionDecision::Denied(reason) the approval system already understands — a programmable second approval layer on top of capabilities + ApprovalMode.
- **Value:** Turns atelier's event-sourced design into a genuine integration platform with almost no new surface: every event already exists, hooks just subscribe. The approval-gated nature makes the blocking tier uniquely valuable — orgs can enforce policy (block writes outside a path, require a ticket id, deny network commands) as code, portable across all runtimes and agents. Desktop-notify-on-approval alone fixes a real UX gap given runs can sit in WaitingForUser indefinitely.
- **Fit:** Observer dispatch hangs off record_event_with_group (src/app/mod.rs:4215) — the single write path every event already funnels through. Blocking hooks slot into the action pipeline at validate_action_request_with_scope / decision_for_command (src/actions/mod.rs:145/decision_for_command) as an extra gate that can downgrade Allowed→Denied, reusing pending_approval/RunState::WaitingForUser plumbing. New [hooks] config section through the config ladder. Hook executions themselves should be recorded as events + projected (apply_history_event) so they appear in chat for transparency.
- **Risks:** Blocking hooks run user code in the hot path — need strict timeouts + kill_on_drop (pattern already exists) and a fail-open/fail-closed policy choice per hook. Must redact payloads before handing to hook stdin (reuse redact_sensitive_text). Avoid recursion (a hook that triggers actions that trigger hooks). Should not block the render/worker thread — dispatch async like the existing pollers.

#### Shareable agent/workflow packs (export + import bundles)  _(M)_

- **Problem:** atelier supports presets (agent overrides) and declarative council presets, but a carefully tuned multi-agent setup — agent roster + models + capabilities + council preset + workflow routing + the skills it relies on — lives trapped in one machine's atelier.toml. There is no way to share 'my code-review crew' or 'my migration squad' with a teammate or the community.
- **What:** atelier export-pack <name> bundles a named slice of config (selected [agents.*], [presets.*], [council] preset, limits, and referenced skill files) into a portable, redacted pack (TOML manifest + skill bodies, or a tarball). atelier import-pack <path|git-url> applies it as a config layer and links its skills into the skills roots. Packs carry a manifest (name, version, required runtimes, declared capabilities) so import can warn on missing runtimes before use. A 'registry' can start as nothing more than git URLs.
- **Value:** This is the feature that exploits atelier's defining trait — multi-agent orchestration — as a SHAREABLE unit. A pack isn't a dotfile, it's an entire reviewing/building crew with its routing and skills. Lowers the activation energy for teams to standardize on a vetted agent setup, and seeds a community ecosystem of crews/workflows. Synergizes with hooks (ship policy with the crew) and the skills registry below.
- **Fit:** Export reuses the already-redaction-aware EffectiveConfig→PrintableConfig projection (build_printable_config) so secrets/api_key_env names never leak into a pack. Import lands as a new config layer in load_effective_config (src/config/mod.rs:1647) ordered between home and local, or via apply_raw replay — presets already model 'apply-before-local-override' (apply_preset mod.rs:1053). New CLI modes in run_cli_with (src/cli.rs) following the existing batch-command/report-struct idiom (DocgenSummary/CodemapSummary). Skill files copy into skill_roots_with_home (src/skills/mod.rs:332).
- **Risks:** Importing config that references runtimes/models the user lacks must degrade gracefully (manifest pre-check, not a hard into_effective failure). Packs that bundle skills are an untrusted-content vector — must preserve the skills-are-guidance disclaimer and show a review/diff on import. Versioning/conflict policy needed when an imported pack collides with existing agent ids.

#### Skill registry & install command with lockfile  _(M)_

- **Problem:** Skills are powerful and already discovered from four roots, but acquiring them is fully manual: a user must hand-copy SKILL.md trees into .agents/skills or .claude/skills, with no versioning, no update path, and no provenance. There is no 'marketplace' on-ramp despite skills being atelier's most user-facing extension point.
- **What:** atelier skill add <git-url|name>, skill update, skill list, skill remove. add fetches a SKILL.md (+ assets) into the project (.agents/skills/) or personal (~/.agents/skills/) root and records source + resolved ref + content checksum in a .agents/skills/skills.lock manifest for reproducible, auditable installs. update re-resolves against the lock; the existing fingerprint cache already invalidates the dropdown automatically. A registry can be a simple index of git URLs to start.
- **Value:** Directly delivers the 'skills marketplace/registry' charter goal and makes the most discoverable extension point installable, versioned, and shareable. Pairs with packs (a pack can declare skill dependencies the installer resolves) and the config importer (imported .claude/skills become managed, updatable installs rather than loose copies).
- **Fit:** Builds entirely on the existing skills subsystem: skill_roots_with_home + discover_skill_metadata (src/skills/mod.rs:332/435) already define precedence and parsing; canonical_id/aliases already handle identity. New CLI subcommands in run_cli_with (src/cli.rs) run before/after config load like --init-config/--codemap. The fingerprint-based SkillSuggestion cache (schema-versioned) already refreshes on disk change, so installs surface in the /skill: dropdown with no extra wiring. Reuse the 0700/0600 perms scaffolding pattern from init_config.
- **Risks:** Installing remote skill content is the classic supply-chain risk — checksums in the lock + a show-once review/diff on add are essential, leaning on the already-tested invariant that skill bodies are guidance-only and never bypass approvals. Network fetch should be off the UI thread (skills I/O currently runs on the render thread — a known smell to avoid replicating). Ambiguity rules already handle same-tier name collisions; install UX should surface them.

#### Config importer from Claude Code / Cursor / Codex (zero-friction onboarding)  _(M)_

- **Problem:** atelier already runs the claude/cursor/codex CLIs, but a new user starts from an empty atelier.toml even when their repo is full of existing conventions: CLAUDE.md, .claude/skills, .mcp.json server definitions, .cursor/rules, AGENTS.md. Re-authoring all of that by hand is the single biggest adoption tax.
- **What:** atelier import-config --from claude-code|cursor|codex inspects a repo's existing agent-tool config and generates a starter atelier.toml plus skill links: it maps .claude/skills (and ~/.claude/skills) into the skills roots, lifts CLAUDE.md/AGENTS.md/.cursor/rules into an agent system-prompt file, and — critically — translates .mcp.json / claude_desktop_config.json server entries straight into the new [mcp.servers] section. Output is reviewable (writes to atelier.toml.new or prints a diff), never destructive.
- **Value:** Collapses onboarding from 'read the config docs and author TOML' to one command, meeting teams where they already are. It is the connective tissue across this whole lens: it feeds the MCP feature (server entries), the skills registry (existing skills become managed), and packs (an imported setup can immediately be exported as a shareable pack). Strong wedge for migrating Claude Code/Cursor users.
- **Fit:** New CLI mode in run_cli_with (src/cli.rs), running before config load like --init-config. Emits the same starter_config_text-shaped TOML the config module already owns, exercising the deny_unknown_fields Raw* schema as validation. Skill discovery already supports .claude/skills (skill_roots_with_home src/skills/mod.rs:332), so imported skills are found with no new code. MCP-server translation depends on the [mcp.servers] schema from the MCP feature, making this a natural follow-on.
- **Risks:** Foreign config formats drift (Claude/Cursor settings schemas change), so the importer is a best-effort translator that must clearly mark uncertain mappings rather than silently producing a broken atelier.toml. Must never copy secrets — translate api_key references to api_key_env names only (matching the redaction-by-construction policy). MCP-server translation is blocked on the MCP feature landing first; ship the skills/prompt translation independently.

### Orchestration

#### Sub-task DAG execution (dependency-ordered fan-out)  _(XL)_

- **Problem:** Parallel groups (DecisionNextStep::ParallelGroup) are flat: every child must run concurrently with exact disjoint write scopes and no inter-step dependencies. Real features are ordered DAGs (e.g. define interface -> implement against it -> write tests), so today the orchestrator must serialize everything or it cannot express the dependency at all, losing the parallelism atelier already has the machinery for.
- **What:** Add a third next-step kind, DecisionNextStep::TaskGraph { nodes, edges }, where each node carries agent/instruction/required_capabilities/file_scope and edges declare depends_on. The driver computes a topological order and executes the graph in waves; each wave is run through the EXISTING run_parallel_group path (so disjoint-scope, approval, and limit guarantees are enforced per wave), and a completed node's AgentResult is appended to run.previous_results so downstream nodes receive upstream outputs as context. Validation rejects cycles, enforces per-wave scope disjointness, and reuses validate_parallel_group_plan path-safety per wave.
- **Value:** Unlocks correct, fast multi-agent execution for the most common real-world shape (ordered work with independent branches) and turns the existing flat fan-out into a general scheduler -- the single highest-leverage orchestration upgrade and a clear differentiator over single-threaded agents.
- **Fit:** New DecisionNextStep variant (src/orchestrator/mod.rs:85) + validate_decision_next_step arm (~mod.rs:486) reusing validate_parallel_group_plan (mod.rs:503); new handler branch in handle_orchestrator_decision (src/app/mod.rs:1884) that loops waves over run_parallel_group (app/mod.rs:2005); new RunStepResult variant (orchestrator/mod.rs:162) + a projection arm in src/app/chat/projection.rs; advertise the kind in build_orchestrator_prompt (orchestrator/mod.rs:724) gated behind a new features flag like the existing parallel_step_groups gate.
- **Risks:** Cross-wave scope validation and cycle detection are subtle; orchestrator prompt complexity grows (models may emit malformed graphs -> lean on the existing parse-repair retry); the disjoint-write invariant must hold per wave, not globally, so the validator needs careful per-wave grouping. Largest surface of the set.

#### Self-grading verify-and-retry loop  _(L)_

- **Problem:** An Edit agent can return Completed work that is wrong or unverified, and nothing automatically checks it. The config already ships max_review_fix_cycles (config/mod.rs:190) but there is no automatic grade->fix loop wired to it -- catching bad work requires a human or an explicitly-requested council review, which the orchestrator only routes to for high-risk prompts.
- **What:** After a configured implementation step completes, automatically route to a grader agent (Review/Verify capability) that emits a structured pass/fail grade plus a concrete critique using AgentResult.verification/findings/blocker. On fail, re-dispatch the SAME agent with the critique appended to its instruction, bounded by max_review_fix_cycles. Implemented as a virtual routing target (a sentinel id resolved like council) so it slots into the existing decision loop rather than a bespoke path, with each grade/retry recorded as events.
- **Value:** Materially raises output quality and trust without human babysitting -- a built-in critic loop is exactly the self-correction larger agent frameworks charge for, and it reuses a limit field atelier already validates but barely exercises.
- **Fit:** Reuses max_review_fix_cycles (config/mod.rs:172-190) and the council-style synthesized-routing pattern (sentinel like COUNCIL_WORKFLOW_AGENT_ID, orchestrator/mod.rs:9; synthesis at app/mod.rs:5503/5557); AgentResult already carries verification/findings/blocker (orchestrator/mod.rs:154-158); new event kind + apply_* arm in src/app/chat/projection.rs to show grade/retry rounds in chat.
- **Risks:** Cost multiplier per implementation step; false-negative grades can loop until the cap; must respect approval gating and the scattered per-step limit re-checks (re-use a shared guard rather than adding a 6th copy). Grader prompt must produce a machine-parsable verdict.

#### Budget-aware orchestration with model tiering  _(L)_

- **Problem:** Limits cover steps, wall-clock, step-time, and actions (config/mod.rs:172) but NOT tokens or cost. A long run can silently burn provider quota with no ceiling, and the new /provider:status usage data is never fed back into routing decisions. The charter's budget-aware + model-tiering goals have no home today.
- **What:** Add a max_run_cost / max_run_tokens Limit and optional per-model cost metadata; accumulate usage from runtime result/stream metadata (Claude and zai surface token/usage data) and re-check the budget at each step entry exactly like the other limits. #### Run memory / shared blackboard  _(M)_

- **Problem:** Context between steps is just run.previous_results (raw prior outputs) plus a recent-history window; there is no curated, durable, typed memory. The RecordNote action and its capability-free mapping already exist (config/mod.rs:48,69) but are underused, and cross-run knowledge (decisions made, conventions discovered, known gotchas) is lost between runs.
- **What:** A structured run-memory store under .atelier/ that agents populate through the existing RecordNote action as typed entries (decision / fact / todo / risk). Entries are fed back into runtime_request alongside recent_context so later steps and later runs see the accumulated blackboard, and they project into chat as a compact memory panel. Optionally project-scoped so a follow-up run recalls prior decisions, reusing the read-only prompt-history recall plumbing.
- **Value:** Gives multi-step and multi-run orchestration a real working memory -- agents stop re-deriving the same facts, decisions persist, and the harness gains a differentiated 'it remembers what we decided' capability built on an action that already exists.
- **Fit:** RecordNote ActionKind/executor already present (src/actions/mod.rs) with no capability gate; persist via the .atelier history store (src/history/mod.rs) following its private-file + show-once patterns; inject into runtime_request next to runtime_recent_context (app/mod.rs:3815); new event kind + apply_* projection arm (src/app/chat/projection.rs).
- **Risks:** Unbounded memory bloats prompts and token cost -> needs capping/eviction (the projection already has an unbounded action_context map smell to avoid repeating); must run notes through the existing secret-redaction and private-file policy; staleness if memory contradicts current code.

#### Best-of-N ensemble step (cross-runtime quorum + judge)  _(XL)_

- **Problem:** atelier's defining asset -- multiple runtimes and models (Codex, Claude, Cursor, zai) -- is never used for quality: every step runs on exactly one model. Hard or high-stakes steps would benefit from competing attempts, but there is no way to race them and pick a winner.
- **What:** A new routing workflow (sentinel-resolved like council) that runs the SAME instruction across N agents/runtimes concurrently into per-attempt scratch scopes (so the disjoint-write invariant is preserved by isolation, not by partitioning the task), then a judge agent with Review capability scores/merges the attempts and only the winning patch is promoted through the normal approval gate. Directly exploits the multi-runtime fleet.
- **Value:** Turns the multi-runtime architecture into a quality lever (best-of-N is a proven accuracy boost) and is something single-provider agent tools structurally cannot offer -- a headline differentiator for the council/review charter.
- **Fit:** Reuses parallel execution scheduling (run_parallel_group, app/mod.rs:2005) but with shared task + isolated scratch scopes; judge via the council synthesis pattern (app/mod.rs:5557); new sentinel + validation alongside COUNCIL_WORKFLOW_AGENT_ID (orchestrator/mod.rs:9); new result variant + projection arm; advertise in build_orchestrator_prompt only when enabled.
- **Risks:** Competing attempts write overlapping files, so it needs a staging/scratch mechanism that the current EXACT-disjoint-write-scope validator forbids -- the biggest design lift. N-times cost; judge reliability is the quality ceiling; promoting one scratch patch cleanly into the real tree must re-run path/approval validation.

#### Upfront plan preview and checkpoint approval  _(L)_

- **What:** On the first orchestrator turn of a run, surface the structured plan (the existing plan field, enriched with per-step agent + risk) as an approval-style preview the user can Accept / Edit / Reject before any write actions run, and let the orchestrator mark high-risk steps as checkpoints that pause for confirmation mid-run. - **Fit:** Builds on RunState::Planning (orchestrator/mod.rs:16) and OrchestratorDecision.plan (mod.rs:56); reuses resolve_pending_clarification / WaitingForUser resume (app/mod.rs:1689) and the help->clarification->approval key-routing cascade (src/tui/mod.rs); new event kind + projection arm to render the plan card and checkpoint pauses.

- **Problem:** atelier routes each step across Codex/Claude/Cursor/zai with per-agent model-fallback chains, council reviews, and parallel groups, yet there is zero visibility into how many tokens or dollars a run consumed. Nothing in any adapter captures usage; RuntimeEvent (runtime/mod.rs:203) has no Usage variant. Heavy solo users have no way to know which agent/model/step is burning their quota — the exact gap provider-usage-status (a pre-run readiness check) explicitly declines to fill.

Surface a live token counter in the roster/footer and a `/cost` AppCommand that prints a per-agent / per-model / per-runtime breakdown for the session.
- **Value:** Cost is the #1 operational anxiety for multi-agent harnesses; making per-agent/per-model spend visible lets users tune model_fallbacks, disable expensive council routing, and catch runaway loops. Pricing is a new config section following the Raw*/Merged*/final ladder.
- **Risks:** Usage fields are inconsistent across providers (Cursor may not expose them; Codex's lossy UTF-8 stream needs care) so coverage will be partial and must degrade to 'unknown' rather than fabricate — same trap provider-usage-status guards against. $ estimates risk being mistaken for billing truth; must be clearly labeled and rate-table-driven, never inferred.

#### Crash recovery & resumable runs from the event log  _(XL)_

- **Problem:** App::new always starts a brand-new session (HistoryStore::new mints a fresh session_id every launch, history/mod.rs:95). If atelier crashes, the terminal closes, or a long council/parallel run is killed, the durable events.jsonl is orphaned — there is no production path to rebuild it. ChatProjection::rebuild (projection.rs:50), the intended fold-the-whole-log entry point, is exercised only under #[cfg(test)]; production folds incrementally and never resumes.
- **What:** Add `atelier --resume [<session_id>]` (and a `/resume` picker) backed by a new HistoryStore::open that reopens a prior session directory. On resume, fold the persisted events through ChatProjection::rebuild to restore chat_items, and reconstruct RunState from the last RunRecord (write_run_record already persists terminal run state). Terminal runs (Completed/Failed/LimitReached) reopen read-only with full transcript; an Interrupted run can be re-driven using the existing PausedStep/StepResume machinery the approval/clarification flow already uses. - **Value:** Resumability is the single biggest reliability gap: long agentic runs are exactly the ones that get interrupted, and today that work is irrecoverable. It finally makes the event-sourcing investment pay off operationally and turns the test-only rebuild path into a load-bearing production feature.
- **Fit:** Reuses the exact contract the architecture already advertises: read_events_from_path + list_session_event_paths (history/mod.rs) feed ChatProjection::rebuild (projection.rs:50). Re-driving an interrupted run reuses StepResume/PausedStep and drive_and_replay (app/mod.rs:1685,1783). A CLI mode slots into run_cli_with's return-Ok dispatch chain (cli.rs).
- **Risks:** Highest-effort item. RunState reconstruction must agree byte-for-byte with the incremental projection or chat will diverge; mid-step interruption mid-action is hard to resume safely (an ApplyPatch/RunCommand may have partially executed). Strongly motivates plan 010 (retire legacy chat rendering) first so resume only has one render path to satisfy. Re-driving must re-gate actions through approvals, not replay them blindly.

#### Shareable run export bundle (--export-session)  _(M)_

- **Problem:** There is no way to get a run out of atelier for sharing, bug reports, review, or record-keeping. The transcript lives only in the live TUI and raw JSONL under .atelier/. #### Rate-limit aware backoff and degraded-mode routing  _(L)_

- **Problem:** Rate-limit handling is the harness's weakest reliability link. RuntimeProviderError carries only a boolean `retryable` (runtime/mod.rs:49); same-model retries fire immediately with no backoff and ignore provider Retry-After, and Codex classifies nothing as retryable so every 429/overload skips the entire retry+fallback machinery. Users just see an opaque failure with no 'throttled, waiting' feedback.
- **What:** Extend RuntimeProviderError with optional retry_after: Option<Duration>; have adapters parse provider throttle signals (zai HTTP 429 + Retry-After header, Claude/Codex stderr keywords). In execute_runtime_step_streaming (runtime/mod.rs:467) honor the backoff between SAME_MODEL_PROVIDER_ATTEMPTS and emit a RuntimeEvent::Status ('rate limited on <model>, retrying in Ns') so the TUI shows an explicit throttled state instead of a stall. Add Codex retryable classification (closing the documented smell). Add an optional config `degraded` policy: when a model chain is exhausted by throttling, route to a designated cheaper/available runtime rather than failing the run.
- **Value:** Directly converts avoidable run failures into successful (if slower or degraded) runs and gives honest live feedback during provider incidents — exactly the multi-runtime advantage atelier should exploit. Backoff + Retry-After also reduces the chance of compounding a rate limit by hammering it.
- **Fit:** Lives in the executor every step already flows through (execute_runtime_step_streaming, runtime/mod.rs:467) and the model_chain/fallback loop; reuses the typed-error chain-walk (is_retryable_provider_error) rather than call-site string sniffing. Throttle feedback rides the existing RuntimeEvent::Status -> projection path. Degraded routing is a config policy consulted in the same loop.
- **Risks:** Provider throttle signals are heuristic (stderr substring for Codex/Claude) and can misclassify; backoff could mask a hard outage as a long wait, so it must be bounded and cancellable (interrupt already exists). Degraded auto-routing must respect the target runtime's capabilities/approval mode and never silently downgrade a high-trust step.

There is no safety net inside the harness for the very FS mutations it is designed to broker.
- **What:** An 'undo last edit' action (palette entry + key) that reverses the most recent WriteFile/ApplyPatch by deleting a just-created file or applying the inverse of a recorded diff, surfaced as a normal harness action so it is itself recorded as an event. A short undo stack lets the user step back several edits within the session.
- **Value:** A genuine safety net for an autonomous, approval-gated file-mutating agent — the difference between 'oops' and a recovery — and a strong confidence-builder for running in Yolo mode. Exploits atelier's event-sourced action history that already carries before/after detail.
- **Fit:** The chat projection's action_context already stashes the diff and a capped content_preview keyed by action_id (projection.rs action_context inserts), and file_edit_applied events record the change. Undo inverts that recorded diff via the existing strict apply_unified_diff machinery (actions/mod.rs:1055) or removes a created file, executed through execute_action_request (actions/mod.rs:278) so it flows through the same capability/scope gate and is event-recorded. Triggered via the command palette / a TuiCommand.
- **Risks:** TOCTOU — the file may have changed since the edit (must verify current content matches the post-edit state before reverting, else refuse). apply_unified_diff rejects create/delete/binary, so created-file undo is a separate delete path; the 8KB content_preview cap means very large edits need the full diff re-fetched from the event, not the preview. Partial-batch writes have no rollback today (existing smell), so multi-file undo must be best-effort and clearly reported.
