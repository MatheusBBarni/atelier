# Atelier Audit & Roadmap

## 1. Executive summary

Atelier is architecturally coherent — a clean event-sourcing spine (`record_event_with_group` → chat projection), a typed orchestrator contract, a pluggable `Runtime` trait, and a single capability/approval action chokepoint — but it has accreted four god-files (`src/app/mod.rs` ~13.4k LOC / 119-method impl, `src/tui/mod.rs` ~11.8k LOC, `src/app/chat/projection.rs` 4.3k LOC, `src/config/mod.rs` 3.4k LOC) and several drift-prone, hand-synced invariants. The most urgent, highest-leverage fix is not in the code at all: **CI never runs `clippy`, `fmt`, or `cargo test` except during a release** (`.github/workflows/release.yml`), so most PRs and pushes to `main` get zero Rust CI — directly contradicting CLAUDE.md and meaning every security/correctness fix below would land unverified. Pair that with a tight cluster of command-classification security gaps (`find`/`cat`/`grep` auto-allowed with no approval, `actions/mod.rs:443-484`) that are real RCE/exfiltration primitives in `normal` mode. The verified correctness/perf findings are mostly contained (a frozen roster tick, per-delta full-transcript clones, a stuck-run error path) — none corrupt data, but they erode the operability of a concurrent harness. Net: the foundations are sound; spend the next cycle making the project *verifiable* (CI, doctor exit codes, targeted tests) and *safe* (command classification, redaction, symlink/VCS hardening), then attack the god-files and ship the operability features (cost telemetry, resume, export) the event-sourced design already enables.

## 4. Strategic refactors (sequenced)

The god-files are extractable because the seams are unusually clean (free functions or `impl App` you can split with `impl super::App`). Do the enabler types first — two of them also fix verified bugs.

1. **Enabler types (M, also bug-fixes).**
   - `enum HistoryEventKind` (serde rename) used by both recorders and `apply_history_event` → a missing projection arm becomes a compile error; fixes the dropped `step_limit_reached`/`provider_status_viewed`/`step_cancel_failed` (P2). Replaces the `schema_version: 1` magic literal (63 sites) too.
   - `struct EventScope { run_id, group_id: Option<String>, step_id }` → collapse every `record_*`/`_with_group` pair and the duplicated `persist_parse_error` body.
2. **Decompose `src/app/mod.rs`** into `impl super::App` submodules: `commands.rs`, `queue.rs`, `parallel.rs`, `council.rs`, `recording.rs` (~30 recorders), `limits.rs`; keep the drive loop in `mod.rs`. Mechanical, no signature changes.
3. **Unify the three step-execution paths** (`execute_runtime_step_with_actions:3935` serial, `spawn_parallel_runtime_task:5795` parallel, `execute_runtime_step:3247` council) into one core taking a policy (pause-vs-queue approval; can-request-actions) + a single per-step limit guard. Highest-value architectural move: it lets council request actions, shares retry/fallback, and ends the triplicated limit/event logic. (This is the natural home for the rate-limit backoff feature.)
4. **Decompose `src/tui/mod.rs`** into `worker.rs`, `input.rs`, `routing.rs`, `dropdowns/`, `render/`, `clarification.rs`. While there, **model dropdowns as one ordered slice of a `Dropdown` trait** computed once per frame — kills the hand-mirrored precedence (`1128-1142` vs `2619-2628`) and the per-frame double-build.
5. **Split `projection.rs`** into `chat/json_humanize.rs` (the `human_json_*`/`readable_*`/`concise` cluster, shared to kill the triplicated `concise()`) and `chat/builders.rs` (the `apply_*` family), leaving the fold/upsert/index in `projection.rs`.
6. **RuntimeKind factory + trait dispatch** (`build_runtime(&RuntimeConfig) -> Box<dyn Runtime>`), with `requires_preflight_availability()` as a trait method (replacing the Claude special-case at `runtime/mod.rs:479`). Unblocks the External-runtime feature.
7. **`config/mod.rs` split** (`types/merge/defaults/validate/scaffold`) and **generate `starter_config_text` from `builtin()`** (or round-trip test) so structural defaults can't drift.

Also fold in the smaller hand-synced-state fixes opportunistically: move `AppState.input` into `TuiUiState` (kill the snapshot back-channel), and derive the singular `active_step`/`live_step` from the plural rather than hand-syncing.

**Cycle 1 — make it verifiable and safe (risk reduction).**

- Land the two enabler types (`HistoryEventKind`, `EventScope`) — they fix the dropped-event-kind bug and unlock the decompositions.

**Cycle 2 — operability + momentum.**
- Fix the verified correctness/perf cluster: run-drive error path (mark `Failed`, clear `active_run_id`), streaming hot-path clones (coalesce live preview to the 250 ms flush, change-gate `set_agent_status`, `Arc<ChatItemView>`), roster-tick freeze, serial-interrupt `live_steps` leak.

- Begin `app/mod.rs` decomposition; ship the first low-effort flagship: **token/cost telemetry (#1)** and **run export (#2)** — both ride existing seams and give immediate operational payoff.

**Later cycles — platform + scale.**
- Finish god-file decompositions (tui, projection, config) and the RuntimeKind factory.
- Execute plan 010 (retire legacy chat rendering) using the new `HistoryEventKind` arms, then build **resume/session browser (#7)**.
- Land the ecosystem bets: **MCP (#8)**, **External runtime (#11)**, **hooks (#10)**, and the **DAG executor (#9)** — each flag-gated like the existing parallel-groups feature.
- Add `tracing`/spans (P2 DX) once the drive loop is decomposed so spans map to clean module boundaries.

Housekeeping (any time, near-zero cost): promote the 6 completed `.compozy/tasks/*` packets to `tasks_done/` and reconcile the stale `MOVE_REPORT.md`/`REPORT_pending.md` counts so the roadmap state stops lying.

## Appendix A — All verified improvements (52)

### ARCHITECTURE

- **[HIGH · L]** app/mod.rs is one 4,070-line `impl App` block (119 methods) with no submodule decomposition
  - _src/app/mod.rs:834-4904_ — A single inherent `impl App` block spans lines 834-4904 and holds 119 methods covering six unrelated concerns: built-in command dispatch (handle_goal/config/provider_status/queue/subtask/workflow), the orchestrator drive loop (drive_run_inner/handle_orchestrator_decision/run_orchestrator_step/run_agent_step), parallel groups (run_parallel_group/handle_parallel_child_action/resolve_parallel_approval, ~11 methods), the council workflow (run_council_workflow + report helpers), ~30 event recorders, and limit guards. These are clearly separable cohesive clusters but live in one impl in one file, so any change forces navigating a 13.4k-LOC file and every method has unrestricted access to all of `self` (state/history/config/channels). Rust permits splitting an inherent impl across files (`impl super::App` in submodules), so the seams are extractable without changing the type.
  - → Split `impl App` into submodules under src/app/: commands.rs (handle_* dispatch), queue.rs (replay/follow-up), parallel.rs (group execution+approval), council.rs, recording.rs (the ~30 record_*/persist_* event recorders), limits.rs (the *_limit_reached/stop_for_* guards). Each becomes an `impl super::App` block in its own file. Keep the core drive loop in mod.rs. This is mechanical (move methods, no signature changes) and immediately shrinks the navigation surface.
- **[HIGH · M]** Event→projection contract is stringly-typed and silently drops three emitted event kinds from chat
  - _src/app/chat/projection.rs:58-111_ — The chat projection (the sole derived chat surface, since the legacy state.events render path at tui/mod.rs:2790 is unreachable once the always-prepended welcome item makes chat_items non-empty) dispatches purely on `event.kind.as_str()` against ~50 string literals, with a catch-all `_ => {}`. The producer in app/mod.rs builds the matching kind strings independently with no shared schema. This has already drifted: the app emits `step_limit_reached` (mod.rs:3676 step-time, 3695 step-action), `provider_status_viewed` (mod.rs:1232 — the entire `/provider:status` output), and `step_cancel_failed` (mod.rs:3638), but none of these has a match arm in apply_history_event, so they hit `_ => {}` and produce no chat item. A step time/action limit stop sets RunState::LimitReached yet is invisible in the transcript, while the sibling `run_limit_reached` is handled. plans/010 plans to retire the legacy fallback but its Step-1 characterization list only names provider status — it omits step_limit_reached and step_cancel_failed, so executing plan 010 as written would permanently delete those flows from chat.
  - → Replace the stringly-typed contract with a shared `enum HistoryEventKind` (with serde rename) used by both the recorders and the projection match, making a missing arm a compile error. As an immediate fix, add apply_* arms for step_limit_reached / provider_status_viewed / step_cancel_failed, and extend plan 010's characterization list to cover them before retiring legacy_chat_line.
- **[HIGH · L]** Three divergent step-execution paths re-implement the same action/approval/limit machinery
  - _src/app/mod.rs:3935,5795,3247_ — The same logical operation — run one runtime step, surface actions, enforce limits, record events, transition status — is implemented three separate ways. (1) Serial: execute_runtime_step_with_actions (3935) → drive_runtime_step_streaming (3835) → execute_runtime_step_streaming (3857), which pauses the whole run for one approval. (2) Parallel: spawn_parallel_runtime_task (5795) → execute_runtime_step_streaming (5807), which queues approvals and keeps siblings running. (3) Council: run_council_workflow → execute_runtime_step (3247, the only other caller) wrapped in its own tokio::time::timeout, using the buffered non-streaming path with bespoke error/timeout handling, so councillors cannot request actions at all. Each path independently re-checks wall_clock/step_time limits and re-records events (with vs without group_id), so a behavior or limit change must be made and kept consistent in three places.
  - → Extract a single step-execution core (input: RuntimeRequest + scope/limit context; output: produced events + StepOutcome) and have serial, parallel, and council call it with a policy parameter (pause-vs-queue approvals; can-request-actions). Unify council onto the streaming executor so it shares retry/fallback and can participate in the action contract. Centralize the per-step limit re-check into one guard.
- **[HIGH · L]** tui/mod.rs is a flat 180-function module mixing lifecycle, input editing, key routing, four dropdowns, and all render surfaces
  - _src/tui/mod.rs:471-4917_ — src/tui/mod.rs (11.8k LOC) is a single flat module of ~180 free functions with no internal boundaries, spanning: process/worker lifecycle (run_tui 471, run_loop 559, run_app_worker 957, shutdown_app_worker 1035), prompt editing (insert_input_character 1528, move_input_cursor 1564, ...), key routing (key_event_to_tui_command* 1056/1388), four near-duplicate dropdowns (agent/skill/command/file_mention each with key_command + apply_* + build + render_* + *_item), the clarification composer (2024-4917 scattered), skill caching, and every render surface (render 2522, render_chat 2732, render_queue_panel 2671, render_help_modal 3682 + tab builders, roster items, footer). Because almost every function operates on `(&mut AppState, &mut TuiUiState)` plus module consts (not private struct internals), the seams are unusually clean to extract — unlike app/mod.rs there is no impl to split, just function moves.
  - → Carve into submodules: tui/worker.rs (run_app_worker + pollers + channels), tui/input.rs (composer editing + recall), tui/routing.rs (key/mouse → TuiCommand), tui/dropdowns/ (one file per dropdown or a shared trait, see precedence finding), tui/render/ (chat, roster, queue, help, footer), tui/clarification.rs. Functions move with no signature changes.
- **[LOW · M]** config/mod.rs encodes structural defaults twice (builtin() vs starter_config_text) with no equivalence test
  - _src/config/mod.rs:709,2195_ — config/mod.rs (3.4k LOC) is a god-module mixing type ladders, the layered merge engine, default-prompt string constants, validators, the redacted projection, and FS scaffolding. Within it, the built-in defaults are encoded twice and by hand: MergedConfig::builtin (709) constructs runtimes/agents/models/capabilities in Rust, while starter_config_text (2195) re-encodes the same runtimes, models, efforts, capabilities and enabled flags as an untyped TOML blob written by --init-config. Alignment tests only cover prompt TEXT (core_builtin_and_starter_prompts_stay_aligned); the structural defaults can silently diverge, and the starter TOML has no compile-time guarantee it even parses against the deny_unknown_fields schema.
  - → Generate starter_config_text from builtin() (serialize the effective defaults to TOML) instead of hand-writing it, or add a round-trip test that parses starter_config_text and asserts the resulting EffectiveConfig equals builtin(). Separately, split config/mod.rs into types.rs / merge.rs / defaults.rs / validate.rs / scaffold.rs.
- **[MEDIUM · M]** Missing EventScope abstraction forces a doubled `_with_group` method family across the recorder layer
  - _src/app/mod.rs:4073-4162_ — Every event recorder threads the run/group/step identity as three positional args (run_id, group_id, step_id). Because group_id is optional and added late, the recorder layer carries paired methods: record_event/record_event_with_group (4164/4215), record_action_completed/_with_group (4366/4376), record_command_started_if_executable/_with_group (4406/4424), flush_runtime_stream_coalescer/_with_group (4560/4570), record_action_specific_events/_with_group (4724/4734). Most non-group variants are thin delegators, but persist_parse_error (4073) and persist_parse_error_with_group (4117) are ~40-line near-identical bodies that do not even delegate. The doubling is a symptom of a missing value type: the (run_id, group_id, step_id) triple should be one `EventScope` struct.
  - → Introduce `struct EventScope { run_id, group_id: Option<String>, step_id }` and make record_event take `&EventScope`. Collapse each `_with_group` pair into one method; serial callers pass scope with group=None, parallel callers set it. Delete persist_parse_error's duplicated body.
- **[MEDIUM · M]** Dropdown precedence is hand-mirrored in two functions with only a comment to keep them in sync
  - _src/tui/mod.rs:1128-1142,2619-2628_ — The agent → skill → @-file-mention → command dropdown precedence is encoded twice with no shared structure: once as the if/else cascade in key_event_to_tui_command_with_ui (1128-1142) that decides which dropdown captures keys, and again as the if/else chain in render (2619-2628) that decides which dropdown is painted. A comment at 2615 states the chain 'MUST stay in sync with key_event_to_tui_command_with_ui'.
